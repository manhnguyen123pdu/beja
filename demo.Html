1. PLATFORM LÀ GÌ? TỔNG QUAN VỀ PAAS

1.1. Platform là gì?

1.1.1. Khái niệm Platform

Trong lĩnh vực phát triển phần mềm, Platform có nghĩa là nền tảng cung cấp môi trường và các công cụ để xây dựng, chạy, triển khai hoặc quản lý ứng dụng.

Tùy theo ngữ cảnh, Platform có thể mang nhiều ý nghĩa khác nhau. Trong bài học này, chúng ta tập trung vào nền tảng triển khai ứng dụng web, đặc biệt là ứng dụng Java Spring Boot.

Ví dụ, sau khi hoàn thành một dự án Spring Boot trên máy tính cá nhân, chúng ta muốn đưa ứng dụng lên Internet để người dùng có thể truy cập API từ bên ngoài.

Nếu sử dụng một nền tảng như Render, chúng ta có thể kết nối repository GitHub, cấu hình cách build ứng dụng và thiết lập biến môi trường. Nền tảng sẽ đảm nhiệm nhiều công việc vận hành cần thiết để chạy ứng dụng.

Thay vì tự cài đặt và cấu hình toàn bộ máy chủ Linux, Java Runtime, tiến trình chạy ứng dụng và các thành phần triển khai cơ bản, chúng ta có thể sử dụng những chức năng đã được nền tảng cung cấp.

1.1.2. Ví dụ thực tế

Giả sử chúng ta có dự án Spring Boot với cấu trúc:

demosecurity/
├── src/
│   └── main/
│       ├── java/
│       └── resources/
├── pom.xml
├── mvnw
└── .gitignore

Ứng dụng cung cấp các API:

POST /api/auth/login
POST /api/auth/refresh
GET  /api/users

Khi chạy trên máy tính cá nhân, API có thể được truy cập qua:

http://localhost:8080

Tuy nhiên, địa chỉ localhost chỉ trỏ đến máy đang thực hiện request. Người dùng trên Internet không thể sử dụng địa chỉ đó để truy cập ứng dụng đang chạy trên máy tính của bạn.

Để công khai API, chúng ta cần triển khai ứng dụng lên một máy chủ hoặc nền tảng có thể nhận request từ Internet.

Nếu sử dụng Render, quy trình có thể diễn ra như sau:

  1. Đẩy source code lên GitHub.
  2. Kết nối tài khoản GitHub với Render.
  3. Chọn repository chứa dự án Spring Boot.
  4. Cấu hình lệnh build và lệnh chạy ứng dụng.
  5. Khai báo biến môi trường.
  6. Triển khai ứng dụng.
  7. Nhận URL công khai và kiểm tra API.

Ví dụ URL minh họa:

https://demosecurity-example.onrender.com

Đây chỉ là URL giả định để minh họa. URL thật sẽ được nền tảng cung cấp khi tạo dịch vụ thành công.

Khi đó, frontend có thể gọi API thông qua URL công khai thay vì gọi localhost trên máy của lập trình viên.

1.1.3. Platform hỗ trợ những công việc nào?

Tùy từng nhà cung cấp và loại dịch vụ, một Platform có thể hỗ trợ:

  • Nhận source code từ GitHub.
  • Build ứng dụng.
  • Cài đặt hoặc sử dụng môi trường chạy phù hợp.
  • Khởi động ứng dụng.
  • Cấp URL truy cập công khai.
  • Cấu hình biến môi trường.
  • Quản lý log ứng dụng.
  • Theo dõi trạng thái triển khai.
  • Triển khai lại khi source code thay đổi.
  • Tích hợp với dịch vụ database hoặc các dịch vụ bên ngoài.

Không phải Platform nào cũng cung cấp đầy đủ mọi chức năng trên trong cùng một gói dịch vụ. Một số tính năng có thể phụ thuộc vào loại dịch vụ, gói sử dụng hoặc cấu hình của dự án.

1.2. PaaS là gì?

1.2.1. Khái niệm PaaS

PaaS là viết tắt của Platform as a Service, nghĩa là Nền tảng như một dịch vụ.

PaaS là mô hình điện toán đám mây cung cấp môi trường và công cụ để lập trình viên triển khai, chạy và quản lý ứng dụng mà không cần tự quản lý toàn bộ hạ tầng máy chủ bên dưới.

Với PaaS, nhà cung cấp thường đảm nhiệm nhiều phần việc về hạ tầng và môi trường chạy ứng dụng. Lập trình viên tập trung nhiều hơn vào source code, cấu hình ứng dụng và dữ liệu.

Ví dụ, khi deploy ứng dụng Spring Boot lên Render, chúng ta thường cần quan tâm đến:

  • Source code.
  • Cấu hình build Maven.
  • Phiên bản Java tương thích.
  • Lệnh khởi động ứng dụng.
  • Biến môi trường.
  • Kết nối database.
  • Kiểm tra log và API.

Trong khi đó, nền tảng đảm nhiệm những phần hạ tầng mà dịch vụ cung cấp, chẳng hạn môi trường chạy ứng dụng và cơ chế triển khai.

Lưu ý: PaaS không có nghĩa là chúng ta không cần quan tâm đến máy chủ hoặc bảo mật. Lập trình viên vẫn phải quản lý cấu hình ứng dụng, thông tin xác thực, quyền truy cập database, lỗi phần mềm và các vấn đề vận hành thuộc phạm vi của mình.

GitHub và PaaS là hai dịch vụ có vai trò khác nhau:

  • PaaS giúp triển khai và vận hành ứng dụng theo khả năng mà nền tảng cung cấp.

1.2.3. PaaS có phải là hosting không?

PaaS và hosting có liên quan nhưng không hoàn toàn giống nhau.

Hosting là thuật ngữ rộng, chỉ các dịch vụ cung cấp tài nguyên hoặc môi trường để lưu trữ và vận hành website, ứng dụng hoặc dữ liệu.

PaaS là một mô hình cung cấp dịch vụ nền tảng, thường bao gồm các công cụ và quy trình hỗ trợ triển khai ứng dụng.

Ví dụ:

  • Shared hosting thường phù hợp với các website hoặc công nghệ được nhà cung cấp hỗ trợ.
  • VPS cung cấp máy chủ ảo để người dùng tự cấu hình môi trường.
  • PaaS có thể cung cấp quy trình build, deploy và vận hành ứng dụng mà không yêu cầu người dùng quản lý toàn bộ máy chủ bên dưới.

Do đó, không nên hiểu rằng mọi dịch vụ hosting đều là PaaS hoặc PaaS chỉ đơn giản là nơi lưu trữ source code.

1.3. Phân biệt IaaS, PaaS và SaaS

Trong điện toán đám mây, ba mô hình thường được nhắc đến là IaaS, PaaS và SaaS.

1.3.1. IaaS – Infrastructure as a Service

IaaS là viết tắt của Infrastructure as a Service, nghĩa là Hạ tầng như một dịch vụ.

Nhà cung cấp cung cấp tài nguyên hạ tầng như máy chủ ảo, lưu trữ và mạng. Người sử dụng có thể phải tự cài đặt, cấu hình hệ điều hành, môi trường chạy và ứng dụng.

Ví dụ điển hình là thuê một VPS Linux.

Khi sử dụng VPS để deploy Spring Boot, chúng ta thường phải tự thực hiện nhiều công việc:

  • Kết nối SSH.
  • Cài đặt Java.
  • Cấu hình firewall.
  • Upload file JAR.
  • Thiết lập biến môi trường.
  • Chạy ứng dụng bằng Java.
  • Tạo dịch vụ systemd.
  • Cấu hình Nginx và HTTPS khi cần.

1.3.2. PaaS – Platform as a Service

PaaS cung cấp môi trường và công cụ để triển khai ứng dụng.

Ví dụ, với một dịch vụ PaaS hỗ trợ Java, chúng ta có thể kết nối GitHub, cấu hình build Maven, khai báo biến môi trường và deploy ứng dụng mà không cần tự thực hiện toàn bộ các bước quản trị máy chủ như trên VPS.

1.3.3. SaaS – Software as a Service

SaaS là viết tắt của Software as a Service, nghĩa là Phần mềm như một dịch vụ.

Người dùng sử dụng phần mềm đã được nhà cung cấp vận hành thông qua trình duyệt hoặc ứng dụng.

Ví dụ:

  • Gmail.
  • Google Docs.
  • Microsoft 365.

Khi sử dụng SaaS, người dùng chủ yếu sử dụng chức năng của phần mềm thay vì tự triển khai ứng dụng trên máy chủ.

1.4. PaaS hoạt động như thế nào với Spring Boot?

Để hiểu PaaS, chúng ta hãy xét một dự án Spring Boot sử dụng Maven.

Giả sử dự án có:

demosecurity/
├── src/
├── pom.xml
├── mvnw
├── mvnw.cmd
└── .gitignore

Bước 1: Lập trình viên phát triển ứng dụng

Trên máy cá nhân, lập trình viên viết controller, service, repository và các thành phần khác của Spring Boot.

Ví dụ:

Java
@RestController
@RequestMapping("/api")
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "Hello from Spring Boot";
    }
}

Khi chạy local, endpoint có thể là:

http://localhost:8080/api/hello

Bước 2: Đưa source code lên GitHub

Sau khi kiểm tra dự án, lập trình viên commit và push source code lên repository.

Bash
git add .
git commit -m "Prepare Spring Boot deployment"
git push origin main

Các lệnh trên giả định repository đã được khởi tạo, cấu hình remote và đang sử dụng nhánh main.

Bước 3: Kết nối GitHub với PaaS

Trên nền tảng triển khai, lập trình viên chọn repository chứa dự án.

Nền tảng cần có quyền truy cập repository theo cơ chế xác thực được hỗ trợ.

Bước 4: Build ứng dụng

Với dự án Maven, quá trình build thường sử dụng lệnh tương tự:

Bash
./mvnw clean package -DskipTests

Lệnh này minh họa cách tạo file JAR mà không chạy test. Trong quy trình Production, nên chạy test phù hợp trước khi deploy; chỉ bỏ qua test khi có lý do rõ ràng.

Trên môi trường Windows, Maven Wrapper thường được gọi bằng:

PowerShell
.\mvnw.cmd clean package

Kết quả build thường là file JAR trong thư mục target/, tùy cấu hình Maven.

Bước 5: Khởi động ứng dụng

Nếu dự án tạo file:

target/demosecurity.jar

thì lệnh chạy minh họa là:

Bash
java -jar target/demosecurity.jar

Trên PaaS, bạn cần cấu hình lệnh chạy tương ứng với môi trường build và vị trí file JAR thực tế.

Bước 6: Cung cấp URL công khai

Sau khi triển khai thành công, nền tảng có thể cung cấp một URL công khai để người dùng truy cập ứng dụng.

Ví dụ:

https://demosecurity-example.onrender.com/api/hello

Đây là URL giả định. URL thực tế phụ thuộc vào dịch vụ đã tạo.

Bước 7: Kiểm tra hoạt động

Sử dụng trình duyệt hoặc Postman để gửi request đến API.

Nếu API yêu cầu xác thực, cần gửi thông tin xác thực đúng cách. Nếu API công khai, có thể kiểm tra response trực tiếp.

1.5. Tổng quan về Render

1.5.1. Render là gì?

Render là một nền tảng Cloud hỗ trợ triển khai và vận hành nhiều loại ứng dụng, bao gồm ứng dụng web, dịch vụ backend và các thành phần hạ tầng liên quan.

Trong khóa học này, chúng ta sử dụng Render để thực hành deploy ứng dụng Java Spring Boot lên Internet.

Render có thể hỗ trợ quy trình làm việc với GitHub, build source code và triển khai dịch vụ. Các khả năng cụ thể phụ thuộc vào loại dịch vụ và cấu hình đang sử dụng.

Trang chủ: https://render.com/

1.5.2. Vì sao chọn Render để học deploy?

Render phù hợp làm ví dụ thực hành vì quy trình triển khai có thể được tổ chức thông qua giao diện quản lý dịch vụ.

Người học có thể tập trung vào các kỹ năng quan trọng:

  • Chuẩn bị source code.
  • Kết nối GitHub.
  • Cấu hình lệnh build.
  • Cấu hình lệnh chạy.
  • Thiết lập biến môi trường.
  • Kiểm tra log.
  • Xử lý lỗi deploy.
  • Kiểm tra API sau khi triển khai.

Nhờ vậy, người học có thể hiểu quy trình deploy trước khi chuyển sang quản trị VPS Linux với nhiều bước cấu hình hệ điều hành và dịch vụ hơn.

1.5.3. Render không thay thế toàn bộ kiến thức Backend

Mặc dù nền tảng giúp giảm công việc quản trị máy chủ, lập trình viên vẫn cần hiểu:

  • Cách Spring Boot khởi động.
  • Cách Maven build dự án.
  • Cách cấu hình application.properties.
  • Cách quản lý biến môi trường.
  • Cách kết nối MySQL.
  • Cách xử lý CORS.
  • Cách đọc log.
  • Cách bảo vệ API.
  • Cách kiểm tra lỗi HTTP.

Nếu ứng dụng có lỗi trong code, sai cấu hình hoặc database không thể truy cập, việc sử dụng PaaS không tự động giải quyết những vấn đề đó.

1.6. Các thành phần cơ bản khi deploy bằng PaaS

Khi deploy Spring Boot lên một nền tảng như Render, chúng ta thường làm việc với những thành phần sau.

1.6.1. Repository

Repository là nơi lưu trữ source code và lịch sử thay đổi của dự án.

Trong bài học này, repository thường được lưu trên GitHub.

Ví dụ:

https://github.com/username/demosecurity

Đây là URL minh họa, không phải repository thật.

1.6.2. Web Service

Web Service là dịch vụ chạy ứng dụng web hoặc backend trên nền tảng.

Với Spring Boot, Web Service thường được dùng để chạy ứng dụng và nhận request HTTP/HTTPS theo cấu hình của nền tảng.

Ví dụ ứng dụng có các API:

GET  /api/products
POST /api/auth/login
POST /api/auth/refresh

Web Service giúp ứng dụng nhận các request đó thông qua URL được cung cấp hoặc cấu hình.

1.6.3. Build Command

Build Command là lệnh được thực thi để xây dựng ứng dụng trước khi chạy.

Với Maven, lệnh có thể là:

Bash
./mvnw clean package

Lệnh này yêu cầu Maven Wrapper làm sạch kết quả build cũ và đóng gói dự án.

Trong một số môi trường, có thể sử dụng:

Bash
mvn clean package

Tuy nhiên, nếu dự án có Maven Wrapper, sử dụng Wrapper giúp kiểm soát phiên bản Maven theo cấu hình dự án tốt hơn.

1.6.4. Start Command

Start Command là lệnh được sử dụng để khởi động ứng dụng đã build.

Ví dụ:

Bash
java -jar target/demosecurity.jar

Tên file JAR cần khớp với kết quả build thực tế. Không nên mặc định rằng mọi dự án đều tạo ra file có cùng tên.

1.6.5. Environment Variables

Đây là nơi cung cấp những giá trị cấu hình mà ứng dụng cần khi chạy.

Ví dụ:

SPRING_PROFILES_ACTIVE=prod
DB_HOST=<hostname database>
DB_PORT=3306
DB_NAME=spring_security
DB_USERNAME=<database username>
DB_PASSWORD=<database password>
JWT_SECRET=<JWT secret>

Các giá trị trong dấu ngoặc nhọn cần được thay bằng thông tin thật của môi trường triển khai.

1.6.6. Logs

Logs là thông tin ghi lại quá trình build và chạy ứng dụng.

Khi deploy gặp lỗi, log giúp xác định nguyên nhân, chẳng hạn:

  • Không tìm thấy Java phù hợp.
  • Build Maven thất bại.
  • Không tìm thấy file JAR.
  • Thiếu biến môi trường.
  • Không kết nối được database.
  • Ứng dụng khởi động thất bại.
  • Có lỗi trong quá trình xử lý request.

1.6.7. Database

Database là nơi lưu trữ dữ liệu của ứng dụng.

Ví dụ, một ứng dụng quản lý bán hàng có thể cần MySQL để lưu:

  • Người dùng.
  • Sản phẩm.
  • Danh mục.
  • Hóa đơn.
  • Chi tiết hóa đơn.

Không phải Web Service nào cũng tự động có database đi kèm. Database có thể là dịch vụ riêng hoặc được triển khai ở nơi khác.

Nếu backend trên Render kết nối đến MySQL bên ngoài, cần sử dụng đúng thông tin kết nối và đảm bảo mạng cho phép truy cập.

1.7. Ưu điểm của PaaS

1.7.1. Giảm công việc quản trị máy chủ

Khi sử dụng VPS, chúng ta thường phải tự cài đặt Java, thiết lập tiến trình chạy ứng dụng, cấu hình khởi động lại và quản lý một số thành phần hệ điều hành.

Với PaaS, nhiều công việc nền tảng được nhà cung cấp quản lý.

Điều này giúp người học tập trung vào việc đưa ứng dụng Spring Boot lên môi trường thực tế.

1.7.2. Quy trình triển khai đơn giản hơn

Nhiều nền tảng hỗ trợ kết nối với GitHub và triển khai từ repository.

Quy trình có thể là:

Sửa source code
      |
      v

      |
      v
Nền tảng build
      |
      v
Triển khai phiên bản mới

Khả năng tự động deploy phụ thuộc vào cài đặt của dịch vụ. Không nên mặc định rằng mọi lần push đều tự động triển khai trong mọi cấu hình.

1.7.3. Có công cụ quản lý log

Thay vì chỉ truy cập máy chủ để đọc file log, người dùng có thể xem log qua giao diện quản lý nền tảng nếu dịch vụ hỗ trợ.

Điều này thuận tiện cho việc kiểm tra lỗi build và lỗi khởi động ứng dụng.

1.7.4. Thuận tiện cho dự án học tập và thử nghiệm

PaaS giúp người mới thực hành các bước triển khai thực tế mà chưa cần học toàn bộ thao tác quản trị Linux.

Đây là lợi thế khi muốn nhanh chóng đưa một API Spring Boot lên Internet để kiểm tra bằng Postman hoặc kết nối với frontend.

1.7.5. Có thể mở rộng theo nhu cầu

Một số nền tảng cung cấp khả năng tăng tài nguyên, số lượng instance hoặc các tùy chọn vận hành khác.

Tuy nhiên, mức độ mở rộng và chi phí phụ thuộc vào nhà cung cấp, loại dịch vụ và gói sử dụng.

1.8. Hạn chế của PaaS

1.8.1. Ít quyền kiểm soát hệ điều hành hơn VPS

Với VPS, người dùng thường có quyền quản trị máy chủ và có thể tự cài đặt nhiều phần mềm.

Với PaaS, người dùng làm việc trong phạm vi dịch vụ được cung cấp. Một số thao tác quản trị hệ điều hành có thể không được hỗ trợ.

1.8.2. Phụ thuộc vào nhà cung cấp

Các nền tảng có thể khác nhau về:

  • Quy trình build.
  • Cấu hình runtime.
  • Cách khai báo biến môi trường.
  • Cách cung cấp domain.
  • Cơ chế lưu trữ.
  • Khả năng mở rộng.
  • Chi phí và giới hạn tài nguyên.

Vì vậy, khi chuyển ứng dụng từ nền tảng này sang nền tảng khác, có thể cần điều chỉnh cấu hình triển khai.

1.8.3. Có thể có giới hạn tài nguyên

Tùy gói dịch vụ, nền tảng có thể giới hạn CPU, RAM, thời gian chạy, dung lượng lưu trữ hoặc số lượng dịch vụ.

Các giới hạn cụ thể cần kiểm tra tại trang giá và tài liệu hiện hành của nhà cung cấp.

1.8.4. Không phải mọi dịch vụ đều miễn phí

Một số nền tảng có gói miễn phí hoặc mức dùng thử, nhưng có thể giới hạn tài nguyên, thời gian hoạt động hoặc tính năng.

Các dịch vụ database, domain, tài nguyên bổ sung hoặc khả năng vận hành nâng cao có thể phát sinh chi phí riêng.

Khi triển khai dự án thực tế, cần đọc kỹ điều kiện gói dịch vụ trước khi quyết định sử dụng.

1.8.5. Không loại bỏ trách nhiệm bảo mật của lập trình viên

PaaS có thể quản lý một phần hạ tầng, nhưng lập trình viên vẫn cần:

  • Bảo vệ biến môi trường.
  • Cấu hình xác thực và phân quyền.
  • Bảo vệ database.
  • Không để lộ secret.
  • Cập nhật thư viện.
  • Xử lý lỗi trong ứng dụng.
  • Kiểm soát dữ liệu nhạy cảm trong log.

1.10. Khi nào nên sử dụng PaaS?

Trường hợp 1: Dự án học tập

Bạn đang học Spring Boot và muốn đưa API lên Internet để thực hành.

PaaS là lựa chọn thuận tiện vì giảm số lượng bước quản trị máy chủ.

Trường hợp 2: Demo sản phẩm

Bạn cần URL công khai để giảng viên, khách hàng hoặc thành viên trong nhóm kiểm thử API.

PaaS có thể giúp triển khai nhanh mà không cần tự cấu hình toàn bộ máy chủ.

Trường hợp 3: Backend phục vụ frontend

Bạn có một frontend viết bằng React hoặc HTML/CSS/JavaScript và cần một URL backend để gọi API.

Có thể triển khai backend trên PaaS, sau đó cấu hình frontend sử dụng URL đó.

Ví dụ:

   | HTTPS Request
   v

   |
   v

Trường hợp 4: Muốn giảm công việc vận hành

Nếu nhóm phát triển muốn tập trung vào code và chưa cần quyền kiểm soát sâu hệ điều hành, PaaS có thể phù hợp.

1.11. Khi nào nên sử dụng VPS?

VPS có thể phù hợp khi:

  • Cần quyền kiểm soát hệ điều hành.
  • Muốn tự cài đặt và quản lý Nginx.
  • Cần triển khai nhiều dịch vụ trên cùng máy chủ.
  • Muốn chủ động cấu hình firewall và mạng.
  • Cần thiết lập tiến trình bằng systemd.
  • Muốn tự tổ chức môi trường chạy hoặc hệ thống giám sát.
  • Có yêu cầu vận hành không phù hợp với giới hạn của PaaS.

Tuy nhiên, quyền kiểm soát cao hơn cũng đi kèm trách nhiệm lớn hơn. Người vận hành phải biết cách cập nhật hệ điều hành, bảo vệ SSH, quản lý firewall, giám sát tài nguyên và xử lý sự cố.

1.12. Quy trình tổng quan deploy Spring Boot lên Render

Trong các phần tiếp theo, chúng ta sẽ triển khai ứng dụng theo quy trình sau.

Giai đoạn 1: Chuẩn bị dự án

  • Kiểm tra source code.
  • Kiểm tra pom.xml.
  • Xác định phiên bản Java tương thích.
  • Build thử file JAR.
  • Kiểm tra cấu hình application.properties.
  • Đảm bảo secrets không bị commit lên GitHub.

Giai đoạn 2: Đưa source code lên GitHub

  • Tạo repository.
  • Cấu hình Git.
  • Commit source code.
  • Push lên GitHub.
  • Kiểm tra repository có đầy đủ file cần thiết.

Giai đoạn 3: Tạo dịch vụ trên Render

  • Đăng nhập Render.
  • Kết nối GitHub.
  • Chọn repository.
  • Tạo Web Service.
  • Thiết lập các thông số triển khai.

Giai đoạn 4: Cấu hình build và start

Ví dụ lệnh build với Maven Wrapper trên môi trường Linux:

Bash
./mvnw clean package

Ví dụ lệnh chạy:

Bash
java -jar target/demosecurity.jar

Tên file JAR và lệnh chính xác cần điều chỉnh theo dự án. Phiên bản Java dùng để build và chạy phải tương thích với phiên bản Spring Boot cùng các thư viện đang sử dụng.

Giai đoạn 5: Khai báo biến môi trường

Ví dụ:

SPRING_PROFILES_ACTIVE=prod
DB_HOST=<hostname database>
DB_PORT=3306
DB_NAME=spring_security
DB_USERNAME=<database username>
DB_PASSWORD=<database password>
JWT_SECRET=<JWT secret>

Chỉ khai báo các biến thực sự cần thiết. Nếu ứng dụng không sử dụng MySQL hoặc JWT, không cần thêm những biến tương ứng.

Giai đoạn 6: Deploy và kiểm tra

  • Khởi chạy quá trình deploy.
  • Đọc build log.
  • Kiểm tra runtime log.
  • Xác nhận ứng dụng khởi động thành công.
  • Kiểm tra URL công khai.
  • Gửi request bằng Postman.
  • Xử lý lỗi nếu có.

Giai đoạn 7: Kết nối frontend

Sau khi API hoạt động, frontend có thể gọi URL backend công khai.

Cần kiểm tra thêm CORS, HTTPS, cấu hình URL API và cơ chế xác thực nếu frontend gọi các endpoint được bảo vệ.

Ghi nhớ trọng tâm
  • Platform là nền tảng cung cấp môi trường và công cụ để xây dựng, chạy, triển khai, quản lý ứng dụng.
  • PaaS (Platform as a Service) là mô hình điện toán đám mây cung cấp môi trường và công cụ triển khai ứng dụng mà không cần tự quản lý toàn bộ hạ tầng máy chủ.
  • Ba mô hình đám mây: IaaS (hạ tầng — VPS), PaaS (nền tảng — Render, Railway), SaaS (phần mềm — Gmail, Google Docs).
  • GitHub quản lý source code; PaaS triển khai và vận hành ứng dụng. Hai dịch vụ có vai trò khác nhau.
  • Các thành phần cơ bản khi deploy bằng PaaS: Repository, Web Service, Build Command, Start Command, Environment Variables, Logs, Database.
  • Ưu điểm PaaS: giảm công việc quản trị máy chủ, quy trình triển khai đơn giản, có công cụ log, thuận tiện cho dự án học tập và demo.
  • Hạn chế PaaS: ít quyền kiểm soát hệ điều hành hơn VPS, phụ thuộc nhà cung cấp, có thể có giới hạn tài nguyên, không phải mọi dịch vụ đều miễn phí.
  • PaaS không loại bỏ trách nhiệm bảo mật của lập trình viên: vẫn cần bảo vệ biến môi trường, cấu hình xác thực, bảo vệ database, không để lộ secret.
  • Không thể kết luận PaaS luôn rẻ hơn hoặc VPS luôn rẻ hơn — cần tính cả tài nguyên, database, domain, thời gian quản trị.
  • Quy trình deploy Spring Boot lên Render gồm 7 giai đoạn: chuẩn bị dự án → đưa source code lên GitHub → tạo dịch vụ trên Render → cấu hình build và start → khai báo biến môi trường → deploy và kiểm tra → kết nối frontend.
  • Render không thay thế kiến thức Backend: vẫn cần hiểu Spring Boot, Maven, cấu hình, biến môi trường, MySQL, CORS, log, bảo vệ API.

2. GIỚI THIỆU RENDER VÀ CÁCH HOẠT ĐỘNG

2.1. Render là gì?

Render là một nền tảng Cloud Platform cho phép lập trình viên triển khai và vận hành ứng dụng trên Internet mà không cần tự cài đặt, cấu hình toàn bộ máy chủ như khi sử dụng VPS truyền thống.

Trang chủ chính thức: https://render.com/

Khi phát triển ứng dụng Spring Boot trên máy tính cá nhân, ứng dụng thường chạy tại địa chỉ:

http://localhost:8080

Địa chỉ này chỉ có ý nghĩa trên máy tính đang chạy ứng dụng. Người dùng ở máy tính khác không thể truy cập ứng dụng thông qua localhost của máy bạn.

Nếu muốn đưa Backend Spring Boot lên Internet, chúng ta cần triển khai ứng dụng lên một máy chủ có thể truy cập công khai.

Có nhiều cách thực hiện việc này:

  • Thuê VPS Linux và tự cài đặt môi trường chạy ứng dụng.
  • Sử dụng dịch vụ Platform as a Service (PaaS) như Render.
  • Sử dụng các nền tảng triển khai ứng dụng Cloud khác.

Trong bài học này, chúng ta sử dụng Render để đưa ứng dụng Spring Boot lên Internet.

Ví dụ thực tế

Giả sử bạn xây dựng một Backend quản lý sản phẩm bằng Spring Boot.

Khi chạy trên máy tính cá nhân, API có địa chỉ:

http://localhost:8080/api/products

Sau khi triển khai thành công lên Render, ứng dụng có thể được truy cập thông qua một địa chỉ công khai, ví dụ:

https://product-api-example.onrender.com/api/products

Đây là địa chỉ minh họa. URL thực tế sẽ do Render cung cấp khi bạn tạo dịch vụ.

Frontend React hoặc ứng dụng khác có thể gửi HTTP request đến URL công khai này để lấy dữ liệu từ Backend.

Lưu ý: Có URL công khai không đồng nghĩa với việc mọi API đều được phép truy cập. Những API được Spring Security bảo vệ vẫn yêu cầu xác thực và phân quyền theo cấu hình của ứng dụng.

2.2. Render giải quyết vấn đề gì?

Để hiểu vai trò của Render, trước tiên chúng ta xem xét những công việc cần thực hiện khi tự triển khai ứng dụng trên một máy chủ.

Giả sử bạn thuê một VPS Linux mới. Máy chủ đó có thể chưa có Java, chưa có Nginx, chưa có ứng dụng và cũng chưa được cấu hình để nhận các request từ Internet.

Nếu triển khai theo cách truyền thống, bạn có thể phải thực hiện những công việc sau:

  1. Truy cập máy chủ thông qua SSH.
  2. Cài đặt Java phù hợp với ứng dụng.
  3. Cài đặt các công cụ cần thiết.
  4. Đưa mã nguồn hoặc file JAR lên máy chủ.
  5. Cấu hình lệnh chạy ứng dụng.
  6. Thiết lập biến môi trường.
  7. Cấu hình cổng mạng và tường lửa.
  8. Cấu hình Nginx nếu cần reverse proxy.
  9. Cấu hình HTTPS và chứng chỉ SSL/TLS.
  10. Thiết lập cơ chế khởi động lại ứng dụng khi máy chủ gặp sự cố.
  11. Theo dõi log và xử lý lỗi trong quá trình vận hành.

Với Render, nhiều công việc vận hành hạ tầng được nền tảng hỗ trợ hoặc tự động hóa.

Ví dụ, khi tạo một Web Service và kết nối repository GitHub, bạn có thể cấu hình lệnh build, lệnh chạy và các biến môi trường ngay trên giao diện Render.

Render sau đó thực hiện quá trình build và khởi chạy ứng dụng theo cấu hình đã cung cấp.

Kết luận

Tuy nhiên, bạn vẫn cần hiểu cách ứng dụng Spring Boot được build, cách cấu hình môi trường, cách kết nối cơ sở dữ liệu và cách kiểm tra lỗi khi ứng dụng không khởi động thành công.

2.3. Các thành phần quan trọng khi sử dụng Render

Khi triển khai một ứng dụng Spring Boot trên Render, chúng ta cần hiểu một số thành phần cơ bản sau.

2.3.1. Repository GitHub

Repository là nơi lưu trữ mã nguồn dự án.

Ví dụ, dự án Spring Boot của bạn có cấu trúc:

product-management/
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/example/product/
│   │   │       ├── controller/
│   │   │       ├── service/
│   │   │       ├── repository/
│   │   │       └── ProductApplication.java
│   │   └── resources/
│   │       └── application.properties
├── mvnw
├── mvnw.cmd
├── pom.xml
└── .gitignore

Bạn đưa mã nguồn lên GitHub, sau đó kết nối repository đó với Render.

Khi triển khai, Render sử dụng mã nguồn trong repository để thực hiện quá trình build theo cấu hình của dịch vụ.

Lưu ý: Không được đưa mật khẩu cơ sở dữ liệu, JWT secret hoặc OAuth2 client secret vào repository công khai.

2.3.2. Web Service

Web Service là loại dịch vụ thường được sử dụng để triển khai Backend Spring Boot cung cấp API qua HTTP hoặc HTTPS.

Ví dụ, Backend có các API:

GET    /api/products
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
DELETE /api/products/{id}

Sau khi ứng dụng được triển khai thành công, các API này có thể được gọi thông qua domain công khai của Web Service.

Ví dụ:

https://product-api-example.onrender.com/api/products

Địa chỉ trên chỉ là ví dụ minh họa.

2.3.3. Build Command

Build Command là lệnh dùng để biên dịch và đóng gói dự án.

Đối với một dự án Spring Boot sử dụng Maven, lệnh build thường gặp là:

Bash
./mvnw clean package -DskipTests

Trong đó:

  • ./mvnw: sử dụng Maven Wrapper đi kèm dự án.
  • clean: xóa kết quả build cũ.
  • package: biên dịch và đóng gói ứng dụng.
  • -DskipTests: bỏ qua việc chạy test trong quá trình build theo cấu hình Maven tương ứng.

Đây là lệnh ví dụ, không phải cấu hình bắt buộc cho mọi dự án.

Nếu muốn chạy kiểm thử trước khi đóng gói, bạn có thể sử dụng:

Bash
./mvnw clean package

Nếu dự án không có Maven Wrapper, có thể cần sử dụng Maven đã được cài đặt trong môi trường build:

Bash
mvn clean package

Trong quá trình triển khai, nếu Build Command không phù hợp với cấu trúc dự án hoặc môi trường build, quá trình build có thể thất bại.

2.3.4. Start Command

Start Command là lệnh dùng để khởi chạy ứng dụng sau khi quá trình build hoàn thành.

Nếu ứng dụng được đóng gói thành file JAR, lệnh chạy có thể có dạng:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Tên file JAR thực tế phụ thuộc vào cấu hình Maven và phiên bản dự án.

Trong môi trường triển khai, bạn cần bảo đảm Start Command trỏ đến đúng file JAR đã được tạo ra.

Ngoài ra, ứng dụng Spring Boot cần lắng nghe trên cổng mà nền tảng cung cấp. Khi triển khai trên Render, có thể cấu hình cổng bằng biến môi trường PORT:

Properties
server.port=${PORT:8080}

Giải thích:

  • Nếu biến môi trường PORT tồn tại, Spring Boot sử dụng giá trị đó.
  • Nếu không có biến môi trường PORT, ứng dụng sử dụng cổng mặc định 8080.

Ví dụ, nếu môi trường cung cấp PORT=10000, ứng dụng sẽ lắng nghe trên cổng 10000.

Không nên mặc định rằng ứng dụng trên Render luôn chạy ở cổng 8080.

2.3.5. Environment Variables

Environment Variables là các biến môi trường dùng để truyền cấu hình cho ứng dụng khi chạy.

Ví dụ:

SPRING_PROFILES_ACTIVE=prod
PORT=10000
SPRING_DATASOURCE_URL=jdbc:mysql://...
SPRING_DATASOURCE_USERNAME=...
SPRING_DATASOURCE_PASSWORD=...
JWT_SECRET_KEY=...

Các giá trị trên chỉ là ví dụ. Cấu hình thực tế phụ thuộc vào dự án và dịch vụ đang sử dụng.

Trong application.properties, bạn có thể tham chiếu biến môi trường như sau:

Properties
spring.profiles.active=${SPRING_PROFILES_ACTIVE:dev}

server.port=${PORT:8080}

spring.datasource.url=${SPRING_DATASOURCE_URL}
spring.datasource.username=${SPRING_DATASOURCE_USERNAME}
spring.datasource.password=${SPRING_DATASOURCE_PASSWORD}

Trong đó:

  • ${PORT:8080} nghĩa là sử dụng biến PORT nếu có, nếu không thì dùng 8080.
  • ${SPRING_DATASOURCE_URL} yêu cầu giá trị biến môi trường tương ứng phải được cung cấp.
  • spring.profiles.active cho phép chọn cấu hình phù hợp với môi trường.

Đối với môi trường production, cần tránh sử dụng cấu hình mặc định không an toàn hoặc vô tình chạy ứng dụng bằng profile phát triển.

2.3.6. Logs

Logs là thông tin được ghi lại trong quá trình build và chạy ứng dụng.

Ví dụ:

Started ProductApplication in 5.2 seconds

Thông báo này cho biết ứng dụng đã khởi động thành công.

Ngược lại, bạn có thể gặp lỗi như:

Failed to configure a DataSource

Hoặc:

Communications link failure

Những lỗi này có thể liên quan đến cấu hình cơ sở dữ liệu, kết nối mạng hoặc thông tin đăng nhập.

Khi triển khai trên Render, bạn có thể xem log của dịch vụ trong Dashboard để xác định nguyên nhân ứng dụng không hoạt động.

Cần phân biệt:

  • Build logs: thông tin trong quá trình tải dependency, biên dịch và đóng gói.
  • Runtime logs: thông tin xuất hiện khi ứng dụng đang chạy.

Phân biệt hai loại log này giúp quá trình sửa lỗi nhanh và chính xác hơn.

Bước 2. Build và kiểm tra dự án

Sử dụng Maven Wrapper để build:

Bash
./mvnw clean package

Trên Windows, bạn có thể sử dụng:

Batch
mvnw.cmd clean package

Nếu build thành công, Maven tạo file JAR trong thư mục target theo cấu hình dự án.

Ví dụ:

target/

Tiếp theo, kiểm tra ứng dụng bằng lệnh:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Tên file cần được thay bằng file JAR thực tế của bạn.

Bước này giúp phát hiện sớm các lỗi liên quan đến biên dịch, dependency hoặc cấu hình chạy ứng dụng.

Bước 3. Đưa source code lên GitHub

Khởi tạo Git nếu dự án chưa được quản lý bằng Git:

Bash
git init
git add .
git commit -m "Prepare project for deployment"

Sau đó, kết nối với repository GitHub và push mã nguồn theo hướng dẫn của GitHub.

Ví dụ:

Bash
git remote add origin https://github.com/your-username/product-management.git
git branch -M main
git push -u origin main

Thay URL minh họa bằng repository thực tế của bạn.

Trước khi push, cần kiểm tra .gitignore và bảo đảm không đưa các thông tin bí mật lên GitHub.

Bước 4. Kết nối GitHub với Render

Trên Render, bạn tạo một Web Service và lựa chọn repository chứa dự án.

Tùy theo quyền truy cập và cách kết nối GitHub, bạn có thể cần cấp quyền để Render đọc repository tương ứng.

Sau khi kết nối, Render có thể lấy mã nguồn từ repository để triển khai ứng dụng.

Bước 5. Render build ứng dụng

Render sử dụng môi trường build để thực hiện Build Command đã cấu hình.

Ví dụ:

Bash
./mvnw clean package -DskipTests

Trong quá trình này, Maven có thể:

  1. Tải các dependency cần thiết.
  2. Biên dịch mã nguồn Java.
  3. Xử lý tài nguyên của dự án.
  4. Đóng gói ứng dụng thành file JAR.

Nếu một bước thất bại, quá trình triển khai có thể dừng lại. Khi đó, bạn cần xem Build Logs để tìm nguyên nhân.

Bước 6. Render khởi chạy ứng dụng

Sau khi build thành công, Render sử dụng Start Command để chạy ứng dụng.

Ví dụ:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Ứng dụng khởi động và sử dụng các cấu hình môi trường đã được cung cấp.

Nếu ứng dụng sử dụng MySQL, bạn phải cấu hình đúng địa chỉ máy chủ, tên cơ sở dữ liệu, username và password.

Điểm quan trọng: Việc triển khai thành công không tự động làm cho cơ sở dữ liệu MySQL trên máy tính cá nhân trở thành cơ sở dữ liệu có thể truy cập từ Render. Nếu ứng dụng cần MySQL, bạn phải cung cấp một cơ sở dữ liệu có thể truy cập từ môi trường triển khai và cấu hình kết nối phù hợp.

Bước 7. Kiểm tra trạng thái và logs

Sau khi ứng dụng khởi chạy, hãy kiểm tra trạng thái dịch vụ và đọc log.

Bạn cần xác nhận:

  • Quá trình build đã hoàn thành.
  • Ứng dụng không bị dừng ngay sau khi khởi động.
  • Cổng mạng được cấu hình phù hợp.
  • Kết nối cơ sở dữ liệu hoạt động.
  • Không có lỗi cấu hình khiến API không phản hồi.

Nếu dịch vụ không hoạt động, đừng vội sửa mã nguồn một cách ngẫu nhiên. Hãy xác định lỗi xuất hiện ở giai đoạn build hay runtime trước.

Bước 8. Kiểm tra API công khai

Khi dịch vụ đã hoạt động, Render cung cấp URL công khai cho Web Service.

Ví dụ:

https://product-api-example.onrender.com

Bạn có thể kiểm tra endpoint:

GET https://product-api-example.onrender.com/api/hello

Có thể sử dụng trình duyệt, Postman hoặc frontend để gửi request.

Nếu endpoint trả về kết quả mong đợi, bạn đã hoàn thành bước triển khai API cơ bản.

Tuy nhiên, một endpoint trả về thành công chưa đủ để kết luận toàn bộ hệ thống đã sẵn sàng cho production. Bạn vẫn cần kiểm tra database, xác thực, phân quyền, CORS, HTTPS và các API nghiệp vụ khác.

2.5. Render có tự động deploy khi cập nhật GitHub không?

Render có thể tự động triển khai lại dịch vụ khi phát hiện thay đổi trên nhánh Git được cấu hình, tùy theo thiết lập Auto-Deploy và cấu hình repository.

Ví dụ:

Ban đầu, controller trả về:

Java

}

Java
@GetMapping
public String hello() {

}

Bash
git add .
git commit -m "Update hello API"
git push

Nếu Auto-Deploy được bật và các điều kiện triển khai được đáp ứng, Render sẽ bắt đầu quá trình triển khai phiên bản mới.

     |

Nếu build thất bại, bạn cần đọc log để xác định nguyên nhân. Không nên mặc định rằng cứ push code lên GitHub là phiên bản mới sẽ triển khai thành công.

Khi nào nên sử dụng Auto-Deploy?

Auto-Deploy phù hợp khi bạn muốn rút ngắn quy trình cập nhật ứng dụng và hạn chế thao tác thủ công.

Trong quá trình học, bạn nên kiểm tra từng lần triển khai để hiểu rõ:

  • Commit nào đang được triển khai.
  • Build Command có chạy thành công không.
  • Ứng dụng có khởi động được không.
  • API có hoạt động sau khi cập nhật không.

2.7. Những điều cần lưu ý khi deploy Spring Boot lên Render

2.7.1. Cổng chạy của ứng dụng

Không nên cố định cổng 8080 nếu nền tảng yêu cầu ứng dụng sử dụng cổng được cung cấp qua biến môi trường.

Cấu hình thường dùng:

Properties
server.port=${PORT:8080}

2.7.2. Java version

Phiên bản Java sử dụng khi build và chạy phải tương thích với phiên bản mà dự án yêu cầu.

3.2. Phân biệt Git và GitHub

Git và GitHub có liên quan chặt chẽ nhưng không phải là một.

3.2.1. Git là gì?

Git là hệ thống quản lý phiên bản phân tán (Distributed Version Control System).

Git giúp theo dõi lịch sử thay đổi của source code, tạo các phiên bản, quay lại phiên bản trước và hỗ trợ làm việc trên nhiều nhánh phát triển.

Ví dụ, ban đầu API trả về:

Java
@GetMapping
public String hello() {
    return "Hello version 1";
}

Sau đó, bạn sửa thành:

Java
@GetMapping
public String hello() {
    return "Hello version 2";
}

Git có thể ghi lại hai lần thay đổi này thông qua các commit.

3.2.2. GitHub là gì?

GitHub là nền tảng trực tuyến cung cấp nơi lưu trữ repository Git và nhiều tính năng cộng tác trong phát triển phần mềm.

GitHub cho phép bạn:

  • Tạo repository trực tuyến.
  • Xem source code trên trình duyệt.
  • Quản lý nhánh và lịch sử commit.
  • Làm việc nhóm thông qua Pull Request.
  • Kết nối với các nền tảng deploy như Render.

3.6. Tạo file .gitignore cho dự án Spring Boot

3.6.1. .gitignore là gì?

.gitignore là file cấu hình cho Git, dùng để chỉ định các file hoặc thư mục không nên được Git theo dõi.

Đối với dự án Java Spring Boot, một số file không cần thiết phải đưa lên GitHub:

  • File biên dịch .class.
  • Thư mục build target/.
  • Cấu hình riêng của IntelliJ IDEA.
  • File log.
  • File chứa thông tin bí mật.
  • Các file tạm do hệ điều hành hoặc công cụ tạo ra.

Tuy nhiên, không nên loại bỏ toàn bộ file cấu hình của dự án. Ví dụ, pom.xml rất quan trọng vì Render cần thông tin dependency và cấu hình Maven để build ứng dụng.

3.6.4. Vì sao không nên đưa .idea/ lên GitHub?

Những thiết lập này thường không cần thiết cho quá trình build bằng Maven trên Render. Bỏ qua thư mục .idea/ cũng giúp repository gọn hơn.

Tuy nhiên, một số dự án làm việc nhóm có thể chủ động chia sẻ một vài cấu hình IDE. Khi đó, cần quyết định cụ thể file nào nên được theo dõi thay vì mặc định bỏ qua tất cả.

3.7. Kiểm tra thông tin nhạy cảm trước khi push

Đây là bước đặc biệt quan trọng đối với các dự án Spring Boot có MySQL, JWT hoặc OAuth2.

3.7.1. Những thông tin không nên công khai

Ví dụ:

Properties
spring.datasource.username=root
spring.datasource.password=123456

jwt.secret-key=my-secret-key

spring.security.oauth2.client.registration.google.client-secret=my-secret

Các giá trị trên chỉ minh họa những cấu hình không an toàn khi công khai.

Không nên đưa mật khẩu cơ sở dữ liệu, JWT secret, OAuth2 client secret hoặc access token thật lên repository.

Thay vào đó, có thể tham chiếu biến môi trường trong application.properties:

Properties
spring.datasource.url=${SPRING_DATASOURCE_URL}
spring.datasource.username=${SPRING_DATASOURCE_USERNAME}
spring.datasource.password=${SPRING_DATASOURCE_PASSWORD}

jwt.secret-key=${JWT_SECRET_KEY}

Khi triển khai, cấu hình giá trị thật trong Environment của Render.

Lưu ý rằng chỉ dùng biến môi trường chưa đủ nếu bạn vẫn commit một file khác chứa giá trị bí mật thật. Cần kiểm tra toàn bộ repository trước khi push.

3.7.2. Kiểm tra các file chuẩn bị commit

Chạy:

Bash
git status

Sau khi thêm file vào staging, chạy:

Bash
git diff --cached

Lệnh này giúp xem các thay đổi đã được đưa vào staging và chuẩn bị commit.

Hãy đọc phần diff để kiểm tra xem có mật khẩu, token hoặc thông tin riêng tư nào xuất hiện hay không.

3.7.3. Nếu đã lỡ push thông tin bí mật

Nếu một secret thật đã được đưa lên GitHub, chỉ xóa dòng đó trong commit tiếp theo là chưa đủ, vì giá trị cũ có thể vẫn tồn tại trong lịch sử Git.

Bạn cần:

  1. Thu hồi hoặc thay đổi secret đã bị lộ.
  2. Cập nhật ứng dụng và môi trường triển khai bằng giá trị mới.
  3. Nếu cần, làm sạch lịch sử repository theo quy trình phù hợp.
  4. Kiểm tra lại các bản sao, log hoặc nơi khác có thể đã lưu giá trị đó.

Đối với mật khẩu database, JWT secret và OAuth2 client secret, ưu tiên đầu tiên là thay đổi hoặc thu hồi giá trị bị lộ.

3.8. Đưa source code lên GitHub bằng Git

Sau khi đã tạo repository GitHub, khởi tạo Git trong dự án và kiểm tra .gitignore, chúng ta bắt đầu đưa mã nguồn lên GitHub.

Bước 1. Thêm file vào staging

Chạy:

Bash
git add .

Lệnh này đưa các file chưa được bỏ qua bởi .gitignore vào staging.

Staging là khu vực chuẩn bị những thay đổi sẽ được ghi nhận trong commit tiếp theo.

Bước 2. Kiểm tra staging

Chạy:

Bash
git status

Kiểm tra lại danh sách file được chuẩn bị commit.

Nếu có file chứa mật khẩu, token hoặc cấu hình riêng tư, hãy dừng lại và loại bỏ khỏi staging trước khi tiếp tục.

Có thể bỏ một file khỏi staging bằng:

Bash
git restore --staged path/to/file

Lệnh này chỉ bỏ file khỏi staging, không tự động xóa file trên máy tính.

Bước 3. Tạo commit

Chạy:

Bash
git commit -m "Initial Spring Boot project"

Commit ghi nhận một phiên bản của những thay đổi đang nằm trong staging.

Ví dụ, sau commit đầu tiên, repository có thể ghi nhận source code ban đầu của dự án quản lý sản phẩm.

Bước 4. Đặt tên nhánh chính

Nếu cần đặt nhánh hiện tại thành main, chạy:

Bash
git branch -M main

Lệnh này đổi tên nhánh hiện tại thành main. Nếu nhánh đã mang tên đó thì không có thay đổi đáng kể.

Bước 5. Kết nối repository GitHub

Sử dụng URL repository thực tế của bạn:

Bash
git remote add origin https://github.com/your-username/product-management.git

Ví dụ trên cần được thay bằng URL của repository đã tạo.

Kiểm tra remote:

Bash
git remote -v

Nếu repository local đã có remote tên origin, không nên chạy lại lệnh git remote add origin. Hãy kiểm tra cấu hình hiện tại và cập nhật URL nếu thực sự cần.

Bước 6. Push source code lên GitHub

Chạy:

Bash
git push -u origin main

Lệnh này đẩy các commit trên nhánh main lên nhánh tương ứng của remote origin.

Lần đầu kết nối, GitHub có thể yêu cầu xác thực. Hãy sử dụng phương thức xác thực được GitHub hỗ trợ, chẳng hạn đăng nhập qua trình duyệt hoặc dùng SSH đã cấu hình. Không nên nhập mật khẩu tài khoản GitHub vào lệnh hoặc lưu mật khẩu trực tiếp trong source code.

Nếu lệnh chạy thành công, bạn sẽ thấy các file xuất hiện trong repository trên GitHub.

3.9. Kiểm tra source code sau khi push

Sau khi push, mở trang repository trên GitHub.

Kiểm tra các thành phần:

product-management/
├── src/
├── mvnw
├── mvnw.cmd
├── pom.xml
└── .gitignore

Cấu trúc thực tế có thể khác tùy dự án, nhưng cần bảo đảm các file cần thiết để build ứng dụng đã được đưa lên.

Checklist kiểm tra

  • [ ] Repository GitHub đã được tạo.
  • [ ] Source code xuất hiện trên GitHub.
  • [ ] Có file pom.xml.
  • [ ] Có mã nguồn trong thư mục src/.
  • [ ] Có Maven Wrapper nếu dự án sử dụng Wrapper.
  • [ ] .gitignore đã loại bỏ các file không cần thiết.
  • [ ] Không có mật khẩu database hoặc secret thật trong mã nguồn.
  • [ ] Có thể xem lịch sử commit.
  • [ ] Đã xác định repository là Public hay Private.
  • [ ] Repository sẵn sàng để kết nối với Render.

Nếu repository là Private, bạn cần bảo đảm tài khoản hoặc tích hợp dùng để triển khai có quyền truy cập repository đó.

3.10. Cập nhật source code sau khi đã push

Trong quá trình phát triển, bạn sẽ thường xuyên sửa code và cần cập nhật phiên bản mới lên GitHub.

Ví dụ, bạn thay đổi controller:

Java
@GetMapping
public String hello() {
    return "Hello from Spring Boot version 2";
}

Sau đó, thực hiện ba bước cơ bản.

Bước 1. Stage các thay đổi

Bash
git add .

Bước 2. Tạo commit mới

Bash
git commit -m "Update hello API"

Bước 3. Push lên GitHub

Bash
git push

Khi push thành công, repository GitHub sẽ nhận commit mới.

Nếu Render đã kết nối với repository và Auto-Deploy được bật, nền tảng có thể bắt đầu quá trình triển khai phiên bản mới.

Quy trình:

Sửa code
   |
   ▼
git add .
   |
   ▼
git commit
   |
   ▼
git push
   |
   ▼
GitHub cập nhật repository
   |
   ▼
Render có thể bắt đầu deploy

Hãy nhớ rằng push code lên GitHub và deploy thành công là hai việc khác nhau. Push thành công chỉ xác nhận mã nguồn đã được cập nhật lên repository; kết quả triển khai còn phụ thuộc vào cấu hình và quá trình build, khởi chạy trên Render.

3.11. Một số lỗi thường gặp khi đưa source code lên GitHub

Lỗi 1. git is not recognized

Nguyên nhân thường gặp:

  • Git chưa được cài đặt.
  • Terminal chưa nhận biến môi trường PATH sau khi cài đặt.

Cách xử lý:

  1. Kiểm tra Git đã được cài đặt chưa.
  2. Mở lại Terminal.
  3. Chạy:
Bash
git --version

Nếu vẫn lỗi, kiểm tra cấu hình PATH hoặc cài đặt Git lại theo hướng dẫn chính thức.

Lỗi 2. remote origin already exists

Nguyên nhân: repository local đã có remote tên origin.

Kiểm tra:

Bash
git remote -v

Nếu URL không đúng, có thể cập nhật:

Bash
git remote set-url origin https://github.com/your-username/product-management.git

Thay bằng URL thực tế của repository.

Lỗi 3. rejected khi push

Một nguyên nhân phổ biến là repository trên GitHub đã có commit mà repository local chưa có, chẳng hạn bạn đã tạo README trực tuyến.

Trước khi xử lý, hãy kiểm tra lịch sử của cả hai repository.

Nếu cần kết hợp lịch sử, có thể phải fetch và merge hoặc rebase theo tình trạng thực tế. Không nên tùy tiện dùng git push --force, vì thao tác này có thể ghi đè lịch sử trên remote.

Để tránh lỗi khi mới học, hãy tạo repository GitHub trống nếu source code đã có sẵn ở máy tính.

Lỗi 4. Authentication failed

Nguyên nhân có thể là:

  • Chưa đăng nhập đúng tài khoản.
  • Phương thức xác thực không phù hợp.
  • Token hoặc thông tin xác thực đã hết hạn.
  • Tài khoản chưa được cấp quyền truy cập repository.

Cách xử lý là xác thực lại bằng phương thức được GitHub hỗ trợ và kiểm tra quyền truy cập repository.

Lỗi 5. Không thấy file trong repository

Nguyên nhân có thể là:

  • Chưa chạy git add.
  • Chưa commit.
  • Chưa push.
  • File bị .gitignore loại bỏ.
  • Đang xem nhầm repository hoặc nhánh.

Kiểm tra lần lượt:

Bash
git status
git log --oneline
git remote -v
git branch

Sau đó đối chiếu với repository và nhánh đang xem trên GitHub.

Lỗi 6. Đã xóa mật khẩu khỏi file nhưng vẫn thấy trong GitHub

Nếu mật khẩu đã xuất hiện trong commit cũ, việc sửa file ở commit mới không xóa giá trị đó khỏi lịch sử.

Cách xử lý ưu tiên là thay đổi hoặc thu hồi thông tin bí mật. Sau đó, đánh giá việc làm sạch lịch sử Git và kiểm tra các bản sao liên quan.

Ghi nhớ trọng tâm
  • Git là công cụ quản lý phiên bản phân tán; GitHub là nền tảng lưu trữ repository trực tuyến và cộng tác.
  • Render cần truy cập source code từ GitHub để build và triển khai ứng dụng Spring Boot.
  • Quy trình cơ bản: git init → tạo .gitignore → git add . → git commit → git branch -M main → git remote add origin → git push -u origin main.
  • .gitignore giúp bỏ qua target/, .idea/, *.class, log, .env và file cấu hình local chứa secret.
  • Không đưa secrets (mật khẩu DB, JWT secret, OAuth2 client secret) lên GitHub. Dùng biến môi trường ${SPRING_DATASOURCE_PASSWORD}, ${JWT_SECRET_KEY}.
  • Nếu secret đã bị push, cần thu hồi hoặc thay đổi giá trị đó ngay — xóa file trong commit mới là chưa đủ.
  • Repository Private vẫn cần bảo vệ secret — không nên xem repository là nơi lưu mật khẩu hay khóa bí mật.
  • Cập nhật source code: git add . → git commit -m "..." → git push.
  • Push code không đồng nghĩa với deploy thành công — kết quả triển khai còn phụ thuộc vào cấu hình và quá trình build/khởi chạy trên Render.
  • Lỗi thường gặp: git is not recognized, remote origin already exists, rejected khi push, Authentication failed, không thấy file trên GitHub, secret vẫn hiện trong lịch sử Git.

4. TẠO WEB SERVICE TRÊN RENDER

4.1. Web Service trên Render là gì?

Web Service là loại dịch vụ dùng để triển khai ứng dụng Backend có khả năng nhận và xử lý các HTTP request từ bên ngoài.

Ví dụ, một ứng dụng Spring Boot cung cấp những API sau:

GET    /api/products
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
DELETE /api/products/{id}

Khi chạy trên máy tính cá nhân, ứng dụng có thể sử dụng địa chỉ:

http://localhost:8080/api/products

Sau khi triển khai thành công trên Render, API có thể được truy cập thông qua URL công khai do Render cung cấp.

Ví dụ minh họa:

https://product-api-example.onrender.com/api/products

URL thực tế sẽ phụ thuộc vào tên dịch vụ và cấu hình của bạn.

Web Service thực hiện những công việc gì?

Khi sử dụng Web Service, Render hỗ trợ quá trình triển khai ứng dụng theo cấu hình của dịch vụ, bao gồm:

  1. Lấy source code từ repository đã kết nối.
  2. Chuẩn bị môi trường build.
  3. Thực hiện Build Command.
  4. Khởi chạy ứng dụng bằng Start Command.
  5. Cung cấp địa chỉ truy cập công khai.
  6. Hiển thị trạng thái dịch vụ và logs.
  7. Hỗ trợ triển khai lại khi source code thay đổi, tùy theo cấu hình Auto-Deploy.

Render quản lý phần lớn hạ tầng của dịch vụ, nhưng lập trình viên vẫn phải cấu hình ứng dụng, bảo mật, kết nối database và xử lý lỗi.

4.2. Chuẩn bị trước khi tạo Web Service

Trước khi truy cập Render, hãy kiểm tra các điều kiện sau.

4.2.1. Dự án Spring Boot đã được đưa lên GitHub

Ví dụ, repository có cấu trúc:

product-management/
├── src/
│   └── main/
│       ├── java/
│       │   └── com/example/product/
│       │       ├── controller/
│       │       ├── service/
│       │       ├── repository/
│       │       └── ProductApplication.java
│       └── resources/
│           └── application.properties
├── mvnw
├── mvnw.cmd
├── pom.xml
└── .gitignore

Đây là cấu trúc minh họa. Dự án thực tế có thể có thêm entity, DTO, cấu hình bảo mật và các thành phần khác.

4.2.2. Dự án có thể build bằng Maven

Trên Windows, mở Terminal tại thư mục gốc của dự án và chạy:

Batch
mvnw.cmd clean package

Trên Linux hoặc macOS:

Bash
./mvnw clean package

Nếu dự án không có Maven Wrapper, có thể sử dụng Maven đã được cài đặt:

Bash
mvn clean package

Nếu build thất bại trên máy tính cá nhân, hãy xử lý lỗi trước khi tiếp tục.

4.2.3. Kiểm tra phiên bản Java

Mở pom.xml và tìm cấu hình phiên bản Java, ví dụ:

XML
<properties>
    <java.version>21</java.version>
</properties>

Đây chỉ là ví dụ. Bạn cần giữ phiên bản Java phù hợp với dự án thực tế.

Môi trường build và runtime trên Render phải tương thích với phiên bản Java mà ứng dụng yêu cầu. Không nên tự ý thay đổi phiên bản chỉ để làm cho quá trình deploy chạy được nếu chưa kiểm tra tính tương thích của dependency.

4.2.4. Kiểm tra thông tin bảo mật

Không đưa các thông tin sau lên repository công khai:

  • Mật khẩu MySQL.
  • JWT secret.
  • OAuth2 client secret.
  • Access token hoặc refresh token thật.
  • Các thông tin xác thực riêng tư khác.

Những giá trị này sẽ được cấu hình trong phần Environment của Web Service khi cần thiết.

4.2.5. Chuẩn bị thông tin kết nối database

Nếu dự án sử dụng MySQL, bạn cần chuẩn bị một cơ sở dữ liệu mà ứng dụng có thể truy cập từ môi trường Render.

Ví dụ, ứng dụng cần:

Database URL
Database name
Database username
Database password

Lưu ý: MySQL đang chạy trên máy tính cá nhân thường không thể được Render truy cập chỉ bằng cách sử dụng localhost. Bạn cần triển khai database ở nơi phù hợp hoặc sử dụng dịch vụ cơ sở dữ liệu có thể truy cập từ ứng dụng.

Trong phần này, chúng ta tập trung tạo Web Service. Cấu hình MySQL production sẽ được thực hiện khi triển khai ứng dụng có sử dụng database.

https://render.com/

Render cung cấp các phương thức đăng nhập theo những tùy chọn hiện hành trên nền tảng.

4.4. Tạo Web Service mới

Bước 1. Mở chức năng tạo dịch vụ

Chọn loại dịch vụ Web Service.

Bước 2. Kết nối repository GitHub

Render sẽ yêu cầu bạn chọn repository chứa mã nguồn ứng dụng.

Nếu GitHub đã được kết nối, hãy tìm repository cần triển khai.

Ví dụ:

Repository: product-management

Tên repository và nhánh ở trên chỉ là ví dụ.

Nếu chưa kết nối GitHub, hãy thực hiện bước kết nối theo hướng dẫn trên giao diện Render và cấp quyền cần thiết.

Bước 3. Chọn repository

Chọn đúng repository chứa pom.xml và source code Spring Boot.

Nếu repository có nhiều dự án con, cần xác định thư mục chứa ứng dụng cần triển khai. Một số cấu hình như Root Directory có thể cần thiết trong trường hợp này.

Ví dụ:

repository/
├── backend/
│   ├── pom.xml
│   └── src/
└── frontend/
    ├── package.json
    └── src/

Nếu Backend nằm trong thư mục backend, bạn cần cấu hình Root Directory phù hợp với cấu trúc repository. Nếu pom.xml nằm ngay tại thư mục gốc, thông thường có thể giữ Root Directory mặc định.

Bước 4. Đặt tên dịch vụ

Nhập tên Web Service.

Ví dụ:

product-management-api

Tên này giúp bạn nhận diện dịch vụ trong Dashboard. URL công khai được tạo theo quy tắc đặt tên và tình trạng khả dụng của Render; tên dịch vụ không nhất thiết luôn là toàn bộ URL cuối cùng.

Bước 5. Chọn Region

Nếu giao diện cho phép lựa chọn Region, hãy chọn khu vực phù hợp với ứng dụng và cơ sở dữ liệu.

Khi có thể, nên cân nhắc đặt Backend gần database để giảm độ trễ mạng.

Nếu Backend và database nằm ở những khu vực khác nhau, request database có thể phải đi qua khoảng cách mạng lớn hơn, làm tăng độ trễ.

4.5. Cấu hình môi trường chạy Spring Boot

Đây là bước quan trọng nhất khi tạo Web Service.

Tùy giao diện và loại dịch vụ, Render có thể yêu cầu bạn cấu hình các mục như Runtime, Root Directory, Build Command, Start Command, Instance Type và Environment Variables.

4.5.1. Runtime

Runtime xác định môi trường dùng để build và chạy ứng dụng.

Đối với dự án Spring Boot sử dụng Maven, bạn cần chọn hoặc cấu hình môi trường Java phù hợp với dự án.

Không nên giả định rằng mọi phiên bản Java đều có sẵn trong mọi runtime hoặc mọi kiểu dịch vụ. Hãy kiểm tra các lựa chọn hiện hành trên giao diện và tài liệu Render.

4.5.2. Root Directory

Root Directory là thư mục gốc mà dịch vụ sử dụng khi thực hiện các lệnh build và chạy ứng dụng.

Nếu pom.xml nằm ngay tại thư mục gốc của repository, thông thường bạn không cần thay đổi mục này.

Ví dụ cấu trúc:

product-management/
├── pom.xml
└── src/

Nếu pom.xml nằm trong thư mục con:

repository/
├── frontend/
└── backend/
    ├── pom.xml
    └── src/

thì cần cấu hình Root Directory trỏ đến backend nếu phù hợp với kiểu dịch vụ đang tạo.

4.5.3. Build Command

Build Command dùng để biên dịch và đóng gói ứng dụng.

Với dự án Maven có Maven Wrapper, có thể bắt đầu bằng:

Bash
./mvnw clean package

Nếu muốn bỏ qua việc chạy test trong lúc build, có thể dùng:

Bash
./mvnw clean package -DskipTests

Cần phân biệt:

  • -DskipTests thường bỏ qua việc thực thi test, nhưng test source vẫn có thể được biên dịch.
  • -Dmaven.test.skip=true có thể bỏ qua cả việc biên dịch và chạy test.

Trong giai đoạn học tập, nên ưu tiên chạy test khi dự án đã có kiểm thử phù hợp. Chỉ bỏ qua test khi hiểu rõ lý do và chấp nhận rủi ro.

Nếu không có Maven Wrapper, bạn cần bảo đảm Maven có sẵn trong môi trường build rồi mới sử dụng:

Bash
mvn clean package

4.5.4. Start Command

Start Command dùng để khởi chạy ứng dụng sau khi build.

Ví dụ:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Tên file JAR phụ thuộc vào cấu hình trong pom.xml.

Bạn cần kiểm tra thư mục target/ sau khi build để biết chính xác tên file được tạo ra.

Nếu không muốn phụ thuộc vào tên phiên bản cụ thể, có thể cân nhắc cấu hình Maven để tạo tên JAR ổn định, hoặc sử dụng lệnh phù hợp với cấu trúc build đã xác minh. Không nên dùng một lệnh wildcard tùy tiện nếu thư mục target/ có nhiều file JAR, vì ứng dụng có thể khởi chạy nhầm file.

4.5.5. Instance Type

Instance Type quyết định loại tài nguyên được cấp cho dịch vụ, tùy theo các gói Render đang cung cấp.

Khi học, hãy kiểm tra các lựa chọn, giới hạn và chi phí hiện hành trước khi chọn.

Không nên mặc định rằng mọi gói đều có cùng khả năng vận hành, tài nguyên hoặc chính sách ngủ khi không hoạt động. Điều này phụ thuộc vào loại dịch vụ và gói cụ thể.

4.6. Cấu hình cổng chạy của Spring Boot

Khi triển khai lên nền tảng, không nên mặc định rằng ứng dụng luôn sử dụng cổng 8080.

Bạn có thể cấu hình application.properties như sau:

Properties
server.port=${PORT:8080}

Giải thích:

  • server.port: cấu hình cổng mà Spring Boot sử dụng.
  • ${PORT:8080}: sử dụng biến môi trường PORT nếu có; nếu không thì dùng 8080.

Ví dụ, nếu môi trường chạy cung cấp:

PORT=10000

thì Spring Boot sẽ sử dụng cổng 10000.

Nếu không có biến môi trường PORT, ứng dụng sử dụng cổng 8080.

Đối với Web Service trên Render, hãy làm theo cách cấu hình cổng được yêu cầu cho loại dịch vụ hiện hành. Không tự đặt một giá trị cổng tùy ý nếu nền tảng yêu cầu ứng dụng sử dụng cổng được cấp.

Ngoài cổng, bạn cũng cần bảo đảm ứng dụng lắng nghe trên giao diện mạng phù hợp với môi trường triển khai. Với cấu hình Spring Boot thông thường, máy chủ web được thiết lập để phục vụ request từ môi trường chạy; nếu bạn chủ động tùy chỉnh địa chỉ bind, hãy kiểm tra để tránh chỉ lắng nghe trên loopback.

4.7. Cấu hình Environment Variables

Environment Variables cho phép truyền cấu hình vào ứng dụng mà không cần ghi giá trị bí mật trực tiếp trong mã nguồn.

Giả sử ứng dụng sử dụng MySQL và JWT, bạn có thể chuẩn bị các biến sau:

Tên biến Mục đích
SPRING_PROFILES_ACTIVEChọn profile chạy ứng dụng
SPRING_DATASOURCE_URLURL kết nối database
SPRING_DATASOURCE_USERNAMETên đăng nhập database
SPRING_DATASOURCE_PASSWORDMật khẩu database
JWT_SECRET_KEYKhóa bí mật dùng trong cấu hình JWT nếu ứng dụng yêu cầu
PORTCổng chạy nếu môi trường cung cấp biến này

Danh sách trên là ví dụ. Chỉ tạo các biến mà ứng dụng thực sự sử dụng và tuân theo quy ước cấu hình trong dự án.

Ví dụ cấu hình application.properties

Properties
spring.application.name=product-management

spring.profiles.active=${SPRING_PROFILES_ACTIVE:prod}

server.port=${PORT:8080}

spring.datasource.url=${SPRING_DATASOURCE_URL}
spring.datasource.username=${SPRING_DATASOURCE_USERNAME}
spring.datasource.password=${SPRING_DATASOURCE_PASSWORD}

Nếu ứng dụng sử dụng các cấu hình JWT, hãy tham chiếu đúng tên biến mà lớp cấu hình của dự án đang đọc.

Ví dụ:

Properties
jwt.secret-key=${JWT_SECRET_KEY}

Cấu hình này chỉ hoạt động nếu ứng dụng thực sự sử dụng thuộc tính jwt.secret-key.

Thêm biến môi trường trên Render

Trong quá trình tạo dịch vụ hoặc sau khi tạo xong, tìm phần Environment của Web Service.

Thêm các cặp tên biến và giá trị tương ứng.

Ví dụ minh họa:

SPRING_PROFILES_ACTIVE = prod
SPRING_DATASOURCE_URL = jdbc:mysql://database-host:3306/product_management
SPRING_DATASOURCE_USERNAME = app_user
SPRING_DATASOURCE_PASSWORD = [giá trị bí mật]

Các giá trị trên chỉ minh họa cách cấu hình. Bạn phải sử dụng thông tin kết nối thực tế của database đang triển khai.

Không công khai mật khẩu database hoặc JWT secret trong tài liệu, repository hay ảnh chụp màn hình chia sẻ công khai.

Sau khi thay đổi Environment Variables, dịch vụ có thể cần được khởi động lại hoặc triển khai lại để nhận cấu hình mới, tùy loại thay đổi và cơ chế của nền tảng.

4.9.1. Theo dõi Build Logs

Trong quá trình build, hãy mở phần Logs hoặc thông tin triển khai tương ứng trên Dashboard.

Build Logs giúp bạn phát hiện các lỗi như:

  • Không tìm thấy pom.xml.
  • Maven không thể tải dependency.
  • Phiên bản Java không tương thích.
  • Mã nguồn không biên dịch được.
  • Build Command sai.
  • Không tạo được file JAR.

Nếu lỗi xuất hiện trong giai đoạn build, hãy xử lý nguyên nhân trước khi kiểm tra API.

4.9.2. Theo dõi Runtime Logs

Nếu build thành công nhưng ứng dụng không chạy được, hãy kiểm tra Runtime Logs.

Một số lỗi thường gặp:

Unable to access jarfile

Có thể Start Command đang trỏ đến file JAR không tồn tại.

Failed to configure a DataSource

Có thể ứng dụng thiếu cấu hình datasource hoặc chưa cung cấp các biến môi trường cần thiết.

Communications link failure

Có thể ứng dụng không kết nối được đến MySQL do URL, thông tin đăng nhập, mạng hoặc cấu hình database.

Đây là các ví dụ minh họa. Cần đọc toàn bộ thông báo lỗi và nguyên nhân gốc trong log trước khi sửa cấu hình.

4.9.3. Kiểm tra trạng thái dịch vụ

Sau khi triển khai, xem trạng thái dịch vụ trong Dashboard.

Khi dịch vụ được báo là hoạt động, bạn vẫn nên gửi request thử để xác nhận API thực sự hoạt động như mong muốn.

Trạng thái dịch vụ và kết quả của một endpoint cụ thể không hoàn toàn giống nhau: ứng dụng có thể khởi chạy nhưng một số API vẫn lỗi do database, quyền truy cập hoặc cấu hình nghiệp vụ.

4.10. Kiểm tra URL công khai của Web Service

Sau khi tạo Web Service, Render cung cấp URL công khai của dịch vụ.

Ví dụ:

https://product-management-api.onrender.com

Đây chỉ là URL minh họa.

Giả sử controller của bạn được khai báo như sau:

Java
@RestController
@RequestMapping("/api/hello")
public class HelloController {

    @GetMapping
    public String hello() {
        return "Hello from Spring Boot!";
    }
}

Bạn có thể kiểm tra API bằng cách gửi request:

HTTP
GET /api/hello

Đến URL đầy đủ:

https://product-management-api.onrender.com/api/hello

Kết quả mong đợi:

Hello from Spring Boot!

Bạn có thể sử dụng:

  • Trình duyệt cho endpoint GET đơn giản.
  • Postman để kiểm tra các HTTP method khác nhau.
  • Frontend React để gọi API.
  • Công cụ kiểm thử tự động để kiểm tra các endpoint.

Nếu API trả về 401 Unauthorized, hãy kiểm tra xem endpoint có yêu cầu JWT hay không. Nếu API trả về 403 Forbidden, hãy kiểm tra quyền truy cập. Đây không nhất thiết là lỗi deploy.

Nếu nhận được 404 Not Found, hãy kiểm tra URL, mapping controller và context path.

4.11. Những lỗi thường gặp khi tạo Web Service

Lỗi 1. Render không tìm thấy pom.xml

Nguyên nhân có thể:

  • Chọn sai repository.
  • pom.xml nằm trong thư mục con.
  • Root Directory chưa được cấu hình đúng.

Cách xử lý:

Kiểm tra cấu trúc repository trên GitHub và đặt Root Directory phù hợp.

Lỗi 2. Build thất bại do phiên bản Java

Nguyên nhân có thể:

Phiên bản Java trong môi trường build không tương thích với dự án.

Cách xử lý:

  1. Kiểm tra java.version trong pom.xml.
  2. Kiểm tra phiên bản Java mà môi trường build hỗ trợ.
  3. Đồng bộ cấu hình build và runtime.
  4. Build lại và xem log mới.

Lỗi 3. Không tìm thấy file JAR

Nguyên nhân có thể:

Start Command sử dụng tên file không đúng.

Cách xử lý:

Build dự án và kiểm tra tên JAR thực tế trong target/. Cập nhật Start Command cho phù hợp.

Lỗi 4. Ứng dụng chạy nhưng không truy cập được

Nguyên nhân có thể:

  • Ứng dụng sử dụng cổng không phù hợp.
  • Start Command chưa chạy đúng ứng dụng.
  • Dịch vụ chưa hoàn tất triển khai.
  • Request gửi đến sai URL hoặc endpoint.

Cách xử lý:

Kiểm tra trạng thái dịch vụ, cấu hình server.port, Runtime Logs và URL thực tế.

Lỗi 5. Ứng dụng không kết nối được MySQL

Nguyên nhân có thể:

  • Chưa cung cấp biến môi trường.
  • URL database không đúng.
  • Username hoặc password không đúng.
  • Database chưa cho phép kết nối từ môi trường chạy ứng dụng.
  • Database chưa hoạt động hoặc cấu hình mạng chưa phù hợp.

Cách xử lý:

Kiểm tra cấu hình datasource và logs. Không sử dụng localhost với giả định rằng đó là MySQL trên máy tính cá nhân.

Lỗi 6. API trả về 401 hoặc 403

Nguyên nhân có thể:

API đang được bảo vệ bằng Spring Security hoặc yêu cầu quyền truy cập.

Kiểm tra cấu hình Security, token gửi trong header và quyền của người dùng. Không nên tắt bảo mật chỉ để làm cho request thử nghiệm trả về 200 OK.

Ghi nhớ trọng tâm
  • Web Service trên Render dùng để triển khai Backend Spring Boot cung cấp REST API qua HTTP/HTTPS.
  • Render hỗ trợ: lấy source code từ GitHub, build, khởi chạy ứng dụng, cấp URL công khai, hiển thị logs, auto-deploy.
  • Chuẩn bị trước khi tạo Web Service: dự án đã đưa lên GitHub, build được bằng Maven, kiểm tra phiên bản Java, không có secret trong source code, chuẩn bị thông tin kết nối database.
  • Các bước tạo Web Service: đăng nhập Render → tạo Web Service → chọn repository và branch → cấu hình Root Directory → đặt tên dịch vụ → chọn Region.
  • Cấu hình môi trường chạy: Runtime (Java), Root Directory (thư mục chứa pom.xml), Build Command (./mvnw clean package), Start Command (java -jar target/...), Instance Type.
  • Cấu hình cổng: server.port=${PORT:8080} — dùng biến PORT nếu có, mặc định 8080.
  • Environment Variables truyền cấu hình: SPRING_PROFILES_ACTIVE, SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME, SPRING_DATASOURCE_PASSWORD, JWT_SECRET_KEY, PORT.
  • Checklist trước khi tạo: Repository, Branch, Root Directory, Runtime, Build Command, Start Command, Environment Variables, Database, Secrets, Instance Type.
  • Quá trình deploy: tạo Web Service → lấy source code → chuẩn bị môi trường → build → khởi chạy → kiểm tra URL và API.
  • Build Logs phát hiện lỗi: không tìm thấy pom.xml, dependency, phiên bản Java, biên dịch, build command, JAR.
  • Runtime Logs phát hiện lỗi: Unable to access jarfile, Failed to configure a DataSource, Communications link failure.
  • Lỗi thường gặp: không tìm thấy pom.xml, build thất bại do Java, không tìm thấy JAR, ứng dụng không truy cập được, không kết nối được MySQL, API trả về 401/403.
  • Không dùng localhost cho database trong môi trường Render — cần dùng địa chỉ database từ xa và biến môi trường.

5. CẤU HÌNH BUILD COMMAND VÀ START COMMAND

5.1. Build Command là gì?

Build Command là lệnh mà nền tảng triển khai sử dụng để xây dựng ứng dụng từ source code.

Đối với dự án Java Spring Boot sử dụng Maven, quá trình build thường bao gồm:

  1. Đọc cấu hình trong pom.xml.
  2. Kiểm tra và tải các dependency cần thiết.
  3. Biên dịch mã nguồn Java.
  4. Xử lý tài nguyên của ứng dụng.
  5. Biên dịch mã kiểm thử nếu được yêu cầu.
  6. Chạy các bài kiểm thử theo cấu hình Maven.
  7. Đóng gói ứng dụng thành file JAR nếu quá trình build thành công.

Ví dụ, Build Command có thể là:

Bash
./mvnw clean package

Lệnh này sử dụng Maven Wrapper để thực hiện quá trình build dự án.

5.1.1. Vì sao cần Build Command?

Source code Java thông thường không thể được triển khai như một ứng dụng Spring Boot hoàn chỉnh chỉ bằng cách đưa các file .java lên máy chủ.

Ví dụ, repository có cấu trúc:

product-management/
├── src/
│   └── main/
│       ├── java/
│       │   └── com/example/product/
│       │       └── ProductApplication.java
│       └── resources/
│           └── application.properties
├── mvnw
├── pom.xml
└── .gitignore

Trong repository này, chúng ta có mã nguồn và cấu hình Maven, nhưng chưa chắc đã có file JAR để chạy.

Sau khi build thành công, Maven có thể tạo ra cấu trúc:

product-management/
├── src/
├── mvnw
├── pom.xml
└── target/
    ├── classes/
    ├── test-classes/
    └── product-management-0.0.1-SNAPSHOT.jar

File JAR là sản phẩm đóng gói của quá trình build, với điều kiện dự án được cấu hình để tạo JAR thực thi của Spring Boot.

Render cần thực hiện bước build này trước khi khởi chạy ứng dụng nếu dịch vụ được cấu hình theo cách build từ source code.

5.1.2. Build Command có tự chạy ứng dụng không?

Thông thường, không.

Lệnh:

Bash
./mvnw clean package

có nhiệm vụ xây dựng và đóng gói ứng dụng. Nó không phải là lệnh khởi chạy lâu dài ứng dụng Spring Boot sau khi đóng gói.

Để chạy ứng dụng, chúng ta cần sử dụng lệnh khác, chẳng hạn:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Đây chính là điểm khác biệt quan trọng giữa Build Command và Start Command.

5.2. Start Command là gì?

Start Command là lệnh dùng để khởi chạy ứng dụng trong môi trường chạy của dịch vụ.

Với ứng dụng Spring Boot đã được đóng gói thành file JAR thực thi, Start Command thường sử dụng lệnh java -jar.

Ví dụ:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Trong đó:

Thành phần Ý nghĩa
javaKhởi chạy môi trường Java
-jarYêu cầu Java chạy ứng dụng từ file JAR
target/Thư mục Maven thường sử dụng để chứa sản phẩm build
product-management-0.0.1-SNAPSHOT.jarTên file JAR cần chạy

Khi lệnh này được thực thi thành công, Spring Boot sẽ khởi tạo ứng dụng, tạo Spring Application Context, khởi động máy chủ web nhúng và bắt đầu tiếp nhận request theo cấu hình.

Ví dụ:

      |

      |
      ▼
Ứng dụng sẵn sàng nhận HTTP request

Tên file JAR trong ví dụ chỉ mang tính minh họa. Bạn phải sử dụng tên phù hợp với dự án thực tế.

5.4. Tìm hiểu Maven Wrapper

Khi tạo Web Service cho dự án Maven, bạn có thể thấy hai cách viết Build Command:

Bash
./mvnw clean package

và:

Bash
mvn clean package

Hai lệnh này có liên quan đến Maven, nhưng cách sử dụng khác nhau.

5.4.1. Maven là gì?

Maven là công cụ quản lý dự án Java, hỗ trợ:

  • Quản lý thư viện phụ thuộc.
  • Biên dịch source code.
  • Chạy test.
  • Đóng gói ứng dụng.
  • Thực hiện các bước trong vòng đời build.

Cấu hình Maven của dự án thường nằm trong file:

pom.xml

5.4.2. Maven Wrapper là gì?

Maven Wrapper là tập hợp file cho phép dự án sử dụng một phiên bản Maven được xác định trong cấu hình Wrapper mà không yêu cầu người dùng phải tự cài Maven theo cách thông thường.

Các file thường gặp:

project/
├── mvnw
├── mvnw.cmd
└── .mvn/
    └── wrapper/
        ├── maven-wrapper.properties
        └── ...

Trong đó:

  • mvnw thường được sử dụng trên Linux và macOS.
  • mvnw.cmd thường được sử dụng trên Windows.
  • .mvn/wrapper/ chứa cấu hình và các thành phần liên quan đến Maven Wrapper.

Trên Render, môi trường chạy lệnh thường là Linux. Vì vậy, nếu dự án có Maven Wrapper đầy đủ và có thể thực thi, bạn thường sử dụng:

Bash
./mvnw clean package

5.4.3. Vì sao nên ưu tiên Maven Wrapper?

Maven Wrapper giúp dự án chủ động hơn về phiên bản Maven sử dụng.

Ví dụ, máy tính của lập trình viên có thể đang cài Maven phiên bản A, trong khi máy chủ triển khai có Maven phiên bản B.

Nếu sử dụng Maven Wrapper được cấu hình đúng, dự án có thể sử dụng phiên bản Maven đã được chỉ định, giảm nguy cơ khác biệt giữa các môi trường.

Tuy nhiên, Maven Wrapper không tự bảo đảm toàn bộ môi trường giống nhau. Bạn vẫn cần kiểm tra phiên bản Java, dependency, cấu hình và những yêu cầu khác của dự án.

5.4.4. Nếu repository không có Maven Wrapper thì sao?

Nếu dự án không có mvnw, bạn có thể sử dụng:

Bash
mvn clean package

Nhưng cần bảo đảm môi trường build có Maven phù hợp.

Nếu Maven không tồn tại trong môi trường chạy lệnh, bạn có thể gặp lỗi tương tự:

mvn: command not found

Với người mới học, nên kiểm tra repository và cân nhắc thêm Maven Wrapper vào dự án để việc build dễ tái lập hơn.

5.5. Tìm hiểu các thành phần trong Build Command

Chúng ta sẽ phân tích lệnh:

Bash
./mvnw clean package

5.5.1. ./mvnw

Đây là cách gọi Maven Wrapper trên hệ điều hành kiểu Unix như Linux.

Dấu ./ có nghĩa là gọi chương trình trong thư mục hiện tại.

Vì vậy, lệnh này yêu cầu môi trường chạy tìm file mvnw tại thư mục hiện tại và thực thi nó.

Nếu Root Directory không trỏ đến thư mục chứa file mvnw, lệnh có thể thất bại.

5.5.2. clean

clean là một Maven goal thuộc vòng đời clean, có nhiệm vụ xóa các sản phẩm build trước đó, thường là thư mục target/.

Ví dụ, trước khi build, thư mục có thể chứa:

target/
├── classes/
└── product-management-old.jar

Sau khi thực hiện giai đoạn clean, những sản phẩm build cũ trong thư mục target/ được xóa theo cấu hình Maven Clean Plugin.

Mục đích là hạn chế việc sử dụng nhầm sản phẩm build cũ.

5.5.3. package

package là một phase trong vòng đời build của Maven.

Với dự án Spring Boot được cấu hình phù hợp, phase này thực hiện các bước cần thiết trước đó rồi đóng gói ứng dụng thành file JAR hoặc định dạng được cấu hình.

Ví dụ:

Bash
./mvnw clean package

Có thể hiểu đơn giản là:

  1. Xóa sản phẩm build cũ.
  2. Thực hiện các bước build cần thiết.
  3. Đóng gói ứng dụng.

5.5.4. Có nên sử dụng install thay cho package?

Maven có các phase như package và install.

Ví dụ:

Bash
./mvnw clean install

install thực hiện các bước trước đó trong vòng đời tương ứng và sau đó cài đặt artifact vào Maven local repository.

Với một Web Service Spring Boot đơn lẻ, thông thường bạn không cần install chỉ để tạo file JAR chạy ứng dụng. package thường đã đủ cho mục tiêu này.

5.6. Cấu hình Build Command trên Render

Giả sử repository của bạn có cấu trúc:

product-management/

│   └── wrapper/

├── mvnw.cmd

Bước 1. Mở Web Service

Truy cập Dashboard Render và chọn Web Service mà bạn đã tạo ở phần trước.

Nếu chưa tạo dịch vụ, hãy hoàn thành quy trình tạo Web Service trước khi thực hiện bước này.

Bước 2. Tìm cấu hình Build Command

Mở phần cấu hình dịch vụ. Tùy giao diện Render hiện hành, vị trí chỉnh sửa Build Command có thể nằm trong phần Settings hoặc mục cấu hình build và deploy.

Bước 3. Nhập Build Command

Bash

Bash
./mvnw clean package -DskipTests

Không nên mặc định bỏ qua test cho mọi dự án. Trong môi trường production, kiểm thử giúp phát hiện lỗi trước khi đưa phiên bản mới lên chạy.

Bước 4. Kiểm tra Root Directory

Nếu ứng dụng nằm trong thư mục con, hãy kiểm tra Root Directory để lệnh build được thực thi tại vị trí đúng.

Ví dụ:

repository/

└── backend/
    ├── mvnw
    ├── pom.xml

Trong trường hợp này, nếu dịch vụ triển khai Backend trong backend, hãy cấu hình Root Directory phù hợp với thư mục đó.

Bước 5. Lưu cấu hình và thực hiện deploy

Sau khi lưu cấu hình, hãy triển khai lại dịch vụ theo giao diện Render.

Theo dõi Build Logs để xác định Maven có thực hiện thành công các bước build hay không.

Lưu ý: Cách đặt tên và vị trí cài đặt Build Command có thể thay đổi theo giao diện Render. Hãy ưu tiên các trường cấu hình thực tế của Web Service đang sử dụng.

5.7. Kiểm tra file JAR sau khi build

Một trong những nguyên nhân thường gặp khiến ứng dụng không khởi chạy là Start Command trỏ đến file JAR không tồn tại.

Để tránh lỗi này, bạn cần biết tên file JAR được tạo ra.

5.7.1. Kiểm tra trên máy tính cá nhân

Trên Windows, mở Terminal tại thư mục dự án và chạy:

Batch
mvnw.cmd clean package

Nếu sử dụng Maven cài sẵn:

Batch
mvn clean package

Sau khi build thành công, kiểm tra thư mục:

target/

Ví dụ:

target/
└── product-management-0.0.1-SNAPSHOT.jar

Tên file thực tế có thể khác.

Trên Windows, bạn có thể liệt kê các file JAR bằng lệnh:

Batch
dir target\*.jar

Trên Linux hoặc macOS:

Bash
ls -lh target/*.jar

5.7.2. Tại sao tên JAR lại khác nhau giữa các dự án?

Tên artifact được tạo ra phụ thuộc vào cấu hình Maven, đặc biệt là thông tin trong pom.xml.

Ví dụ:

XML
<groupId>com.example</groupId>
<artifactId>product-management</artifactId>
<version>0.0.1-SNAPSHOT</version>

Với cấu hình thông thường, Maven có thể tạo file:

product-management-0.0.1-SNAPSHOT.jar

Tên file có thể thay đổi nếu bạn chỉnh sửa artifactId, version, finalName hoặc những cấu hình liên quan.

Vì vậy, không nên sao chép một tên JAR từ tài liệu rồi mặc định rằng dự án của mình cũng có cùng tên.

5.7.3. File JAR nào cần chạy?

Với ứng dụng Spring Boot dùng spring-boot-maven-plugin theo cấu hình thông thường, package có thể tạo JAR thực thi chứa ứng dụng và các dependency cần thiết.

Tuy nhiên, một số cấu hình build có thể tạo thêm file JAR ban đầu, chẳng hạn file có hậu tố .original.

Ví dụ minh họa:

target/
├── product-management-0.0.1-SNAPSHOT.jar
└── product-management-0.0.1-SNAPSHOT.jar.original

Trong cấu hình Spring Boot Maven Plugin thông thường, file .jar đã được plugin đóng gói lại mới là file cần dùng với java -jar.

Không nên chạy file .jar.original nếu mục tiêu là khởi chạy executable JAR đã được Spring Boot đóng gói.

5.8. Cấu hình Start Command trên Render

Sau khi xác định tên file JAR, bạn có thể cấu hình Start Command.

Giả sử file được tạo ra là:

target/product-management-0.0.1-SNAPSHOT.jar

Start Command tương ứng:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Bước 1. Mở cấu hình Web Service

Truy cập Dashboard và chọn dịch vụ cần cấu hình.

Bước 2. Tìm Start Command

Tìm trường Start Command trong phần cấu hình build/deploy hoặc Settings tùy giao diện hiện hành.

Bước 3. Nhập lệnh chạy ứng dụng

Nhập:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Thay tên file ví dụ bằng tên JAR thực tế của dự án.

Bước 4. Lưu và deploy

Lưu cấu hình rồi thực hiện deploy lại nếu Render yêu cầu.

Sau khi quá trình build và khởi chạy hoàn tất, hãy kiểm tra Runtime Logs.

Nếu Spring Boot khởi động thành công, logs thường sẽ hiển thị thông tin liên quan đến việc khởi tạo ứng dụng và máy chủ web.

5.8.1. Có thể sử dụng java -jar target/*.jar không?

Không nên sử dụng wildcard một cách tùy tiện:

Bash
java -jar target/*.jar

Lý do là thư mục target/ có thể chứa nhiều file JAR. Khi wildcard khớp nhiều file, lệnh có thể không hoạt động như mong muốn hoặc không xác định đúng file cần chạy.

Cách an toàn hơn cho người mới học là chỉ rõ file JAR thực tế:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Nếu muốn dùng tên file ổn định, bạn có thể cấu hình finalName trong Maven. Tuy nhiên, cần kiểm tra tương tác với Spring Boot Maven Plugin để chắc chắn file được tạo ra có đúng tên và đúng định dạng mong muốn.

5.9. Cấu hình Maven để tạo tên JAR dễ quản lý

Để tránh phải cập nhật Start Command mỗi khi thay đổi phiên bản ứng dụng, bạn có thể cân nhắc cấu hình tên file ổn định.

Ví dụ trong pom.xml:

XML
<build>
    <finalName>product-management</finalName>
</build>

Khi cấu hình này được áp dụng, tên artifact được đóng gói thường sẽ là:

target/product-management.jar

Khi đó, Start Command có thể là:

Bash
java -jar target/product-management.jar

Giải thích

finalName cho phép đặt tên cuối cùng cho artifact được tạo ra trong quá trình build.

Nếu không khai báo, Maven thường tạo tên dựa trên artifactId và version.

Khi khai báo:

XML
<finalName>product-management</finalName>

bạn không cần đưa phiên bản vào tên file trong Start Command.

Tuy nhiên, cần nhớ:

  • Tên file phải thực sự được tạo ra sau khi build.
  • Dự án phải được cấu hình để tạo executable JAR.
  • Không được giả định rằng finalName tự bổ sung toàn bộ cấu hình Spring Boot còn thiếu.

Sau khi thay đổi pom.xml, hãy build lại trên máy tính cá nhân để xác minh:

Bash
./mvnw clean package

Trên Windows:

Batch
mvnw.cmd clean package

Sau đó kiểm tra:

target/product-management.jar

Nếu file tồn tại và có thể khởi chạy thành công trên môi trường phù hợp, bạn mới nên cập nhật Start Command theo tên mới.

5.10. Tìm hiểu cấu hình pom.xml liên quan đến executable JAR

Để java -jar khởi chạy được ứng dụng Spring Boot, dự án cần được cấu hình phù hợp để tạo JAR thực thi.

Ví dụ phần cấu hình Maven có thể bao gồm:

XML
<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>

Đây là ví dụ cấu hình plugin. Dự án thực tế cần có các dependency, parent hoặc cấu hình phiên bản tương thích theo cách quản lý dependency mà dự án đang sử dụng.

Vai trò của Spring Boot Maven Plugin

Plugin này hỗ trợ các tác vụ liên quan đến build ứng dụng Spring Boot. Với cấu hình phù hợp, plugin có thể đóng gói JAR theo dạng executable JAR để chạy bằng:

Bash
java -jar target/product-management.jar

Nếu dự án thiếu cấu hình cần thiết, quá trình build có thể tạo ra JAR không thể khởi chạy theo cách mong muốn.

Kiểm tra khi java -jar thất bại

Nếu nhận được lỗi liên quan đến manifest hoặc không tìm thấy lớp chính, hãy kiểm tra:

  1. Dự án có sử dụng Spring Boot Maven Plugin hay không.
  2. Plugin có được cấu hình và thực thi trong quá trình package hay không.
  3. File JAR đang chạy có đúng là executable JAR không.
  4. Phiên bản Java đang chạy có tương thích với bytecode của ứng dụng không.
  5. Logs có chỉ ra nguyên nhân cụ thể khác hay không.

Không nên thêm plugin hoặc thay đổi cấu hình một cách máy móc mà chưa kiểm tra cấu hình hiện tại của dự án.

5.11. Quan hệ giữa Java version, Build Command và Start Command

Build thành công không đồng nghĩa chắc chắn ứng dụng sẽ khởi chạy thành công.

Ví dụ, một dự án được biên dịch bằng phiên bản Java mới hơn nhưng môi trường chạy lại sử dụng phiên bản Java thấp hơn có thể gặp lỗi tương thích.

Do đó, cần phân biệt:

  • Build environment: môi trường thực hiện biên dịch và đóng gói.
  • Runtime environment: môi trường thực thi file JAR.

Cả hai cần tương thích với yêu cầu của dự án.

Ví dụ, pom.xml có cấu hình:

XML
<properties>
    <java.version>21</java.version>
</properties>

Đây chỉ là ví dụ. Nếu dự án yêu cầu Java 21, hãy bảo đảm môi trường build và runtime đều đáp ứng yêu cầu tương thích đó.

Các bước kiểm tra:

  1. Xem cấu hình Java trong pom.xml.
  2. Kiểm tra runtime mà Render đang sử dụng.
  3. Xác minh các dependency có yêu cầu Java cao hơn hay không.
  4. Đọc logs khi build và khi khởi chạy.
  5. Điều chỉnh môi trường hoặc cấu hình dự án dựa trên nguyên nhân thực tế.

Không nên chỉ sửa java.version thành một con số thấp hơn để cố gắng deploy, vì dependency hoặc mã nguồn có thể đang cần tính năng của phiên bản Java mới hơn.

5.12. Cấu hình cổng và biến môi trường khi Start Command chạy ứng dụng

Start Command khởi chạy JVM và ứng dụng Spring Boot. Sau khi ứng dụng bắt đầu chạy, nó còn phải sử dụng cấu hình phù hợp với môi trường production.

Ví dụ, trong application.properties:

Properties
spring.application.name=product-management

server.port=${PORT:8080}

Giải thích:

  • spring.application.name đặt tên ứng dụng.
  • server.port xác định cổng mà máy chủ web của Spring Boot sử dụng.
  • ${PORT:8080} sử dụng biến môi trường PORT nếu có, nếu không thì dùng 8080.

Đối với Web Service trên Render, hãy kiểm tra yêu cầu cổng của loại dịch vụ và cấu hình thực tế được cung cấp. Không nên tự giả định một cổng cố định nếu môi trường triển khai yêu cầu cách cấu hình khác.

Start Command có cần ghi cổng không?

Với cách chạy thông thường:

Bash
java -jar target/product-management.jar

bạn không cần truyền cổng trực tiếp trong lệnh nếu ứng dụng đã được cấu hình cổng qua application.properties hoặc biến môi trường.

Nếu cần truyền tham số cho Spring Boot, có thể dùng cú pháp phù hợp, nhưng với người mới học, nên ưu tiên cấu hình rõ ràng và thống nhất giữa application.properties và Environment Variables.

5.13. Những lỗi phổ biến và cách xử lý

Lỗi 1. ./mvnw: Permission denied

Nguyên nhân có thể:

File mvnw chưa có quyền thực thi trong môi trường Linux.

Cách xử lý:

Kiểm tra quyền thực thi của file trong repository. Nếu cần, cấp quyền thực thi trên máy Linux hoặc môi trường phát triển phù hợp rồi commit thay đổi vào Git.

Ví dụ trên Linux/macOS:

Bash
chmod +x mvnw
git add mvnw
git commit -m "Make Maven Wrapper executable"
git push

Sau đó triển khai lại.

Lỗi 2. ./mvnw: No such file or directory

Nguyên nhân có thể:

  • Repository không có file mvnw.
  • Root Directory trỏ đến thư mục không chứa mvnw.
  • Cấu trúc repository khác với cấu hình dự kiến.

Cách xử lý:

Kiểm tra repository GitHub và Root Directory. Nếu dự án chưa có Maven Wrapper, hãy bổ sung đúng cách hoặc sử dụng Maven đã được cài trong môi trường build.

Lỗi 3. mvn: command not found

Nguyên nhân có thể:

Build Command sử dụng mvn, nhưng môi trường build không có Maven trong PATH.

Cách xử lý:

Cân nhắc sử dụng Maven Wrapper nếu dự án đã có Wrapper đầy đủ:

Bash
./mvnw clean package

Lỗi 4. BUILD FAILURE

Nguyên nhân có thể:

  • Source code có lỗi biên dịch.
  • Dependency không tải được.
  • Test thất bại.
  • Phiên bản Java không tương thích.
  • Cấu hình pom.xml chưa đúng.

Cách xử lý:

Đọc phần lỗi đầu tiên có ý nghĩa trong Build Logs, xác định nguyên nhân gốc rồi sửa. Không nên chỉ nhìn dòng BUILD FAILURE cuối cùng vì dòng đó thường chỉ là kết luận.

Lỗi 5. Unable to access jarfile

Ví dụ:

Error: Unable to access jarfile target/app.jar

Nguyên nhân có thể:

Start Command đang trỏ đến file không tồn tại.

Ví dụ, file thực tế là:

target/product-management-0.0.1-SNAPSHOT.jar

nhưng lệnh chạy lại là:

Bash
java -jar target/app.jar

Cách xử lý:

Kiểm tra tên JAR thực tế và sửa Start Command:

Bash
java -jar target/product-management-0.0.1-SNAPSHOT.jar

Lỗi 6. no main manifest attribute

Nguyên nhân có thể:

File JAR không có thông tin cần thiết để chạy trực tiếp bằng java -jar, hoặc bạn đang chạy nhầm file JAR.

Cách xử lý:

  • Kiểm tra Spring Boot Maven Plugin.
  • Kiểm tra quá trình package.
  • Xác nhận file JAR cần chạy.
  • Build lại rồi kiểm tra kết quả.

Lỗi 7. UnsupportedClassVersionError

Nguyên nhân có thể:

Ứng dụng được biên dịch bằng phiên bản Java không tương thích với phiên bản Java runtime đang sử dụng.

Cách xử lý:

Kiểm tra phiên bản Java ở cả môi trường build và runtime. Đồng bộ chúng theo yêu cầu thực tế của dự án và dependency.

Lỗi 8. Build thành công nhưng ứng dụng thoát ngay sau khi khởi chạy

Nguyên nhân có thể:

  • Ứng dụng gặp exception trong quá trình khởi tạo.
  • Không kết nối được database.
  • Thiếu biến môi trường bắt buộc.
  • Cấu hình Spring Profile sai.
  • Có lỗi trong quá trình khởi tạo bean.

Cách xử lý:

Kiểm tra Runtime Logs. Không nên kết luận rằng Start Command sai chỉ vì ứng dụng không chạy được; lệnh có thể đã khởi chạy đúng nhưng ứng dụng bị lỗi bên trong.

Ví dụ:

student-management/
├── .mvn/
│   └── wrapper/
├── src/
│   └── main/
│       ├── java/
│       │   └── com/example/student/
│       │       ├── StudentApplication.java
│       │       └── controller/

6.2.2. Lớp khởi chạy ứng dụng

File StudentApplication.java:

Java
package com.example.student;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class StudentApplication {

    public static void main(String[] args) {
        SpringApplication.run(StudentApplication.class, args);
    }
}

Giải thích:

  • @SpringBootApplication đánh dấu lớp cấu hình chính của Spring Boot.
  • main() là điểm bắt đầu khi chạy chương trình Java.
  • SpringApplication.run() khởi tạo Spring Boot và khởi chạy ứng dụng.

Khi Render thực thi Start Command bằng java -jar, JVM sẽ khởi chạy ứng dụng đã được đóng gói. Spring Boot sau đó thực hiện quá trình khởi tạo các thành phần cần thiết.

6.2.3. Tạo REST API kiểm tra

File HelloController.java:

Java
package com.example.student.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public String hello() {
        return "Hello from Spring Boot on Render!";
    }
}

Giải thích:

  • @RestController khai báo controller phục vụ các HTTP request và trả dữ liệu trực tiếp về client.
  • @GetMapping("/api/hello") ánh xạ request GET vào phương thức hello().
  • return trả về nội dung phản hồi.

Sau khi chạy ứng dụng, endpoint có thể được gọi tại:

HTTP
GET http://localhost:8080/api/hello

Kết quả mong đợi:

Hello from Spring Boot on Render!

Đây là endpoint kiểm tra đơn giản. Trong dự án thực tế, bạn cần kiểm tra các API nghiệp vụ của mình.

http://localhost:8080/api/hello

Nếu API hoạt động ở môi trường phát triển, bạn đã có cơ sở tốt hơn để tiếp tục triển khai. Tuy nhiên, kết quả chạy local không bảo đảm deploy sẽ thành công, vì môi trường Render có thể khác về Java, biến môi trường, mạng và database.

6.4. Cấu hình application.properties

File application.properties chứa các cấu hình của ứng dụng Spring Boot.

Ví dụ:

Properties

server.port=${PORT:8080}

6.4.1. Cấu hình tên ứng dụng

Properties
spring.application.name=student-management

Thuộc tính này đặt tên ứng dụng trong môi trường Spring.

6.4.2. Cấu hình cổng chạy

Properties
server.port=${PORT:8080}

Giải thích:

  • server.port là thuộc tính cấu hình cổng của máy chủ web Spring Boot.
  • PORT là tên biến môi trường được tham chiếu.
  • 8080 là giá trị mặc định nếu biến môi trường không tồn tại.

Cách cấu hình này cho phép ứng dụng nhận cổng từ môi trường khi có biến PORT, thay vì luôn cố định cổng trong source code.

Lưu ý: Hãy kiểm tra yêu cầu cổng của loại Web Service đang sử dụng trên Render. Không nên tự giả định rằng mọi dịch vụ đều cấp cùng một giá trị cổng.

6.7. Cấu hình Build Command và Start Command

Đây là bước quan trọng trong quá trình tạo hoặc chỉnh sửa Web Service.

6.7.1. Build Command

Nếu dự án có Maven Wrapper và file mvnw nằm tại thư mục làm việc của dịch vụ, có thể sử dụng:

Bash
./mvnw clean package -DskipTests

Tuy nhiên, nên ưu tiên chạy test khi có bộ kiểm thử phù hợp. Bỏ qua test có thể làm giảm khả năng phát hiện lỗi trước khi triển khai.

6.7.2. Start Command

target/student-management-0.0.1-SNAPSHOT.jar

Bash
java -jar target/student-management-0.0.1-SNAPSHOT.jar

Nếu tên file thực tế khác, hãy cập nhật lệnh cho đúng.

6.8. Cấu hình Environment Variables

Environment Variables cho phép ứng dụng nhận cấu hình từ môi trường triển khai.

Với ứng dụng ví dụ chưa sử dụng database hay JWT, bạn có thể chỉ cần cấu hình những biến thực sự cần thiết.

Nếu ứng dụng có MySQL, JWT hoặc các dịch vụ bên ngoài, có thể cần thêm biến môi trường tương ứng.

Ví dụ:

Tên biến Mục đích
SPRING_PROFILES_ACTIVEChọn Spring Profile
SPRING_DATASOURCE_URLURL database
SPRING_DATASOURCE_USERNAMETên đăng nhập database
SPRING_DATASOURCE_PASSWORDMật khẩu database
JWT_SECRET_KEYKhóa bí mật nếu cấu hình JWT sử dụng biến này

Chỉ tạo những biến mà ứng dụng thực sự tham chiếu.

6.8.1. Cấu hình trên Render

Mở Web Service trong Dashboard và tìm phần Environment.

Thêm tên biến cùng giá trị tương ứng.

Ví dụ:

SPRING_PROFILES_ACTIVE = prod

Nếu ứng dụng không sử dụng profile prod, không nên đặt biến này một cách máy móc. Trước tiên, hãy xác nhận cấu hình profile tương ứng trong dự án.

6.8.2. Tham chiếu biến môi trường trong application.properties

Ví dụ:

Properties
spring.application.name=student-management

server.port=${PORT:8080}

spring.profiles.active=${SPRING_PROFILES_ACTIVE:default}

Ở đây, default chỉ là giá trị dự phòng minh họa. Hãy điều chỉnh theo cấu hình thực tế.

Nếu ứng dụng dùng MySQL:

Properties
spring.datasource.url=${SPRING_DATASOURCE_URL}
spring.datasource.username=${SPRING_DATASOURCE_USERNAME}
spring.datasource.password=${SPRING_DATASOURCE_PASSWORD}

Các thuộc tính datasource chỉ nên được thêm khi dự án thực sự sử dụng database và đã có dependency, driver cùng cấu hình cần thiết.

Bảo mật: Không ghi mật khẩu thật hoặc JWT secret trực tiếp trong repository. Hãy quản lý chúng qua Environment Variables hoặc cơ chế quản lý secret phù hợp.

6.9. Thực hiện deploy ứng dụng

Sau khi hoàn thành cấu hình, hãy kiểm tra lại trước khi bắt đầu triển khai.

Checklist trước khi deploy

  • [ ] Source code đã được push lên GitHub.
  • [ ] Repository và branch được chọn đúng.
  • [ ] Root Directory trỏ đến vị trí phù hợp.
  • [ ] Build Command sử dụng đúng Maven Wrapper hoặc Maven.
  • [ ] Start Command trỏ đến đúng file JAR.
  • [ ] Phiên bản Java tương thích với dự án.
  • [ ] Cấu hình server.port phù hợp với môi trường chạy.
  • [ ] Environment Variables bắt buộc đã được thiết lập.
  • [ ] Không có mật khẩu hoặc secret bị đưa lên GitHub.
  • [ ] Database và các dịch vụ phụ thuộc đã sẵn sàng nếu ứng dụng cần sử dụng.

Bước 1. Bắt đầu deploy

Trên giao diện Render, thực hiện thao tác tạo dịch vụ hoặc triển khai theo hướng dẫn hiển thị.

Render sẽ lấy source code từ repository đã kết nối và thực hiện quá trình triển khai.

Bước 2. Theo dõi Build Logs

Trong quá trình build, hãy kiểm tra logs để xác nhận:

  • Repository được lấy thành công.
  • Maven Wrapper hoặc Maven chạy được.
  • Dependency được tải thành công.
  • Source code được biên dịch.
  • Quá trình package hoàn tất.

Nếu Build Command thất bại, ứng dụng thường chưa thể chuyển sang giai đoạn khởi chạy bình thường. Hãy sửa lỗi build trước khi kiểm tra API.

Bước 3. Theo dõi Runtime Logs

Sau khi build, Render sẽ thực hiện khởi chạy ứng dụng theo cấu hình dịch vụ.

Kiểm tra Runtime Logs để xác định:

  • Start Command có chạy được không.
  • File JAR có tồn tại không.
  • JVM có khởi chạy ứng dụng được không.
  • Spring Boot có khởi tạo thành công không.
  • Có lỗi cấu hình, database hoặc bean nào xảy ra không.

Bước 4. Chờ dịch vụ hoàn tất triển khai

Không nên chỉ dựa vào việc Build Command thành công để kết luận rằng ứng dụng đã sẵn sàng.

Cần kiểm tra trạng thái dịch vụ và logs khởi chạy. Sau đó, hãy gửi request thử đến API để xác nhận hoạt động thực tế.

6.12. Các lỗi thường gặp khi deploy

Lỗi 1. Build thất bại

Biểu hiện: Render không hoàn tất giai đoạn build.

Nguyên nhân có thể:

  • Mã nguồn có lỗi biên dịch.
  • Maven không tải được dependency.
  • Phiên bản Java không phù hợp.
  • Root Directory sai.
  • Build Command không đúng.
  • Test thất bại.

Cách xử lý:

  1. Mở Build Logs.
  2. Tìm lỗi cụ thể đầu tiên có ý nghĩa.
  3. Kiểm tra pom.xml, source code và phiên bản Java.
  4. Sửa nguyên nhân rồi deploy lại.

Lỗi 2. Không tìm thấy file JAR

Thông báo ví dụ:

Error: Unable to access jarfile target/app.jar

Nguyên nhân: Start Command trỏ đến tên file không tồn tại.

Cách xử lý:

  • Xác định tên JAR thực tế.
  • Kiểm tra cấu hình Maven.
  • Cập nhật Start Command cho đúng.

Lỗi 3. Java không tương thích

Thông báo có thể liên quan đến UnsupportedClassVersionError.

Cách xử lý:

  • Kiểm tra Java version của dự án.
  • Kiểm tra môi trường build và runtime.
  • Bảo đảm cả hai tương thích với mã nguồn và dependency.

Lỗi 4. Ứng dụng không kết nối được MySQL

Nguyên nhân có thể:

  • Database chưa hoạt động.
  • URL database sai.
  • Username hoặc password sai.
  • Chưa cấu hình biến môi trường.
  • Database không cho phép kết nối từ môi trường triển khai.
  • Cấu hình mạng chưa phù hợp.

Cách xử lý:

Kiểm tra datasource configuration, Environment Variables và Runtime Logs.

Đặc biệt, localhost bên trong môi trường chạy ứng dụng trên Render không mặc định trỏ đến MySQL đang chạy trên máy tính cá nhân của bạn.

Lỗi 5. API trả về 404

Nguyên nhân có thể:

  • URL không đúng.
  • Mapping controller khác với URL đang gọi.
  • Có cấu hình context path.
  • Đang gọi nhầm endpoint.

Cách xử lý:

Đối chiếu URL thực tế với các annotation như @RequestMapping, @GetMapping và cấu hình context path.

Lỗi 6. API trả về 401 hoặc 403

Nếu dự án sử dụng Spring Security, endpoint có thể yêu cầu đăng nhập hoặc quyền truy cập.

Cách xử lý:

  • Kiểm tra cấu hình Security.
  • Kiểm tra endpoint có cần JWT hay không.
  • Kiểm tra header Authorization.
  • Xác minh quyền truy cập theo yêu cầu nghiệp vụ.

Không nên tắt bảo mật chỉ để khiến API thử nghiệm trả về 200 OK.

Lỗi 7. Ứng dụng khởi chạy chậm hoặc request đầu tiên phản hồi chậm

Một số nền tảng hoặc loại dịch vụ có thể áp dụng chính sách tài nguyên và trạng thái hoạt động khác nhau. Vì vậy, thời gian phản hồi có thể khác giữa các gói dịch vụ và trạng thái vận hành.

Cách xử lý:

  • Kiểm tra trạng thái dịch vụ.
  • Kiểm tra logs.
  • Kiểm tra tài nguyên và giới hạn của gói đang dùng.
  • Đánh giá lại thời gian khởi tạo ứng dụng và kết nối database.

Không nên mặc định mọi Web Service đều có cùng chính sách vận hành hoặc thời gian phản hồi.

  • Deploy Spring Boot lên Render gồm 10 bước: chuẩn bị dự án → kiểm tra Maven/Java → đưa source code lên GitHub → tạo Web Service → cấu hình Build Command → cấu hình Start Command → thiết lập Environment Variables → deploy → kiểm tra logs → kiểm tra API.
  • Build Command phổ biến: ./mvnw clean package — build và đóng gói JAR.
  • Start Command phổ biến: java -jar target/<tên-file>.jar — khởi chạy ứng dụng.
  • Cấu hình cổng: server.port=${PORT:8080} — dùng biến PORT nếu có, mặc định 8080.
  • Environment Variables truyền cấu hình: SPRING_PROFILES_ACTIVE, SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME, SPRING_DATASOURCE_PASSWORD, JWT_SECRET_KEY.
  • Build Logs phát hiện lỗi biên dịch, dependency, Java version, Root Directory, Build Command.
  • Runtime Logs phát hiện lỗi JAR không tồn tại, JVM, Spring Boot khởi tạo, database, bean.
  • Kiểm tra API bằng trình duyệt, Postman hoặc cURL. Đọc đúng HTTP status code: 200, 400, 401, 403, 404, 500.
  • Cập nhật ứng dụng: sửa code → build local → commit → push → Render deploy → kiểm tra logs và API.
  • Lỗi thường gặp: build thất bại, không tìm thấy JAR, Java không tương thích, không kết nối MySQL, API trả về 404/401/403, ứng dụng khởi chạy chậm.
  • Không dùng localhost để kết nối MySQL trên máy cá nhân từ Render — cần dùng database từ xa và biến môi trường.
  • Không đưa secrets (mật khẩu DB, JWT secret) vào source code hoặc repository. Dùng Environment Variables.

7. Cấu hình biến môi trường (Environment Variables)

7.1. Biến môi trường là gì?

7.1.1. Khái niệm

Environment Variables (biến môi trường) là những biến cấu hình được lưu trong môi trường hệ điều hành hoặc môi trường chạy ứng dụng.

Các biến này cho phép chúng ta cung cấp thông tin cấu hình cho ứng dụng mà không cần ghi trực tiếp các giá trị đó vào source code.

Ví dụ, một ứng dụng Spring Boot cần những thông tin sau để kết nối MySQL:

  • Tên máy chủ cơ sở dữ liệu.
  • Cổng kết nối cơ sở dữ liệu.
  • Tên database.
  • Tên đăng nhập MySQL.
  • Mật khẩu MySQL.

Thay vì viết trực tiếp các thông tin này vào source code, chúng ta có thể sử dụng biến môi trường.

Ví dụ:

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

Trong đó:

Biến môi trường Ý nghĩa
DB_URLĐịa chỉ kết nối database
DB_USERNAMETên đăng nhập database
DB_PASSWORDMật khẩu database

Khi ứng dụng khởi động, Spring Boot đọc các giá trị tương ứng từ môi trường chạy ứng dụng để sử dụng.

7.1.2. Ví dụ thực tế

Giả sử dự án có file application.properties:

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

Trên Render, chúng ta cấu hình:

DB_URL=jdbc:mysql://example-host:3306/student_management
DB_USERNAME=student_user
DB_PASSWORD=your_database_password

Khi ứng dụng chạy, Spring Boot sử dụng các giá trị đã cấu hình trên Render.

Lưu ý: Những giá trị trên chỉ là ví dụ minh họa. Khi triển khai thật, bạn phải sử dụng thông tin kết nối do nhà cung cấp database cung cấp.

Biến môi trường giúp tách biệt cấu hình triển khai khỏi mã nguồn của ứng dụng.

7.2. Tại sao cần sử dụng biến môi trường?

7.2.1. Bảo vệ thông tin nhạy cảm

Giả sử bạn viết trực tiếp mật khẩu database vào application.properties:

Properties
spring.datasource.url=jdbc:mysql://localhost:3306/student_management
spring.datasource.username=root
spring.datasource.password=123456

Nếu bạn đẩy source code lên GitHub ở chế độ công khai, những người khác có thể xem được mật khẩu này.

Điều đó có thể dẫn đến:

  • Người khác truy cập trái phép vào database.
  • Dữ liệu bị đọc, chỉnh sửa hoặc xóa.
  • Tài nguyên bị sử dụng trái phép.
  • Phát sinh chi phí ngoài dự kiến nếu thông tin truy cập bị lộ.

Thay vào đó, hãy sử dụng biến môi trường:

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

Mật khẩu thật được cấu hình trong môi trường chạy ứng dụng, không cần ghi trực tiếp vào file cấu hình được đưa lên GitHub.

Lưu ý: Biến môi trường giúp hạn chế việc lộ bí mật qua source code, nhưng không tự động bảo vệ bí mật trước người có quyền truy cập Dashboard, log hoặc môi trường chạy ứng dụng.

7.2.2. Dễ dàng chuyển đổi giữa các môi trường

Trong quá trình phát triển, một dự án thường có nhiều môi trường:

Môi trường Mục đích

StagingKiểm thử gần giống môi trường thật
ProductionMôi trường phục vụ người dùng thực tế

Ví dụ:

Ở môi trường Development:

DB_URL=jdbc:mysql://localhost:3306/student_management

Ở môi trường Production:

DB_URL=jdbc:mysql://production-host:3306/student_management

Ứng dụng có thể sử dụng cùng một cấu trúc source code, nhưng kết nối tới các database khác nhau tùy theo cấu hình của môi trường.

7.2.3. Không cần sửa code mỗi khi đổi cấu hình

Giả sử bạn đổi mật khẩu database.

Nếu mật khẩu được ghi trực tiếp trong source code, bạn phải sửa file, build lại ứng dụng và triển khai phiên bản mới.

Nếu sử dụng biến môi trường, bạn chỉ cần cập nhật giá trị biến tương ứng trên Render rồi khởi động lại hoặc triển khai lại ứng dụng theo yêu cầu của nền tảng.

Cách này giúp việc quản lý cấu hình thuận tiện hơn.

7.3. Phân biệt application.properties và biến môi trường

Hai thành phần này có vai trò khác nhau.

7.3.1. File application.properties

Đây là file cấu hình của Spring Boot.

7.3.2. Environment Variables

Đây là nơi cung cấp giá trị thực tế cho những cấu hình cần thiết.

7.4. Cấu hình biến môi trường trong Spring Boot

7.4.1. Sử dụng cú pháp ${...}

Spring Boot hỗ trợ tham chiếu biến môi trường trong application.properties bằng cú pháp:

Properties
${TEN_BIEN}

Ví dụ:

Properties
spring.datasource.url=${DB_URL}

Spring Boot sẽ tìm giá trị cấu hình DB_URL trong các nguồn cấu hình mà nó nhận được, bao gồm biến môi trường hệ điều hành.

Nếu không tìm thấy giá trị bắt buộc và không có giá trị mặc định, ứng dụng có thể gặp lỗi khi khởi động.

7.4.2. Sử dụng giá trị mặc định

Cú pháp:

Properties
${TEN_BIEN:gia_tri_mac_dinh}

Ví dụ:

Properties
server.port=${PORT:8080}

Giải thích:

  • PORT: tên biến môi trường.
  • 8080: giá trị mặc định.
  • Nếu có cấu hình PORT, Spring Boot sử dụng giá trị được cung cấp.
  • Nếu không có PORT, Spring Boot sử dụng 8080.

Đối với các thông tin nhạy cảm như mật khẩu database, không nên đặt mật khẩu thật làm giá trị mặc định.

Ví dụ không nên dùng:

Properties
spring.datasource.password=${DB_PASSWORD:123456}

Cách tốt hơn:

Properties
spring.datasource.password=${DB_PASSWORD}

Khi chạy ứng dụng, hãy bảo đảm DB_PASSWORD được cấu hình đúng.

7.4.3. Cấu hình file application.properties hoàn chỉnh

Ví dụ cho dự án Spring Boot sử dụng MySQL:

Properties
spring.application.name=student-management

# Port của ứng dụng
server.port=${PORT:8080}

# Cấu hình MySQL
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

# Cấu hình Hibernate nếu dự án sử dụng Spring Data JPA
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=false

Giải thích:

  • spring.application.name: tên ứng dụng.
  • server.port: cổng chạy ứng dụng.
  • spring.datasource.url: địa chỉ database.
  • spring.datasource.username: tài khoản database.
  • spring.datasource.password: mật khẩu database.
  • spring.jpa.hibernate.ddl-auto=validate: nếu dùng Hibernate/JPA, kiểm tra cấu trúc bảng thay vì tự động tạo hoặc xóa bảng.
  • spring.jpa.show-sql=false: không hiển thị câu SQL ra log theo cấu hình này.

Nếu dự án không sử dụng Spring Data JPA/Hibernate, có thể bỏ các cấu hình spring.jpa.*.

7.5. Cấu hình biến môi trường trên Render

7.5.1. Truy cập dịch vụ

Sau khi đã tạo Web Service và triển khai ứng dụng trên Render:

  1. Đăng nhập Render.
  2. Mở Dashboard.
  3. Chọn Web Service của dự án Spring Boot.
  4. Tìm mục Environment trong phần quản lý dịch vụ.
  5. Thêm hoặc chỉnh sửa các biến môi trường cần thiết.

Tên mục hoặc vị trí giao diện có thể thay đổi theo phiên bản Render.

7.5.2. Thêm biến môi trường

Giả sử ứng dụng sử dụng MySQL.

Bạn có thể cần khai báo:

Key Value minh họa
DB_URLjdbc:mysql://db-host:3306/student_management
DB_USERNAMEstudent_user
DB_PASSWORDMật khẩu database thực tế

Thao tác:

  1. Chọn thêm biến môi trường.
  2. Nhập tên biến vào trường Key.
  3. Nhập giá trị tương ứng vào trường Value.
  4. Lưu cấu hình.
  5. Thực hiện deploy lại hoặc khởi động lại dịch vụ nếu Render yêu cầu.

Quan trọng: Không sao chép nguyên các giá trị minh họa ở trên để kết nối database thật. Hãy thay bằng thông tin do nhà cung cấp database cung cấp.

7.5.3. Nếu ứng dụng chưa sử dụng database

Nếu dự án chỉ có API đơn giản, ví dụ:

Java
@RestController
@RequestMapping("/api")
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "Hello from Spring Boot!";

}

Bạn chưa cần cấu hình DB_URL, DB_USERNAME và DB_PASSWORD nếu ứng dụng không có cấu hình kết nối database.

Tuy nhiên, nếu application.properties đang tham chiếu các biến này hoặc dự án có cấu hình DataSource bắt buộc, bạn cần cung cấp các giá trị hợp lệ hoặc điều chỉnh cấu hình phù hợp.

7.6. Quản lý thông tin kết nối MySQL trên Render

7.6.1. Các thông tin cần có

Khi kết nối Spring Boot với MySQL trong môi trường Production, bạn thường cần:

  • Host: địa chỉ máy chủ database.
  • Port: cổng database.
  • Database name: tên database.
  • Username: tài khoản kết nối.
  • Password: mật khẩu.
  • Các tham số kết nối cần thiết khác, tùy cấu hình máy chủ.

URL JDBC thường có dạng:

jdbc:mysql://HOST:PORT/DATABASE_NAME

Ví dụ:

jdbc:mysql://mysql.example.com:3306/student_management

Đây là URL minh họa, không phải địa chỉ database thực tế.

7.6.2. Cấu hình trong application.properties

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

7.6.3. Khai báo trên Render

DB_URL=jdbc:mysql://HOST:PORT/DATABASE_NAME
DB_USERNAME=YOUR_DATABASE_USERNAME
DB_PASSWORD=YOUR_DATABASE_PASSWORD

Thay các giá trị viết hoa bằng thông tin thật từ nhà cung cấp.

Nếu dùng database bên ngoài Render, hãy kiểm tra:

  • Database có cho phép kết nối từ môi trường triển khai hay không.
  • Host và port có chính xác không.
  • Tài khoản có quyền truy cập database hay không.
  • Nhà cung cấp có yêu cầu SSL hoặc tham số JDBC bổ sung không.
  • Database có đang hoạt động và cho phép kết nối từ địa chỉ mạng của dịch vụ hay không.

Lưu ý: Nếu sử dụng database nội bộ do nền tảng cung cấp, URL kết nối có thể khác với URL dùng từ máy tính cá nhân. Hãy làm theo hướng dẫn kết nối của nhà cung cấp.

7.7. Quản lý JWT Secret và các thông tin bảo mật

Trong các ứng dụng Spring Security sử dụng JWT, có thể tồn tại các cấu hình nhạy cảm như:

Properties
jwt.secret-key=${JWT_SECRET}

Khi triển khai, bạn cấu hình JWT_SECRET trong môi trường chạy ứng dụng.

Ví dụ:

JWT_SECRET=<gia_tri_bi_mat_duoc_tao_ngau_nhien>

Không sử dụng chuỗi ví dụ này làm secret thật. Hãy tạo khóa bí mật đủ mạnh, phù hợp với thuật toán ký JWT đang sử dụng.

Nếu dùng HMAC như HS256, khóa cần đáp ứng yêu cầu độ dài và định dạng của thuật toán. Nếu dùng khóa bất đối xứng như RSA, cách quản lý khóa công khai và khóa riêng sẽ khác.

Những thông tin cần bảo vệ bao gồm:

  • Mật khẩu database.
  • JWT signing secret hoặc private key.
  • API key của dịch vụ bên ngoài.
  • OAuth2 client secret.
  • Thông tin đăng nhập dịch vụ gửi email.

Không nên đưa các giá trị này trực tiếp vào GitHub hoặc ghi chúng trong log.

7.8. Không commit thông tin bí mật lên GitHub

7.8.1. Ví dụ cấu hình không an toàn

Properties
spring.datasource.url=jdbc:mysql://production-host:3306/student_management
spring.datasource.username=root
spring.datasource.password=myRealPassword123
jwt.secret-key=myRealJwtSecret

Đây là cách cấu hình không nên sử dụng cho source code công khai.

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}

7.8.3. Kiểm tra .gitignore

Bạn có thể sử dụng file application-local.properties để lưu cấu hình riêng cho máy tính cá nhân và thêm file này vào .gitignore:

Gitignore

Tuy nhiên, đừng loại bỏ mọi file application.properties khỏi Git một cách máy móc. File cấu hình cơ bản, không chứa bí mật, thường vẫn cần được quản lý bằng Git.

Nếu một mật khẩu hoặc khóa bí mật đã được commit lên GitHub, chỉ xóa dòng đó trong commit mới là chưa đủ vì giá trị cũ có thể còn trong lịch sử Git. Bạn cần thay đổi hoặc thu hồi thông tin bí mật đã lộ, sau đó xử lý lịch sử repository nếu cần.

7.9. Phân biệt biến môi trường trên máy tính và Render

Một lỗi thường gặp là ứng dụng chạy được trên máy cá nhân nhưng thất bại khi triển khai.

Nguyên nhân có thể là biến môi trường đã tồn tại trên máy tính cá nhân nhưng chưa được cấu hình trên Render.

Ví dụ, trên máy cá nhân bạn đã đặt:

DB_URL=jdbc:mysql://localhost:3306/student_management

Nhưng trên Render chưa có biến DB_URL.

Khi ứng dụng khởi động trên Render, Spring Boot không tìm thấy cấu hình cần thiết và có thể báo lỗi.

Một trường hợp khác: bạn cấu hình URL như sau:

jdbc:mysql://localhost:3306/student_management

URL này chỉ phù hợp khi MySQL thực sự chạy tại máy chủ mà ứng dụng đang coi là localhost.

Trên Render, localhost thường trỏ đến môi trường chạy ứng dụng, không phải máy tính cá nhân của bạn. Vì vậy, ứng dụng trên Render không thể sử dụng URL MySQL ở máy cá nhân theo cách đó.

Cách xử lý:

  1. Xác định nơi database đang chạy.
  2. Lấy thông tin kết nối phù hợp với môi trường triển khai.
  3. Cấu hình DB_URL, DB_USERNAME và DB_PASSWORD trên Render.
  4. Kiểm tra log sau khi khởi động lại ứng dụng.

7.10. Các lỗi thường gặp khi cấu hình biến môi trường

Lỗi 1: Không tìm thấy biến môi trường

Ví dụ:

Could not resolve placeholder 'DB_URL'

Nguyên nhân có thể là:

  • Chưa tạo biến DB_URL trên Render.
  • Đặt sai tên biến.
  • Cấu hình chưa được lưu hoặc chưa áp dụng.

Cách xử lý:

  • Kiểm tra đúng tên DB_URL.
  • Kiểm tra cấu hình trên dịch vụ Render.
  • Khởi động lại hoặc deploy lại sau khi cập nhật cấu hình.

Lỗi 2: Không kết nối được MySQL

Ví dụ:

Communications link failure

Nguyên nhân có thể là:

  • URL database không đúng.
  • Host hoặc port không chính xác.
  • Database chưa hoạt động.
  • Nhà cung cấp chặn kết nối từ môi trường triển khai.
  • Thông tin SSL hoặc tham số kết nối chưa đúng.

Cách xử lý:

  • Kiểm tra DB_URL.
  • Kiểm tra host và port.
  • Kiểm tra trạng thái database.
  • Kiểm tra quyền kết nối mạng và hướng dẫn kết nối của nhà cung cấp.

Lỗi 3: Sai tài khoản hoặc mật khẩu database

Ví dụ:

Access denied for user

Cách xử lý:

  • Kiểm tra DB_USERNAME.
  • Kiểm tra DB_PASSWORD.
  • Kiểm tra quyền của tài khoản đối với database.
  • Tránh thêm dấu cách không mong muốn vào giá trị biến.

Lỗi 4: Ứng dụng không khởi động do cấu hình JWT

Nếu log cho biết không thể tạo bean liên quan đến JWT hoặc không đọc được JWT_SECRET, hãy kiểm tra:

  • Biến JWT_SECRET đã được cấu hình chưa.
  • Giá trị khóa có đúng định dạng và độ dài yêu cầu không.
  • Cấu hình application.properties có đúng tên biến không.

Lỗi 5: Thay đổi biến môi trường nhưng ứng dụng vẫn dùng giá trị cũ

Có thể cấu hình mới chưa được áp dụng cho tiến trình đang chạy.

Cách xử lý:

  1. Kiểm tra giá trị mới trên Render.
  2. Lưu thay đổi.
  3. Thực hiện thao tác deploy hoặc restart phù hợp.
  4. Kiểm tra log để xác nhận ứng dụng đã khởi động với cấu hình mới.

Không in mật khẩu hoặc khóa bí mật ra log để kiểm tra.

Bước 4: Mở mục Logs của dịch vụ.

Ví dụ:

Ghi nhớ trọng tâm
  • Environment Variables là biến cấu hình lưu trong môi trường chạy, giúp tách cấu hình khỏi source code.
  • application.properties khai báo cấu hình; Environment Variables cung cấp giá trị thực tế.
  • Cú pháp ${TEN_BIEN} tham chiếu biến môi trường; ${TEN_BIEN:gia_tri_mac_dinh} đặt giá trị mặc định.
  • Các biến quan trọng: PORT, DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET.
  • Không commit secrets (mật khẩu DB, JWT secret, OAuth2 client secret, API key) lên GitHub. Dùng Environment Variables hoặc secret manager.
  • Không dùng localhost cho database trong môi trường Render — cần dùng địa chỉ database từ xa.
  • Nếu secret đã bị commit, cần thay đổi hoặc thu hồi giá trị đó, sau đó xử lý lịch sử Git.
  • Lỗi thường gặp: Could not resolve placeholder, Communications link failure, Access denied for user, ứng dụng không khởi động do thiếu JWT_SECRET, thay đổi biến nhưng chưa áp dụng.
  • Sau khi cấu hình, cần kiểm tra application.properties → kiểm tra biến trên Render → deploy/restart → xem logs → gọi API.

8.1. Phân biệt MySQL trên máy cá nhân và MySQL trên máy chủ

8.1.1. MySQL trên máy tính cá nhân

Trong quá trình phát triển ứng dụng Spring Boot, lập trình viên thường cài đặt MySQL trực tiếp trên máy tính cá nhân.

Ví dụ, dự án quản lý sinh viên sử dụng database student_management với cấu hình:

Properties
spring.datasource.url=jdbc:mysql://localhost:3306/student_management
spring.datasource.username=root
spring.datasource.password=your_local_password

Trong cấu hình trên:

  • localhost: máy tính đang chạy ứng dụng.

  • student_management: tên database.
  • root: tài khoản MySQL.
  • your_local_password: mật khẩu tài khoản.

Khi chạy Spring Boot trên máy tính cá nhân, ứng dụng có thể kết nối đến MySQL đang chạy trên chính máy tính đó.

8.1.2. MySQL trên môi trường Production

8.2. Vì sao ứng dụng trên Render không thể sử dụng localhost để kết nối MySQL trên máy cá nhân?

localhost là địa chỉ trỏ đến chính môi trường đang thực hiện kết nối.

Spring Boot trên máy cá nhân
          |
          | localhost:3306
          v
MySQL trên máy cá nhân

Khi chạy ứng dụng trên Render:

Spring Boot trên Render
          |
          | localhost:3306
          v
Môi trường Render đang chạy ứng dụng

Trong trường hợp thứ hai, localhost không trỏ về máy tính cá nhân của bạn. Nó trỏ về môi trường mà ứng dụng đang chạy trên Render.

Nếu MySQL không chạy trong chính môi trường đó, kết nối sẽ thất bại.

8.2.2. Ví dụ lỗi thường gặp

Bạn đang có cấu hình:

Properties
spring.datasource.url=jdbc:mysql://localhost:3306/student_management

Ứng dụng chạy tốt trên IntelliJ IDEA, nhưng sau khi deploy lên Render, log có thể xuất hiện lỗi tương tự:

Communications link failure

Nguyên nhân có thể là Spring Boot đang cố kết nối đến MySQL tại localhost:3306 trong môi trường Render, nơi không có MySQL lắng nghe tại địa chỉ đó.

8.2.3. Cách giải quyết

Có hai hướng phổ biến:

  • Hướng 1: Triển khai MySQL thành một dịch vụ riêng trên Render và kết nối qua địa chỉ nội bộ.
  • Hướng 2: Sử dụng MySQL từ một nhà cung cấp bên ngoài, sau đó cấu hình hostname, port, tài khoản và các yêu cầu bảo mật tương ứng.

Trong phần này, chúng ta chọn triển khai MySQL thành một dịch vụ riêng trên Render, sử dụng mẫu MySQL Docker chính thức trong tài liệu Render. Cách này giúp thực hành cả việc tạo database, lưu dữ liệu và kết nối giữa hai dịch vụ trên cùng nền tảng.

8.4.5. Cấu hình Persistent Disk

Đây là bước rất quan trọng.

MySQL lưu dữ liệu trên hệ thống tệp, thường tại:

/var/lib/mysql

Trong phần cấu hình dịch vụ MySQL, thêm một Persistent Disk với các thông số theo tài liệu Render:

Thuộc tính Giá trị
Mount Path/var/lib/mysql
Size10 GB hoặc dung lượng phù hợp

Dung lượng 10 GB là ví dụ theo hướng dẫn triển khai của Render; hãy kiểm tra giới hạn và chi phí hiện hành trước khi chọn.

Vì sao phải có Persistent Disk?

Nếu dữ liệu chỉ nằm trong lớp lưu trữ tạm thời của container, việc thay thế hoặc triển khai lại container có thể làm mất dữ liệu. Persistent Disk giúp lưu dữ liệu MySQL qua các lần triển khai lại trong phạm vi đặc tính dịch vụ.

Cấu hình sai mount path có thể khiến MySQL ghi dữ liệu ra nơi không được lưu trữ bền vững.

Tài liệu Render yêu cầu mount path của MySQL phải khớp với /var/lib/mysql.

8.6. Tạo database và đưa cấu trúc bảng, dữ liệu mẫu lên Production

Tạo dịch vụ MySQL không có nghĩa là tất cả bảng của dự án đã được tạo sẵn.

Nếu dự án đang có database trên máy tính cá nhân, bạn cần chuyển cấu trúc bảng và dữ liệu cần thiết lên database Production.

8.6.1. Xác định cấu trúc database hiện tại

Ví dụ, dự án quản lý sinh viên có bảng:

SQL
CREATE TABLE students (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    student_code VARCHAR(20) NOT NULL UNIQUE,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE
);

Nếu dự án đã có nhiều bảng như users, roles, students và courses, hãy chuẩn bị đầy đủ schema cùng các quan hệ cần thiết.

Không chỉ sao chép một bảng ví dụ nếu ứng dụng thực tế phụ thuộc vào nhiều bảng khác.

8.6.2. Tạo file SQL từ MySQL Local

Có thể sử dụng MySQL Workbench để xuất database:

  1. Mở MySQL Workbench.
  2. Kết nối MySQL Local.
  3. Chọn chức năng xuất dữ liệu, thường là Data Export.
  4. Chọn database cần xuất.
  5. Chọn các bảng cần đưa lên Production.
  6. Xuất schema và dữ liệu cần thiết thành file SQL.
  7. Kiểm tra nội dung file trước khi nhập.

Ví dụ file xuất:

student_management.sql

File có thể chứa:

  • Các câu lệnh tạo bảng.
  • Primary key và foreign key.
  • Index.
  • Các câu lệnh INSERT dữ liệu.
  • Các thành phần schema khác tùy lựa chọn khi xuất.

8.6.3. Đưa file SQL lên MySQL Production

Vì dịch vụ MySQL trong bài được cấu hình là Private Service, máy tính cá nhân không mặc nhiên truy cập được địa chỉ nội bộ của Render.

Bạn có thể sử dụng một trong những cách phù hợp:

Cách A: Sử dụng shell của dịch vụ

Nếu gói dịch vụ và cấu hình hiện hành cho phép truy cập shell, có thể sử dụng MySQL client để nhập file SQL từ môi trường có thể truy cập database.

Ví dụ tổng quát:

Bash
mysql -h <MYSQL_HOST> \
      -P 3306 \
      -u <MYSQL_USERNAME> \
      -p \
      <MYSQL_DATABASE> < student_management.sql

Lệnh này minh họa cú pháp nhập file SQL. Nó chỉ chạy được khi:

  • MySQL client đã được cài đặt.
  • File student_management.sql tồn tại tại đường dẫn hiện tại.
  • Môi trường chạy lệnh có thể kết nối đến host MySQL.
  • Tài khoản có đủ quyền.

Không phải mọi gói Render đều hỗ trợ shell. Hãy kiểm tra khả năng truy cập thực tế của dịch vụ.

Cách B: Triển khai một công cụ quản trị database nội bộ

Có thể triển khai một công cụ như Adminer theo hướng dẫn của Render để thao tác database qua giao diện quản trị.

Nếu lựa chọn cách này, cần bảo vệ công cụ quản trị bằng xác thực và giới hạn phạm vi truy cập. Không để một giao diện quản trị database không được bảo vệ công khai trên Internet.

Cách C: Sử dụng MySQL từ nhà cung cấp bên ngoài

Nếu cần thường xuyên kết nối trực tiếp bằng MySQL Workbench từ máy tính cá nhân, một dịch vụ MySQL có kết nối từ xa được nhà cung cấp hỗ trợ có thể thuận tiện hơn. Khi đó cần cấu hình đúng hostname, cổng, quyền mạng và SSL/TLS.

Không được tự mở cổng hoặc công khai MySQL trên Render chỉ để thuận tiện cho việc nhập dữ liệu.

8.6.4. Kiểm tra sau khi nhập dữ liệu

8.7. Cấu hình spring.datasource.url, spring.datasource.username và spring.datasource.password

Properties

Giải thích:

jdbc:mysql://HOST:PORT/DATABASE_NAME

Trong đó:

  • 3306: port MySQL.
  • student_management: tên database.

Phải thay hostname bằng địa chỉ nội bộ thực tế được Render cung cấp.

Tránh sử dụng tùy tiện create hoặc create-drop trên Production vì có thể dẫn đến việc tạo lại hoặc xóa schema, ảnh hưởng dữ liệu đang lưu.

8.11. Xử lý lỗi kết nối database và lỗi xác thực

8.11.1. Lỗi Communications link failure

Ví dụ:

com.mysql.cj.jdbc.exceptions.CommunicationsException:
Communications link failure

Nguyên nhân thường gặp:

  • Sai hostname hoặc port.
  • MySQL chưa chạy.
  • Không thể truy cập mạng nội bộ.
  • Firewall chặn kết nối.
  • Dịch vụ database chưa sẵn sàng.

Cách xử lý:

  1. Mở Logs của dịch vụ MySQL.
  2. Xác nhận MySQL đã khởi động.
  3. Kiểm tra hostname và port.
  4. Kiểm tra điều kiện mạng giữa hai dịch vụ.
  5. Kiểm tra lại DB_URL.

8.11.2. Lỗi Access denied for user

Ví dụ:

Access denied for user 'student_user'

Nguyên nhân:

  • Username không đúng.
  • Password không đúng.
  • Tài khoản chưa được cấp quyền.
  • Thông tin đăng nhập trong biến môi trường không khớp với tài khoản MySQL.

Cách xử lý:

  1. Kiểm tra DB_USERNAME.
  2. Kiểm tra DB_PASSWORD.
  3. Xác nhận tài khoản tồn tại.
  4. Kiểm tra quyền trên database.
  5. Đảm bảo không vô tình sử dụng mật khẩu của tài khoản khác.

Không ghi password thật vào log khi xử lý lỗi.

8.11.3. Lỗi Unknown database

Ví dụ:

Unknown database 'student_management'

Nguyên nhân:

  • Database chưa được tạo.
  • Tên database trong URL không đúng.
  • Đang kết nối nhầm MySQL server.

Cách xử lý:

  • Kiểm tra DB_URL.
  • Kiểm tra database đã được khởi tạo chưa.
  • Xác nhận đang sử dụng đúng dịch vụ MySQL.

8.11.4. Lỗi Table doesn't exist

Ví dụ:

Table 'student_management.students' doesn't exist

Nguyên nhân:

  • Chưa nhập file SQL.
  • Bảng được tạo với tên khác.
  • Entity không ánh xạ đúng bảng.
  • Quá trình migration chưa hoàn thành.

Cách xử lý:

  1. Kiểm tra schema Production.
  2. Nhập schema hoặc chạy migration phù hợp.
  3. Kiểm tra mapping entity và bảng.
  4. Kiểm tra các bảng liên quan nếu có khóa ngoại.

8.11.5. Lỗi Could not resolve placeholder

Ví dụ:

Could not resolve placeholder 'DB_URL'

Nguyên nhân:

Spring Boot không tìm được biến môi trường DB_URL.

Cách xử lý:

  • Kiểm tra biến trong Environment của đúng Web Service.
  • Kiểm tra chính tả tên biến.
  • Lưu cấu hình.
  • Deploy hoặc restart lại ứng dụng theo yêu cầu của Render.

8.11.6. Lỗi schema không tương thích

Nếu sử dụng JPA và cấu hình:

Properties
spring.jpa.hibernate.ddl-auto=validate

Ứng dụng có thể không khởi động nếu schema Production khác với entity.

Cách xử lý:

  • Kiểm tra tên bảng và cột.
  • Kiểm tra kiểu dữ liệu.
  • Kiểm tra quan hệ và khóa.
  • Áp dụng migration phù hợp trước khi khởi động ứng dụng.

Không khắc phục bằng cách tùy tiện xóa hoặc tạo lại toàn bộ schema khi database đã chứa dữ liệu quan trọng.

8.12. Sao lưu dữ liệu, bảo mật và quản lý thông tin kết nối

8.12.1. Sao lưu database

Persistent Disk giúp lưu dữ liệu qua những lần triển khai lại phù hợp, nhưng không thay thế hoàn toàn việc sao lưu database.

Cần xây dựng kế hoạch backup, bao gồm:

  • Tần suất sao lưu.
  • Thời gian lưu bản sao.
  • Nơi lưu bản sao lưu độc lập.
  • Quyền truy cập bản sao.
  • Quy trình khôi phục và kiểm tra dữ liệu sau khôi phục.

Với MySQL, có thể sử dụng công cụ như mysqldump để tạo bản sao lưu logic.

Ví dụ cú pháp:

Bash
mysqldump \
  -h <MYSQL_HOST> \
  -P 3306 \
  -u <MYSQL_USERNAME> \
  -p \
  <MYSQL_DATABASE> > backup.sql

Lệnh trên yêu cầu MySQL client có thể truy cập database và tài khoản có đủ quyền đọc dữ liệu. Nó tạo file backup.sql trong môi trường đang thực thi lệnh.

Không lưu bản sao lưu chứa dữ liệu nhạy cảm trong repository công khai.

8.12.2. Bảo vệ tài khoản database

Các nguyên tắc cần thực hiện:

  • Không dùng tài khoản root cho ứng dụng nếu không cần.
  • Không cấp quyền vượt quá nhu cầu.
  • Không sử dụng mật khẩu yếu.
  • Thay đổi thông tin đăng nhập khi có dấu hiệu bị lộ.
  • Hạn chế người được phép truy cập database.
  • Không công khai endpoint quản trị MySQL tùy tiện.

8.12.3. Quản lý biến môi trường

Thông tin kết nối cần được quản lý bằng biến môi trường hoặc hệ thống quản lý bí mật phù hợp.

Ví dụ:

Properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

Không commit thông tin đăng nhập thật vào application.properties.

Nếu password đã bị đẩy lên GitHub, chỉ xóa password khỏi file là chưa đủ. Cần thay đổi mật khẩu đã bị lộ và rà soát lịch sử, quyền truy cập liên quan.

8.12.4. Cập nhật và vận hành MySQL

Vì phương án trong bài sử dụng MySQL tự triển khai bằng Docker, bạn cần quan tâm đến:

  • Phiên bản MySQL.
  • Cập nhật image và bản vá bảo mật.

  • Trạng thái hoạt động của dịch vụ.
  • Log database.
  • Sao lưu và khôi phục.
  • Chi phí và giới hạn của gói dịch vụ.

Đối với ứng dụng quan trọng, cần đánh giá liệu việc tự vận hành database có đáp ứng yêu cầu về độ sẵn sàng, khả năng phục hồi và bảo trì hay không.

Tổng kết phần 8

Trong phần này, chúng ta đã đi qua toàn bộ quy trình triển khai database cho ứng dụng Spring Boot:

  1. Phân biệt MySQL Local và MySQL Production.
  2. Hiểu vì sao localhost không thể đại diện cho MySQL trên máy tính cá nhân khi ứng dụng chạy trên Render.
  3. Lựa chọn phương án triển khai MySQL.
  4. Tạo dịch vụ MySQL riêng trên Render.
  5. Cấu hình biến môi trường và Persistent Disk.
  6. Lấy thông tin kết nối database.
  7. Đưa schema và dữ liệu mẫu lên Production.
  8. Cấu hình spring.datasource.* trong Spring Boot.
  9. Kiểm tra kết nối mạng và quyền truy cập.
  10. Kiểm thử CRUD và xử lý lỗi.
  11. Xây dựng kế hoạch bảo mật, sao lưu và vận hành.

Kết quả cần đạt: Ứng dụng Spring Boot đã deploy trên Render có thể kết nối với MySQL được triển khai riêng, đọc và ghi dữ liệu trên database Production thay vì phụ thuộc vào database trên máy tính cá nhân.

Ghi nhớ trọng tâm
  • MySQL Local và MySQL Production là hai môi trường riêng biệt. localhost trên Render không trỏ đến máy cá nhân.
  • Có 3 phương án: MySQL trên Render, MySQL từ nhà cung cấp bên ngoài, MySQL trên VPS.
  • Bài học dùng MySQL Private Service trên Render với Docker và Persistent Disk mount tại /var/lib/mysql.
  • Biến môi trường MySQL: MYSQL_DATABASE, MYSQL_USER, MYSQL_PASSWORD, MYSQL_ROOT_PASSWORD.
  • Spring Boot cấu hình qua DB_URL, DB_USERNAME, DB_PASSWORD — không hardcode secrets.
  • URL JDBC: jdbc:mysql://HOST:PORT/DATABASE_NAME. Dùng địa chỉ nội bộ khi cả hai dịch vụ chạy trên Render.
  • Phải đưa schema và dữ liệu mẫu lên Production — deploy JAR không tự chuyển database từ máy cá nhân.
  • Dùng ddl-auto=validate trong Production; tránh create, create-drop khi có dữ liệu thật.
  • Không mở MySQL ra Internet nếu không cần. Ưu tiên mạng nội bộ, giới hạn nguồn, TLS/SSL.
  • Tài khoản ứng dụng chỉ nên có quyền cần thiết: SELECT, INSERT, UPDATE, DELETE.
  • Lỗi thường gặp: Communications link failure, Access denied for user, Unknown database, Table doesn't exist, Could not resolve placeholder, schema không tương thích.
  • Persistent Disk không thay thế backup. Cần kế hoạch sao lưu (mysqldump), kiểm tra khôi phục, bảo vệ bản backup.
  • Kiểm thử CRUD trên Production: GET → POST → GET → PUT → GET → DELETE → GET. Kiểm tra dữ liệu còn tồn tại sau khi restart.

Phần 9. Kiểm thử API bằng Postman

9.1. Postman là gì?

Postman là công cụ hỗ trợ gửi HTTP request đến API và kiểm tra HTTP response mà máy chủ trả về. Công cụ này được sử dụng phổ biến khi phát triển và triển khai Backend Java Spring Boot.

Sau khi deploy ứng dụng Spring Boot lên Render, chúng ta cần kiểm tra xem các API có thể được truy cập qua Internet hay không, ứng dụng có xử lý request đúng không và dữ liệu có được lưu vào database Production hay không.

Ví dụ, khi chạy ứng dụng trên máy tính cá nhân, API có thể có địa chỉ:

http://localhost:8080/api/students

Sau khi deploy lên Render, API sẽ có địa chỉ công khai, ví dụ:

https://student-management.onrender.com/api/students

Địa chỉ trên chỉ là ví dụ minh họa. Khi thực hành, cần sử dụng URL thực tế được Render cung cấp cho Web Service của bạn.

Postman giúp chúng ta kiểm thử API mà không cần xây dựng giao diện Frontend bằng HTML, CSS, JavaScript hoặc React.

9.5. Kiểm thử API GET — Lấy danh sách dữ liệu

Mục tiêu: Kiểm tra API có trả về danh sách sinh viên từ database Production hay không.

Bước 1: Tạo request

Mở Postman, tạo một HTTP request mới.

Cấu hình:

  • Method: GET
  • URL: https://student-management.onrender.com/api/students

Thay hostname bằng URL thực tế của ứng dụng.

Bước 2: Gửi request

Nhấn Send.

Nếu API hoạt động đúng và trả về danh sách sinh viên, response có thể giống như sau:

JSON
[
  {
    "id": 1,
    "name": "Nguyen Van A",
    "email": "a@example.com"
  },
  {
    "id": 2,
    "name": "Tran Thi B",
    "email": "b@example.com"
  }
]

Đây chỉ là dữ liệu minh họa; cấu trúc response phụ thuộc vào DTO hoặc entity mà dự án trả về.

Bước 3: Kiểm tra kết quả

Cần kiểm tra:

  • HTTP status có đúng với thiết kế API không.
  • Response Body có đúng định dạng JSON không.
  • Dữ liệu có đúng với database Production không.
  • Các trường dữ liệu có đầy đủ và chính xác không.
  • Thời gian phản hồi có bất thường không.

Nếu API trả về danh sách rỗng [], cần kiểm tra dữ liệu trong database Production trước khi kết luận API bị lỗi.

9.6. Kiểm thử API POST — Thêm dữ liệu

Mục tiêu: Kiểm tra ứng dụng có nhận request và lưu dữ liệu vào database Production hay không.

Giả sử API thêm sinh viên có endpoint:

POST /api/students

Bước 1: Chọn HTTP Method

Trong Postman, chọn POST.

Bước 2: Nhập URL

https://student-management.onrender.com/api/students

Bước 3: Cấu hình Body

Chọn Body → raw → JSON, sau đó nhập:

JSON
{
  "name": "Le Van C",
  "email": "c@example.com"
}

Tên các trường phải khớp với DTO nhận dữ liệu của dự án. Nếu DTO có thêm trường bắt buộc, cần bổ sung chúng vào JSON.

Bước 4: Kiểm tra Headers

Postman thường tự đặt Content-Type phù hợp khi chọn JSON. Nếu cần, có thể thêm:

HTTP
Content-Type: application/json

Bước 5: Nhấn Send

Nếu thêm thành công, API có thể trả về 201 Created hoặc 200 OK, tùy thiết kế.

Ví dụ response:

JSON
{
  "id": 3,
  "name": "Le Van C",
  "email": "c@example.com"
}

Bước 6: Xác nhận dữ liệu

Gọi lại API GET để xác nhận sinh viên vừa thêm đã xuất hiện trong danh sách.

Điểm quan trọng: Không chỉ dựa vào thông báo thành công trong response. Cần xác nhận dữ liệu thực sự đã được lưu và có thể truy vấn lại.

9.7. Kiểm thử API PUT — Cập nhật dữ liệu

Mục tiêu: Kiểm tra API có cập nhật đúng bản ghi đã tồn tại hay không.

Ví dụ endpoint:

PUT /api/students/3

Trong Postman, cấu hình:

  • Method: PUT
  • URL: https://student-management.onrender.com/api/students/3
  • Body: raw → JSON

Nội dung request:

JSON
{
  "name": "Le Van C Updated",
  "email": "c.updated@example.com"
}

Nhấn Send, sau đó kiểm tra response.

Tiếp theo, gọi:

GET /api/students/3

Xác nhận tên và email đã được cập nhật.

Các trường hợp cần thử:

  • ID tồn tại.
  • ID không tồn tại.
  • Dữ liệu gửi lên thiếu trường bắt buộc.
  • Email không đúng định dạng nếu dự án có validation.
  • Request không có quyền thực hiện nếu API được bảo vệ.

Mã phản hồi cụ thể như 200, 204, 400 hoặc 404 phụ thuộc vào cách thiết kế Controller và xử lý ngoại lệ của ứng dụng.

9.8. Kiểm thử API DELETE — Xóa dữ liệu

Mục tiêu: Kiểm tra API có xóa đúng bản ghi hay không.

Ví dụ endpoint:

DELETE /api/students/3

Trong Postman:

  • Method: DELETE
  • URL: https://student-management.onrender.com/api/students/3

Nhấn Send.

Nếu xóa thành công, API có thể trả về 204 No Content, 200 OK hoặc một response khác theo thiết kế.

Sau đó gọi lại:

GET /api/students/3

Kiểm tra bản ghi đã bị xóa hoặc được đánh dấu không còn hoạt động, tùy cơ chế mà dự án sử dụng.

Cảnh báo: Khi kiểm thử trên Production, không nên tùy tiện xóa dữ liệu thật. Hãy sử dụng dữ liệu thử nghiệm và đảm bảo có phương án khôi phục khi cần.

9.10. Kiểm thử API có bảo vệ bằng JWT

Nếu ứng dụng sử dụng Spring Security và OAuth2 Resource Server JWT, những API được bảo vệ cần nhận access token hợp lệ.

Ví dụ endpoint:

GET /api/students

Bước 1: Đăng nhập

Gửi request đến API đăng nhập của dự án, ví dụ:

POST https://student-management.onrender.com/api/auth/login

Body minh họa:

JSON
{
  "username": "student",
  "password": "your-test-password"
}

Đường dẫn và tên trường cần khớp với API đăng nhập thực tế.

Bước 2: Lấy access token

Nếu đăng nhập thành công, response có thể chứa:

JSON
{
  "accessToken": "eyJhbGciOi..."
}

Đây là ví dụ minh họa. Cần sử dụng token thực tế được API trả về.

Bước 3: Gửi token trong request

Trong Postman, chọn tab Authorization:

  • Type: Bearer Token
  • Token: dán access token vừa nhận được.

Hoặc thêm header:

HTTP
Authorization: Bearer <access-token>

Sau đó gửi request đến API được bảo vệ.

Bước 4: Kiểm tra quyền

Nên kiểm thử ít nhất ba trường hợp:

  1. Không gửi token.
  2. Gửi token hết hạn hoặc không hợp lệ.
  3. Gửi token hợp lệ nhưng người dùng không có quyền yêu cầu.

Với cấu hình Spring Security thông thường, hai trường hợp đầu thường trả về 401 Unauthorized, còn trường hợp thứ ba thường trả về 403 Forbidden. Kết quả thực tế phụ thuộc vào cấu hình bảo mật và cách xử lý lỗi.

Không chia sẻ access token hoặc refresh token thật trong ảnh chụp màn hình, log hay tài liệu công khai.

9.11. Sử dụng Postman Environment để quản lý URL

Khi kiểm thử nhiều môi trường, chẳng hạn Local và Production, không nên sửa URL thủ công trong từng request.

Postman hỗ trợ Environment Variables để quản lý các giá trị dùng chung.

Ví dụ tạo hai môi trường:

Variable Local Production
baseUrlhttp://localhost:8080https://student-management.onrender.com

Trong request, sử dụng:

{{baseUrl}}/api/students

Khi chọn môi trường Local, request được gửi đến máy tính cá nhân. Khi chọn Production, request được gửi đến Render.

Nếu kiểm thử API có JWT, có thể tạo thêm biến accessToken trong Environment và sử dụng:

Authorization: Bearer {{accessToken}}

Chỉ lưu token thử nghiệm ở môi trường phù hợp. Tránh đồng bộ hoặc chia sẻ token bí mật trong các Collection công khai.

Collection là tập hợp các request được nhóm theo dự án hoặc chức năng. Tạo Collection giúp tổ chức bộ kiểm thử và thực hiện lại các request thuận tiện hơn.

    +-- Unauthorized Request
    +-- Not Found

Các endpoint trên là cấu trúc minh họa. Chỉ tạo những request mà dự án thực sự hỗ trợ.

Nên đặt tên request rõ ràng và lưu các giá trị có thể thay đổi như URL, ID và token vào biến thay vì ghi cố định trong từng request.

9.13. Một số lỗi thường gặp khi kiểm thử API trên Render

Lỗi 1: Request bị timeout

Nguyên nhân có thể là dịch vụ chưa sẵn sàng, ứng dụng đang khởi động, API xử lý quá lâu hoặc có vấn đề kết nối đến database.

Cách xử lý:

  1. Kiểm tra trạng thái Web Service.
  2. Đọc Logs trên Render.
  3. Kiểm tra kết nối database.
  4. Thử lại sau khi dịch vụ đã sẵn sàng.
  5. Nếu lỗi tiếp diễn, kiểm tra thời gian truy vấn và xử lý request.

Lỗi 2: HTTP 404

Kiểm tra:

  • URL có đúng không.
  • Có thiếu tiền tố /api không.
  • Controller có @RequestMapping phù hợp không.
  • Endpoint có đúng HTTP Method không.
  • Nếu lấy một bản ghi, ID có tồn tại không.

Lỗi 3: HTTP 500

Không nên đoán nguyên nhân chỉ từ mã 500. Mở Logs trên Render, tìm exception xuất hiện cùng thời điểm gửi request và kiểm tra phần Caused by.

Lỗi 4: API hoạt động ở Local nhưng lỗi trên Render

Một số nguyên nhân thường gặp:

  • Cấu hình Environment Variables thiếu hoặc sai.
  • Database Production chưa có bảng hoặc dữ liệu cần thiết.
  • Hostname database không đúng.
  • Cấu hình Java hoặc dependency khác với môi trường Local.
  • API phụ thuộc vào tệp trên máy tính cá nhân nhưng tệp đó không có trên Render.

Lỗi 5: API trả về 401 hoặc 403

Kiểm tra access token, thời hạn token, header Authorization, quyền của người dùng và cấu hình Spring Security.

Nếu token được phát hành bởi một hệ thống khác, cần kiểm tra cấu hình xác thực JWT tương ứng, chẳng hạn issuer hoặc các điều kiện xác thực mà ứng dụng yêu cầu.

Ghi nhớ trọng tâm
  • Postman giúp gửi HTTP request và kiểm tra response của API Spring Boot sau khi deploy lên Render.
  • Quy trình: lấy URL Production → cấu hình Method/URL → nhập Body/Headers → Send → kiểm tra Status Code và Response Body.
  • Kiểm thử đủ 4 thao tác CRUD: GET (danh sách, theo ID), POST (tạo), PUT (cập nhật), DELETE (xóa).
  • Không dùng localhost:8080 để kiểm thử Production — phải dùng URL Render cấp.
  • Hiểu HTTP Status Code: 200, 201, 204, 400, 401, 403, 404, 405, 500, 502, 503.
  • Với API bảo vệ bằng JWT: đăng nhập → lấy access token → gửi Authorization: Bearer <token>.
  • Dùng Environment Variables để quản lý baseUrl, accessToken; dùng Collection để tổ chức request.
  • Lỗi thường gặp: timeout, 404, 500, API khác biệt Local vs Render, 401/403.
  • Không chỉ kiểm tra endpoint có phản hồi — cần xác nhận dữ liệu, nghiệp vụ và bảo mật hoạt động đúng trong môi trường Production.
