PHẦN 1: LOMBOK TRONG JAVA VÀ SPRING BOOT

1.1. Lombok là gì?

1.1.1. Khái niệm

Lombok là một thư viện dành cho Java, được sử dụng để giảm các đoạn boilerplate code – những đoạn code lặp đi lặp lại và ít chứa logic nghiệp vụ.
Trong Java, khi xây dựng một class, chúng ta thường phải viết:

  • Getter.
  • Setter.
  • Constructor.
  • toString().
  • equals().
  • hashCode().

Ví dụ không sử dụng Lombok
public class Student {

    private Long id;
    private String name;
    private String email;

    public Student() {
    }

    public Student(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }
}

Có thể nhận thấy phần lớn code ở trên chỉ phục vụ cho việc đọc, ghi và khởi tạo dữ liệu.
Nếu class có 10 hoặc 20 thuộc tính, số lượng code lặp lại sẽ rất lớn.
Lombok giải quyết vấn đề này bằng cách cho phép chúng ta sử dụng annotation.

Ví dụ với Lombok
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
    private String email;
}

Code ngắn hơn rất nhiều nhưng vẫn có getter, setter và constructor tương ứng.

1.1.2. Boilerplate Code là gì?

Boilerplate Code là những đoạn code cần thiết nhưng thường được lặp lại trong nhiều class.
Ví dụ:

Ví dụ
public String getName() {
    return name;
}

Đây là code hợp lệ và cần thiết, nhưng nếu class có 20 field thì chúng ta phải viết rất nhiều getter tương tự.
Lombok giúp tự động sinh các đoạn code này.

1.1.3. Lombok hoạt động như thế nào?

Lombok sử dụng cơ chế Annotation Processing của Java.
Ví dụ:

Ví dụ
@Getter
public class Student {

    private String name;
}

Annotation: @Getter nói cho Lombok biết rằng class cần getter.
Về mặt tư duy, có thể hình dung:

Java Source Code
       ↓
Lombok Annotation
       ↓
Annotation Processing
       ↓
Sinh code cần thiết
       ↓
Java Compiler
       ↓
.class

Do đó, Lombok không phải là một "phép thuật" làm thay đổi Java.
Nó chỉ giúp sinh tự động những phần code mà lập trình viên có thể viết thủ công.

1.1.4. Lombok sử dụng Annotation

Annotation là những thông tin được đặt trước class, method hoặc field.
Ví dụ:

Ví dụ
@Getter
public class Student {
}

Trong đó:
@Getter: là annotation của Lombok.
Một số annotation thường gặp:

  • @Getter
  • @Setter
  • @Data
  • @Builder
  • @NoArgsConstructor
  • @AllArgsConstructor
  • @RequiredArgsConstructor
  • @ToString
  • @EqualsAndHashCode

1.1.5. Khi nào nên sử dụng Lombok?

Lombok đặc biệt hữu ích trong các project:

  • Spring Boot.
  • Spring MVC.
  • Spring Data JPA.
  • REST API.
  • Các project có nhiều DTO.
  • Các project có nhiều Entity/Model.

Ví dụ một project Spring Boot có:

  • User
  • Product
  • Order
  • Medicine
  • Invoice
  • Customer
  • Employee
  • ...

Nếu mỗi class đều phải viết getter, setter, constructor thì lượng code sẽ rất lớn. Lombok giúp giảm đáng kể phần code này.

1.3. @Getter, @Setter

1.3.1. Lý thuyết về Getter

Trong Java, thuộc tính thường được khai báo private.
Ví dụ:
private String name;
Do thuộc tính là private, class bên ngoài không nên truy cập trực tiếp:student.name;
Thay vào đó, sử dụng getter:

Getter truyền thống
public String getName() {
    return name;
}

Getter có nhiệm vụ:
Lấy giá trị của một thuộc tính.

1.3.2. Cú pháp getter truyền thống

Getter truyền thống
public String getName() {
    return name;
}

Giải thích:
public→ phương thức có thể được gọi từ bên ngoài class.
String→ kiểu dữ liệu trả về.
getName()→ tên phương thức getter.
return name;→ trả về giá trị của thuộc tính name.

1.3.3. @Getter

Thay vì viết:

Getter truyền thống
public String getName() {
    return name;
}

có thể viết:

@Getter
@Getter
private String name;

Hoặc:

@Getter ở cấp class
@Getter
public class Student {

    private String name;
    private String email;
}

Lombok tự tạo getter.

1.3.4. Getter ở cấp class

@Getter ở cấp class
@Getter
public class Student {

    private Long id;
    private String name;
    private int age;
}

Lombok sẽ tạo tương ứng:

public Long getId() {
    return id;
}

public String getName() {
    return name;
}

public int getAge() {
    return age;
}

1.3.5. Getter ở cấp field

Có thể chỉ tạo getter cho một field:

Getter riêng field
public class User {

    @Getter
    private String username;

    private String password;
}

Khi đó:
user.getUsername();
có thể sử dụng.
Nhưng:
user.getPassword();
không được Lombok tạo.

1.3.6. Lý thuyết về Setter

Setter được sử dụng để thay đổi giá trị của thuộc tính.
Ví dụ:

Setter truyền thống
public void setName(String name) {
    this.name = name;
}

Giải thích:
void
→ setter không trả về giá trị.
setName(...)
→ phương thức thay đổi thuộc tính name.
this.name
→ thuộc tính của object hiện tại.
name
→ tham số được truyền vào.

1.3.7. @Setter

Thay vì viết:

Setter truyền thống
public void setName(String name) {
    this.name = name;
}

có thể:

@Setter
@Setter
private String name;

Hoặc:

@Setter ở cấp class
@Setter
public class Student {

    private String name;
    private String email;
}

1.3.8. Sử dụng cả Getter và Setter

Getter + Setter
@Getter
@Setter
public class Student {

    private Long id;
    private String name;
    private String email;
}

Sử dụng:

Sử dụng

Luồng hoạt động:

      ↓

      ↓
getName()
      ↓

1.3.9. Lưu ý khi sử dụng Setter

Không phải field nào cũng nên có setter.
Ví dụ:

Ví dụ
@Getter
public class User {

    private Long id;

    @Setter
    private String email;
}

Ở đây:

→ chỉ có getter

→ có getter + setter
Cách này giúp kiểm soát tốt hơn việc thay đổi dữ liệu.

1.4. @NoArgsConstructor, @AllArgsConstructor

1.4.1. Constructor là gì?

Constructor là phương thức đặc biệt được gọi khi tạo object.
Ví dụ:

Ví dụ
Student student = new Student();

Java gọi constructor:

public Student() {
}

Constructor có cùng tên với class và không có kiểu trả về.

1.4.2. @NoArgsConstructor

Cú pháp:

@NoArgsConstructor
@NoArgsConstructor
public class Student {
}

Lombok tạo:

public Student() {
}

Do đó:
Student student = new Student();
có thể thực hiện bình thường.

1.4.3. Khi nào sử dụng @NoArgsConstructor?

Thường sử dụng khi:
Cần constructor mặc định.
Làm việc với JPA Entity.
Framework cần tạo object.
DTO cần khởi tạo rỗng.
Ví dụ Entity:

Entity
@Entity
@NoArgsConstructor
public class Product {

    @Id
    private Long id;

    private String name;
}

1.4.4. @AllArgsConstructor

Cú pháp:

@AllArgsConstructor
@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
    private int age;
}

Lombok tạo:

public Student(
        Long id,
        String name,
        int age) {

    this.id = id;
    this.name = name;
    this.age = age;
}

Có thể:

Sử dụng
Student student =
        new Student(
                1L,
                "An",

        );

1.4.5. Kết hợp

Kết hợp
@NoArgsConstructor
@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
}

Có:
new Student();
và:
new Student(1L, "An");

1.5. @RequiredArgsConstructor

1.5.1. Khái niệm

@RequiredArgsConstructor tạo constructor chứa các field bắt buộc.
Trường hợp quan trọng nhất:
private final ...
Ví dụ:

@RequiredArgsConstructor
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
}

Lombok tạo:

public UserService(
        UserRepository userRepository) {

    this.userRepository = userRepository;
}

1.5.2. Vì sao dùng final?

private final UserRepository userRepository;
final đảm bảo biến phải được khởi tạo và không thể gán sang dependency khác sau đó.
Điều này phù hợp với constructor injection.

1.5.3. Sử dụng trong Spring Boot

Không dùng Lombok:

Không Lombok
@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}

Dùng Lombok:

Với Lombok
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
}

Đây là một trong những cách sử dụng Lombok phổ biến nhất trong Spring Boot.

1.7. @Builder

1.7.1. Khái niệm Builder Pattern

Builder Pattern là một cách xây dựng object bằng cách thiết lập từng thuộc tính.
Ví dụ:

Builder
User.builder()
        .name("An")
        .email("an@gmail.com")
        .age(20)
        .build();

Cách này dễ đọc hơn constructor có quá nhiều tham số.

1.7.2. Cú pháp

@Builder
public class User {

    private Long id;
    private String name;
    private String email;
}

Sau đó:

Sử dụng
User user = User.builder()
        .id(1L)
        .name("An")
        .email("an@gmail.com")
        .build();

1.7.3. Giải thích cú pháp

User.builder()
→ bắt đầu quá trình xây dựng object.
.id(1L)
→ thiết lập id.
.name("An")
→ thiết lập name.
.email("an@gmail.com")
→ thiết lập email.
.build()
→ kết thúc và tạo object.

Sử dụng

1.8. @ToString

1.8.1. Khái niệm

toString() dùng để chuyển object thành chuỗi biểu diễn.
Ví dụ:

Ví dụ
System.out.println(user);

Java sẽ gọi:
user.toString();
Nếu không override, kết quả thường khó đọc.

1.8.2. Sử dụng @ToString

@ToString
@ToString
public class User {

    private Long id;
    private String username;
}

Kết quả có thể dạng:
User(id=1, username=admin)

1.8.3. Cú pháp loại trừ field

@ToString.Exclude
@ToString
public class User {

    private Long id;

    private String username;

    @ToString.Exclude
    private String password;
}

password sẽ không được đưa vào toString().

1.8.4. Tại sao cần loại trừ password?

Không nên log:

vì log có thể được lưu lại hoặc được người khác truy cập.
Do đó:
@ToString.Exclude
private String password;
là một biện pháp hữu ích để tránh vô tình đưa dữ liệu nhạy cảm vào chuỗi debug.

Nó đặc biệt quan trọng với:

HashMap

+

để xử lý việc so sánh object trong các cấu trúc dữ liệu dựa trên hash.

1.9.3. Sử dụng Lombok

Lombok tự sinh:

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;

    public MedicineResponse findById(Long id) {

        Medicine medicine =
                medicineRepository.findById(id)
                        .orElseThrow();

        return MedicineResponse.builder()
                .id(medicine.getId())
                .name(medicine.getName())
                .price(medicine.getPrice())
                .build();
    }
}

    @GetMapping("/{id}")
    public MedicineResponse findById(

        return medicineService.findById(id);
    }
}

1.12. Bảng ghi nhớ

Annotation Ý nghĩa Thường dùng ở đâu
@Getter Sinh getter Entity, DTO
@Setter Sinh setter Entity, DTO
@NoArgsConstructor Constructor rỗng Entity, DTO
@AllArgsConstructor Constructor đầy đủ DTO, Model
@RequiredArgsConstructor Constructor cho field bắt buộc Service, Controller
@Data Getter + Setter + nhiều chức năng khác DTO
@Builder Xây dựng object DTO, Response
@ToString Sinh toString() DTO, Model
@EqualsAndHashCode Sinh equals/hashCode Model, một số DTO

Quy tắc quan trọng cần nhớ
DTO
→ @Data + @Builder

Service
→ @RequiredArgsConstructor

Controller
→ @RequiredArgsConstructor

Entity
→ @Getter + @Setter + @NoArgsConstructor
Và đặc biệt:
Không sử dụng @Data một cách máy móc cho JPA Entity, nhất là Entity có quan hệ @OneToMany, @ManyToOne, @ManyToMany, @OneToOne.

Nếu soạn theo chuẩn giáo trình tự học, mỗi phần từ 1.3 đến 1.10 nên giữ đúng cấu trúc này: Lý thuyết → Cú pháp → Giải thích từng thành phần cú pháp → Ví dụ → Phân tích ví dụ → Ứng dụng Spring Boot → Lưu ý. Đây sẽ phù hợp hơn nhiều so với kiểu chỉ liệt kê annotation và code.

Trong các ứng dụng Spring Boot, đặc biệt là những project sử dụng Entity – DTO – Service – Controller, chúng ta thường xuyên phải chuyển đổi dữ liệu giữa các object.
Ví dụ:

Database
   ↓
Entity
   ↓
Mapper
   ↓
DTO
   ↓
Controller
   ↓
Client

Hoặc theo chiều ngược lại:

Client
   ↓
Request DTO
   ↓
Mapper
   ↓
Entity
   ↓
Database

Mapper giúp tách biệt object dùng để làm việc với database và object dùng để giao tiếp với client/API.

2.1. Mapper là gì?

2.1.1. Khái niệm Mapper

Mapper là thành phần có nhiệm vụ chuyển đổi dữ liệu từ một object sang một object khác.
Ví dụ trong Spring Boot chúng ta có Entity:

Entity
@Entity
public class Medicine {

    private Long id;
    private String name;
    private Double price;
}

Và DTO:

DTO
public class MedicineResponse {

    private Long id;
    private String name;
    private Double price;
}

Hai class có cấu trúc tương đối giống nhau nhưng chúng là hai object khác nhau.
Chúng ta cần chuyển:

Medicine
    ↓
MedicineResponse

Đây chính là công việc của Mapper.

2.1.2. Tại sao cần Mapper?

Trong một ứng dụng Spring Boot, chúng ta thường không muốn trả trực tiếp Entity ra API.
Ví dụ:

Ví dụ
@GetMapping("/{id}")
public Medicine getById(@PathVariable Long id) {
    return medicineRepository.findById(id)
            .orElseThrow();
}

Cách này có thể khiến API trả trực tiếp toàn bộ dữ liệu của Entity.
Trong thực tế, Entity có thể chứa:
Thông tin nội bộ.
Quan hệ với Entity khác.
Field không muốn trả về client.
Dữ liệu phục vụ database nhưng không phục vụ API.
Do đó thường sử dụng:

Entity
   ↓
Mapper
   ↓
DTO
   ↓
API Response

Ví dụ:

Ví dụ
@GetMapping("/{id}")
public MedicineResponse getById(@PathVariable Long id) {

    Medicine medicine = medicineService.findById(id);

    return medicineMapper.toResponse(medicine);
}

2.1.3. Entity và DTO có vai trò khác nhau

Entity
Entity đại diện cho dữ liệu được quản lý bởi JPA/Hibernate và thường ánh xạ với database.
Ví dụ:

Entity
@Entity
public class Medicine {

    @Id
    private Long id;

    private String name;

    private Double price;
}

DTO
DTO – Data Transfer Object – được sử dụng để truyền dữ liệu giữa các tầng hoặc giữa server và client.
Ví dụ:

DTO
public class MedicineResponse {

    private Long id;

    private String name;

    private Double price;
}

Có thể hình dung:
Entity
→ phục vụ persistence/database

DTO
→ phục vụ truyền dữ liệu
Mapper đứng giữa hai object này.

2.2. Mapping thủ công

2.2.1. Mapping thủ công là gì?

Mapping thủ công là cách lập trình viên tự viết code để lấy dữ liệu từ object nguồn và gán sang object đích.
Ví dụ:

Mapping thủ công
public MedicineResponse toResponse(Medicine medicine) {

    MedicineResponse response = new MedicineResponse();

    response.setId(medicine.getId());
    response.setName(medicine.getName());
    response.setPrice(medicine.getPrice());

    return response;
}

Đây là mapping thủ công.

2.2.2. Phân tích quá trình mapping

Object nguồn:
Medicine medicine
Object đích:
MedicineResponse response
Các bước:

medicine.getId()
       ↓
response.setId()

medicine.getName()
       ↓
response.setName()

medicine.getPrice()
       ↓
response.setPrice()

Entity

Entity

@Setter
@NoArgsConstructor

    @GeneratedValue(strategy = GenerationType.IDENTITY)

DTO

DTO

Mapper

Mapper

2.3. Hạn chế của Mapping thủ công

Mapping thủ công dễ hiểu và không phụ thuộc thư viện bên ngoài.
Tuy nhiên, khi project lớn, cách này có nhiều hạn chế.

2.3.1. Nhiều code lặp lại

Ví dụ DTO có 10 field:

response.setId(entity.getId());
response.setName(entity.getName());
response.setPrice(entity.getPrice());
response.setQuantity(entity.getQuantity());
response.setDescription(entity.getDescription());
response.setCategory(entity.getCategory());

Nếu có 50 DTO, số lượng code mapping sẽ rất lớn.

2.3.2. Dễ quên field

Ví dụ Entity có:

private String name;
private Double price;
private Integer quantity;
private String description;

Nhưng lập trình viên chỉ viết:

response.setName(entity.getName());
response.setPrice(entity.getPrice());

và quên:
quantity
description
Chương trình vẫn có thể chạy nhưng dữ liệu trả về không đầy đủ.

2.3.3. Khó bảo trì

Khi Entity thêm:

private String manufacturer;

Mapper cũng cần sửa:

response.setManufacturer(
    entity.getManufacturer()
);

Với project lớn, việc này trở nên mất thời gian.

2.3.4. Mapping danh sách dài

Nếu có:
List<Medicine>
chúng ta phải lặp:

Stream API
List<MedicineResponse> responses =
        medicines.stream()
                .map(medicineMapper::toResponse)
                .toList();

Bản thân đoạn này không quá phức tạp, nhưng nếu logic mapping ngày càng nhiều thì việc quản lý thủ công sẽ trở nên khó khăn.

2.4. ModelMapper

2.4.1. ModelMapper là gì?

ModelMapper là thư viện Java hỗ trợ tự động mapping dữ liệu giữa các object.
Thay vì phải viết:

response.setId(medicine.getId());
response.setName(medicine.getName());
response.setPrice(medicine.getPrice());

có thể sử dụng:

ModelMapper
MedicineResponse response =
        modelMapper.map(
                medicine,
                MedicineResponse.class
        );

ModelMapper sẽ dựa trên tên và kiểu dữ liệu của các thuộc tính để thực hiện mapping.

2.4.2. Cơ chế hoạt động cơ bản

Giả sử:
Medicine
có:

name
price
và:
MedicineResponse
cũng có:
id
name
price
ModelMapper có thể hiểu:

Medicine.id
     ↓
MedicineResponse.id

Medicine.name
     ↓
MedicineResponse.name

Medicine.price
     ↓
MedicineResponse.price

2.4.3. Điều kiện mapping cơ bản

ModelMapper hoạt động thuận lợi nhất khi:
Tên field giống nhau.
Kiểu dữ liệu tương thích.
Object nguồn và object đích có cấu trúc tương đối tương đồng.
Ví dụ:

private String name;
→

hoặc:

2.10. MapStruct

2.10.1. MapStruct là gì?

MapStruct là một thư viện hỗ trợ mapping object trong Java.
Điểm khác biệt quan trọng:
MapStruct tạo code mapping tại thời điểm compile thay vì thực hiện mapping chủ yếu bằng reflection lúc runtime như cách tiếp cận phổ biến của ModelMapper.
Ví dụ chúng ta khai báo:

MapStruct Mapper
@Mapper(componentModel = "spring")
public interface MedicineMapper {

    MedicineResponse toResponse(Medicine medicine);

    Medicine toEntity(MedicineRequest request);
}

MapStruct sẽ tạo implementation tương ứng trong quá trình build.

    Medicine toEntity(MedicineRequest request);
}

Service

    private final MedicineMapper medicineMapper;

2.15. Tổng kết

Cần ghi nhớ 3 cấp độ mapping:

Cấp độ 1 – Mapping thủ công

Ưu điểm: dễ hiểu, toàn quyền kiểm soát.

Cấp độ 2 – ModelMapper

    entity,
    MedicineResponse.class
);

Ưu điểm: đơn giản, nhanh triển khai.

Cấp độ 3 – MapStruct

medicineMapper.toResponse(entity);

Ưu điểm: rõ ràng, sinh code khi compile, phù hợp với project lớn.

Kiến thức quan trọng nhất

hay:

mà phải hiểu bản chất:

  ↑             ↓
  └──── DTO ────┘

hay cụ thể:

    ↓

    ↓

    ↓
Medicine

Nếu hiểu được luồng này, học viên sẽ hiểu tại sao trong một project Spring Boot thực tế thường có Entity, Request DTO, Response DTO và Mapper thay vì dùng trực tiếp Entity trong Controller.

PHẦN 3: CHUẨN HÓA RESPONSE TRONG SPRING BOOT

3.1. Response trong REST API

3.1.1. Response là gì?

Trong REST API, Response là dữ liệu mà server gửi trả về cho client sau khi nhận và xử lý một HTTP Request.
Ví dụ client gửi:

GET /api/medicines/1

Server xử lý yêu cầu và trả về:

{
    "id": 1,
    "name": "Paracetamol",
    "price": 15000
}

Trong trường hợp này:

Client
   │
   │ GET /api/medicines/1
   ▼
Server
   │
   │ JSON Response
   ▼
Client

3.1.2. Response gồm những thành phần nào?

Một HTTP Response thường gồm:

HTTP Response
│
├── Status Code
├── Headers
└── Body

Ví dụ:

HTTP/1.1 200 OK
Content-Type: application/json
Body:
{
    "id": 1,
    "name": "Paracetamol"
}

Status Code
Cho biết kết quả xử lý Request.
Ví dụ:
200 → Thành công
201 → Tạo thành công
400 → Request không hợp lệ
404 → Không tìm thấy
500 → Lỗi server

Headers
Chứa thông tin bổ sung về Response.
Ví dụ:
Content-Type: application/json
cho biết Body đang chứa dữ liệu JSON.

Body
Chứa dữ liệu thực tế mà server muốn trả về.
Ví dụ:

{
    "id": 1,
    "name": "Paracetamol"
}

3.3. Xây dựng ApiResponse

3.3.1. ApiResponse là gì?

ApiResponse là một class dùng để đóng gói Response của API vào một cấu trúc thống nhất.
Thay vì trả trực tiếp:

return medicineResponse;

chúng ta có thể trả:

return new ApiResponse<>(
        200,
        "Success",
        medicineResponse
);

3.3.2. Thiết kế ApiResponse cơ bản

Ví dụ:

ApiResponse
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

Ở đây có 3 thành phần:
status
→ trạng thái

message
→ thông báo

data
→ dữ liệu

3.3.3. Getter và Setter

Nếu chưa sử dụng Lombok:

ApiResponse không Lombok
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;

    public ApiResponse() {
    }

    public ApiResponse(
            int status,
            String message,
            T data) {

        this.status = status;
        this.message = message;
        this.data = data;
    }

    public int getStatus() {
        return status;
    }

    public void setStatus(int status) {
        this.status = status;
    }

    public String getMessage() {
        return message;
    }

    public void setMessage(String message) {
        this.message = message;
    }

    public T getData() {
        return data;
    }

    public void setData(T data) {
        this.data = data;
    }
}

Code khá dài.
Vì chúng ta đã học Lombok, có thể sử dụng:

ApiResponse với Lombok
@Data
@NoArgsConstructor
@AllArgsConstructor
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

3.3.4. Giải thích cấu trúc

private int status;
Lưu mã trạng thái.
Ví dụ:
200
201
400
404
500

private String message;
Chứa thông báo.
Ví dụ:
"Success"
hoặc:
"Medicine not found"

Chứa dữ liệu Response.
Điểm quan trọng ở đây là T.

Phần này cần hiểu kỹ.

3.4. Generic trong ApiResponse

3.4.1. Generic là gì?

Generic cho phép một class hoặc method làm việc với nhiều kiểu dữ liệu khác nhau mà vẫn đảm bảo kiểm tra kiểu dữ liệu tại compile time.
Ví dụ class:

Generic
public class Box<T> {

    private T value;
}

T là một kiểu dữ liệu chưa xác định.
Khi sử dụng:
Box<String>
thì:
T = String
Nếu:
Box<Integer>
thì:
T = Integer

3.4.2. Tại sao ApiResponse cần Generic?

Giả sử chúng ta viết:

ApiResponse không Generic
public class ApiResponse {

    private int status;

    private String message;

    private Object data;
}

Có thể sử dụng:
data = MedicineResponse;
hoặc:
data = List<MedicineResponse>;
hoặc:
data = UserResponse;
Tuy nhiên sử dụng Object làm mất đi nhiều lợi ích của type safety.
Generic tốt hơn:

ApiResponse với Generic
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

3.4.3. T hoạt động như thế nào?

Khi:
ApiResponse<MedicineResponse>
thì:
T = MedicineResponse
Do đó:
private T data;
tương đương với:
private MedicineResponse data;

Nếu:
ApiResponse<List<MedicineResponse>>
thì:
T = List<MedicineResponse>
và:
private T data;
tương đương:
private List<MedicineResponse> data;

Ví dụ

Ở đây:

Với danh sách:

        new ApiResponse<>(

Ở đây:

Ví dụ:

thì data phải là:
MedicineResponse
Không nên truyền:

Điều này giúp phát hiện lỗi kiểu dữ liệu sớm hơn.

PHẦN 4: XỬ LÝ EXCEPTION TRONG SPRING BOOT

Trong các ứng dụng Spring Boot, Exception là một vấn đề rất quan trọng cần được xử lý đúng cách.
Một API thực tế không thể chỉ xử lý trường hợp thành công. Trong quá trình chạy, rất nhiều lỗi có thể xảy ra:

  • Không tìm thấy dữ liệu.
  • Dữ liệu bị trùng.
  • Request không hợp lệ.
  • Validation thất bại.
  • Người dùng không có quyền.
  • Lỗi database.
    Lỗi logic nghiệp vụ.
  • Lỗi không xác định.
  • Nếu không xử lý Exception đúng cách, client có thể nhận được những Response khó hiểu như: 

{
    "timestamp": "2026-08-24T10:20:30",
    "status": 500,
    "error": "Internal Server Error",
    "trace": "java.lang.NullPointerException..."
}

Trong một API chuyên nghiệp, chúng ta thường muốn biến những Exception đó thành Response có cấu trúc rõ ràng:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

4.1. Exception trong REST API

4.1.1. Exception là gì?

Exception là một tình huống bất thường xảy ra trong quá trình chương trình thực thi, khiến luồng xử lý bình thường bị gián đoạn.
Ví dụ:

int a = 10;
int b = 0;

int result = a / b;

Code trên gây ra:
ArithmeticException

Một ví dụ khác:

Medicine medicine = medicineRepository
        .findById(id)
        .orElse(null);

return medicine.getName();

Nếu medicine == null:
NullPointerException

4.1.2. Exception trong API

Giả sử client gọi:
GET /api/medicines/100
Nhưng Medicine có ID 100 không tồn tại.
Trong Service có thể viết:

Medicine medicine =
        medicineRepository.findById(id)
                .orElseThrow();

Khi không tìm thấy dữ liệu, Spring/JPA có thể phát sinh Exception.
Nếu không xử lý, client có thể nhận:
500 Internal Server Error
Trong khi về mặt nghiệp vụ, vấn đề thực sự là:
Medicine không tồn tại
Đúng hơn nên trả:
404 Not Found
và:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

4.1.3. Tại sao cần xử lý Exception?

Xử lý Exception giúp:

  1. API trả HTTP Status phù hợp
    Ví dụ:
    404 → Không tìm thấy
    400 → Request không hợp lệ
    409 → Dữ liệu bị trùng
    500 → Lỗi server
  2. Client dễ hiểu lỗi
    Thay vì nhận Stack Trace:
    NullPointerException...
    client nhận:
    { "status": 404, "message": "Medicine not found", "data": null }
  3. Không để lộ thông tin nội bộ
    Không nên trả cho client:
    Stack trace.
    Tên class nội bộ.
    SQL query.
    Thông tin database.
    Đường dẫn server.
    Thông tin cấu hình hệ thống.
  4. Dễ bảo trì
    Các lỗi được xử lý tập trung thay vì viết:
    try {
    ...
    } catch (...) {
    ...
    }
    ở hàng chục Controller.

public UserResponse create(UserRequest request) {

    if (userRepository.existsByEmail(
            request.getEmail())) {

        throw new DuplicateResourceException(
                "Email already exists"
        );

    User user =
            userMapper.toEntity(request);

    User saved =
            userRepository.save(user);

    return userMapper.toResponse(saved);
}

GlobalExceptionHandler.java
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>>
    handleResourceNotFound(
            ResourceNotFoundException ex) {

        ApiResponse<Void> response =
                new ApiResponse<>(
                        404,
                        ex.getMessage(),
                        null
                );

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }


    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>>
    handleDuplicateResource(
            DuplicateResourceException ex) {

        ApiResponse<Void> response =
                new ApiResponse<>(
                        409,
                        ex.getMessage(),
                        null
                );

        return ResponseEntity
                .status(HttpStatus.CONFLICT)
                .body(response);
    }


    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<
            ApiResponse<Map<String, String>>
            > handleValidationException(
                    MethodArgumentNotValidException ex) {

        Map<String, String> errors =
                new HashMap<>();

        ex.getBindingResult()
                .getFieldErrors()
                .forEach(error ->
                        errors.put(
                                error.getField(),
                                error.getDefaultMessage()
                        )
                );

        ApiResponse<Map<String, String>> response =
                new ApiResponse<>(
                        400,
                        "Validation failed",
                        errors
                );

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(response);
    }


    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>>
    handleException(Exception ex) {

        log.error(
                "Unexpected error occurred",
                ex
        );

        ApiResponse<Void> response =
                new ApiResponse<>(
                        500,
                        "Internal server error",
                        null
                );

        return ResponseEntity
                .status(
                        HttpStatus.INTERNAL_SERVER_ERROR
                )
                .body(response);
    }
}

@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ApiResponse<>(404, ex.getMessage(), null));
    }

    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>> handleDuplicate(DuplicateResourceException ex) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ApiResponse<>(409, ex.getMessage(), null));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Map<String, String>>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors()
            .forEach(error -> errors.put(error.getField(), error.getDefaultMessage()));
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ApiResponse<>(400, "Validation failed", errors));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleException(Exception ex) {
        log.error("Unexpected error", ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ApiResponse<>(500, "Internal server error", null));
    }

@Service
@RequiredArgsConstructor
public class MedicineService {
    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {
        Medicine medicine = medicineRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Medicine not found with id: " + id));
        return medicineMapper.toResponse(medicine);
    }

    public MedicineResponse create(MedicineRequest request) {
        if (medicineRepository.existsByName(request.getName())) {
            throw new DuplicateResourceException("Medicine name already exists");
        }
        Medicine medicine = medicineMapper.toEntity(request);
        Medicine saved = medicineRepository.save(medicine);
        return medicineMapper.toResponse(saved);
    }
}
