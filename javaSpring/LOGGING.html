PHẦN 1. TỔNG QUAN VỀ LOGGING

1.1. Logging là gì?

Trong quá trình một ứng dụng chạy, rất nhiều hoạt động xảy ra:

  • Người dùng gửi Request đến Server.
  • Controller tiếp nhận Request.
  • Service xử lý nghiệp vụ.
  • Repository truy vấn Database.
  • Server trả Response về Client.
  • Có thể xảy ra Exception.
  • Một số thao tác có thể mất nhiều thời gian.
  • Một số dữ liệu có thể không hợp lệ.

Trong quá trình phát triển và vận hành ứng dụng, chúng ta cần một cơ chế để ghi lại các thông tin quan trọng xảy ra trong hệ thống.

Cơ chế ghi lại những thông tin này được gọi là Logging.

Có thể hiểu đơn giản:

Logging là quá trình ghi lại các sự kiện và thông tin
xảy ra trong quá trình ứng dụng hoạt động.

Ví dụ, khi một API được gọi:

HTTP
GET /api/users/10

Ứng dụng có thể ghi Log:

INFO  - Request GET /api/users/10
INFO  - Find user with id = 10
INFO  - User found successfully

Nếu xảy ra lỗi:

ERROR - Cannot find user with id = 10

Những thông tin này giúp Developer biết ứng dụng đang làm gì, đã xảy ra chuyện gì và lỗi xảy ra ở đâu.

1.2. Tại sao ứng dụng cần Logging?

Một ứng dụng thực tế có thể có hàng trăm API và hàng nghìn dòng code.

Khi ứng dụng xảy ra lỗi, Developer rất khó biết chính xác nguyên nhân nếu không có Log.

Ví dụ:

Client
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database

Giả sử API trả về:

500 Internal Server Error

Chỉ nhìn vào Response:

JSON
{
    "status": 500,
    "message": "Internal Server Error"
}

chúng ta chưa biết chính xác lỗi xảy ra ở đâu.

Có thể lỗi nằm ở:

  • Controller.
  • Service.
  • Repository.
  • Database.
  • Một phép tính trong Business Logic.
  • Một NullPointerException.
  • Một cấu hình bị sai.

Nếu hệ thống có Logging, chúng ta có thể nhìn vào Log:

INFO  - Request GET /api/users/10
INFO  - UserService.getUserById(10)
INFO  - Searching user from database
ERROR - Database connection failed

Như vậy Developer có thể xác định được vấn đề dễ dàng hơn.

Logging thường được sử dụng để:

Mục đích Ví dụ
Theo dõi chương trìnhAPI nào đang được gọi
DebugGiá trị của biến
Phát hiện lỗiException xảy ra
Theo dõi DatabaseQuery hoặc thao tác dữ liệu
Theo dõi hiệu năngAPI mất 2 giây để xử lý
Theo dõi hệ thốngServer khởi động
Điều tra sự cốRequest nào gây ra lỗi

1.3. Logging khác với System.out.println() như thế nào?

Khi mới học Java, chúng ta thường sử dụng:

Java
System.out.println("Hello");

Ví dụ:

Java
System.out.println("Get user successfully");

Cách này có thể sử dụng trong quá trình học hoặc kiểm tra nhanh.

Tuy nhiên, trong một ứng dụng Spring Boot thực tế, không nên sử dụng System.out.println() để thực hiện Logging.

1.3.1. Hạn chế của System.out.println()

Hạn chế 1: Không có Log Level

Với:

Java
System.out.println("User created");

chúng ta không biết đây là:

INFO
DEBUG
WARN
ERROR

Trong khi Logging Framework cho phép phân loại rõ ràng.

Hạn chế 2: Khó quản lý

Một Project lớn có thể có:

100
500
1000

lệnh System.out.println().

Việc kiểm soát chúng trở nên rất khó khăn.

Hạn chế 3: Không dễ ghi Log ra File

System.out.println() chủ yếu ghi ra Console.

Trong ứng dụng thực tế, chúng ta thường muốn:

Console
   +
File
   +
Log theo ngày
   +
Log theo kích thước

Logging Framework hỗ trợ những cơ chế này.

Hạn chế 4: Không phân biệt mức độ quan trọng

Ví dụ:

Thông tin bình thường
Cảnh báo
Lỗi
Thông tin Debug

System.out.println() không cung cấp cơ chế chuẩn để phân loại những thông tin này.

1.3.2. Logging Framework giải quyết vấn đề như thế nào?

Thay vì:

Java
System.out.println("User created");

chúng ta có thể sử dụng:

Java
logger.info("User created");

Hoặc:

Java
logger.error("Cannot create user");

Hoặc:

Java
logger.debug("User id = {}", id);

Nhờ đó Log có thể được phân loại và quản lý tốt hơn.

1.4. Log dùng để làm gì?

Một Log không đơn giản chỉ là một dòng chữ.

Log thường chứa những thông tin giúp Developer hiểu được một sự kiện xảy ra trong hệ thống.

Ví dụ:

2026-09-27 10:30:15 INFO  UserService - Get user id = 10

Có thể phân tích thành:

        ↓
Thời gian xảy ra sự kiện

INFO
        ↓
Mức độ Log

UserService
        ↓

        ↓
Nội dung Log

Nhờ đó chúng ta biết: Vào thời điểm nào, Class nào đã ghi Log và sự kiện gì đã xảy ra.

1.4.1. Log quá trình xử lý

Ví dụ một API tạo User:

Request received
        ↓
Validate User
        ↓
Save User
        ↓
Database
        ↓

Có thể ghi:

INFO - Create user request received
DEBUG - Validate user data
INFO - Saving user

1.4.2. Log lỗi

Nếu Database xảy ra lỗi:

ERROR - Cannot save user

Hoặc:

ERROR - Database connection failed

Khi đó Developer có thể tìm Log để xác định nguyên nhân.

1.4.3. Log để Debug

Trong quá trình phát triển, chúng ta đôi khi cần biết giá trị của dữ liệu:

Java
logger.debug("userId = {}", userId);

Ví dụ:

DEBUG - userId = 15

Điều này rất hữu ích khi tìm lỗi trong Business Logic.

Spring Boot sử dụng Logging Framework để ghi lại thông tin trong quá trình ứng dụng khởi động và hoạt động.

Ví dụ:

1.6. Logback là gì?

Logback là một Logging Framework được sử dụng phổ biến trong các ứng dụng Java.

Trong Spring Boot, Logback được sử dụng làm Logging implementation mặc định trong cấu hình thông thường của Spring Boot.

Logback chịu trách nhiệm thực hiện việc:

  • Nhận Log.
  • Xử lý Log.
  • Phân loại Log.
  • Định dạng Log.
  • Ghi Log ra Console.
  • Ghi Log ra File.
  • Quản lý File Log.

Có thể hình dung:

Application
     │
     │ ghi Log
     ↓
   SLF4J
     │
     ↓
  Logback
     │
     ├──────────────┐
     ↓              ↓
 Console          File

1.7. Mối quan hệ giữa SLF4J và Logback

Đây là một phần rất quan trọng khi học Logging trong Spring Boot.

Học viên cần phân biệt:

SLF4J

và

Logback

Hai thành phần này không phải là một.

1.7.1. SLF4J là gì?

SLF4J là một abstraction cho Logging trong Java.

Có thể hiểu đơn giản:

SLF4J cung cấp một API để ứng dụng thực hiện việc Logging
mà không cần phụ thuộc trực tiếp vào một Logging Framework cụ thể.

Ví dụ:

Java
logger.info("User created");

Code của chúng ta sử dụng API của SLF4J.

1.7.2. Logback làm gì?

Logback là phần thực hiện việc ghi Log.

Có thể hình dung:

Developer
    ↓
SLF4J
    ↓
Logback
    ↓
Console / File

Hay đơn giản hơn:

SLF4J là giao diện/API để gọi Logging,
còn Logback là một implementation thực hiện Logging.

1.8. Tại sao Spring Boot sử dụng SLF4J?

Một lợi ích quan trọng của việc sử dụng Logging abstraction là chúng ta không phải viết code phụ thuộc quá chặt vào một Logging Framework.

Ví dụ Application sử dụng:

Java
logger.info("Hello");

Code Application làm việc với API Logging.

Phía dưới có thể sử dụng:

SLF4J
   ↓
Logback

Nếu hệ thống thay đổi Logging implementation, Application không nhất thiết phải thay đổi toàn bộ code Logging.

Đây là một trong những lợi ích của việc sử dụng abstraction.

1.9. Logging Flow trong Spring Boot

Đây là kiến thức cần nắm trước khi chuyển sang phần cấu hình Logback.

Giả sử chúng ta có:

Java
logger.info("Get user successfully");

Luồng xử lý có thể hình dung:

┌──────────────────────┐
│ Spring Boot          │
│ Application          │
└──────────┬───────────┘
           │
           │ logger.info()
           ↓
┌──────────────────────┐
│       SLF4J          │
│  Logging Abstraction │
└──────────┬───────────┘
           │
           ↓

Trong đó:

  • Application: Là nơi chúng ta viết logger.info(...).
  • SLF4J: Cung cấp API Logging.
  • Logback: Thực hiện việc xử lý và ghi Log.
  • Console: Hiển thị Log trên Console của IntelliJ/Eclipse/Terminal.
  • File: Có thể lưu Log vào File nếu cấu hình.

1.10. Các thành phần cơ bản của một hệ thống Logging

Một hệ thống Logging thường có các thành phần chính:

Logger
   ↓
Log Level
   ↓
Appender
   ↓
Encoder / Formatter
   ↓
Output

Trong đó:

  • Logger: Là đối tượng được sử dụng để ghi Log. Ví dụ: logger.info(...)
  • Log Level: Xác định mức độ của Log (TRACE, DEBUG, INFO, WARN, ERROR).
  • Appender: Xác định Log sẽ được ghi đi đâu (Console, File).
  • Encoder / Pattern: Xác định Log được hiển thị với định dạng như thế nào. Ví dụ: 2026-09-27 10:30:15 INFO UserService - Get user

2.1. SLF4J là gì?

2.1.1. Khái niệm

SLF4J là viết tắt của:

Simple Logging Facade for Java

SLF4J cung cấp một abstraction/API chung cho việc Logging trong Java.

Nói đơn giản, SLF4J cung cấp cho Developer các API để ghi Log mà không cần viết code phụ thuộc trực tiếp vào một Logging Framework cụ thể.

Ví dụ:

Java
logger.info("User created successfully");

Trong đoạn code trên, chúng ta đang sử dụng API của SLF4J.

2.1.2. Tại sao cần SLF4J?

Trong Java có nhiều Logging Framework:

Logback
Log4j2
java.util.logging

Nếu Application sử dụng trực tiếp một Framework cụ thể, code của Application sẽ phụ thuộc vào Framework đó.

Ví dụ, nếu toàn bộ code phụ thuộc trực tiếp vào một Logging Framework, khi muốn thay đổi Framework, Developer có thể phải thay đổi rất nhiều code.

SLF4J giải quyết vấn đề này bằng cách tạo ra một lớp trung gian:

Application
     ↓
   SLF4J
     ↓
Logging Framework

Trong Spring Boot thông thường:

Application
     ↓
   SLF4J
     ↓
  Logback
     ↓
Console / File

2.2. Logger là gì?

2.2.1. Khái niệm

Logger là đối tượng được sử dụng để ghi Log trong ứng dụng.

Ví dụ:

Java
logger.info("User created successfully");

Ở đây:

logger

là đối tượng thực hiện việc ghi Log.

Logger cung cấp nhiều phương thức:

Java
logger.trace();
logger.debug();
logger.info();
logger.warn();
logger.error();

Mỗi phương thức tương ứng với một Log Level.

2.2.2. Ví dụ thực tế

Giả sử chúng ta có một Service:

Java
public class UserService {

}

Trong quá trình xử lý User, chúng ta muốn ghi lại:

Đang lấy User
User ID = 10
Lấy User thành công

Có thể sử dụng:

Java
logger.info("Get user");
logger.debug("User ID = {}", id);
logger.info("Get user successfully");

Khi chạy ứng dụng, Console có thể hiển thị:

INFO  - Get user
DEBUG - User ID = 10
INFO  - Get user successfully

2.2.3. Logger giúp ích gì?

Logger giúp Developer:

Theo dõi hoạt động của Application

Ví dụ:

INFO - Application started
INFO - User created
INFO - Order created

Debug chương trình

DEBUG - userId = 10
DEBUG - username = manh

Phát hiện lỗi

ERROR - Cannot connect to database

Theo dõi cảnh báo

WARN - Product stock is low

2.3. Tạo Logger trong Spring Boot

Sau khi tạo Project Spring Boot, chúng ta có thể sử dụng SLF4J để tạo Logger.

Ví dụ tạo class:

Java
@Service
public class UserService {

}

Import:

Java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

Sau đó tạo Logger:

Java
private static final Logger logger =
        LoggerFactory.getLogger(UserService.class);

Class hoàn chỉnh:

Java
@Service
public class UserService {

    private static final Logger logger =
            LoggerFactory.getLogger(UserService.class);

}

2.3.1. Cách hoạt động

Dòng code:

Java
private static final Logger logger =
        LoggerFactory.getLogger(UserService.class);

có thể hiểu theo luồng:

UserService
     ↓
LoggerFactory
     ↓
Tạo Logger
     ↓
Logger gắn với UserService

Sau đó chúng ta có thể sử dụng:

Java
logger.info("...");
logger.debug("...");
logger.warn("...");
logger.error("...");

2.3.2. Ví dụ

Java
@Service
public class UserService {

    private static final Logger logger =
            LoggerFactory.getLogger(UserService.class);

    public void getUser() {

        logger.info("Get user");

    }
}

Khi gọi:

Java
getUser();

Logger sẽ ghi:

INFO - Get user

2.4. LoggerFactory

2.4.1. LoggerFactory là gì?

LoggerFactory là class của SLF4J dùng để tạo Logger.

Import:

Java
import org.slf4j.LoggerFactory;

Phương thức thường sử dụng:

Java
LoggerFactory.getLogger(...)

2.4.2. Cú pháp

Java
LoggerFactory.getLogger(ClassName.class);

Ví dụ:

Java
LoggerFactory.getLogger(UserService.class);

Kết quả là một Logger được gắn với:

UserService

2.4.3. Tại sao truyền Class vào getLogger()?

Giả sử Project có:

UserController
UserService
ProductController
ProductService
OrderService

Mỗi class tạo Logger tương ứng:

Java
LoggerFactory.getLogger(UserController.class);
LoggerFactory.getLogger(UserService.class);
LoggerFactory.getLogger(ProductService.class);

Khi xem Log, chúng ta có thể biết Log được tạo từ class nào.

Ví dụ:

INFO  UserController - Get user request
INFO  UserService - Find user
INFO  ProductService - Get product

Điều này rất hữu ích khi Debug.

2.5. Khai báo Logger

Cách khai báo Logger phổ biến:

Java

        LoggerFactory.getLogger(UserService.class);

2.6. Các mức Log cơ bản

Trong SLF4J, chúng ta thường làm việc với 5 Log Level:

  • Khi Debug rất sâu.
  • Khi cần theo dõi từng bước xử lý.
  • Khi cần điều tra một vấn đề khó.

DEBUG

Ví dụ:

Java

DEBUG - userId = 10

Trạng thái xử lý

Java

Java

2.16. Ví dụ tổng hợp

Sau khi học xong toàn bộ Phần 2, chúng ta có thể viết một Service như sau:

Java
@Service
public class UserService {

    private static final Logger logger =
            LoggerFactory.getLogger(UserService.class);

    public User getUserById(Integer id) {

        logger.info(
            "Get user request"
        );

        logger.debug(
            "User id = {}",
            id
        );

        if (id == null) {

            logger.warn(
                "User id is null"
            );

            return null;
        }

        try {

            logger.trace(
                "Start searching user"
            );

            // tìm User

            logger.trace(
                "Finish searching user"
            );

            logger.info(
                "Get user successfully, id = {}",
                id
            );

            return user;

        } catch (Exception e) {

            logger.error(
                "Cannot get user with id = {}",
                id,
                e
            );

            throw e;
        }
    }
}

→ id không hợp lệ

Tạo Logger

PHẦN 3. CẤU HÌNH LOGBACK TRONG SPRING BOOT

Sau khi đã biết cách sử dụng Logger và các mức Log trong phần trước, chúng ta cần tìm hiểu cách điều khiển Log trong ứng dụng Spring Boot.

Trong thực tế, chúng ta không thể để ứng dụng ghi tất cả Log ở mọi mức độ.

Ví dụ:

  • Khi lập trình, chúng ta muốn xem nhiều thông tin để kiểm tra chương trình.
  • Khi chạy Production, chúng ta không muốn xuất quá nhiều Log DEBUG.
  • Một số Package có thể cần Log chi tiết hơn các Package khác.
  • Có thể muốn tắt những Log không cần thiết.
  • Có thể muốn thay đổi định dạng Log.

Spring Boot cung cấp sẵn cơ chế cấu hình Logging và mặc định sử dụng Logback khi sử dụng Starter của Spring Boot.

3.1. Logback mặc định trong Spring Boot

3.1.1. Spring Boot có sẵn Logback

Khi tạo một dự án Spring Boot và sử dụng:

XML
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter</artifactId>
</dependency>

hoặc phổ biến hơn:

XML
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Spring Boot đã cung cấp sẵn hệ thống Logging.

Thông thường luồng hoạt động có thể hình dung:

Code Java
   │
   │ logger.info(...)
   ▼
SLF4J
   │
   ▼
Logback
   │
   ├── Console
   │
   └── File

Trong đó:

Thành phần Vai trò
LoggerĐược sử dụng trong code để ghi Log
SLF4JCung cấp API Logging
LogbackThực hiện việc ghi Log
ConsoleHiển thị Log trên terminal/console
FileCó thể lưu Log vào file

3.1.2. Không cần tự cài Logback trong trường hợp thông thường

Đây là một điểm quan trọng.

Khi sử dụng Spring Boot Starter, chúng ta thường không cần tự thêm Logback dependency.

Ví dụ:

XML
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Spring Boot đã chuẩn bị hệ thống Logging phù hợp.

Do đó chúng ta có thể viết:

Java
private static final Logger logger =
        LoggerFactory.getLogger(UserService.class);

và sử dụng ngay:

Java
logger.info("Get all users");

3.1.3. Log mặc định được hiển thị ở đâu?

Mặc định, Log được hiển thị trên Console.

Ví dụ:

2026-09-27T10:20:15.123+07:00  INFO 12345 --- [main]
c.e.demo.DemoApplication : Starting DemoApplication

Khi Controller gọi Service:

Java
logger.info("Get all users");

Console có thể hiển thị:

Như vậy, nếu chúng ta chưa cấu hình gì thì Logging vẫn hoạt động.

3.2. File cấu hình Logback

Có hai hướng phổ biến để cấu hình Logging trong Spring Boot.

Cách 1: Cấu hình thông qua application.properties

Ví dụ:

Properties

Hoặc:

Properties

Cách này đơn giản và phù hợp với các cấu hình cơ bản.

Cách 2: Sử dụng file cấu hình Logback

Spring Boot hỗ trợ các file cấu hình Logback như:

logback.xml

hoặc:

logback-spring.xml

Trong Spring Boot, logback-spring.xml thường rất hữu ích vì có thể tận dụng các cơ chế cấu hình của Spring Boot.

Ví dụ cấu trúc:

└── main
    └── resources
        ├── application.properties
        └── logback-spring.xml

3.2.1. Khi nào sử dụng application.properties?

Nếu chỉ cần:

  • thiết lập Log Level;
  • thiết lập Log Level cho Package;
  • thay đổi một số cấu hình đơn giản;

thì application.properties thường là đủ.

Ví dụ:

Properties

Log được ghi vào một File.

logs/application.log

4.4.3. Rolling File Appender

Log được ghi vào File và File có thể được xoay vòng.

application.log
application.2026-09-27.log
application.2026-09-28.log
application.2026-09-29.log

Hoặc xoay vòng khi File đạt kích thước nhất định.

Ví dụ:

Logger
   │
   ├── CONSOLE
   │
   └── FILE

Khi đó cùng một Log có thể xuất ra:

Console
   +
File

Java

có thể đồng thời xuất ra Console và File logs/application.log.

4.5. encoder

encoder xác định cách Log được chuyển thành nội dung đầu ra.

Ví dụ:

XML
<encoder>

    <pattern>
        %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n

Có thể hiểu:

Logger
   │
   ▼
Appender
   │
   ▼
Encoder
   │
   ▼
Output

4.5.1. Tại sao cần Encoder?

Logger tạo ra thông tin:

Time
Level
Thread
Logger
Message

Encoder giúp chúng ta quyết định những thông tin đó được xuất ra như thế nào.

Ví dụ:

4.6. pattern

pattern quyết định định dạng cuối cùng của Log.

Ví dụ:

XML
<pattern>
    %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n
</pattern>

Đây là một trong những phần quan trọng nhất của Logback.

4.6.1. %d

%d đại diện cho thời gian.

Ví dụ: 2026-09-27 10:30:15

Có thể định dạng:

Pattern
%d{yyyy-MM-dd HH:mm:ss}

Kết quả: 2026-09-27 10:30:15

4.6.2. %level

%level hiển thị Log Level.

INFO
DEBUG
WARN
ERROR

Có thể sử dụng %-5level để tạo khoảng cách giúp các dòng Log dễ đọc hơn.

4.6.3. %thread

%thread hiển thị Thread tạo ra Log.

main
http-nio-8080-exec-1

Trong ứng dụng Web, thông tin Thread có thể hữu ích khi theo dõi Request.

4.6.4. %logger

%logger hiển thị tên Logger.

Thông thường Logger được tạo từ Class:

Java
private static final Logger logger =
        LoggerFactory.getLogger(UserService.class);

Khi đó Logger có thể là: com.example.service.UserService.

Có thể rút gọn bằng %logger{36} để tránh dòng Log quá dài.

4.6.5. %msg

%msg hiển thị nội dung mà chúng ta truyền vào Logger.

Ví dụ:

Java
logger.info("Get user successfully");

thì %msg sẽ tương ứng: Get user successfully.

4.6.6. %n

%n tạo dòng mới.

Ví dụ:

XML
<pattern>
    %level %msg%n
</pattern>

Có thể tạo:

INFO Get user successfully
INFO Create user successfully
INFO Delete user successfully

Mỗi Log nằm trên một dòng riêng.

4.7. root

root đại diện cho Root Logger.

Ví dụ:

XML
<root level="INFO">

    <appender-ref ref="CONSOLE"/>

</root>

Trong đó level="INFO" xác định Log Level.

4.7.1. root level

Ví dụ: <root level="INFO"> có nghĩa Root Logger sử dụng INFO.

Các Log INFO, WARN, ERROR được phép xử lý.

4.7.2. appender-ref

Ví dụ:

XML
<appender-ref ref="CONSOLE"/>

có nghĩa Root Logger sử dụng Appender có tên CONSOLE.

Tên name="CONSOLE" phải tương ứng với ref="CONSOLE".

4.7.3. Ví dụ hoàn chỉnh

XML
<configuration>

    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">

        <encoder>
            <pattern>
                %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n
            </pattern>
        </encoder>

    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>

Đây là cấu hình cơ bản mà học viên cần hiểu rõ trước khi chuyển sang File Appender.

4.10. Rolling File Appender

File Appender đơn giản có một vấn đề:

Nếu ứng dụng chạy trong thời gian dài, File application.log có thể ngày càng lớn.

Ví dụ:

application.log
     ↓
100 MB
     ↓
500 MB
     ↓
2 GB
     ↓
10 GB

Điều này không phù hợp với hệ thống Production.

Rolling File Appender giải quyết vấn đề này bằng cách xoay vòng File Log.

4.10.1. Ý tưởng Rolling

Thay vì chỉ có application.log, chúng ta có thể có:

application.log
application.2026-09-25.log
application.2026-09-26.log
application.2026-09-27.log

File hiện tại là application.log, còn các File cũ được lưu riêng.

4.10.2. Cấu hình cơ bản

XML
<appender name="ROLLING_FILE"
          class="ch.qos.logback.core.rolling.RollingFileAppender">

    <file>logs/application.log</file>

    <encoder>
        <pattern>
            %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n
        </pattern>
    </encoder>

    <rollingPolicy
            class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">

        <fileNamePattern>
            logs/application.%d{yyyy-MM-dd}.log
        </fileNamePattern>

    </rollingPolicy>

</appender>

4.11. Log theo ngày

Một cách phổ biến là tạo File Log mới mỗi ngày.

Ví dụ:

logs/
│
├── application.2026-09-25.log
├── application.2026-09-26.log
├── application.2026-09-27.log
└── application.log

4.11.1. Cấu hình

XML
<appender name="ROLLING_FILE"
          class="ch.qos.logback.core.rolling.RollingFileAppender">

    <file>logs/application.log</file>

    <encoder>
        <pattern>
            %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n
        </pattern>
    </encoder>

    <rollingPolicy
            class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">

        <fileNamePattern>
            logs/application.%d{yyyy-MM-dd}.log
        </fileNamePattern>

    </rollingPolicy>

</appender>

Phần quan trọng: %d{yyyy-MM-dd} được sử dụng để tạo tên File theo ngày.

4.11.2. Cách hoạt động

Ngày 2026-09-27, Log được ghi vào application.log.

Khi chuyển sang 2026-09-28, Log cũ được xoay thành File theo cấu hình ngày.

Kết quả có thể có application.2026-09-27.log và File hiện tại tiếp tục nhận Log.

4.12. Log theo kích thước File

Ngoài thời gian, chúng ta có thể xoay File khi File đạt một kích thước nhất định.

Ví dụ: 10MB.

Khi application.log đạt 10 MB, Logback có thể thực hiện Rolling.

4.12.1. Size-based Rolling

Một cấu hình phổ biến sử dụng:

XML
<rollingPolicy
        class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">

Ví dụ:

XML
<appender name="ROLLING_FILE"
          class="ch.qos.logback.core.rolling.RollingFileAppender">

    <file>logs/application.log</file>

    <encoder>
        <pattern>
            %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n
        </pattern>
    </encoder>

    <rollingPolicy
            class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">

        <fileNamePattern>
            logs/application.%d{yyyy-MM-dd}.%i.log
        </fileNamePattern>

        <maxFileSize>10MB</maxFileSize>

    </rollingPolicy>

</appender>

Ở đây:

XML
<maxFileSize>10MB</maxFileSize>

quy định kích thước tối đa cho mỗi File trong quá trình Rolling.

4.12.2. %i là gì?

Trong application.%d{yyyy-MM-dd}.%i.log thì:

%d
đại diện cho thời gian.

%i
đại diện cho chỉ số của File trong cùng một khoảng thời gian.

Ví dụ:

application.2026-09-27.0.log
application.2026-09-27.1.log
application.2026-09-27.2.log

Nếu File đầu tiên đạt giới hạn 10MB, Logback có thể chuyển sang File tiếp theo.

4.13. Giới hạn số lượng File Log

Nếu mỗi ngày đều tạo File mới thì sau một thời gian có thể có rất nhiều File:

application.2026-01-01.log
application.2026-01-02.log
application.2026-01-03.log
...
application.2026-09-27.log

Vì vậy chúng ta có thể giới hạn số lượng File cũ được giữ lại.

Ví dụ:

XML
<maxHistory>30</maxHistory>

4.13.1. Ví dụ

XML
<rollingPolicy
        class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">

    <fileNamePattern>
        logs/application.%d{yyyy-MM-dd}.log
    </fileNamePattern>

    <maxHistory>30</maxHistory>

</rollingPolicy>

Ý nghĩa: chỉ giữ lại khoảng 30 đơn vị thời gian theo cấu hình Rolling.

Nếu Pattern là theo ngày %d{yyyy-MM-dd} thì có thể hiểu đơn giản là giữ khoảng 30 ngày.

Log cũ hơn sẽ được loại bỏ theo chính sách Rolling.

4.14. Giới hạn dung lượng Log

Ngoài việc giới hạn số ngày, chúng ta có thể giới hạn dung lượng tổng của các File Log.

Ví dụ:

XML
<totalSizeCap>1GB</totalSizeCap>

Ví dụ đầy đủ:

XML
<rollingPolicy
        class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">

    <fileNamePattern>
        logs/application.%d{yyyy-MM-dd}.%i.log
    </fileNamePattern>

    <maxFileSize>10MB</maxFileSize>

    <maxHistory>30</maxHistory>

    <totalSizeCap>1GB</totalSizeCap>

</rollingPolicy>

4.14.1. Ý nghĩa

maxFileSize
      ↓
Kích thước tối đa của một File

maxHistory
      ↓
Số lượng khoảng thời gian được giữ

totalSizeCap
      ↓
Tổng dung lượng Log được giữ

Ví dụ:

maxFileSize = 10MB
maxHistory = 30
totalSizeCap = 1GB

Có thể hiểu:

  • Một File tối đa khoảng 10MB.
  • Giữ lịch sử theo tối đa 30 đơn vị thời gian.
  • Tổng dung lượng các File Log được giữ không vượt quá khoảng 1GB theo chính sách Rolling.

4.15. Định dạng Log

Đây là phần rất quan trọng vì Log không chỉ cần có thông tin, mà còn cần dễ đọc.

Ví dụ Log mong muốn:

2026-09-27 10:30:15 INFO [main] c.example.service.UserService
- Get user successfully

Có thể phân tích:

Timestamp
    ↓
Log Level
    ↓
Thread
    ↓
Logger
    ↓
Message

4.15.1. Timestamp

Ví dụ: 2026-09-27 10:30:15

Được tạo bởi: %d{yyyy-MM-dd HH:mm:ss}

Trong đó:

yyyy
là năm.

MM
là tháng.

dd
là ngày.

HH
là giờ.

mm
là phút.

ss
là giây.

4.15.2. Log Level

Ví dụ: INFO

Được tạo bởi %level hoặc %-5level để tạo khoảng cách cố định giúp Log dễ đọc.

4.15.3. Thread

Ví dụ: [main] được tạo bởi [%thread].

Trong Web Application có thể thấy [http-nio-8080-exec-1] — cho biết Thread đang xử lý Log.

4.15.4. Logger

Ví dụ: c.example.service.UserService được tạo bởi %logger hoặc %logger{36}.

Nếu Class là UserService và Logger được khai báo bằng LoggerFactory.getLogger(UserService.class) thì tên Logger thường dựa trên tên đầy đủ của Class.

4.15.5. Message

Ví dụ: Get user successfully được tạo bởi %msg.

Khi code logger.info("Get user successfully"); thì %msg chính là Get user successfully.

4.15.6. Ghép tất cả thành một Pattern

Ví dụ:

XML

        <appender-ref ref="ROLLING_FILE"/>

Những kiến thức cần nhớ

Sau Phần 4, học viên cần hiểu được 5 khái niệm cốt lõi:

1. Appender
      ↓
Log đi đâu?

2. Encoder
      ↓
Log được chuyển thành dạng đầu ra như thế nào?

3. Pattern
      ↓
Log hiển thị theo format nào?

4. Root
      ↓
Logger gốc sử dụng Appender nào và Log Level nào?

5. Rolling Policy
      ↓
Khi nào File Log được xoay vòng?

Đặc biệt cần phân biệt:

Logger
   ↓
Tạo Log

Appender
   ↓
Đưa Log đến nơi cần ghi

Encoder
   ↓
Định dạng Log

Pattern
   ↓
Quy định nội dung/format

Rolling Policy
   ↓
Quản lý File Log theo thời gian/kích thước
Ghi nhớ trọng tâm
  • logback-spring.xml đặt trong src/main/resources, dùng cho cấu hình nâng cao.
  • Appender = Log đi đâu; Encoder/Pattern = Log hiển thị thế nào.
  • ConsoleAppender ghi ra Console, FileAppender ghi vào File, RollingFileAppender hỗ trợ xoay vòng.
  • TimeBasedRollingPolicy xoay theo thời gian; SizeAndTimeBasedRollingPolicy xoay theo cả thời gian + kích thước.
  • maxFileSize, maxHistory, totalSizeCap giúp kiểm soát dung lượng Log.
  • %i là chỉ số File trong cùng một khoảng thời gian khi dùng size-based rolling.
  • Pattern phổ biến: %d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n.
  • <appender-ref ref="..."> phải khớp với <appender name="...">.
  • Nền tảng cho phần tiếp theo: cấu hình Logger theo Package/Class, additivity, tách Log File theo loại, Profile Dev/Prod.

  • xử lý Exception thống nhất;
  • Logging tập trung;

Đây chính là mục tiêu của Logging trong một ứng dụng Spring Boot thực tế.

Ghi nhớ trọng tâm
  • Controller log: HTTP method, endpoint, tham số quan trọng, thời gian xử lý — dùng INFO/DEBUG.
  • Service log: Business Logic, các bước xử lý, điều kiện nghiệp vụ, kết quả — dùng DEBUG/INFO.
  • Repository log: thao tác DB quan trọng, tham số truy vấn, lỗi DB — dùng DEBUG/ERROR; không tự log mọi SQL nếu Hibernate/JPA đã lo.
  • GlobalExceptionHandler (@RestControllerAdvice) log Exception tập trung — dùng WARN/ERROR.
  • Level phụ thuộc ngữ cảnh, không phải quy tắc cứng theo tầng. User không tồn tại có thể là WARN, mất DB là ERROR.
  • Luôn truyền e khi log Exception để có Stack Trace.
  • Không log dữ liệu nhạy cảm: password, access token, refresh token, secret, API key, thông tin thanh toán.
  • Không log trùng: chỉ định rõ tầng nào log Exception cuối cùng.
  • Không log quá nhiều: tập trung sự kiện có ý nghĩa, dùng DEBUG cho chi tiết khi cần điều tra.
  • Log thời gian xử lý API để phát hiện endpoint chậm.

6.15. Những lỗi thường gặp khi cấu hình Logback

Trong quá trình sử dụng Logback, học viên thường gặp một số lỗi.

6.15.1. Sai tên File

Ví dụ đặt logback-spring.xml sai vị trí.

Nên đặt tại:

src/main/resources/logback-spring.xml

Ví dụ:

src
└── main
    └── resources
        └── logback-spring.xml

6.15.2. Sai XML

Ví dụ:

XML
<appender>

nhưng không đóng </appender>. XML phải hợp lệ.

Ví dụ đúng:

XML
<appender name="CONSOLE"
          class="ch.qos.logback.core.ConsoleAppender">

    ...

</appender>

6.15.3. Sai tên Appender

Ví dụ khai báo:

XML
<appender name="CONSOLE"
          class="ch.qos.logback.core.ConsoleAppender">

nhưng lại:

XML
<appender-ref ref="CONSOLE_APPENDER"/>

Đây là hai tên khác nhau. Phải:

XML
<appender-ref ref="CONSOLE"/>

6.15.4. Quên appender-ref

Có thể khai báo:

XML
<appender name="CONSOLE"
          class="ch.qos.logback.core.ConsoleAppender">

nhưng Root không sử dụng:

XML
<root level="INFO">
</root>

Khi đó Appender không được kết nối với Root Logger theo cấu hình này.

Cần:

XML
<root level="INFO">

    <appender-ref ref="CONSOLE"/>

</root>

6.15.5. Sai fileNamePattern

Ví dụ Rolling File:

XML
<fileNamePattern>
    logs/application.%d{yyyy-MM-dd}.%i.log
</fileNamePattern>

Nếu sử dụng %i, cần sử dụng Rolling Policy phù hợp với Time + Size.

Ví dụ:

XML
<rollingPolicy
        class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">

6.15.6. File Log không được tạo

Có thể kiểm tra:

1. Đường dẫn File
2. Quyền ghi File
3. Appender
4. Root
5. appender-ref
6. Rolling Policy
7. Cấu hình XML

Ví dụ <file>logs/application.log</file> thì cần kiểm tra thư mục và quyền ghi của Process chạy ứng dụng.

Ví dụ:

        UserNotFoundException e

            e.getMessage()
    );

    return ResponseEntity
            .status(404)
            .body(e.getMessage());

Ghi nhớ trọng tâm
  • Log Exception phải truyền e để có Stack Trace — không chỉ log e.getMessage().
  • Không dùng System.out.println() trong Project Spring Boot.
  • Không log dữ liệu nhạy cảm: password, access token, refresh token, API key, secret key, thông tin thanh toán.
  • Không log cả Object nếu Object có thể chứa field nhạy cảm — chỉ log field cần thiết.
  • Exception nghiệp vụ dự kiến (User không tồn tại) → WARN; lỗi hệ thống (DB mất kết nối) → ERROR.
  • Log Rotation theo ngày + kích thước; dùng maxFileSize, maxHistory, totalSizeCap để kiểm soát dung lượng.
  • Development: ưu tiên DEBUG, Console; Production: ưu tiên INFO/WARN/ERROR, có File + Rolling, không log dữ liệu nhạy cảm.
  • Nắm các lỗi thường gặp: sai tên file, sai XML, sai tên Appender, quên appender-ref, sai fileNamePattern, log bị trùng, file tăng quá nhanh.
