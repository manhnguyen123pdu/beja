PHẦN 1. Tổng quan về AOP

1.1. AOP là gì?

1.1.1. Khái niệm AOP

AOP (Aspect-Oriented Programming), hay lập trình hướng khía cạnh, là một phương pháp lập trình cho phép chúng ta tách những logic dùng chung ra khỏi logic nghiệp vụ chính của chương trình.

Trong các ứng dụng Backend, có rất nhiều chức năng xuất hiện ở nhiều nơi khác nhau.

Ví dụ:

  • Ghi log.
  • Kiểm tra thời gian thực thi.
  • Ghi lịch sử thao tác.
  • Theo dõi exception.
  • Kiểm tra quyền.
  • Quản lý transaction.
  • Theo dõi hoạt động của người dùng.

Những chức năng này thường không phải là nhiệm vụ chính của một method nghiệp vụ, nhưng chúng lại có thể xuất hiện trong rất nhiều method.

Ví dụ một ứng dụng quản lý người dùng có:

UserService
    ├── getUserById()
    ├── createUser()
    ├── updateUser()
    └── deleteUser()

Ứng dụng lại yêu cầu ghi log cho tất cả các method:

getUserById()
    → ghi log

createUser()
    → ghi log

updateUser()
    → ghi log

deleteUser()
    → ghi log

Nếu viết code logging trực tiếp trong từng method, chúng ta sẽ phải lặp lại cùng một loại code rất nhiều lần.

AOP cung cấp một cách tiếp cận khác:

                   Logging
                       │
                       │
              ┌────────┼────────┐
              │        │        │
              ▼        ▼        ▼
          getUser   createUser updateUser
              │        │        │
              └────────┼────────┘
                       │
                    deleteUser

Thay vì đưa code logging vào từng method, chúng ta có thể đặt logic logging vào một thành phần riêng và để Spring tự động áp dụng nó cho những method phù hợp.

1.1.2. Ý tưởng cốt lõi của AOP

Có thể hiểu AOP thông qua một nguyên tắc đơn giản:

Tách những logic dùng chung ra khỏi logic nghiệp vụ chính.

Ví dụ:

Java
public User getUserById(Integer id) {

    // Logic nghiệp vụ
    return userRepository.findById(id)
            .orElseThrow();
}

Nhiệm vụ của method trên là: Tìm User theo ID. Đó là logic nghiệp vụ.

Nếu chúng ta muốn đo thời gian thực thi:

Java
long start = System.currentTimeMillis();

User user = userRepository.findById(id)
        .orElseThrow();

long end = System.currentTimeMillis();

System.out.println(
        "Time: " + (end - start) + " ms"
);

return user;

Phần đo thời gian không phải nhiệm vụ chính của getUserById(). Nó chỉ là một logic bổ sung.

AOP cho phép chúng ta đưa phần logic này ra khỏi method:

┌──────────────────────────────┐
│        PerformanceAspect     │
│                              │
│  Đo thời gian thực thi       │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│        UserService           │
│                              │
│  getUserById()               │
│                              │
│  Logic nghiệp vụ             │
└──────────────────────────────┘

Kết quả là code nghiệp vụ trở nên tập trung hơn vào đúng nhiệm vụ của nó.

1.2. Tại sao cần AOP?

Để hiểu AOP, trước hết cần hiểu vấn đề mà AOP muốn giải quyết.

1.2.1. Ví dụ không sử dụng AOP

Giả sử chúng ta có UserService:

Java
@Service
public class UserService {

    public User getUserById(Integer id) {

        System.out.println("START getUserById");

        User user = userRepository.findById(id)
                .orElseThrow();

        System.out.println("END getUserById");

        return user;
    }
}

Method này thực hiện ba nhóm công việc:

  1. Ghi log bắt đầu
  2. Tìm User
  3. Ghi log kết thúc

Trong đó chỉ có userRepository.findById(id) là logic chính của method.

Hai đoạn:

Java
System.out.println("START getUserById");

và:

Java
System.out.println("END getUserById");

là logic logging.

1.2.2. Vấn đề khi số lượng method tăng

Giả sử Service có 10 method:

getUserById()
getUsers()
createUser()
updateUser()
deleteUser()
searchUser()
changePassword()
enableUser()
disableUser()
resetPassword()

Nếu tất cả đều cần logging, chúng ta sẽ phải viết:

START
Business Logic
END

cho từng method.

Ví dụ:

Java
public User getUserById(Integer id) {

    System.out.println("START");

    // Business Logic

    System.out.println("END");

    return user;
}
Java
public User createUser(User user) {

    System.out.println("START");

    // Business Logic

    System.out.println("END");

    return result;
}
Java
public void deleteUser(Integer id) {

    System.out.println("START");

    // Business Logic

    System.out.println("END");
}

Khi số lượng method tăng lên, code logging cũng tăng theo.

Đây chính là vấn đề mà AOP có thể giải quyết.

1.3. Code Duplication

1.3.1. Code Duplication là gì?

Code Duplication là tình trạng cùng một đoạn logic hoặc cùng một cách xử lý được viết lặp lại ở nhiều vị trí.

Ví dụ:

Java
System.out.println("START");

xuất hiện trong rất nhiều method.

Hoặc:

Java
long start = System.currentTimeMillis();

được viết trong nhiều Service khác nhau.

Khi đó chúng ta có:

UserService
    └── Logging code

ProductService
    └── Logging code

OrderService
    └── Logging code

PaymentService
    └── Logging code

1.3.2. Tại sao code lặp lại là vấn đề?

Code duplication gây ra nhiều khó khăn.

Vấn đề 1: Code dài hơn

Một Service đáng lẽ chỉ cần tập trung vào nghiệp vụ:

Java
public User getUserById(Integer id) {

    return userRepository.findById(id)
            .orElseThrow();
}

lại chứa thêm:

Logging
Timing
Audit
Exception handling
...

Code trở nên dài và khó đọc hơn.

Vấn đề 2: Khó bảo trì

Giả sử cách ghi log thay đổi.

Trước đây:

START
END

Sau này muốn chuyển thành:

[INFO] Start method: getUserById
[INFO] End method: getUserById

Nếu logging được viết trong 50 method, chúng ta có thể phải sửa 50 nơi.

Nếu logging được tập trung trong một Aspect, việc thay đổi sẽ được thực hiện tại một nơi.

Vấn đề 3: Dễ thiếu sót

Giả sử có 20 Service nhưng lập trình viên chỉ thêm logging vào 18 Service.

Khi đó hệ thống có thể xảy ra tình trạng:

UserService      → có log
ProductService   → có log
OrderService     → có log
PaymentService   → quên log

Nếu sử dụng AOP với Pointcut phù hợp, chúng ta có thể áp dụng một quy tắc chung cho cả nhóm method.

1.4. Cross-cutting Concerns

Đây là một khái niệm rất quan trọng trong AOP.

1.4.1. Cross-cutting Concern là gì?

Cross-cutting Concern có thể hiểu là:

Một chức năng có liên quan đến nhiều phần khác nhau của ứng dụng và thường cắt ngang nhiều module hoặc nhiều method.

Ví dụ:

                   Logging
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
     UserService   ProductService   OrderService

Logging không chỉ thuộc riêng UserService.

Nó có thể được sử dụng ở:

UserService
ProductService
OrderService
PaymentService
...

Vì vậy Logging là một ví dụ điển hình của Cross-cutting Concern.

1.4.2. Những Cross-cutting Concern thường gặp

Trong Backend Java/Spring Boot, một số Cross-cutting Concern phổ biến là:

1.5. Logic nghiệp vụ và Logic dùng chung

Để hiểu AOP tốt, học viên cần phân biệt hai loại logic này.

1.5.1. Logic nghiệp vụ

Business Logic là phần logic trực tiếp thực hiện yêu cầu nghiệp vụ của hệ thống.

Ví dụ hệ thống quản lý User có chức năng: Tìm User theo ID.

Code:

Java
public User getUserById(Integer id) {

    return userRepository.findById(id)
            .orElseThrow();
}

Logic chính là:

Nhận ID
   ↓
Tìm User
   ↓
Trả về User

Đây là Business Logic.

1.5.2. Logic dùng chung

Bây giờ hệ thống yêu cầu:

Mỗi khi Service được gọi phải ghi lại thời gian bắt đầu và kết thúc.

Logic này không liên quan trực tiếp đến việc tìm User. Nó chỉ là logic hỗ trợ:

Ghi log
Đo thời gian
Theo dõi exception
Audit

Đây là những logic có thể được tách thành các Aspect.

1.5.3. So sánh

Logic nghiệp vụ Logic dùng chung
Tạo UserLogging
Tìm UserĐo thời gian
Cập nhật ProductAudit
Xóa OrderTheo dõi exception
Tính tổng tiềnTracing

Có thể hình dung:

                Application
                      │
          ┌───────────┴───────────┐
          │                       │
    Business Logic       Cross-cutting Logic
          │                       │
     ┌────┼────┐          ┌───────┼───────┐
     │    │    │          │       │       │
    User Product Order   Log     Audit   Timing

AOP chủ yếu hỗ trợ xử lý nhóm logic thứ hai.

nhiều method

1.10. Khi nào không nên sử dụng AOP?

Không phải logic nào cũng nên đưa vào AOP.

Nếu một logic:

  • chỉ sử dụng ở một method;
  • rất đơn giản;
  • thuộc trực tiếp vào nghiệp vụ;
  • cần người đọc nhìn thấy ngay trong method;

thì việc viết trực tiếp có thể dễ hiểu hơn.

Ví dụ:

Java
public BigDecimal calculateTotal(
        BigDecimal price,
        Integer quantity
) {

    return price.multiply(
            BigDecimal.valueOf(quantity)
    );
}

Đây là logic nghiệp vụ.

Không nên cố đưa phép tính này vào AOP.

1.12. Hạn chế của AOP

AOP cũng có những điểm cần lưu ý.

1.12.1. Code có thể khó theo dõi

Khi nhìn vào:

Java

            .orElseThrow();

học viên có thể không nhìn thấy ngay:

Logging
Performance
Audit

đang được áp dụng từ Aspect bên ngoài.

Do đó nếu sử dụng AOP quá nhiều, chương trình có thể trở nên khó hiểu.

Áp dụng cho quá nhiều method

có thể dẫn đến hành vi ngoài mong muốn.

Một số method không được áp dụng

Nguyên tắc đơn giản

Business Logic nên nằm ở Business Layer; Cross-cutting Logic có thể được tách bằng AOP.

PHẦN 2. Các khái niệm cốt lõi của AOP

2.1. Tổng quan các thành phần trong AOP

Ở phần trước, chúng ta đã biết AOP được sử dụng để tách những logic dùng chung như: Logging, Performance, Audit, Exception Monitoring, Security ra khỏi Business Logic.

Để thực hiện điều đó, AOP sử dụng một số khái niệm quan trọng.

Có thể hình dung:

                      AOP
                        │
        ┌───────────────┼────────────────┐
        │               │                │
     Aspect           Advice          Pointcut
        │               │                │
        │               │                │
        └───────────────┼────────────────┘
                        │
                        ▼
                   Join Point
                        │
                        ▼
                 Business Method

Ngoài ra còn có: Weaving – là cơ chế kết hợp Aspect với đối tượng mục tiêu.

Năm khái niệm quan trọng:

Khái niệm Ý nghĩa đơn giản
AspectChứa logic AOP
AdviceQuy định logic AOP chạy khi nào
Join PointĐiểm có thể áp dụng AOP
PointcutXác định Join Point nào được chọn
WeavingKết hợp Aspect với đối tượng mục tiêu

Đây là 5 khái niệm học viên cần nắm chắc trước khi chuyển sang phần thực hành.

2.2. Aspect

2.2.1. Aspect là gì?

Aspect là thành phần chứa một hoặc nhiều logic liên quan đến một Cross-cutting Concern.

Ví dụ: Logging là một Cross-cutting Concern.

Chúng ta có thể tạo: LoggingAspect để xử lý tất cả logic liên quan đến Logging.

Tương tự: PerformanceAspect, AuditAspect, ExceptionAspect, SecurityAspect.

Có thể hình dung:

                 ASPECT
                     │
       ┌─────────────┼─────────────┐
       │             │             │
     Logging      Performance     Audit
       │             │             │
       ▼             ▼             ▼
   LoggingAspect PerformanceAspect AuditAspect

2.2.2. Ví dụ về Aspect

Giả sử ứng dụng có yêu cầu: Ghi log trước và sau khi Service được thực hiện.

Chúng ta có thể tạo LoggingAspect. Aspect này chịu trách nhiệm:

  1. Ghi log trước method.
  2. Ghi log sau method.
  3. Có thể ghi tên method.
  4. Có thể ghi tham số.
  5. Có thể ghi kết quả.

Trong Spring Boot, một Aspect thường được khai báo bằng @Aspect.

Ví dụ:

Java
@Aspect
public class LoggingAspect {

}

Ở giai đoạn này, học viên chưa cần quan tâm chi tiết về cách cấu hình. Phần code sẽ được thực hiện ở các phần sau.

2.3. Advice

2.3.1. Advice là gì?

Nếu Aspect là nơi chứa logic AOP thì Advice xác định: Logic đó sẽ được thực hiện vào thời điểm nào.

Ví dụ chúng ta có method getUserById().

Chúng ta muốn ghi log:

  • Trước khi method chạy → sử dụng @Before
  • Sau khi method chạy → sử dụng @After
  • Sau khi method chạy thành công → sử dụng @AfterReturning
  • Khi method xảy ra exception → sử dụng @AfterThrowing
  • Kiểm soát cả trước và sau method → sử dụng @Around

2.4. Các loại Advice

Spring AOP cung cấp các loại Advice phổ biến:

@Before
@After
@AfterReturning
@AfterThrowing
@Around

Có thể hình dung:

                   Method
                      │
        ┌─────────────┼─────────────┐
        │             │             │
      Before         Method        After
        │             │             │
        │             │             │
        └─────────────┼─────────────┘
                      │
              Returning / Throwing

Trong đó @Around có khả năng bao quanh toàn bộ quá trình.

2.5. @Before

2.5.1. Khái niệm

@Before là Advice được thực hiện trước khi method mục tiêu được thực thi.

Ví dụ:

Client
  │
  ▼
@Before
  │
  ▼
Business Method

Nếu method getUserById() được gọi thì:

@Before
   ↓
getUserById()

2.5.2. Ví dụ thực tế

Giả sử chúng ta muốn ghi START: getUserById trước khi method chạy.

Luồng:

Request
   ↓
@Before
   ↓
START: getUserById
   ↓
getUserById()
   ↓
Response

2.5.3. Khi nào sử dụng @Before?

Một số trường hợp:

  • Ghi log bắt đầu.
  • Kiểm tra một điều kiện.
  • Ghi nhận thông tin request.
  • Theo dõi method được gọi.
  • Ghi audit trước khi thực hiện.

Tuy nhiên, nếu cần ngăn method chạy hoặc thay đổi luồng xử lý, cần hiểu rõ cơ chế AOP và lựa chọn Advice phù hợp thay vì mặc định dùng @Before.

2.6. @After

2.6.1. Khái niệm

@After được thực hiện sau khi method kết thúc.

Điểm quan trọng:

@After không chỉ dành cho trường hợp method chạy thành công. Nó có thể được thực hiện khi method:

Thành công

hoặc:

Xảy ra Exception

Có thể hình dung:

            Method
             /    \
            /      \
       Success    Exception
          │           │
          └─────┬─────┘
                ▼
             @After

2.6.2. Ví dụ

getUserById()
      │
      ▼
Business Logic
      │
      ▼
Method kết thúc
      │
      ▼
@After

Nếu xảy ra lỗi:

getUserById()
      │
      ▼
Exception
      │
      ▼
@After

2.7. @AfterReturning

2.7.1. Khái niệm

@AfterReturning được thực hiện khi method kết thúc thành công và trả về kết quả.

Ví dụ:

getUserById()
      │
      ▼
Business Logic
      │
      ▼
return User
      │
      ▼
@AfterReturning

Nếu method xảy ra exception:

getUserById()
      │
      ▼
Exception
      │
      X
@AfterReturning không chạy

2.7.2. Khi nào sử dụng?

@AfterReturning phù hợp khi muốn xử lý kết quả trả về.

Ví dụ:

Service trả về User
        ↓
@AfterReturning
        ↓
Ghi log User

Hoặc:

Service trả về Order
        ↓
@AfterReturning
        ↓
Ghi audit

2.8. @AfterThrowing

2.8.1. Khái niệm

@AfterThrowing được thực hiện khi method xảy ra exception.

Luồng:

Method
   │
   ▼
Exception
   │
   ▼
@AfterThrowing

Ví dụ:

getUserById(100)
        │
        ▼
User không tồn tại
        │
        ▼
Exception
        │
        ▼
@AfterThrowing

2.8.2. Ứng dụng thực tế

Có thể dùng để:

  • Ghi log lỗi.
  • Ghi nhận exception.
  • Theo dõi lỗi hệ thống.
  • Gửi thông tin lỗi đến hệ thống monitoring.
  • Audit các thao tác thất bại.

Ví dụ log:

ERROR
Method: getUserById
Message: User not found

2.9. @Around

2.9.1. Khái niệm

@Around là loại Advice mạnh nhất trong các Advice cơ bản.

Nó cho phép chúng ta thực hiện logic:

Trước method
       ↓
Method
       ↓
Sau method

Có thể hình dung:

               @Around
                   │
         ┌─────────┴─────────┐
         │                   │
      Before                After
         │                   │
         ▼                   │
      Method ────────────────┘

2.9.2. Ví dụ đo thời gian

Đây là một ứng dụng rất phổ biến.

Ta muốn đo:

Method bắt đầu
       ↓
   thực thi
       ↓
Method kết thúc

Logic:

start = currentTime

       ↓

Business Method

       ↓

end = currentTime

       ↓

end - start

Vì cần thực hiện logic ở cả trước và sau method nên @Around rất phù hợp.

2.10. Join Point

2.10.1. Join Point là gì?

Join Point là một điểm trong quá trình thực thi chương trình mà Aspect có thể can thiệp.

Trong Spring AOP, Join Point chủ yếu liên quan đến việc thực thi method.

Ví dụ:

Java
userService.getUserById(10);

Việc thực thi getUserById() có thể được xem là một Join Point mà Aspect can thiệp.

2.10.2. Ví dụ

Giả sử có:

UserService
    │
    ├── getUserById()
    ├── createUser()
    ├── updateUser()
    └── deleteUser()

Mỗi method execution có thể là một điểm mà AOP có thể áp dụng.

getUserById()  ← Join Point
createUser()   ← Join Point
updateUser()   ← Join Point
deleteUser()   ← Join Point

Tuy nhiên, việc một Join Point có được Aspect áp dụng hay không còn phụ thuộc vào Pointcut. Đây là điểm rất quan trọng.

2.11. Pointcut

2.11.1. Pointcut là gì?

Nếu Join Point là: Điểm có thể can thiệp.

thì Pointcut là: Điều kiện dùng để lựa chọn những Join Point nào sẽ được áp dụng Aspect.

Ví dụ ứng dụng có:

UserService
ProductService
OrderService
PaymentService

Chúng ta muốn logging cho tất cả Service.

Khi đó cần một quy tắc:

Chọn tất cả method trong Service

Quy tắc đó chính là Pointcut.

2.12. Join Point và Pointcut khác nhau như thế nào?

Đây là phần học viên rất dễ nhầm.

Có thể nhớ:

Join Point
→ "Điểm nào có thể can thiệp?"

Pointcut
→ "Tôi muốn chọn điểm nào?"

Ví dụ:

UserService
    ├── getUserById()
    ├── createUser()
    └── deleteUser()

Các method có thể là Join Point.

Nhưng Pointcut có thể chỉ chọn: getUserById()

Khi đó:

Join Points
    │
    ├── getUserById()   ← được chọn
    ├── createUser()    ← không chọn
    └── deleteUser()    ← không chọn

2.13. Ví dụ thực tế về Pointcut

Giả sử chúng ta có:

com.example.demo.service

và bên trong:

UserService
ProductService
OrderService

Mỗi class có nhiều method.

Chúng ta muốn: Áp dụng Logging cho tất cả method trong Service.

Pointcut sẽ mô tả quy tắc:

Tất cả method
+
trong các class Service
+
thuộc package service

Sau này chúng ta có thể biểu diễn quy tắc này bằng biểu thức như:

Pointcut Expression
execution(* com.example.demo.service.*.*(..))

Ở phần này chỉ cần hiểu ý nghĩa. Phần tiếp theo sẽ phân tích cú pháp Pointcut chi tiết.

2.14. Weaving

2.14.1. Weaving là gì?

Weaving là quá trình kết hợp Aspect với đối tượng hoặc code mục tiêu để Aspect có thể được thực thi.

Có thể hiểu đơn giản:

Weaving là quá trình "đưa" logic của Aspect vào luồng thực thi của đối tượng mục tiêu.

Trong Spring AOP, cơ chế Proxy đóng vai trò rất quan trọng.

2.15. Spring AOP Proxy

Khi một Bean được Spring quản lý và có Aspect áp dụng, Spring có thể tạo một Proxy để đứng trước object thật.

Ví dụ chúng ta có UserService.

Thay vì request đi trực tiếp:

Controller
    ↓
UserService

có thể hình dung:

Controller
    ↓
Spring Proxy
    ↓
UserService

Proxy có thể thực hiện logic AOP trước khi gọi object thật.

2.15.1. Luồng thực thi

Ví dụ có @Before. Luồng có thể hình dung:

Client
   │
   ▼
Controller
   │
   ▼
Spring Proxy
   │
   ▼
@Before
   │
   ▼
UserService
   │
   ▼
getUserById()

Nếu có @After:

Client
   │
   ▼
Controller
   │
   ▼
Spring Proxy
   │
   ├── @Before
   │
   ▼
UserService
   │
   ├── getUserById()
   │
   ▼
Spring Proxy
   │
   └── @After
   │
   ▼
Response

Đây là cách hình dung rất quan trọng để hiểu Spring AOP.

2.21. Những nhầm lẫn thường gặp

Nhầm lẫn 1: Aspect và Advice giống nhau

Không giống nhau.

Aspect
→ Thành phần chứa logic AOP.

Advice
→ Cách/thời điểm logic AOP được thực hiện.

Nhầm lẫn 2: Join Point và Pointcut giống nhau

Không giống nhau.

Join Point
→ Điểm có thể áp dụng.

Pointcut
→ Quy tắc chọn điểm nào được áp dụng.

Nhầm lẫn 3: @After chỉ chạy khi thành công

Không đúng.

@After được thực hiện sau khi method kết thúc, kể cả trường hợp method kết thúc do exception.

Nếu chỉ muốn xử lý khi thành công thì dùng: @AfterReturning

Nếu muốn xử lý khi có exception thì dùng: @AfterThrowing

Nhầm lẫn 4: @Around chỉ dùng để logging

Không đúng.

@Around có thể được sử dụng cho nhiều mục đích:

  • Logging
  • Performance
  • Kiểm soát execution
  • Thay đổi kết quả
  • Xử lý trước/sau method

Trong đó một ứng dụng rất phổ biến là đo thời gian thực thi.

Ghi nhớ trọng tâm
  • Aspect = nơi chứa logic AOP.
  • Advice = thời điểm logic AOP chạy.
  • Join Point = điểm có thể can thiệp.
  • Pointcut = quy tắc chọn Join Point.
  • Weaving = cơ chế kết hợp Aspect vào đối tượng.

PHẦN 3. Cài đặt và xây dựng AOP trong Spring Boot

3.1. Mục tiêu của phần học

Sau khi hoàn thành phần này, học viên có thể:

  • Tạo một project Spring Boot có sử dụng AOP.
  • Cài đặt dependency cần thiết cho Spring AOP.
  • Hiểu vị trí của AOP trong cấu trúc project Spring Boot.
  • Tạo một Service làm đối tượng cần áp dụng AOP.
  • Tạo một Aspect.
  • Sử dụng @Aspect.
  • Sử dụng @Component để Spring quản lý Aspect.
  • Tạo một Pointcut đơn giản.
  • Sử dụng @Before để thực hiện logic trước khi method chạy.
  • Quan sát được quá trình Spring tạo Proxy và thực thi Aspect.
  • Hiểu được luồng xử lý từ Controller → Service → Aspect → Service.
  • Tự xây dựng được ví dụ AOP đầu tiên.

3.2. Chuẩn bị project Spring Boot

Để thực hành AOP, chúng ta tạo một project Spring Boot đơn giản.

3.5. Tạo class UserService

Đầu tiên chúng ta tạo một Service đơn giản.

File: service/UserService.java

Java
package com.example.aop.service;

import org.springframework.stereotype.Service;

@Service
public class UserService {

    public void getUser() {
        System.out.println("Đang thực hiện lấy thông tin User");
    }
}

3.5.1. Giải thích

Annotation @Service cho Spring biết rằng UserService là một Spring Bean.

Spring sẽ quản lý object này.

Thông thường nếu không có AOP, khi Controller gọi userService.getUser(); thì method getUser() sẽ được thực thi trực tiếp.

Nhưng khi AOP được áp dụng, Spring có thể tạo một Proxy bao quanh Bean này.

Có thể hình dung:

UserService
    ▲
    │
    │ được Spring quản lý

5.20. Aspect hoàn chỉnh

Bây giờ chúng ta có:

Java
package com.example.aop.aspect;

import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.*;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class LoggingAspect {

    @Pointcut("execution(* com.example.aop.service..*(..))")
    public void serviceMethods() {
    }

    @Before("serviceMethods()")
    public void before(JoinPoint joinPoint) {

        System.out.println(
            "START METHOD: " +
            joinPoint.getSignature().getName()
        );
    }

    @AfterReturning(
        pointcut = "serviceMethods()",
        returning = "result"
    )
    public void afterReturning(Object result) {

        System.out.println(
            "METHOD SUCCESS | RESULT: " + result
        );
    }

    @AfterThrowing(
        pointcut = "serviceMethods()",
        throwing = "exception"
    )
    public void afterThrowing(Exception exception) {

        System.out.println(
            "METHOD ERROR | " +
            exception.getMessage()
        );
    }

    @Around("serviceMethods()")
    public Object measureTime(
            ProceedingJoinPoint joinPoint)
            throws Throwable {

        long start = System.currentTimeMillis();

        Object result = joinPoint.proceed();

        long end = System.currentTimeMillis();

        System.out.println(
            "METHOD: " +
            joinPoint.getSignature().getName()
            + " | TIME: "
            + (end - start)
            + " ms"
        );

        return result;
    }
}

5.25. Sử dụng try-finally trong @Around

Nếu muốn chắc chắn phần tính thời gian kết thúc được thực hiện cả khi có exception, có thể viết:

Java
@Around("serviceMethods()")
public Object measureTime(
        ProceedingJoinPoint joinPoint)
        throws Throwable {

    long start = System.currentTimeMillis();

    try {

        return joinPoint.proceed();

    } finally {

        long end = System.currentTimeMillis();

        System.out.println(
            "METHOD: "
            + joinPoint.getSignature().getName()
            + " | TIME: "
            + (end - start)
            + " ms"
        );
    }
}

Đây là cách viết phù hợp hơn cho mục đích đo thời gian.

Khi hiểu được nguyên tắc này, học viên sẽ biết khi nào AOP thực sự có ích thay vì sử dụng AOP cho mọi tình huống.

Ở phần cuối, chúng ta sẽ tổng hợp toàn bộ kiến thức AOP, xây dựng bài tập lớn, đồng thời tìm hiểu thêm các nội dung nâng cao như @Order, Pointcut theo annotation, giới hạn của Spring AOP, self-invocation và một số lỗi thường gặp trong dự án thực tế.

Ghi nhớ trọng tâm
  • Business Logic → đặt trong Service.
  • Cross-Cutting Concern (Logging, Performance, Exception, Audit, Security…) → đặt trong Aspect.
  • @Pointcut riêng giúp tái sử dụng Pointcut, tránh lặp execution(...).
  • @Around cần proceed() và thường nên dùng try-finally khi đo thời gian.
  • Luôn trả về result trong @Around để không làm mất kết quả của method.
  • joinPoint.getSignature() lấy tên method/class; joinPoint.getArgs() lấy tham số.
  • Không log dữ liệu nhạy cảm (password, token, thông tin thanh toán…).
  • Tách Aspect theo trách nhiệm: LoggingAspect, PerformanceAspect, ExceptionAspect… khi project lớn.
  • Không lạm dụng AOP cho Business Logic.
