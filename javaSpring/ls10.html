CHUẨN HÓA RESPONSE TRONG SPRING BOOT

1.1. Response trong REST API

1.1.1. Response là gì?

Trong REST API, Response là dữ liệu mà server gửi trả về cho client sau khi nhận và xử lý một HTTP Request.
Ví dụ client gửi:

GET /api/medicines/1

Server xử lý yêu cầu và trả về:

{
    "id": 1,
    "name": "Paracetamol",
    "price": 15000
}

Trong trường hợp này:

Client
   │
   │ GET /api/medicines/1
   ▼
Server
   │
   │ JSON Response
   ▼
Client

1.1.2. Response gồm những thành phần nào?

Một HTTP Response thường gồm:

HTTP Response
│
├── Status Code
├── Headers
└── Body

Ví dụ:

HTTP/1.1 200 OK
Content-Type: application/json
Body:
{
    "id": 1,
    "name": "Paracetamol"
}

Status Code
Cho biết kết quả xử lý Request.
Ví dụ:
200 → Thành công
201 → Tạo thành công
400 → Request không hợp lệ
404 → Không tìm thấy
500 → Lỗi server

Headers
Chứa thông tin bổ sung về Response.
Ví dụ:
Content-Type: application/json
cho biết Body đang chứa dữ liệu JSON.

Body
Chứa dữ liệu thực tế mà server muốn trả về.
Ví dụ:

{
    "id": 1,
    "name": "Paracetamol"
}

1.1.3. Response đơn giản trong Spring Boot

Trong Spring Boot, Controller có thể trả trực tiếp một object:

Controller
@GetMapping("/{id}")
public MedicineResponse getById(
        @PathVariable Long id) {

    return medicineService.findById(id);
}

Spring Boot sẽ tự chuyển object Java thành JSON.
Ví dụ:

MedicineResponse response = new MedicineResponse(
        1L,
        "Paracetamol",
        15000.0
);

API có thể trả:

{
    "id": 1,
    "name": "Paracetamol",
    "price": 15000.0
}

Cách này hoàn toàn hợp lệ.
Tuy nhiên, khi project phát triển lớn, chúng ta thường muốn Response có một cấu trúc thống nhất.

1.2. Tại sao cần chuẩn hóa Response?

1.2.1. Vấn đề khi không chuẩn hóa

Giả sử project có nhiều API.
API 1 trả:

{
    "id": 1,
    "name": "Paracetamol"
}

API 2 trả:

[
    {
        "id": 1,
        "name": "Paracetamol"
    },
    {
        "id": 2,
        "name": "Aspirin"
    }
]

API 3 trả lỗi:

{
    "message": "Medicine not found"
}

API 4 lại trả:

{
    "error": "Invalid medicine"
}

API 5:

{
    "status": 400,
    "message": "Validation failed"
}

Như vậy cấu trúc Response không thống nhất.
Frontend phải xử lý rất nhiều kiểu dữ liệu khác nhau.

1.2.2. Chuẩn hóa Response là gì?

Chuẩn hóa Response là việc quy định một cấu trúc Response thống nhất cho các API trong hệ thống.
Ví dụ chúng ta thống nhất:

{
    "status": 200,
    "message": "Success",
    "data": {}
}

Khi đó:
Lấy một Medicine

{
    "status": 200,
    "message": "Get medicine successfully",
    "data": {
        "id": 1,
        "name": "Paracetamol",
        "price": 15000
    }
}

Lấy danh sách Medicine

{
    "status": 200,
    "message": "Get medicines successfully",
    "data": [
        {
            "id": 1,
            "name": "Paracetamol",
            "price": 15000
        },
        {
            "id": 2,
            "name": "Aspirin",
            "price": 20000
        }
    ]
}

Lỗi

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

Như vậy frontend luôn biết:
status
message
data
nằm ở đâu.

1.2.3. Lợi ích của chuẩn hóa Response

  1. API thống nhất
    Các API sử dụng cùng một cấu trúc.
  2. Frontend dễ xử lý
    Frontend có thể thống nhất:
    response.data
    để lấy dữ liệu.
  3. Dễ bảo trì
    Khi có hàng chục hoặc hàng trăm API, việc thống nhất Response giúp code dễ quản lý hơn.
  4. Dễ xử lý lỗi
    Frontend có thể kiểm tra:
    if (response.status === 200) {
    // thành công
    }
    hoặc dựa vào HTTP status code.
  5. API chuyên nghiệp hơn
    Một hệ thống REST API thực tế thường có quy ước rõ ràng về:
    Status.
    Message.
    Data.
    Error.
    Validation errors.

1.3. Xây dựng ApiResponse

3.1.1. ApiResponse là gì?

ApiResponse là một class dùng để đóng gói Response của API vào một cấu trúc thống nhất.
Thay vì trả trực tiếp:

return medicineResponse;

chúng ta có thể trả:

return new ApiResponse<>(
        200,
        "Success",
        medicineResponse
);

3.1.2. Thiết kế ApiResponse cơ bản

Ví dụ:

ApiResponse
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

Ở đây có 3 thành phần:
status
→ trạng thái

message
→ thông báo

data
→ dữ liệu

1.3.3. Getter và Setter

Nếu chưa sử dụng Lombok:

ApiResponse không Lombok
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;

    public ApiResponse() {
    }

    public ApiResponse(
            int status,
            String message,
            T data) {

        this.status = status;
        this.message = message;
        this.data = data;
    }

    public int getStatus() {
        return status;
    }

    public void setStatus(int status) {
        this.status = status;
    }

    public String getMessage() {
        return message;
    }

    public void setMessage(String message) {
        this.message = message;
    }

    public T getData() {
        return data;
    }

    public void setData(T data) {
        this.data = data;
    }
}

Code khá dài.
Vì chúng ta đã học Lombok, có thể sử dụng:

ApiResponse với Lombok
@Data
@NoArgsConstructor
@AllArgsConstructor
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

1.1.4. Giải thích cấu trúc

private int status;
Lưu mã trạng thái.
Ví dụ:
200
201
400
404
500

private String message;
Chứa thông báo.
Ví dụ:
"Success"
hoặc:
"Medicine not found"

private T data;
Chứa dữ liệu Response.
Điểm quan trọng ở đây là T.
T chính là Generic Type.
Phần này cần hiểu kỹ.

1.4. Generic trong ApiResponse

1.2.1. Generic là gì?

Generic cho phép một class hoặc method làm việc với nhiều kiểu dữ liệu khác nhau mà vẫn đảm bảo kiểm tra kiểu dữ liệu tại compile time.
Ví dụ class:

Generic
public class Box<T> {

    private T value;
}

T là một kiểu dữ liệu chưa xác định.
Khi sử dụng:
Box<String>
thì:
T = String
Nếu:
Box<Integer>
thì:
T = Integer

1.2.2. Tại sao ApiResponse cần Generic?

Giả sử chúng ta viết:

ApiResponse không Generic
public class ApiResponse {

    private int status;

    private String message;

    private Object data;
}

Có thể sử dụng:
data = MedicineResponse;
hoặc:
data = List<MedicineResponse>;
hoặc:
data = UserResponse;
Tuy nhiên sử dụng Object làm mất đi nhiều lợi ích của type safety.
Generic tốt hơn:

ApiResponse với Generic
public class ApiResponse<T> {

    private int status;

    private String message;

    private T data;
}

1.2.3. T hoạt động như thế nào?

Khi:
ApiResponse<MedicineResponse>
thì:
T = MedicineResponse
Do đó:
private T data;
tương đương với:
private MedicineResponse data;

Nếu:
ApiResponse<List<MedicineResponse>>
thì:
T = List<MedicineResponse>
và:
private T data;
tương đương:
private List<MedicineResponse> data;

1.2.4. Ví dụ

Ví dụ
MedicineResponse medicine = ...;

ApiResponse<MedicineResponse> response =
        new ApiResponse<>(
                200,
                "Success",
                medicine
        );

Ở đây:
T = MedicineResponse

Với danh sách:

Ví dụ danh sách
List<MedicineResponse> medicines = ...;

ApiResponse<List<MedicineResponse>> response =
        new ApiResponse<>(
                200,
                "Success",
                medicines
        );

Ở đây:
T = List<MedicineResponse>

1.2.5. Generic giúp kiểm tra kiểu dữ liệu

Ví dụ:
ApiResponse<MedicineResponse> response;
thì data phải là:
MedicineResponse
Không nên truyền:
UserResponse
Điều này giúp phát hiện lỗi kiểu dữ liệu sớm hơn.

1.5. Response thành công

1.5.1. Response thành công là gì?

Khi server xử lý Request thành công, Response thường sử dụng các HTTP Status Code thuộc nhóm 2xx.
Phổ biến nhất:
200 OK
201 Created
204 No Content

1.5.2. Response lấy một object

Ví dụ:

Lấy một object
@GetMapping("/{id}")
public ApiResponse<MedicineResponse> findById(
        @PathVariable Long id) {

    MedicineResponse medicine =
            medicineService.findById(id);

    return new ApiResponse<>(
            200,
            "Get medicine successfully",
            medicine
    );
}

Response:

{
    "status": 200,
    "message": "Get medicine successfully",
    "data": {
        "id": 1,
        "name": "Paracetamol",
        "price": 15000
    }
}

1.5.3. Response danh sách

Ví dụ:

Danh sách
@GetMapping
public ApiResponse<List<MedicineResponse>> findAll() {

    List<MedicineResponse> medicines =
            medicineService.findAll();

    return new ApiResponse<>(
            200,
            "Get medicines successfully",
            medicines
    );
}

Response:

{
    "status": 200,
    "message": "Get medicines successfully",
    "data": [
        {
            "id": 1,
            "name": "Paracetamol",
            "price": 15000
        },
        {
            "id": 2,
            "name": "Aspirin",
            "price": 20000
        }
    ]
}

Điểm quan trọng:
ApiResponse<List<MedicineResponse>>
không phải:
ApiResponse<MedicineResponse>
vì data là một danh sách.

1.5.4. Response tạo mới

Khi tạo Resource thành công, thông thường sử dụng:
201 Created

Tạo mới
@PostMapping
public ApiResponse<MedicineResponse> create(
        @RequestBody MedicineRequest request) {

    MedicineResponse medicine =
            medicineService.create(request);

    return new ApiResponse<>(
            201,
            "Create medicine successfully",
            medicine
    );
}

1.5.5. Response cập nhật

Thông thường có thể sử dụng:
200 OK

Cập nhật
@PutMapping("/{id}")
public ApiResponse<MedicineResponse> update(
        @PathVariable Long id,
        @RequestBody MedicineRequest request) {

    MedicineResponse medicine =
            medicineService.update(id, request);

    return new ApiResponse<>(
            200,
            "Update medicine successfully",
            medicine
    );
}

1.6. Response lỗi

1.6.1. Tại sao Response lỗi cũng cần chuẩn hóa?

Không chỉ Response thành công cần thống nhất.
Response lỗi cũng cần có cấu trúc rõ ràng.
Ví dụ:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

Frontend có thể xử lý thống nhất:
status
message
data

1.6.2. Lỗi không tìm thấy dữ liệu

Ví dụ client gọi:
GET /api/medicines/100
nhưng Medicine 100 không tồn tại.
Có thể trả: 

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

1.6.3. Tạo Response lỗi

Có thể sử dụng:

return new ApiResponse<>(
        404,
        "Medicine not found",
        null
);

Ở đây:
status
→ 404

message
→ Medicine not found

data
→ null

1.6.4. Không nên trả lỗi tùy tiện

Không nên để API này:

{
    "message": "Not found"
}

API khác:

{
    "error": "User does not exist"
}

API khác:

{
    "status": false,
    "msg": "Invalid"
}

Việc này làm frontend khó xử lý.
Nên quy định:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

1.6.5. Response lỗi Validation

Ví dụ client gửi:

{
    "name": "",
    "price": -100
}

Nếu DTO có:

@NotBlank
private String name;

@Positive
private Double price;

thì validation có thể thất bại.
Response có thể thiết kế:

{
    "status": 400,
    "message": "Validation failed",
    "data": {
        "name": "Name must not be blank",
        "price": "Price must be greater than 0"
    }
}

Điều này giúp frontend biết chính xác field nào bị lỗi.

1.6.6. Response lỗi Server

Nếu server xảy ra lỗi không mong muốn:
500 Internal Server Error
Có thể trả:

{
    "status": 500,
    "message": "Internal server error",
    "data": null
}

Trong môi trường production, không nên trả stack trace hoặc thông tin nội bộ của hệ thống cho client.

1.7. Kết hợp ApiResponse với ResponseEntity

1.7.1. ResponseEntity là gì?

ResponseEntity là một class của Spring dùng để biểu diễn toàn bộ HTTP Response.
Nó cho phép chúng ta kiểm soát:
HTTP Status Code.
Headers.
Response Body.
Ví dụ:

return ResponseEntity.ok(data);

Trong đó:
200 OK
và:
data
là Body.

1.7.2. Tại sao kết hợp ApiResponse và ResponseEntity?

Hai thành phần này có nhiệm vụ khác nhau.
ApiResponse
Quản lý cấu trúc dữ liệu bên trong Body:

{
    "status": 200,
    "message": "Success",
    "data": {}
}

ResponseEntity
Quản lý HTTP Response:
HTTP Status
Headers
Body

Có thể hình dung:

ResponseEntity
│
├── HTTP Status
├── Headers
└── Body
      │
      └── ApiResponse
             ├── status
             ├── message
             └── data

1.7.3. Ví dụ cơ bản

Ví dụ
@GetMapping("/{id}")
public ResponseEntity<ApiResponse<MedicineResponse>> findById(
        @PathVariable Long id) {

    MedicineResponse medicine =
            medicineService.findById(id);

    ApiResponse<MedicineResponse> response =
            new ApiResponse<>(
                    200,
                    "Get medicine successfully",
                    medicine
            );

    return ResponseEntity.ok(response);
}

1.7.4. ResponseEntity.ok()

ResponseEntity.ok(response)
tương đương:
HTTP Status = 200 OK
Body = response

1.7.5. Sử dụng ResponseEntity.status()

Nếu muốn trả 201 Created:

return ResponseEntity
        .status(HttpStatus.CREATED)
        .body(response);

Trong đó:
HttpStatus.CREATED
tương ứng:
201

1.7.6. Ví dụ Create

Create
@PostMapping
public ResponseEntity<ApiResponse<MedicineResponse>> create(
        @RequestBody MedicineRequest request) {

    MedicineResponse medicine =
            medicineService.create(request);

    ApiResponse<MedicineResponse> response =
            new ApiResponse<>(
                    201,
                    "Create medicine successfully",
                    medicine
            );

    return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(response);
}

1.7.7. Response lỗi với ResponseEntity

Ví dụ:

Response lỗi
@GetMapping("/{id}")
public ResponseEntity<ApiResponse<MedicineResponse>> findById(
        @PathVariable Long id) {

    MedicineResponse medicine =
            medicineService.findById(id);

    if (medicine == null) {

        ApiResponse<MedicineResponse> response =
                new ApiResponse<>(
                        404,
                        "Medicine not found",
                        null
                );

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }

    ApiResponse<MedicineResponse> response =
            new ApiResponse<>(
                    200,
                    "Success",
                    medicine
            );

    return ResponseEntity.ok(response);
}

Tuy nhiên, khi project lớn, không nên viết kiểu kiểm tra lỗi này trong từng Controller.
Sau này chúng ta có thể sử dụng:

Exception
     ↓
Global Exception Handler
     ↓
ApiResponse lỗi

Ví dụ:

@RestControllerAdvice
public class GlobalExceptionHandler {
}

Phần này sẽ được học trong Exception Handling.

1.7.8. Nên đặt HTTP Status ở đâu?

Khi sử dụng:
ApiResponse<T>
chúng ta có:
private int status;
đồng thời ResponseEntity cũng có:
HTTP Status
Ví dụ:
HTTP Status: 200
và:

{
    "status": 200,
    "message": "Success",
    "data": {}
}

Có vẻ như chúng ta đang lưu status hai lần.
Điều này cần được hiểu rõ.
HTTP Status
Là status thực sự của HTTP Response.
ApiResponse.status
Là dữ liệu nằm trong JSON Body.
Một số project thích giữ cả hai để frontend dễ xử lý và Response thống nhất.
Ví dụ:
HTTP
200 OK

Body

{
    "status": 200,
    "message": "Success",
    "data": {}
}

Tuy nhiên, đây là quy ước thiết kế API, không phải bắt buộc của REST.
Một thiết kế khác có thể không đưa status vào Body:

{
    "message": "Success",
    "data": {}
}

và chỉ sử dụng HTTP Status:
200 OK
Điều quan trọng là project phải có một quy ước nhất quán.

1.8. HTTP Status Code

1.8.1. HTTP Status Code là gì?

HTTP Status Code là mã số server sử dụng để thông báo kết quả xử lý Request.
Status Code được chia thành 5 nhóm:
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client Error
5xx → Server Error
Trong lập trình REST API, chúng ta chủ yếu làm việc với:
2xx
4xx
5xx

1.8.2. 200 OK

200 OK
Có nghĩa:
Request được xử lý thành công.
Ví dụ:
GET /api/medicines/1
trả:
200 OK
Body:

{
    "status": 200,
    "message": "Get medicine successfully",
    "data": {
        "id": 1,
        "name": "Paracetamol"
    }
}

Spring Boot:

return ResponseEntity.ok(response);

1.8.3. 201 Created

201 Created
Dùng khi một Resource mới được tạo thành công.
Ví dụ:
POST /api/medicines
Spring Boot:

return ResponseEntity
        .status(HttpStatus.CREATED)
        .body(response);

1.8.4. 204 No Content

204 No Content
Request thành công nhưng không có dữ liệu Body cần trả về.
Ví dụ một API xóa:
DELETE /api/medicines/1
Có thể trả:
204 No Content
Trong trường hợp này thường không cần:

{
    "status": 204,
    "message": "...",
    "data": null
}

vì 204 có ý nghĩa là Response không có content.

1.8.5. 400 Bad Request

400 Bad Request
Dùng khi Request từ client không hợp lệ.
Ví dụ:

{
    "name": "",
    "price": -100
}

Response:

{
    "status": 400,
    "message": "Validation failed",
    "data": {
        "name": "Name must not be blank",
        "price": "Price must be greater than 0"
    }
}

1.8.6. 401 Unauthorized

401 Unauthorized
Thường dùng khi client chưa được xác thực hoặc thông tin xác thực không hợp lệ.
Ví dụ:

Client
  ↓
GET /api/admin/users
  ↓
Không có / không hợp lệ authentication
  ↓
401

Ví dụ:

{
    "status": 401,
    "message": "Authentication required",
    "data": null
}

1.8.7. 403 Forbidden

403 Forbidden
Dùng khi client đã được xác thực nhưng không có quyền thực hiện hành động.
Ví dụ:

User
 ↓
Đã đăng nhập
 ↓
ROLE_USER
 ↓
Gọi API dành cho ADMIN
 ↓
403 Forbidden

Response:

{
    "status": 403,
    "message": "Access denied",
    "data": null
}

1.8.8. Phân biệt 401 và 403

Đây là kiến thức rất quan trọng.
401
Bạn là ai?
Client chưa được xác thực hợp lệ.
403
Tôi biết bạn là ai,
nhưng bạn không có quyền làm việc này.
Ví dụ:
401
→ chưa đăng nhập / authentication không hợp lệ

403
→ đã đăng nhập nhưng không đủ quyền

1.8.9. 404 Not Found

404 Not Found
Dùng khi Resource được yêu cầu không tồn tại.
Ví dụ:
GET /api/medicines/999

XỬ LÝ EXCEPTION TRONG SPRING BOOT

Trong các ứng dụng Spring Boot, Exception là một vấn đề rất quan trọng cần được xử lý đúng cách.
Một API thực tế không thể chỉ xử lý trường hợp thành công. Trong quá trình chạy, rất nhiều lỗi có thể xảy ra:

  • Không tìm thấy dữ liệu.
  • Dữ liệu bị trùng.
  • Request không hợp lệ.
  • Validation thất bại.
  • Người dùng không có quyền.
  • Lỗi database.
    Lỗi logic nghiệp vụ.
  • Lỗi không xác định.
  • Nếu không xử lý Exception đúng cách, client có thể nhận được những Response khó hiểu như: 

{
    "timestamp": "2026-08-24T10:20:30",
    "status": 500,
    "error": "Internal Server Error",
    "trace": "java.lang.NullPointerException..."
}

Trong một API chuyên nghiệp, chúng ta thường muốn biến những Exception đó thành Response có cấu trúc rõ ràng:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

2.1. Exception trong REST API

2.1.1. Exception là gì?

Exception là một tình huống bất thường xảy ra trong quá trình chương trình thực thi, khiến luồng xử lý bình thường bị gián đoạn.
Ví dụ:

int a = 10;
int b = 0;

int result = a / b;

Code trên gây ra:
ArithmeticException

Một ví dụ khác:

Medicine medicine = medicineRepository
        .findById(id)
        .orElse(null);

return medicine.getName();

Nếu medicine == null:
NullPointerException

2.1.2. Exception trong API

Giả sử client gọi:
GET /api/medicines/100
Nhưng Medicine có ID 100 không tồn tại.
Trong Service có thể viết:

Medicine medicine =
        medicineRepository.findById(id)
                .orElseThrow();

Khi không tìm thấy dữ liệu, Spring/JPA có thể phát sinh Exception.
Nếu không xử lý, client có thể nhận:
500 Internal Server Error
Trong khi về mặt nghiệp vụ, vấn đề thực sự là:
Medicine không tồn tại
Đúng hơn nên trả:
404 Not Found
và:

{
    "status": 404,
    "message": "Medicine not found",
    "data": null
}

2.1.3. Tại sao cần xử lý Exception?

Xử lý Exception giúp:

  1. API trả HTTP Status phù hợp
    Ví dụ:
    404 → Không tìm thấy
    400 → Request không hợp lệ
    409 → Dữ liệu bị trùng
    500 → Lỗi server
  2. Client dễ hiểu lỗi
    Thay vì nhận Stack Trace:
    NullPointerException...
    client nhận:
    { "status": 404, "message": "Medicine not found", "data": null }
  3. Không để lộ thông tin nội bộ
    Không nên trả cho client:
    Stack trace.
    Tên class nội bộ.
    SQL query.
    Thông tin database.
    Đường dẫn server.
    Thông tin cấu hình hệ thống.
  4. Dễ bảo trì
    Các lỗi được xử lý tập trung thay vì viết:
    try {
    ...
    } catch (...) {
    ...
    }
    ở hàng chục Controller.

2.1.4. Exception Handling trong Spring Boot

    ↓

    ↓

2.2. Custom Exception

2.2.1. Custom Exception là gì?

Custom Exception là Exception do lập trình viên tự định nghĩa để biểu diễn những lỗi nghiệp vụ cụ thể của hệ thống.

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {

        Medicine medicine =
                medicineRepository.findById(id)
                        .orElseThrow(
                                () -> new ResourceNotFoundException(
                                        "Medicine not found with id: " + id
                                )
                        );

        return medicineMapper.toResponse(medicine);
    }
}

Nếu không có ID 10, Exception:

2.4. DuplicateResourceException

2.2.1. DuplicateResourceException là gì?

Exception này dùng khi client cố tạo dữ liệu đã tồn tại.
Ví dụ:

đã tồn tại nhưng client lại muốn đăng ký email đó.
Có thể tạo:

public class DuplicateResourceException
        extends RuntimeException {

    public DuplicateResourceException(String message) {
        super(message);
    }
}

2.2.2. Ví dụ kiểm tra dữ liệu trùng

Repository:

UserRepository.java
public interface UserRepository
        extends JpaRepository<User, Long> {

    boolean existsByEmail(String email);
}

Service:

UserService.java
public UserResponse create(UserRequest request) {

    if (userRepository.existsByEmail(
            request.getEmail())) {

        throw new DuplicateResourceException(
                "Email already exists"
        );
    }

    User user =
            userMapper.toEntity(request);

    User saved =
            userRepository.save(user);

    return userMapper.toResponse(saved);
}

2.5. @ExceptionHandler

2.5.1. @ExceptionHandler là gì?

@ExceptionHandler là annotation của Spring MVC dùng để đánh dấu một method chuyên xử lý một hoặc nhiều loại Exception.
Ví dụ:

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<?> handleResourceNotFound(
        ResourceNotFoundException ex) {

    ...
}

Spring sẽ biết:
Khi ResourceNotFoundException xảy ra, hãy gọi method này.

2.5.2. Ví dụ cơ bản

MedicineController.java
@RestController
public class MedicineController {

    @GetMapping("/{id}")
    public MedicineResponse findById(
            @PathVariable Long id) {

        throw new ResourceNotFoundException(
                "Medicine not found"
        );
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<String> handleNotFound(
            ResourceNotFoundException ex) {

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(ex.getMessage());
    }
}

Khi Exception xảy ra:

ResourceNotFoundException
        ↓
@ExceptionHandler
        ↓
handleNotFound()
        ↓
404

2.9.8. Global Exception Handler hoàn chỉnh

Sau khi kết hợp các kiến thức trên:

GlobalExceptionHandler.java
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>>
    handleResourceNotFound(
            ResourceNotFoundException ex) {

        ApiResponse<Void> response =
                new ApiResponse<>(
                        404,
                        ex.getMessage(),
                        null
                );

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }


    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>>
    handleDuplicateResource(
            DuplicateResourceException ex) {

        ApiResponse<Void> response =
                new ApiResponse<>(
                        409,
                        ex.getMessage(),
                        null
                );

        return ResponseEntity
                .status(HttpStatus.CONFLICT)
                .body(response);
    }


    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<
            ApiResponse<Map<String, String>>
            > handleValidationException(
                    MethodArgumentNotValidException ex) {

        Map<String, String> errors =
                new HashMap<>();

        ex.getBindingResult()
                .getFieldErrors()
                .forEach(error ->
                        errors.put(
                                error.getField(),
                                error.getDefaultMessage()
                        )
                );

        ApiResponse<Map<String, String>> response =
                new ApiResponse<>(
                        400,
                        "Validation failed",
                        errors
                );

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(response);
    }


    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>>
    handleException(Exception ex) {

        log.error(
                "Unexpected error occurred",
                ex
        );

        ApiResponse<Void> response =
                new ApiResponse<>(
                        500,
                        "Internal server error",
                        null
                );

        return ResponseEntity
                .status(
                        HttpStatus.INTERNAL_SERVER_ERROR
                )
                .body(response);
    }
}

@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ApiResponse<>(404, ex.getMessage(), null));
    }

    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>> handleDuplicate(DuplicateResourceException ex) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ApiResponse<>(409, ex.getMessage(), null));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Map<String, String>>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors()
            .forEach(error -> errors.put(error.getField(), error.getDefaultMessage()));
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ApiResponse<>(400, "Validation failed", errors));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleException(Exception ex) {
        log.error("Unexpected error", ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ApiResponse<>(500, "Internal server error", null));
    }
}

Service

MedicineService.java
@Service
@RequiredArgsConstructor
public class MedicineService {
    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {
        Medicine medicine = medicineRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Medicine not found with id: " + id));
        return medicineMapper.toResponse(medicine);
    }

    public MedicineResponse create(MedicineRequest request) {
        if (medicineRepository.existsByName(request.getName())) {
            throw new DuplicateResourceException("Medicine name already exists");
        }
        Medicine medicine = medicineMapper.toEntity(request);
        Medicine saved = medicineRepository.save(medicine);
        return medicineMapper.toResponse(saved);
    }
}

@RestController
@RequestMapping("/api/medicines")
@RequiredArgsConstructor
public class MedicineController {
    private final MedicineService medicineService;

    @GetMapping("/{id}")
    public ResponseEntity<ApiResponse<MedicineResponse>> findById(@PathVariable Long id) {
        MedicineResponse data = medicineService.findById(id);
        return ResponseEntity.ok(new ApiResponse<>(200, "Success", data));
    }

    @PostMapping
    public ResponseEntity<ApiResponse<MedicineResponse>> create(@Valid @RequestBody MedicineRequest request) {
        MedicineResponse data = medicineService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED)
            .body(new ApiResponse<>(201, "Created", data));
    }
}
