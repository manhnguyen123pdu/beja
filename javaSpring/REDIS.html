PHẦN 1. TỔNG QUAN VỀ REDIS VÀ CACHING

Redis Cache là một trong những kỹ thuật thường được sử dụng trong các hệ thống Backend hiện đại nhằm giảm số lần truy cập Database, tăng tốc độ phản hồi API và giảm tải cho hệ thống.

Trong một ứng dụng Spring Boot, dữ liệu thường được lưu trữ lâu dài trong Database như MySQL. Tuy nhiên, không phải mọi request đều cần truy vấn Database. Với những dữ liệu được truy cập thường xuyên nhưng không thay đổi liên tục, chúng ta có thể lưu tạm dữ liệu vào Cache.

Redis là một trong những hệ thống được sử dụng phổ biến để xây dựng Cache.

Một luồng xử lý đơn giản có thể hình dung:

Client
   │
   │ Request
   ▼
Spring Boot
   │
   ▼
Redis Cache
   │
   ├── Có dữ liệu → Trả dữ liệu ngay
   │
   └── Không có → Query Database
                     │
                     ▼
                  MySQL
                     │
                     ▼
                Lưu vào Redis
                     │
                     ▼
                 Trả Client

Mục tiêu của phần này là giúp học viên hiểu:

  • Redis là gì.
  • Cache là gì.
  • Tại sao cần Cache.
  • Redis hoạt động như thế nào.
  • Cache Hit và Cache Miss là gì.
  • Redis khác Database như thế nào.
  • Khi nào nên và không nên sử dụng Redis.
  • Redis được sử dụng trong những bài toán thực tế nào.

1.1. Redis là gì?

1.1.1. Khái niệm

Redis là một hệ thống lưu trữ dữ liệu dạng key-value hoạt động chủ yếu trên bộ nhớ RAM.

Tên Redis thường được hiểu là:

Remote Dictionary Server

Redis được thiết kế để có tốc độ đọc và ghi dữ liệu rất nhanh.

Thay vì dữ liệu chỉ được lưu trên ổ đĩa như cách chúng ta thường hình dung về Database truyền thống, Redis sử dụng RAM làm nơi lưu trữ dữ liệu chính trong quá trình hoạt động.

Ví dụ:

Key              Value
--------------------------------
user:1           Nguyễn Văn A
user:2           Trần Văn B
product:10       iPhone 17

Có thể hiểu đơn giản:

Redis

"product:10" → "iPhone 17"
"user:1"     → "Nguyễn Văn A"

Khi ứng dụng cần dữ liệu product:10, Redis có thể trả về dữ liệu rất nhanh.

1.1.2. Redis không chỉ là Cache

Một điểm quan trọng: Redis không chỉ được sử dụng để làm Cache.

Redis còn có thể được sử dụng cho nhiều bài toán khác như:

  • Cache.
  • Session Storage.
  • Counter.
  • Rate Limiting.
  • Message Queue ở một số kiến trúc.
  • Pub/Sub.
  • Distributed Lock.
  • Lưu trạng thái tạm thời.
  • Leaderboard.
  • Lưu dữ liệu có thời gian hết hạn.

Tuy nhiên, trong bài học này chúng ta tập trung chủ yếu vào:

Spring Boot
      ↓
Redis
      ↓
Cache

1.1.3. Redis sử dụng Key và Value

Redis hoạt động dựa trên mô hình: Key → Value

Ví dụ "user:100" có thể chứa:

JSON
{
    "id": 100,
    "name": "Nguyễn Văn A",
    "email": "a@gmail.com"
}

Khi đó:

Key:
user:100

Value:
thông tin User có id = 100

Ứng dụng có thể sử dụng Key để tìm dữ liệu tương ứng.

1.1.4. Redis hỗ trợ nhiều kiểu dữ liệu

Redis không chỉ lưu String.

Redis hỗ trợ nhiều kiểu dữ liệu như:

Kiểu dữ liệu Ý nghĩa
StringChuỗi hoặc dữ liệu đơn giản
ListDanh sách
SetTập hợp không trùng
HashDữ liệu dạng field-value
Sorted SetTập hợp có sắp xếp
StreamDữ liệu dạng stream

Trong bài toán Spring Boot Cache, chúng ta thường quan tâm nhiều đến việc lưu Key → Object / JSON.

Ví dụ:

product:100
       ↓
{
    "id": 100,
    "name": "Laptop",
    "price": 25000000
}

1.2. Redis dùng để làm gì?

Redis có rất nhiều ứng dụng.

Trong Backend, một trong những trường hợp phổ biến nhất là Caching.

1.2.1. Redis dùng để Cache

Giả sử ứng dụng có API:

HTTP
GET /api/products/100

Nếu mỗi request đều truy vấn MySQL:

Client
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
MySQL

Khi có hàng nghìn request, Database phải xử lý rất nhiều truy vấn.

Có thể sử dụng Redis:

Client
   ↓
Controller
   ↓
Service
   ↓
Redis
   │
   ├── Có → trả kết quả
   │
   └── Không có
          ↓
        MySQL

Nhờ vậy, các request lặp lại có thể lấy dữ liệu từ Redis thay vì truy vấn MySQL.

1.2.2. Redis lưu Session

Redis có thể được sử dụng để lưu Session của người dùng.

Ví dụ:

session:abc123
       ↓
{
    "userId": 10,
    "username": "admin"
}

Điều này đặc biệt hữu ích trong hệ thống có nhiều Server.

1.2.3. Redis làm Counter

Redis có khả năng tăng/giảm giá trị rất nhanh.

Ví dụ: view:product:100 → 1000

Mỗi khi có người xem:

1000
 ↓
1001
 ↓
1002
 ↓
1003

Có thể sử dụng Redis để xây dựng:

  • Lượt xem.
  • Lượt Like.
  • Số lượng truy cập.
  • Bộ đếm request.

1.2.4. Redis dùng cho Rate Limiting

Rate Limiting là cơ chế giới hạn số lượng request.

Ví dụ:

IP: 192.168.1.10

Trong 1 phút:
Tối đa 100 request

Redis có thể lưu số lượng request: rate_limit:192.168.1.10 → 75

Khi request tiếp theo đến:

75 → 76

Nếu vượt giới hạn:

100 → Request bị từ chối

1.2.5. Redis dùng cho Distributed Lock

Trong hệ thống nhiều Server, có thể xảy ra trường hợp nhiều Server cùng thực hiện một công việc.

Redis có thể được sử dụng để tạo cơ chế Lock nhằm đảm bảo tại một thời điểm chỉ một process thực hiện một tác vụ nhất định.

Ví dụ:

Server A ──┐
           ├── Redis Lock
Server B ──┘

1.3. Redis khác Database như thế nào?

Đây là một khái niệm rất quan trọng.

Redis có thể lưu dữ liệu, nhưng không nên hiểu Redis đơn giản là "Database thay thế MySQL".

Hai hệ thống thường có vai trò khác nhau.

MySQL
→ Database chính
→ Lưu dữ liệu lâu dài

Redis
→ Cache / dữ liệu tạm thời
→ Tối ưu tốc độ truy cập

1.3.1. Database dùng để làm gì?

Database như MySQL thường được sử dụng để lưu dữ liệu chính của ứng dụng.

Ví dụ:

users
products
orders
categories
payments

Dữ liệu cần được lưu trữ lâu dài.

Ví dụ:

User
id = 100
name = Nguyễn Văn A
email = a@gmail.com

Nếu Server Restart, dữ liệu trong MySQL vẫn tồn tại.

1.3.2. Redis thường đóng vai trò gì?

Redis thường được sử dụng để:

  • Cache dữ liệu.
  • Lưu dữ liệu tạm thời.
  • Lưu Session.
  • Counter.
  • Rate Limiting.
  • Lock.

Ví dụ:

MySQL
    ↓
Dữ liệu chính

Redis
    ↓
Dữ liệu phục vụ nhanh

1.3.4. Có thể dùng Redis thay MySQL không?

Trong một số hệ thống, Redis có thể được sử dụng như một data store thực sự.

Tuy nhiên, trong kiến trúc Backend thông thường:

MySQL
    ↓
Nguồn dữ liệu chính

Redis
    ↓
Cache / dữ liệu tạm thời

Hai hệ thống thường bổ sung cho nhau thay vì thay thế hoàn toàn cho nhau.

1.4. Redis khác MySQL như thế nào?

Redis và MySQL khác nhau ngay từ mục đích thiết kế.

Ví dụ một hệ thống bán hàng:

                   Spring Boot
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
          Redis                    MySQL
          Cache                  Database
             │                       │
             │                       │
      Dữ liệu thường              Dữ liệu chính
      xuyên truy cập              lâu dài

1.4.1. MySQL phù hợp với dữ liệu quan hệ

Ví dụ:

users
products
orders
order_details

Có thể có quan hệ:

User
 ↓
Order
 ↓
OrderDetail
 ↓
Product

MySQL rất phù hợp với loại dữ liệu này.

1.4.2. Redis phù hợp với truy cập nhanh

Ví dụ product:100. Redis chỉ cần tìm Key product:100 và trả về Value tương ứng.

Không cần thực hiện các thao tác JOIN phức tạp như trong Database quan hệ.

1.4.3. Không nên hiểu đơn giản là "Redis nhanh hơn nên thay MySQL"

Đây là một cách hiểu sai.

Redis và MySQL giải quyết những bài toán khác nhau.

Ví dụ:

MySQL:
Tôi cần lưu đơn hàng của khách hàng.

Redis:
Tôi cần truy cập nhanh thông tin sản phẩm đang được xem nhiều.

Trong hệ thống thực tế, có thể dùng cả hai:

Client
  ↓
Spring Boot
  ↓
Redis
  ↓ Cache Hit
  │
  └── Cache Miss
          ↓
        MySQL

1.5. Cache là gì?

1.5.1. Khái niệm

Cache là một vùng lưu trữ dữ liệu tạm thời được sử dụng để giữ những dữ liệu có khả năng được truy cập lại trong thời gian ngắn.

Mục tiêu chính:

Giảm thời gian lấy dữ liệu
và giảm tải cho nguồn dữ liệu chính.

Ví dụ một API lấy thông tin Product:

HTTP
GET /api/products/100

Lần đầu:

API
 ↓
MySQL
 ↓
Product

Ứng dụng có thể lưu kết quả vào Cache:

Redis

product:100
     ↓
Product

Lần sau:

API
 ↓
Redis
 ↓
Product

Không cần truy vấn MySQL nếu dữ liệu vẫn còn trong Cache.

1.5.2. Cache không nhất thiết phải là Redis

Cache có thể được triển khai bằng nhiều cách.

Ví dụ:

Application Memory
Redis
Memcached
CDN
Browser Cache

Redis chỉ là một trong những công nghệ phổ biến để xây dựng Cache.

1.5.3. Đặc điểm của Cache

Một Cache thường có những đặc điểm:

  • Truy cập nhanh.
  • Có thể có thời gian hết hạn.
  • Có thể bị xóa.
  • Có thể được tạo lại từ Database.
  • Không nhất thiết là nguồn dữ liệu chính.

Ví dụ:

Database
   ↓
Nguồn dữ liệu chính

Cache
   ↓
Bản sao dữ liệu để truy cập nhanh

1.6. Vì sao cần sử dụng Cache?

Giả sử có một API:

HTTP
GET /api/products/1

API này trả về thông tin sản phẩm.

Có 10.000 request:

Request 1 → MySQL
Request 2 → MySQL
Request 3 → MySQL
...
Request 10000 → MySQL

Database phải xử lý 10.000 lần truy vấn.

Nếu dữ liệu Product rất ít thay đổi, việc truy vấn Database liên tục có thể không cần thiết.

1.6.1. Giảm tải Database

Khi sử dụng Cache:

10000 Request
      ↓
Redis
      │
      ├── 9500 Cache Hit
      │
      └── 500 Cache Miss
                ↓
              MySQL

Trong ví dụ này, MySQL chỉ cần xử lý khoảng 500 request thay vì 10.000 request.

Đây chỉ là ví dụ minh họa; tỷ lệ Cache Hit thực tế phụ thuộc vào dữ liệu, TTL, cách thiết kế Key và hành vi người dùng.

1.6.2. Tăng tốc độ phản hồi

Truy vấn Database thường cần:

Application
    ↓
Database Connection
    ↓
SQL Query
    ↓
Database Processing
    ↓
Result

Trong khi Cache có thể giảm đáng kể phần xử lý này.

Do đó:

Cache Hit
    ↓
Lấy dữ liệu nhanh

API có thể phản hồi nhanh hơn.

1.6.3. Giảm số lần thực hiện Query

Ví dụ:

SQL
SELECT *
FROM products
WHERE id = 100;

Nếu API được gọi rất nhiều lần với cùng một Product, không nhất thiết mọi request đều phải thực hiện query này.

Có thể:

Lần đầu:
MySQL → Redis

Các lần sau:
Redis → Client

1.6.4. Hỗ trợ hệ thống có lượng truy cập lớn

Khi lượng request tăng:

100 request
      ↓
1.000 request
      ↓
10.000 request
      ↓
100.000 request

Database có thể trở thành một trong những điểm chịu tải lớn.

Cache giúp giảm số request phải đi trực tiếp tới Database.

Tuy nhiên, Cache không phải giải pháp duy nhất cho khả năng mở rộng hệ thống.

           ↓

1.7.1. Bước 1: Client gửi Request

HTTP
GET /api/products/100

1.7.2. Bước 2: Application kiểm tra Cache

Application tạo Cache Key: product:100

Sau đó kiểm tra Redis:

Java
Redis.get("product:100")

1.7.3. Bước 3: Nếu Cache có dữ liệu

Redis trả về: Product 100

Application trả dữ liệu cho Client.

Client
  ↑
Spring Boot
  ↑
Redis

Không cần truy vấn MySQL.

1.7.4. Bước 4: Nếu Cache không có dữ liệu

Application truy vấn MySQL:

SQL
SELECT *
FROM products
WHERE id = 100;

Sau khi nhận được dữ liệu:

MySQL
  ↓
Product

Application lưu dữ liệu vào Redis: product:100 → Product

Sau đó trả kết quả cho Client.

1.7.5. Đây là Cache Aside Pattern

Một cách triển khai phổ biến là:

Read:
Cache
 ↓
Có → Return

Không có
 ↓
Database
 ↓
Cache
 ↓
Return

Tên thường được gọi là: Cache-Aside Pattern.

Đây là một pattern quan trọng sẽ được học sâu hơn khi xây dựng Redis Cache trong Spring Boot.

1.8. Cache Hit và Cache Miss

Hai khái niệm rất quan trọng: Cache Hit và Cache Miss.

1.8.1. Cache Hit

Cache Hit xảy ra khi dữ liệu cần tìm đã tồn tại trong Cache.

Ví dụ Request:

HTTP
GET /api/products/100

Application kiểm tra product:100. Redis có dữ liệu:

product:100
    ↓
{
    "id": 100,
    "name": "Laptop"
}

Đây là CACHE HIT.

Luồng:

Client
 ↓
Spring Boot
 ↓
Redis
 ↓
Có dữ liệu
 ↓
Response

1.8.2. Cache Miss

Cache Miss xảy ra khi dữ liệu cần tìm không tồn tại trong Cache hoặc không còn hợp lệ theo cơ chế Cache đang sử dụng.

Ví dụ product:100 không tồn tại trong Redis.

Luồng:

Client
 ↓
Spring Boot
 ↓
Redis
 ↓
Không có
 ↓
MySQL
 ↓
Product
 ↓
Redis
 ↓
Response

Đây là CACHE MISS.

1.8.3. So sánh

Cache Hit Cache Miss
Dữ liệu trong CacheCóKhông
Truy vấn DatabaseThường khôngThường có
Tốc độNhanh hơnChậm hơn
Cần cập nhật CacheKhông nhất thiếtThường có
Mục tiêuTận dụng dữ liệu đã CacheLấy dữ liệu từ nguồn chính

1.8.4. Cache Hit Rate

Có thể sử dụng chỉ số Cache Hit Rate.

Công thức:

Cache Hit Rate
=
Cache Hit
----------------------------
Cache Hit + Cache Miss
× 100%

Ví dụ:

Cache Hit  = 900
Cache Miss = 100

Khi đó:

Hit Rate
=
900 / (900 + 100)
× 100%

= 90%

Cache Hit Rate cao thường cho thấy Cache đang được sử dụng hiệu quả đối với workload đó, nhưng không nên đánh giá hệ thống chỉ dựa vào một chỉ số này.

1.9.2. Vấn đề

Khi hệ thống lớn, việc này có thể dẫn đến:

  • Database chịu nhiều truy vấn.
  • Connection Pool chịu tải.
  • CPU Database tăng.
  • I/O tăng.
  • Thời gian phản hồi có thể tăng.
  • Khả năng mở rộng hệ thống bị ảnh hưởng.

Cache có thể được sử dụng để giảm bớt những truy cập lặp lại này.

1.11. Ưu điểm của Redis Cache

1.11.1. Tốc độ truy cập cao

Redis lưu dữ liệu chủ yếu trong RAM nên có khả năng cung cấp tốc độ truy cập rất nhanh.

Đây là một trong những lý do Redis thường được sử dụng làm Cache.

1.11.2. Giảm tải Database

Ví dụ:

10000 Request
       ↓
     Redis
       │
       ├── 9000 Hit
       │
       └── 1000 Miss
                  ↓
                MySQL

Database giảm được nhiều truy vấn lặp lại.

1.11.3. Có thể thiết lập thời gian hết hạn

Redis hỗ trợ TTL.

Ví dụ:

product:100
TTL = 300 seconds

Sau khoảng thời gian đó, dữ liệu Cache có thể hết hạn.

Điều này rất hữu ích với những dữ liệu chỉ cần Cache trong một khoảng thời gian.

String
List
Set

Sorted Set
Stream
...

Do đó Redis không chỉ phục vụ một loại bài toán.

1.11.5. Hỗ trợ nhiều ứng dụng khác nhau

Redis có thể được sử dụng cho:

  • Cache.

1.11.6. Giảm thời gian xử lý một số API

1.12. Nhược điểm và giới hạn của Redis

Redis rất nhanh nhưng không phải giải pháp cho mọi bài toán.

1.12.1. Sử dụng RAM

Redis hoạt động chủ yếu trên RAM.

RAM thường có chi phí cao hơn Disk.

Ví dụ:

MySQL
→ lưu trữ lượng dữ liệu lớn trên Disk

Redis
→ dữ liệu phục vụ nhanh trong RAM

Do đó không nên đưa toàn bộ Database vào Redis một cách tùy tiện.

1.12.2. Chi phí bộ nhớ

Nếu Cache quá nhiều dữ liệu:

Redis
 ↓
RAM tăng
 ↓
RAM gần đầy

Điều này có thể gây ảnh hưởng đến Redis và hệ thống.

Vì vậy cần quan tâm:

TTL
Kích thước dữ liệu
Số lượng Key
Chính sách loại bỏ dữ liệu
maxmemory

1.12.3. Cache có thể bị Stale Data

Một vấn đề phổ biến:

MySQL:
Product price = 20.000.000

Redis:
Product price = 18.000.000

Nếu Database được cập nhật nhưng Cache chưa được cập nhật hoặc xóa, Client có thể nhận dữ liệu cũ.

Đây được gọi là vấn đề: Stale Data.

1.12.4. Redis có thể gặp sự cố

Tùy kiến trúc, Redis có thể là thành phần hỗ trợ hoặc là thành phần quan trọng của hệ thống.

1.12.5. Không nên Cache mọi dữ liệu

Không phải dữ liệu nào cũng nên Cache.

Ví dụ dữ liệu thay đổi liên tục hoặc không được phép sử dụng dữ liệu cũ thì việc Cache cần được cân nhắc rất kỹ.

1.14. Khi nào không nên sử dụng Redis?

Không phải lúc nào thêm Redis cũng tốt.

1.14.1. Dữ liệu thay đổi liên tục

1.14.3. Dữ liệu rất ít được truy cập

1.15.3. Session Storage

Ví dụ: session:abc123

Lưu:

loginTime

Redis có tốc độ truy cập nhanh và hỗ trợ TTL nên phù hợp với nhiều mô hình Session.

2

Ví dụ: otp:user:100

Giá trị: 928351

TTL: 300 seconds

Sau 5 phút, OTP có thể tự hết hạn.

Đây là một ví dụ điển hình cho dữ liệu tạm thời có thời gian sống ngắn.

1.15.6. Lưu mã xác thực tạm thời

Ví dụ hệ thống có:

Server B
Server C

Cả ba Server cùng muốn xử lý một công việc.

            Redis
               │
        ┌──────┴──────┐
        │             │
    Server A       Server B
        │
      LOCK

Chỉ Server lấy được Lock hợp lệ mới thực hiện công việc.

1.15.10. Pub/Sub

Redis hỗ trợ cơ chế Publish/Subscribe.

Ví dụ:

Publisher
    │
    ▼

    │
 ┌──┴───┐
 ▼      ▼
Sub A  Sub B

Một Server gửi message vào Channel, các Subscriber đang lắng nghe Channel có thể nhận được message.

Ghi nhớ trọng tâm
  • Redis là hệ thống lưu trữ Key-Value trên RAM, tốc độ rất nhanh; không chỉ dùng làm Cache mà còn cho Session, Counter, Rate Limiting, Pub/Sub, Distributed Lock…
  • Cache là vùng lưu tạm dữ liệu để giảm thời gian truy cập và giảm tải nguồn dữ liệu chính.
  • Redis và MySQL có vai trò khác nhau: MySQL là database chính, Redis là Cache/dữ liệu tạm thời. Không nên xem Redis là "MySQL nhanh hơn".
  • Cache Hit: có dữ liệu trong Cache → trả ngay. Cache Miss: không có → query DB → lưu Cache → trả.
  • Cache-Aside Pattern là pattern phổ biến: đọc Cache trước, miss thì đọc DB rồi ghi lại Cache.
  • TTL giúp dữ liệu Cache tự hết hạn, tránh stale quá lâu.
  • Stale Data là vấn đề khi DB đã cập nhật nhưng Cache chưa → cần chiến lược invalidate/update rõ ràng.
  • Không phải dữ liệu nào cũng nên Cache: tránh dữ liệu thay đổi liên tục, không được phép cũ, kích thước quá lớn, hoặc ít truy cập.
  • Redis tốn RAM — cần quan tâm TTL, kích thước dữ liệu, chính sách eviction, maxmemory.
  • Cần có chiến lược fallback khi Redis gặp sự cố (ví dụ fallback xuống DB).

Trong phần này, chúng ta sẽ bắt đầu làm việc trực tiếp với Redis.

Mục tiêu của phần này là giúp học viên:

  • Hiểu kiến trúc hoạt động cơ bản của Redis.
  • Phân biệt Redis Server và Redis Client.
  • Cài đặt Redis.
  • Kiểm tra Redis Server.
  • Sử dụng Redis CLI.
  • Kết nối tới Redis.
  • Hiểu Key và Value.
  • Làm việc với các kiểu dữ liệu phổ biến.
  • Thực hiện các lệnh Redis cơ bản.
  • Thiết lập thời gian hết hạn cho dữ liệu.
  • Kiểm tra và xóa dữ liệu trong Redis.

Sau phần này, học viên có thể sử dụng Redis ở mức cơ bản mà chưa cần Spring Boot.

2.1. Kiến trúc hoạt động của Redis

2.1.1. Tổng quan

Redis hoạt động theo mô hình:

Client
   │
   │ Request
   ▼
Redis Server
   │
   ▼
Redis Data

Trong đó:

  • Redis Server chịu trách nhiệm lưu trữ và xử lý dữ liệu.
  • Redis Client gửi các command tới Redis Server.
  • Redis Server xử lý command và trả kết quả về Client.

Ví dụ:

Redis Client
     │
     │ SET name "Nguyen Van A"
     ▼
Redis Server
     │
     │ lưu dữ liệu
     ▼
Redis

Sau đó Client có thể yêu cầu:

GET name

Redis Server trả về: "Nguyen Van A"

2.1.2. Redis hoạt động theo mô hình Client - Server

Có thể hình dung:

                 Redis
                    │
             ┌──────┴──────┐
             │ Redis Server │
             └──────┬──────┘
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
      CLI      Spring Boot    Tool khác

Nhiều Client có thể kết nối tới một Redis Server.

Ví dụ:

Redis CLI ────────┐
                  │
Spring Boot ──────┼──→ Redis Server
                  │
Redis GUI ────────┘

2.1.3. Redis Server làm nhiệm vụ gì?

Redis Server là thành phần chính.

Nó chịu trách nhiệm:

  • Nhận request từ Client.
  • Phân tích Redis command.
  • Đọc dữ liệu.
  • Ghi dữ liệu.
  • Xóa dữ liệu.
  • Quản lý TTL.
  • Trả kết quả cho Client.

Ví dụ:

Client
  │
  │ SET user:1 "Nguyen Van A"
  ▼
Redis Server
  │
  │ xử lý
  ▼
Lưu Key/Value

2.1.4. Redis lưu dữ liệu ở đâu?

Redis hoạt động chủ yếu trong RAM, vì vậy việc đọc và ghi dữ liệu có thể rất nhanh.

Ví dụ:

Redis cũng có các cơ chế persistence để ghi dữ liệu xuống Disk khi được cấu hình phù hợp.

Tuy nhiên, khi học Redis Cache, cần nhớ:

Cache thường được xem là dữ liệu có thể tạo lại
từ nguồn dữ liệu chính.

2.7. Key và Value trong Redis

Redis sử dụng khái niệm: Key → Value

2.7.1. Key là gì?

Key là tên dùng để xác định dữ liệu.

Ví dụ:

name
user:1
product:100

2.7.2. Value là gì?

Value là dữ liệu được lưu tương ứng với Key.

Ví dụ:

Key:
name

Value:
Nguyen Van A

Có thể hình dung:

┌───────────────────────┐
│ Key: name             │
│ Value: Nguyen Van A   │
└───────────────────────┘

2.7.3. Ví dụ

Command:

Redis
SET name "Nguyen Van A"

Redis lưu: name → Nguyen Van A

Lấy dữ liệu:

Redis
GET name

Kết quả: "Nguyen Van A"

2.7.4. Đặt tên Key

Trong project thực tế nên đặt Key có cấu trúc rõ ràng.

Ví dụ:

user:1
user:2
user:3

Product:
product:1
product:2
product:3

Category:
category:1
category:2

Điều này giúp:

  • Dễ đọc.
  • Dễ quản lý.
  • Dễ phân biệt loại dữ liệu.
  • Dễ kiểm tra khi Debug.

2.7.5. Key trong Cache

Ví dụ: product:100 có thể chứa:

JSON
{
    "id": 100,
    "name": "Laptop",
    "price": 25000000
}

Khi đó:

Key:
product:100

Value:
Thông tin Product 100

2.8. Các kiểu dữ liệu trong Redis

Redis hỗ trợ nhiều kiểu dữ liệu.

Trong phần này tập trung vào: String, List, Set, Hash, Sorted Set.

2.8.1. String

Lưu dữ liệu dạng đơn giản.

Ví dụ: name → Nguyen Van A

2.8.2. List

Lưu một danh sách các phần tử theo thứ tự.

Ví dụ:

tasks
 ↓
["Task A", "Task B", "Task C"]

2.8.3. Set

Lưu tập hợp các phần tử không trùng nhau.

Ví dụ:

tags
 ↓
Java
Spring
Redis

Nếu thêm Java lần nữa thì Set vẫn chỉ có một Java.

2.8.4. Hash

Lưu nhiều field-value dưới một Key.

Ví dụ user:1 có:

name  → Nguyen Van A
email → a@gmail.com
age   → 29

2.8.5. Sorted Set

Lưu các phần tử kèm theo Score.

Ví dụ:

Player A → 100
Player B → 200
Player C → 150

Redis có thể sử dụng Score để sắp xếp.

2.9. String

2.9.1. String là gì?

String là kiểu dữ liệu đơn giản nhất trong Redis.

Có thể sử dụng để lưu:

Chuỗi
Số
JSON
Token
Counter
Một số dữ liệu dạng text

2.9.2. SET String

Redis
SET name "Nguyen Van A"

Kết quả: OK

2.9.3. GET String

Redis
GET name

Kết quả: "Nguyen Van A"

2.9.4. String chứa số

Redis
SET age 29

Lấy:

Redis
GET age

Kết quả: "29"

Redis String cũng có thể được sử dụng cho các thao tác số phù hợp.

2.9.5. Counter

Ví dụ:

Redis
SET view:product:100 100

Tăng:

Redis
INCR view:product:100

Kết quả: 101

Tăng tiếp:

Redis
INCR view:product:100

Kết quả: 102

2.10. List

2.10.1. List là gì?

List là một danh sách các phần tử có thứ tự.

Ví dụ:

tasks
 ↓
Task A
Task B
Task C

2.10.2. Thêm phần tử

Sử dụng:

Redis
LPUSH tasks "Task A"

Sau đó:

Redis
LPUSH tasks "Task B"

Danh sách:

Task B
Task A

2.10.3. Lấy dữ liệu

Sử dụng:

Redis
LRANGE tasks 0 -1

Kết quả:

1) "Task B"
2) "Task A"

0 là vị trí bắt đầu. -1 biểu thị phần tử cuối cùng.

2.10.4. Thêm vào cuối List

Redis
RPUSH tasks "Task C"

Khi đó:

Task B
Task A
Task C

2.10.5. Xóa phần tử đầu

Redis
LPOP tasks

2.10.6. Xóa phần tử cuối

Redis
RPOP tasks

2.11. Set

2.11.1. Set là gì?

Set là tập hợp các phần tử không trùng nhau.

Ví dụ:

tags
 ↓
Java
Spring
Redis

2.11.2. Thêm dữ liệu

Redis
SADD tags "Java"
SADD tags "Spring"
SADD tags "Redis"

2.11.3. Thêm phần tử trùng

Redis
SADD tags "Java"

Redis không tạo thêm một Java mới.

Set vẫn:

Java
Spring
Redis

2.11.4. Xem các phần tử

Redis
SMEMBERS tags

Kết quả có thể:

1) "Java"
2) "Spring"
3) "Redis"

Thứ tự trả về của Set không nên được hiểu là thứ tự cố định.

2.11.5. Kiểm tra phần tử

Redis
SISMEMBER tags "Java"

Nếu tồn tại: 1. Nếu không: 0.

2.12. Hash

2.12.1. Hash là gì?

Hash cho phép lưu nhiều cặp field → value dưới một Key.

Ví dụ user:1 có:

name  → Nguyen Van A
email → a@gmail.com
age   → 29

2.12.2. Tạo Hash

Redis
HSET user:1 name "Nguyen Van A"

Thêm:

Redis
HSET user:1 email "a@gmail.com"

Thêm:

Redis
HSET user:1 age 29

2.12.3. Xem toàn bộ Hash

Redis
HGETALL user:1

Kết quả:

1) "name"
2) "Nguyen Van A"
3) "email"
4) "a@gmail.com"
5) "age"
6) "29"

2.12.4. Lấy một field

Redis
HGET user:1 name

Kết quả: "Nguyen Van A"

2.12.5. Hash phù hợp với dữ liệu dạng Object đơn giản

Ví dụ user:1:

name  → Nguyen Van A
email → a@gmail.com
age   → 29

Tuy nhiên trong Spring Cache, Object thường được serialize thành JSON hoặc một định dạng khác tùy cấu hình. Không nên đồng nhất Hash Redis với Java Object một cách máy móc.

2.13. Sorted Set

2.13.1. Sorted Set là gì?

Sorted Set, thường gọi là ZSet, lưu: Member + Score

Ví dụ:

Player A → 100
Player B → 200
Player C → 150

2.13.2. Thêm dữ liệu

Redis
ZADD leaderboard 100 "Player A"
ZADD leaderboard 200 "Player B"
ZADD leaderboard 150 "Player C"

2.13.3. Xem dữ liệu

Redis
ZRANGE leaderboard 0 -1 WITHSCORES

Kết quả được sắp xếp theo Score tăng dần:

Player A
100

Player C
150

Player B
200

2.13.4. Xem theo thứ tự giảm dần

Có thể sử dụng:

Redis

Kết quả:

Player B
200

Player C
150

Player A
100

2.13.5. Ứng dụng thực tế

Sorted Set phù hợp với một số bài toán:

Leaderboard
Ranking
Xếp hạng người dùng
Điểm số
Một số dữ liệu cần sắp xếp theo Score

Redis
GET name

2.15.3. SET lại Key

Nếu Key đã tồn tại:

Redis
SET name "Nguyen Van A"

Sau đó:

2.15.4. Ví dụ Product

Redis

Redis

2.16. GET

2.16.1. Công dụng

GET dùng để lấy Value của một Key.

Cú pháp:

Redis
GET key

Ví dụ:

Redis
GET name

2.16.2. Key tồn tại

Nếu name → Nguyen Van A thì GET name trả: "Nguyen Van A".

2.16.3. Key không tồn tại

Ví dụ:

Redis
GET unknown

Redis trả: (nil)

Điều này có nghĩa Key không có dữ liệu tương ứng.

2.17. DEL

2.17.1. Công dụng

DEL dùng để xóa Key.

Cú pháp:

Redis
DEL key

Ví dụ:

Redis
SET name "Nguyen Van A"

Sau đó:

Redis
DEL name

Kết quả: (integer) 1

Sau khi xóa:

Redis
GET name

Kết quả: (nil)

2.17.2. Xóa nhiều Key

Có thể:

Redis
DEL name age email

Redis sẽ xóa các Key được chỉ định nếu chúng tồn tại.

2.17.3. DEL trong Cache

Ví dụ product:100.

Khi Product được cập nhật:

HTTP
PUT /api/products/100

ứng dụng có thể cần xóa Cache:

Redis
DEL product:100

Sau đó lần GET tiếp theo sẽ lấy dữ liệu mới từ Database và tạo lại Cache.

2.18. EXISTS

2.18.1. Công dụng

EXISTS dùng để kiểm tra Key có tồn tại hay không.

Cú pháp:

Redis
EXISTS key

2.18.2. Key tồn tại

Redis
SET name "Nguyen Van A"

Sau đó:

Redis
EXISTS name

Kết quả: (integer) 1

2.18.3. Key không tồn tại

Redis
EXISTS username

Kết quả: (integer) 0

2.18.4. Ý nghĩa

Có thể hiểu:

1 → tồn tại
0 → không tồn tại

2.19. KEYS

2.19.1. Công dụng

KEYS dùng để tìm các Key phù hợp với pattern.

Ví dụ:

Redis
KEYS *

Hiển thị các Key:

1) "name"
2) "user:1"
3) "product:100"

2.19.2. Tìm Key theo Prefix

Ví dụ:

Redis
KEYS user:*

Có thể trả:

user:1
user:2
user:3

2.19.3. Pattern *

* đại diện cho chuỗi ký tự bất kỳ.

Ví dụ user:* nghĩa là các Key bắt đầu bằng user:.

2.19.4. Lưu ý quan trọng về KEYS

Trong môi trường học tập, KEYS * rất tiện để xem dữ liệu.

Nhưng trong Redis production với lượng Key rất lớn, không nên tùy tiện sử dụng KEYS *, vì command này có thể phải duyệt toàn bộ Keyspace và gây ảnh hưởng hiệu năng.

Trong hệ thống thực tế thường cân nhắc:

SCAN

thay cho KEYS.

Ở phần cơ bản này chỉ cần nhớ: KEYS phù hợp để học và kiểm tra dữ liệu nhỏ; không nên lạm dụng trong Production.

2.20. EXPIRE

2.20.1. Công dụng

EXPIRE dùng để thiết lập thời gian sống cho một Key.

Cú pháp:

Redis
EXPIRE key seconds

Ví dụ:

Redis
SET otp "123456"

Sau đó:

Redis
EXPIRE otp 60

Key sẽ có TTL khoảng 60 giây.

2.20.2. Ví dụ

Redis
SET otp "123456"
EXPIRE otp 60

Kiểm tra:

Redis
TTL otp

Có thể nhận: (integer) 58

Sau khi hết thời gian:

Redis
GET otp

Kết quả: (nil)

2.20.3. Tại sao Cache cần EXPIRE?

Cache không nên tồn tại mãi mãi trong nhiều trường hợp.

Ví dụ:

product:100
TTL = 300 seconds

Sau 5 phút, Cache hết hạn.

Request tiếp theo:

Redis
 ↓
MISS
 ↓
MySQL
 ↓
Dữ liệu mới
 ↓

2.21. TTL

2.21.1. Công dụng

TTL dùng để kiểm tra số giây còn lại trước khi Key hết hạn.

Redis
TTL name

2.21.3. TTL bằng -1

Nếu TTL name trả (integer) -1, thường có nghĩa: Key tồn tại nhưng không có thời gian hết hạn.

không thiết lập EXPIRE.

2.21.4. TTL bằng -2

Nếu TTL name trả (integer) -2, thường có nghĩa: Key không tồn tại.

-1Có Key nhưng không có TTL

3.1. Spring Cache là gì?

3.1.1. Khái niệm

Spring Cache là cơ chế Cache abstraction được Spring cung cấp để ứng dụng có thể sử dụng Cache thông qua các Annotation và API thống nhất.

Thay vì tự viết RedisTemplate cho từng API, chúng ta có thể sử dụng @Cacheable.

Ví dụ:

Java
@Cacheable("products")
public Product getProductById(Integer id) {
    return productRepository.findById(id).orElse(null);
}

Spring sẽ giúp quản lý quá trình Cache.

3.1.2. Spring Cache không phải Redis

Đây là điểm rất quan trọng.

Không nên hiểu: Spring Cache = Redis

Hai khái niệm này khác nhau.

Spring Cache

Là một abstraction. Nó cung cấp cách làm việc thống nhất với Cache.

Redis

Là một hệ thống lưu trữ dữ liệu có thể được sử dụng làm Cache.

Có thể hình dung:

            Spring Cache
                  │
          Cache Abstraction
                  │
        ┌─────────┴─────────┐
        │                   │
      Redis              Cache khác

Khi sử dụng Redis:

Spring Cache
      ↓
Redis Cache
      ↓
Redis Server

3.1.3. Tại sao Spring cung cấp Cache abstraction?

Nếu không có abstraction, code có thể phụ thuộc trực tiếp vào Redis.

Ví dụ:

Java
redisTemplate.opsForValue()
        .set("product:100", product);

Nếu sau này muốn thay Redis bằng một Cache khác, code có thể phải thay đổi nhiều.

Spring Cache giúp tách:

Business Logic
      │
      ▼
Spring Cache
      │
      ▼
Cache Provider

Nhờ vậy Business Code ít phụ thuộc trực tiếp vào công nghệ Cache hơn.

Không sử dụng Cache:

Thay vì tự viết code kiểm tra Redis, lấy dữ liệu từ Redis hoặc lưu dữ liệu vào Redis, chúng ta có thể sử dụng các annotation như:

4.4. Cache Key

4.4.1. Cache Key là gì?

Cache Key là khóa dùng để xác định dữ liệu được lưu trong Cache.

Ví dụ:

Java
@Cacheable("products")
public Product getProductById(Integer id) {
    ...
}

Khi id = 10, Spring có thể tạo key tương ứng với method và tham số.

Một cách hình dung đơn giản: products::10

4.4.2. Sử dụng key

Chúng ta có thể chủ động xác định key:

Java
@Cacheable(
        value = "products",
        key = "#id"
)
public Product getProductById(Integer id) {

    return productRepository
            .findById(id)
            .orElse(null);
}

Ở đây key = "#id" nghĩa là sử dụng giá trị của tham số id làm Cache Key.

Ví dụ id = 10 thì key sẽ là 10.

4.4.3. Vì sao nên chủ động khai báo Key?

Khi project lớn, việc xác định rõ Cache Key giúp:

  • dễ đọc code;
  • dễ kiểm tra Redis;
  • tránh nhầm key;
  • dễ quản lý Cache;
  • dễ đồng bộ giữa các method.

Ví dụ:

Java
@Cacheable(
        value = "products",
        key = "#id"
)

rõ ràng hơn rất nhiều so với việc để toàn bộ logic key mặc định khi project có nhiều loại Cache.

4.5. Cache Value

4.5.1. Cache Value là gì?

Cache Value là dữ liệu được lưu vào Cache.

Ví dụ:

Java
@Cacheable(
        value = "products",
        key = "#id"
)
public Product getProductById(Integer id) {

    return productRepository
            .findById(id)
            .orElse(null);
}

Giả sử database trả về:

id = 10
name = Laptop
price = 15000000

Spring Cache sẽ lưu kết quả của method vào Cache.

Có thể hình dung:

Key
 ↓
products::10
       ↓
Value
       ↓
Product

4.5.2. Key và Value

Có thể hình dung Redis Cache giống như:

KEY                    VALUE
--------------------------------
products::10           Product
products::20           Product
products::30           Product

Key dùng để tìm dữ liệu. Value là dữ liệu được lưu.

4.6. @CachePut

4.6.1. @CachePut là gì?

@CachePut được sử dụng khi muốn:

Thực hiện method và đồng thời cập nhật dữ liệu vào Cache.

Đây là điểm khác biệt rất quan trọng so với @Cacheable.

4.6.2. Ví dụ

Java
@CachePut(
        value = "products",
        key = "#product.id"
)
public Product updateProduct(Product product) {

    return productRepository.save(product);
}

Khi gọi updateProduct():

  • method vẫn được thực hiện;
  • Database vẫn được cập nhật;
  • sau đó kết quả trả về được đưa vào Cache.

4.6.3. So sánh @Cacheable và @CachePut

Annotation Method có chạy không? Cache
@CacheableCó thể không chạyĐọc Cache trước
@CachePutLuôn chạyCập nhật Cache

Ví dụ @Cacheable("products") phù hợp với GET.

Trong khi @CachePut("products") thường phù hợp với UPDATE.

4.7. @CacheEvict

4.7.1. @CacheEvict là gì?

@CacheEvict dùng để xóa dữ liệu khỏi Cache.

Ví dụ:

Java
@CacheEvict(
        value = "products",
        key = "#id"
)
public void deleteProduct(Integer id) {

    productRepository.deleteById(id);
}

Khi gọi deleteProduct(10); Spring sẽ xóa Cache tương ứng:

products::10

4.7.2. Vì sao Delete phải xóa Cache?

Giả sử Redis đang chứa:

products::10
        ↓
Laptop
price = 15.000.000

Database xóa Product ID 10.

Nhưng nếu Cache vẫn tồn tại:

Redis
products::10
        ↓
Laptop

thì API lấy Product ID 10 có thể vẫn lấy được dữ liệu cũ từ Cache.

Do đó khi xóa dữ liệu Database, cần xử lý Cache tương ứng.

4.8. Xóa toàn bộ Cache

Nếu muốn xóa toàn bộ dữ liệu trong một Cache:

Java
@CacheEvict(
        value = "products",
        allEntries = true
)
public void clearProductCache() {

}

allEntries = true nghĩa là xóa toàn bộ entry thuộc Cache products.

Ví dụ Redis có:

products::1
products::2
products::3
products::4

Sau khi:

Java
@CacheEvict(
        value = "products",
        allEntries = true
)

thì các entry trên sẽ được xóa khỏi Cache products.

4.8.1. Khi nào sử dụng?

Thường dùng khi:

  • dữ liệu thay đổi hàng loạt;
  • import dữ liệu mới;
  • đồng bộ dữ liệu;
  • cập nhật nhiều Product;
  • muốn làm mới toàn bộ Cache.

4.9. @Caching

4.9.1. @Caching là gì?

@Caching cho phép kết hợp nhiều annotation Cache trên cùng một method.

Ví dụ:

Java
@Caching(
        put = {
            @CachePut(
                    value = "products",
                    key = "#product.id"
            )
        },
        evict = {
            @CacheEvict(
                    value = "productList",
                    allEntries = true
            )
        }
)
public Product updateProduct(Product product) {

    return productRepository.save(product);
}

Ở đây một lần update có thể:

  • cập nhật Cache Product theo ID;
  • xóa Cache danh sách Product.

4.9.2. Vì sao cần @Caching?

Giả sử có Cache Product theo ID và Cache danh sách Product.

Khi update Product, products::10 cần cập nhật.

Nhưng productList cũng có thể chứa dữ liệu cũ.

Vì vậy cần xử lý cả hai.

4.10. condition

4.10.1. condition là gì?

condition cho phép xác định: Method có được Cache hay không dựa trên điều kiện.

Ví dụ:

Java
@Cacheable(
        value = "products",
        key = "#id",
        condition = "#id > 0"
)
public Product getProductById(Integer id) {

    return productRepository
            .findById(id)
            .orElse(null);
}

Nếu id = 10 thì 10 > 0 → Cache được sử dụng.

Nếu id = -1 thì -1 > 0 → không sử dụng Cache.

4.10.2. Ví dụ với giá trị

Java
@Cacheable(
        value = "products",
        key = "#id",
        condition = "#id != null"
)
public Product getProductById(Integer id) {

    return productRepository
            .findById(id)
            .orElse(null);
}

Chỉ Cache khi id != null.

4.11. unless

4.11.1. unless là gì?

unless dùng để quyết định: Sau khi method thực hiện xong, có lưu kết quả vào Cache hay không.

Đây là điểm khác biệt quan trọng giữa condition và unless.

4.11.2. Ví dụ

Java
@Cacheable(
        value = "products",
        key = "#id",
        unless = "#result == null"
)
public Product getProductById(Integer id) {

    return productRepository
            .findById(id)
            .orElse(null);
}

Nếu method trả về Product → Cache.

Nếu method trả về null → không Cache.

4.11.3. So sánh

condition unless
Kiểm traTrước khi method chạySau khi method chạy
Quyết địnhCó thực hiện cơ chế Cache hay khôngCó lưu kết quả hay không
#resultKhông dùngCó thể sử dụng

Ví dụ condition = "#id > 0" kiểm tra id trước khi method chạy.

Trong khi unless = "#result == null" kiểm tra kết quả result sau khi method chạy.

    ↓

    ↓
Spring Cache
    ↓
Redis
    ↓

    ↓
MySQL

Mục tiêu cuối cùng của Redis Cache là giảm số lần truy vấn Database đối với những dữ liệu được truy cập nhiều và có thể chấp nhận một mức độ trễ nhất định trong việc cập nhật dữ liệu Cache.

Phần tiếp theo hợp lý sẽ đi vào cấu hình nâng cao Cache với Redis như TTL, thời gian hết hạn, RedisCacheManager, JSON Serializer, cấu hình từng Cache riêng biệt và xử lý Cache Object/DTO.

Ghi nhớ trọng tâm
  • @EnableCaching phải được bật để Spring xử lý các annotation Cache.
  • @Cacheable: đọc Cache trước — HIT thì trả Cache, MISS thì chạy method và lưu kết quả.
  • @CachePut: luôn chạy method và cập nhật Cache — phù hợp UPDATE.
  • @CacheEvict: xóa Cache theo key, hoặc allEntries = true để xóa cả vùng Cache.
  • @Caching: gộp nhiều thao tác Cache trên cùng method (ví dụ UPDATE vừa put vừa evict).
  • condition kiểm tra trước khi method chạy; unless kiểm tra sau khi method chạy (có thể dùng #result).
  • Cache Key nên khai báo rõ (key = "#id") để dễ quản lý và debug.
  • Cache thường đặt ở Service Layer, không nên rải ở Controller hay Repository.
  • Khi có CREATE/UPDATE/DELETE phải xử lý Cache tương ứng để tránh Stale Data.
  • Cache danh sách (productList) rất dễ stale — thường phải @CacheEvict(allEntries = true) khi dữ liệu thay đổi.
  • Kiểm tra Cache Hit/Miss bằng Log, redis-cli, hoặc quan sát SQL — không dùng System.out.println trong code thật.

5.4. TTL của Cache

5.4.1. TTL là gì?

TTL là viết tắt của:

Time To Live

TTL xác định: Một dữ liệu được phép tồn tại trong Cache bao lâu trước khi Redis tự động xóa nó.

Ví dụ: TTL = 10 phút.

Nếu dữ liệu được lưu lúc 10:00 thì đến khoảng 10:10 dữ liệu có thể hết hạn.

5.4.2. Vì sao cần TTL?

Cache không nên tồn tại mãi mãi trong mọi trường hợp.

Ví dụ Product:

Product ID: 10
Price: 15.000.000

Database thay đổi:

Price: 14.500.000

nhưng Redis vẫn có:

15.000.000

Nếu Cache không được cập nhật hoặc xóa, API có thể trả dữ liệu cũ.

TTL giúp dữ liệu Cache tự động hết hạn.

5.4.3. Kiểm tra TTL bằng Redis CLI

Có thể sử dụng:

Redis
TTL products::10

Redis có thể trả 299 nghĩa là còn khoảng 299 giây.

Nếu trả -1 thường có nghĩa key không có thời gian hết hạn.

Nếu trả -2 thường có nghĩa key không tồn tại.

5.5. Thiết lập TTL mặc định

5.5.1. TTL cho toàn bộ Cache

Có thể cấu hình TTL mặc định:

Java
@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager redisCacheManager(
            RedisConnectionFactory connectionFactory
    ) {

        RedisCacheConfiguration configuration =
                RedisCacheConfiguration
                        .defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(10));

        return RedisCacheManager
                .builder(connectionFactory)
                .cacheDefaults(configuration)
                .build();
    }
}

TTL Duration.ofMinutes(10) nghĩa là 10 phút.

5.5.2. Ví dụ TTL khác

1 phút:

Java
Duration.ofMinutes(1)

30 phút:

Java
Duration.ofMinutes(30)

1 giờ:

Java
Duration.ofHours(1)

1 ngày:

Java
Duration.ofDays(1)

     │
     ▼

     │
     ▼
Lưu Cache
     │
     ▼

     │

Không phải tất cả Cache đều nên có cùng TTL.

Ví dụ:

    TTL = 10 phút

    TTL = 5 phút

Có thể cấu hình riêng.

5.6.1. Tạo nhiều Cache Configuration

Java
@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager redisCacheManager(
            RedisConnectionFactory connectionFactory
    ) {

        RedisCacheConfiguration defaultConfig =
                RedisCacheConfiguration
                        .defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(10));

        RedisCacheConfiguration productListConfig =
                RedisCacheConfiguration
                        .defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(5));

        RedisCacheConfiguration productSearchConfig =
                RedisCacheConfiguration
                        .defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(2));

        Map<String, RedisCacheConfiguration> cacheConfigurations =
                new HashMap<>();

        cacheConfigurations.put(
                "products",
                defaultConfig
        );

        cacheConfigurations.put(
                "productList",
                productListConfig
        );

        cacheConfigurations.put(
                "productSearch",
                productSearchConfig
        );

        return RedisCacheManager
                .builder(connectionFactory)
                .cacheDefaults(defaultConfig)
                .withInitialCacheConfigurations(
                        cacheConfigurations
                )
                .build();
    }
}

Đây có thể hữu ích trong một số trường hợp để tránh truy vấn lặp lại cho một ID không tồn tại.

5.16.1. Ví dụ cấu hình

Java
@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager redisCacheManager(
            RedisConnectionFactory connectionFactory
    ) {

        RedisCacheConfiguration defaultConfig =
                RedisCacheConfiguration
                        .defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(10))
                        .disableCachingNullValues()
                        .serializeKeysWith(
                                RedisSerializationContext
                                        .SerializationPair
                                        .fromSerializer(
                                                new StringRedisSerializer()
                                        )
                        );

        RedisCacheConfiguration productSearchConfig =
                defaultConfig
                        .entryTtl(Duration.ofMinutes(2));

        RedisCacheConfiguration userConfig =
                defaultConfig
                        .entryTtl(Duration.ofMinutes(30));

        Map<String, RedisCacheConfiguration> configurations =
                new HashMap<>();

        configurations.put(
                "products",
                defaultConfig
        );

        configurations.put(
                "productList",
                defaultConfig
        );

        configurations.put(
                "productSearch",
                productSearchConfig
        );

        configurations.put(
                "users",
                userConfig
        );

        return RedisCacheManager
                .builder(connectionFactory)
                .cacheDefaults(defaultConfig)
                .withInitialCacheConfigurations(
                        configurations
                )
                .build();
    }
}

Phần 7 nếu tiếp tục theo lộ trình này nên chuyển sang các vấn đề nâng cao của Redis Cache trong hệ thống thực tế: Cache Invalidation, Cache Stampede, Cache Penetration, Cache Breakdown, xử lý Concurrent Request, TTL/Jitter và chiến lược chống quá tải Database.

Ghi nhớ trọng tâm
  • GET phù hợp nhất với Cache — đọc nhiều, ít thay đổi.
  • POST tạo dữ liệu mới → phải @CacheEvict các Cache danh sách (productList) để tránh stale.
  • PUT cập nhật → @CachePut Cache theo ID và @CacheEvict Cache danh sách (dùng @Caching).
  • DELETE xóa → @CacheEvict theo ID và Cache danh sách.
  • Cache Aside Pattern: Application tự kiểm tra Cache → miss thì đọc DB → ghi Cache → trả về. Spring Cache triển khai phần lớn logic này qua @Cacheable.
  • Database là Source of Truth; Redis chỉ là lớp Cache tăng tốc.
  • Cache danh sách rất dễ stale — mỗi khi CREATE/UPDATE/DELETE nên evict.
  • Redis lỗi không nên làm sập API — cần chiến lược fallback rõ ràng (không mặc định tự động).
  • Log khi Cache update/evict, không log password/token/secret.
  • Kiểm tra hiệu năng đúng cách: đo cả 5 trường hợp (không Cache, MISS, HIT, hết TTL, Redis lỗi).
  • Tư duy đúng: không phải "API này dùng Redis" mà là "dữ liệu này có nên Cache? Key nào? TTL bao lâu? Khi CRUD thì làm gì?"

PHẦN 7. CÁC VẤN ĐỀ THỰC TẾ KHI SỬ DỤNG REDIS CACHE

Ở các phần trước, chúng ta đã tìm hiểu cách sử dụng Redis làm Cache trong Spring Boot, bao gồm @Cacheable, @CachePut, @CacheEvict, TTL, Serialization và Cache trong REST API.

Tuy nhiên, khi triển khai một hệ thống thực tế, việc sử dụng Cache không chỉ đơn giản là:

Database → Redis → API

Cache có thể phát sinh rất nhiều vấn đề:

  • Dữ liệu trong Cache cũ hơn Database.
  • Cache không được cập nhật khi Database thay đổi.
  • Một lượng lớn request cùng lúc truy cập Database.
  • Redis lưu quá nhiều dữ liệu.
  • Key bị thiết kế sai hoặc bị trùng.
  • Redis hết bộ nhớ.
  • Redis mất kết nối.
  • Serialization không tương thích.
  • TTL được cấu hình không hợp lý.

Vì vậy, hiểu được các vấn đề này là rất quan trọng khi xây dựng hệ thống Backend thực tế.

7.3. Cache Stampede

7.3.1. Cache Stampede là gì?

Cache Stampede xảy ra khi một Cache quan trọng hết hạn hoặc bị xóa, khiến rất nhiều request cùng lúc truy cập Database.

Ví dụ:

Redis:

products::1
TTL = 0

Cache hết hạn.

Đồng thời có 1.000 request cùng gọi:

HTTP
GET /api/products/1

Tất cả đều nhận: Cache MISS

Sau đó:

Request 1 ──┐
Request 2 ──┤
Request 3 ──┤
Request 4 ──┤──→ MySQL
...         │
Request 1000┘

Database phải xử lý hàng loạt request giống nhau.

7.3.2. Vì sao nguy hiểm?

Bình thường:

1000 request
      ↓
Redis
      ↓
1000 HIT

Database gần như không phải xử lý.

Nhưng khi Cache hết hạn:

1000 request
      ↓
1000 MISS
      ↓
MySQL

Database có thể bị tăng tải đột ngột.

7.3.3. Một số giải pháp

Giải pháp 1: TTL hợp lý

Không nên để toàn bộ Cache quan trọng hết hạn cùng một thời điểm.

Giải pháp 2: Random TTL

Ví dụ TTL cơ bản = 3600 giây.

Có thể tạo thời gian hết hạn khác nhau:

3500 giây
3700 giây
3900 giây

Thay vì: Tất cả = 3600 giây.

Giải pháp 3: Lock

Chỉ cho một request thực hiện việc lấy dữ liệu từ Database.

Request A
   ↓
Cache MISS
   ↓
LOCK
   ↓
Database
   ↓
Redis

Request B
   ↓
Cache MISS
   ↓
Chờ

Request C
   ↓
Cache MISS
   ↓
Chờ

Sau khi Request A cập nhật Cache:

Request B → Redis HIT

Request C → Redis HIT

7.4. Cache Penetration

7.4.1. Cache Penetration là gì?

Cache Penetration xảy ra khi request liên tục yêu cầu dữ liệu không tồn tại.

Ví dụ:

HTTP
GET /api/products/999999

Database không có Product: ID 999999

Luồng:

Redis
   ↓
MISS

Database
   ↓
Không tìm thấy

Redis
   ↓
Không lưu gì

Request tiếp theo lại:

Redis MISS
   ↓
Database
   ↓
Không tồn tại

Nếu có hàng nghìn request như vậy:

1000 request
     ↓
1000 Redis MISS
     ↓
1000 Database Query

Database bị truy vấn liên tục cho những dữ liệu không tồn tại.

7.4.2. Giải pháp

Một giải pháp đơn giản là cache cả kết quả null hoặc sử dụng cơ chế đánh dấu dữ liệu không tồn tại.

Ví dụ:

products::999999 = NULL

Request sau:

Redis
   ↓
Đã biết ID không tồn tại
   ↓
Không cần truy vấn Database

Tuy nhiên, không nên cache null vô thời hạn. Nên sử dụng TTL ngắn.

Ví dụ:

product::999999

value = NULL

TTL = 60 seconds

Sau 60 giây, hệ thống có thể kiểm tra lại Database.

7.5. Cache Avalanche

7.5.1. Cache Avalanche là gì?

Cache Avalanche xảy ra khi một lượng lớn Cache hết hạn hoặc bị mất cùng lúc.

Ví dụ:

Cache:

Product 1 → TTL 3600
Product 2 → TTL 3600
Product 3 → TTL 3600
Product 4 → TTL 3600
...
Product 100000 → TTL 3600

Nếu tất cả được tạo cùng thời điểm 13:00:00 thì khoảng 14:00:00 rất nhiều Cache có thể hết hạn cùng lúc.

Kết quả:

Redis
  ↓
大量 MISS
  ↓
Database
  ↓
Database Load tăng mạnh

7.5.2. Stampede và Avalanche khác nhau như thế nào?

Vấn đề Đặc điểm
Cache StampedeMột Cache hoặc một nhóm Cache quan trọng hết hạn → nhiều request cùng truy vấn
Cache AvalancheMột lượng rất lớn Cache hết hạn/mất cùng lúc → Database chịu tải lớn

Có thể hiểu đơn giản:

Stampede
→ Một điểm Cache bị "dẫm" bởi nhiều request

Avalanche
→ Một lượng lớn Cache cùng "sập" một lúc

7.5.3. Giải pháp

Random TTL

Thay vì TTL = 3600, có thể phân bố:

TTL = 3500
TTL = 3640
TTL = 3720
TTL = 3890

Cache Warm-up

Một số hệ thống chủ động load dữ liệu quan trọng vào Cache trước khi có request.

Application Start
      ↓
Load dữ liệu quan trọng
      ↓
Redis

Monitoring

Theo dõi:

Redis memory
Cache hit rate
Cache miss rate
Database load

7.6. Cache Key bị trùng

7.6.1. Cache Key là gì?

Cache Key là khóa dùng để xác định dữ liệu trong Redis.

Ví dụ:

products::1
products::2
products::3

Trong đó products là Cache Name, 1, 2, 3 là ID.

7.6.2. Key bị trùng là gì?

Nếu hai loại dữ liệu sử dụng cùng một Key:

users::1
products::1

thì có thể không vấn đề nếu Cache Name khác nhau.

Nhưng nếu cùng sử dụng 1 thì có nguy cơ xung đột.

Ví dụ:

1 → User

sau đó:

1 → Product

Dữ liệu trước có thể bị ghi đè tùy cách thiết kế.

7.6.3. Cách đặt Key

Nên có namespace rõ ràng:

user::1
product::1
order::1
category::1

Hoặc:

users::1
products::1
orders::1
categories::1

Trong Spring Cache:

Java
@Cacheable(
    value = "products",
    key = "#id"
)

Spring sẽ tạo Cache theo Cache Name và Key. Việc phân biệt Cache Name giúp hạn chế xung đột.

7.7. Cache quá nhiều dữ liệu

Redis lưu dữ liệu trong bộ nhớ RAM.

Do đó, nếu ứng dụng cache quá nhiều dữ liệu:

Redis
   ↓
Memory tăng
   ↓
Memory gần đầy
   ↓
Redis không thể lưu thêm dữ liệu

Ví dụ:

Redis Memory = 1 GB

Cache:
Product       = 200 MB
User          = 250 MB
Order         = 300 MB
Search Result = 200 MB
Session       = 100 MB

Tổng:
1.05 GB

Redis đã vượt quá dung lượng dự kiến.

7.7.1. Không nên Cache tất cả

Không phải dữ liệu nào cũng nên Cache.

Nên ưu tiên:

Dữ liệu đọc nhiều
+
Ít thay đổi
+
Truy vấn tốn tài nguyên

Ví dụ:

Danh sách Category
Danh sách Product nổi bật
Thông tin cấu hình
Dữ liệu thống kê được truy cập thường xuyên

7.7.2. Cần sử dụng TTL

Ví dụ:

products::1
TTL = 30 phút

Sau 30 phút:

Redis
   ↓
Expire
   ↓
Xóa dữ liệu

Điều này giúp Cache không tồn tại mãi mãi.

7.8. TTL quá ngắn

TTL quá ngắn khiến Cache nhanh chóng hết hạn.

Ví dụ: TTL = 10 giây

Request:

10:00:00 → MISS → Database
10:00:05 → HIT
10:00:11 → MISS → Database
10:00:20 → MISS → Database

Database phải được truy vấn thường xuyên.

7.8.1. Hậu quả

TTL quá ngắn
     ↓
Cache nhanh hết hạn
     ↓
Cache MISS tăng
     ↓
Database Query tăng

Khi đó lợi ích của Cache giảm.

7.8.2. Có nên để TTL càng dài càng tốt?

Không.

TTL cần phụ thuộc vào tính chất dữ liệu.

Dữ liệu TTL minh họa
Cấu hình ít thay đổiVài giờ
CategoryVài giờ
ProductVài phút đến vài giờ
Thông tin realtimeRất ngắn
Kết quả tìm kiếmVài phút

Đây chỉ là ví dụ. TTL thực tế phải dựa trên tần suất thay đổi dữ liệu và yêu cầu về độ mới.

7.9. TTL quá dài

TTL quá dài có vấn đề ngược lại.

Ví dụ:

Product Price
TTL = 7 ngày

Database thay đổi:

15.000.000
↓
17.000.000

Nhưng Redis vẫn giữ: 15.000.000

Nếu Cache không được evict/update: 7 ngày người dùng có thể nhận dữ liệu cũ.

7.9.1. Hậu quả

TTL quá dài
     ↓
Cache tồn tại lâu
     ↓
Dữ liệu cũ lâu bị xóa
     ↓
Stale Data

Vì vậy: TTL không phải cơ chế duy nhất để đảm bảo dữ liệu đúng.

Khi dữ liệu thay đổi, ứng dụng vẫn nên chủ động:

Update Cache
hoặc:
Evict Cache

7.10. Serialization Error

7.10.1. Serialization là gì?

Serialization là quá trình chuyển Object thành dạng dữ liệu có thể lưu trữ hoặc truyền đi.

Ví dụ:

Java
Product product = new Product();

Redis không trực tiếp hiểu Object Java theo cách mà Java đang giữ trong RAM.

Ứng dụng cần chuyển Object thành dạng phù hợp.

Ví dụ JSON:

JSON
{
    "id": 1,
    "name": "Laptop",
    "price": 15000000
}

7.10.2. Serialization Error

Ví dụ ứng dụng đang lưu Product với một Serializer.

Sau đó thay đổi cấu trúc Class:

Java
class Product {
    private Integer id;
    private String name;
    private BigDecimal price;

    // thêm field mới
    private String description;
}

Dữ liệu cũ trong Redis có thể không còn tương thích với cách ứng dụng mới đọc dữ liệu.

Khi đó có thể xuất hiện lỗi Serialization/Deserialization.

7.10.3. Một số nguyên nhân

Serializer không phù hợp
JSON không đúng cấu trúc
Class thay đổi
Kiểu dữ liệu thay đổi
Redis đang chứa dữ liệu được tạo bởi phiên bản ứng dụng cũ
Cache chứa dữ liệu không đúng format

7.10.4. Cách xử lý

Khi thay đổi cấu trúc dữ liệu lớn:

Application Version 1
        ↓
Redis Data Version 1

sang:

Application Version 2
        ↓
Redis Data Version 2

Có thể cần:

Xóa Cache cũ
hoặc sử dụng:
Cache Key Versioning

Ví dụ:

v1:products::1
v2:products::1

7.12. Redis hết bộ nhớ

Redis lưu dữ liệu trong RAM.

Nếu RAM dành cho Redis đã đầy:

Memory
████████████████████
100%

Redis không thể tiếp tục lưu dữ liệu theo cách thông thường nếu không có cơ chế xử lý phù hợp.

7.12.1. Vì sao Redis hết bộ nhớ?

Cache quá nhiều
TTL quá dài
Cache Object quá lớn
Cache danh sách rất lớn
Cache kết quả tìm kiếm quá nhiều
Không giới hạn Cache
Có dữ liệu không bao giờ expire

7.12.2. Cần theo dõi Memory

Có thể kiểm tra thông tin Redis bằng:

Có thể quan tâm đến các thông tin như:

used_memory

Ví dụ used_memory_human:512.50M cho biết Redis đang sử dụng khoảng 512.5 MB theo cách hiển thị của Redis.

7.12.3. Chính sách Eviction

Khi Redis đạt giới hạn bộ nhớ, Redis có thể sử dụng eviction policy tùy cấu hình.

Một số policy phổ biến liên quan đến Cache:

allkeys-lru
allkeys-lfu
volatile-lru
volatile-ttl
noeviction

Ví dụ:

LRU

Least Recently Used

Ưu tiên loại bỏ những key ít được sử dụng gần đây.

LFU

Least Frequently Used

Ưu tiên loại bỏ những key có tần suất sử dụng thấp.

noeviction

Không tự động loại bỏ key để giải phóng bộ nhớ; các thao tác ghi mới có thể thất bại khi đạt giới hạn bộ nhớ.

Việc chọn policy phải dựa trên cách hệ thống sử dụng Redis.

7.13. Xử lý khi Redis bị mất kết nối

Đây là tình huống rất quan trọng trong hệ thống thực tế.

Giả sử:

Client
   ↓
Spring Boot
   ↓
Redis
   X
Connection Failed

Câu hỏi là: Application có tiếp tục hoạt động được không?

Câu trả lời phụ thuộc vào kiến trúc và cách cấu hình ứng dụng.

7.13.1. Nếu Redis chỉ dùng làm Cache

Trong kiến trúc:

Database = Source of Truth
Redis = Cache

thì việc Redis bị lỗi không nhất thiết có nghĩa Database cũng bị lỗi.

Ví dụ:

Redis DOWN
    ↓
Cache không sử dụng được
    ↓
Database vẫn hoạt động

Ứng dụng có thể được thiết kế để xử lý Cache failure và tiếp tục sử dụng Database.

7.13.2. Nhưng không nên mặc định rằng Spring sẽ luôn tự động fallback

Đây là điểm rất quan trọng.

Không nên suy nghĩ:

Redis lỗi
   ↓
Spring tự động bỏ qua Redis
   ↓
Database tự động chạy

Trong mọi cấu hình thì không thể đảm bảo như vậy.

Việc fallback phụ thuộc vào:

Cache configuration
Exception handling
Cache manager
Kiến trúc ứng dụng
Cách ứng dụng sử dụng Redis

7.13.3. Cần phân biệt Cache Failure và Database Failure

Ví dụ:

Redis Error

khác:

MySQL Error

Logger nên phân biệt:

Java
logger.error(
    "Redis cache operation failed, key={}",
    key,
    exception

với:

Java

    "Database operation failed",
    exception
);

Điều này rất quan trọng khi Debug Production.

7.16.1. Quên bật Cache

Java

Sau đó tạo Product D.

Đây là những yếu tố phân biệt việc "biết sử dụng @Cacheable" với việc "biết thiết kế Redis Cache cho một hệ thống thực tế".

Nếu đi tiếp theo mạch giáo trình này, phần sau nên chuyển từ "các vấn đề" sang "cách thiết kế và tối ưu Redis Cache trong hệ thống thực tế", đặc biệt là Cache Invalidation, Cache Stampede/Breakdown/Penetration và chiến lược TTL.

Ghi nhớ trọng tâm
  • Stale Data — Cache cũ hơn Database → @CachePut/@CacheEvict khi dữ liệu thay đổi.
  • Cache không đồng bộ DB — Chọn chiến lược: Update Cache hoặc Evict Cache. Evict đơn giản và an toàn hơn.
  • Cache Stampede — Một Cache quan trọng hết hạn → nhiều request cùng MISS → dùng Lock + TTL hợp lý.
  • Cache Penetration — Request dữ liệu không tồn tại → cache negative result với TTL ngắn + validation.
  • Cache Avalanche — Nhiều Cache hết hạn cùng lúc → Random TTL + warm-up + monitoring.
  • Cache Key phải có namespace rõ ràng (products::1, users::1) để tránh xung đột.
  • TTL không nên quá ngắn (MISS liên tục) cũng không quá dài (Stale Data lâu). Phải dựa trên đặc tính dữ liệu.
  • Serialization Error — Khi đổi cấu trúc class, cần xóa Cache cũ hoặc dùng Cache Key Versioning.
  • Redis Connection Error — Kiểm tra server/host/port/network. Log phân biệt rõ Cache Error vs Database Error.
  • Redis hết RAM — Dùng TTL + eviction policy (allkeys-lru, allkeys-lfu…) + monitoring.
  • Không mặc định Spring tự fallback khi Redis lỗi — phải thiết kế exception handling rõ ràng.
  • Không cache password, token, secret, private key, thông tin thanh toán.
  • Ưu tiên DTO hơn Entity JPA khi cache — tránh Lazy Loading và quan hệ phức tạp.
  • Một hệ thống Cache tốt = đúng dữ liệu + key đúng + TTL hợp lý + serialization ổn định + bảo mật + chịu được Redis failure + không làm Database quá tải.

Java
package com.example.productcache.config;

import org.springframework.cache.CacheManager;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.connection.RedisConnectionFactory;

import java.time.Duration;

@Configuration
@EnableCaching
public class RedisConfig {

    @Bean
    public CacheManager cacheManager(
            RedisConnectionFactory connectionFactory
    ) {

        RedisCacheConfiguration configuration =
                RedisCacheConfiguration.defaultCacheConfig()
                        .entryTtl(Duration.ofMinutes(10));

        return RedisCacheManager
                .builder(connectionFactory)
                .cacheDefaults(configuration)
                .build();
    }
}

Khi đó products::1 có TTL khoảng 10 phút nếu không được cấu hình TTL riêng.

8.4.5. Cấu hình Serialization

Redis cần biết cách chuyển dữ liệu Java thành dữ liệu có thể lưu và đọc lại.

Trong dự án thực tế, JSON thường dễ quan sát và thuận tiện khi kiểm tra dữ liệu.

Một hướng cấu hình là sử dụng StringRedisSerializer cho Key và Jackson JSON serializer cho Value.

Ví dụ:

Java
@Bean
public RedisCacheConfiguration redisCacheConfiguration() {

    return RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .serializeKeysWith(
                    RedisSerializationContext
                            .SerializationPair
                            .fromSerializer(
                                    new StringRedisSerializer()
                            )
            );
}

Với Value, cần lựa chọn Serializer phù hợp với version Spring Data Redis đang sử dụng.

Trong project thực tế, nên cấu hình Serializer một cách rõ ràng thay vì phụ thuộc hoàn toàn vào cấu hình mặc định.

Mục tiêu cần đạt được:

Java Object
     ↓
JSON Serializer
     ↓
Redis
     ↓
JSON
     ↓
Deserializer
     ↓
Java Object

Hit Rate
=
Hit / (Hit + Miss) × 100%

Ví dụ:

Hit = 850
Miss = 150

thì:

Hit Rate
=
850 / (850 + 150)
× 100

= 85%

Có thể xây dựng một bộ đếm
