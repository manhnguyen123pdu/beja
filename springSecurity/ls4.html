1. TỔNG QUAN VỀ JWT

1.1. JWT là gì?

1.1.1. Khái niệm

JWT (JSON Web Token) là một chuẩn token dùng để truyền tải thông tin giữa các bên dưới dạng một chuỗi JSON được mã hóa theo cấu trúc chuẩn.

Trong ứng dụng Web/API, JWT thường được sử dụng để xác thực người dùng (Authentication) và xác định quyền truy cập (Authorization).

Client
   │
   │ username + password
   ▼
Server
   │
   │ xác thực thành công
   ▼
JWT Token
   │
   │ trả về Client
   ▼
Client lưu JWT

Sau đó, mỗi khi Client gọi API:

Client
   │
   │ Authorization: Bearer <JWT>
   ▼
Server
   │
   │ kiểm tra JWT
   ▼
Cho phép / Từ chối

1.1.2. JWT có phải là mã hóa không?

Cần phân biệt:

  • JWT thường được ký (signed) chứ không mặc định được mã hóa.
  • Nội dung Payload có thể được đọc nếu người khác có được token.
  • Chữ ký dùng để kiểm tra token có bị thay đổi hay không.
JWT
 │
 ├── Header
 ├── Payload      ← Có thể đọc
 └── Signature    ← Dùng để kiểm tra tính hợp lệ

Không nên đưa thông tin bí mật vào Payload, chẳng hạn:

  • ❌ password
  • ❌ số thẻ ngân hàng
  • ❌ secret key

1.2. JWT dùng để làm gì?

JWT thường được sử dụng trong hai mục đích chính.

1.2.1. Authentication – Xác thực

Xác định: "Người đang gọi API là ai?"

Username: admin
Password: 123456

Server xác thực thành công và tạo JWT:

JWT
↓
Client

Sau đó Client gửi JWT trong các request tiếp theo.

1.2.2. Authorization – Phân quyền

Sau khi biết người dùng là ai, Server có thể kiểm tra người đó có quyền gì.

Ví dụ Payload
{
  "sub": "admin",
  "role": "ADMIN"
}

Server có thể kiểm tra:

role = ADMIN
       ↓
Cho phép /admin/users

Trong khi:

role = USER
       ↓
Không được phép /admin/users

1.3. Cấu trúc JWT

JWT có cấu trúc:

Header.Payload.Signature

Ba phần được ngăn cách bởi dấu ..

xxxxx.yyyyy.zzzzz
  • xxxxx → Header
  • yyyyy → Payload
  • zzzzz → Signature

JWT sử dụng Base64URL encoding cho Header và Payload.

1.4. Header

1.4.1. Khái niệm

Header chứa thông tin mô tả JWT.

Ví dụ Header
{
  "alg": "HS256",
  "typ": "JWT"
}

1.4.2. Các thông tin thường gặp

  • alg: Cho biết thuật toán được sử dụng để tạo chữ ký. Ví dụ: HS256, RS256, ES256.
  • typ: Cho biết loại token. Thông thường: "typ": "JWT".

1.5. Payload

1.5.1. Khái niệm

Payload chứa các thông tin gọi là Claims.

Ví dụ Payload
{
  "sub": "admin",
  "role": "ADMIN",
  "iat": 1720000000,
  "exp": 1720003600
}

1.5.2. Một số Claim phổ biến

ClaimÝ nghĩa
subSubject – đối tượng của token
iatThời điểm token được tạo
expThời điểm token hết hạn
issIssuer – bên phát hành
audAudience – đối tượng nhận token

Lưu ý: Payload không phải nơi để lưu dữ liệu bí mật.

1.6. Signature

1.6.1. Khái niệm

Signature là phần chữ ký được sử dụng để kiểm tra:

  • Token có được tạo bởi bên hợp lệ hay không.
  • Token có bị thay đổi sau khi tạo hay không.

Ví dụ với HS256:

Signature =
HMACSHA256(
    Base64URL(Header) + "." + Base64URL(Payload),
    SecretKey
)
Header
   +
Payload
   +
Secret Key
   ↓
Signature

1.6.2. Tại sao cần Signature?

Giả sử JWT ban đầu:

JWT ban đầu
{
  "sub": "user",
  "role": "USER"
}

Kẻ tấn công sửa thành:

JWT bị sửa
{
  "sub": "user",
  "role": "ADMIN"
}
Payload mới
    ↓
Tạo lại Signature
    ↓
Không khớp Signature cũ
    ↓
Token không hợp lệ

Vì vậy người dùng không thể đơn giản sửa Payload để tự nâng quyền.

1.8. JWT khác Basic Authentication như thế nào?

1.8.1. Basic Authentication

Client gửi username và password trong mỗi request.

Authorization: Basic base64(username:password)
Request
   │
   ├── Username
   └── Password
          │
          ▼
       Server

Mỗi request cần gửi lại thông tin xác thực.

1.8.2. JWT Authentication

Client đăng nhập một lần:

Username + Password
        ↓
      Server
        ↓
       JWT

Sau đó các request tiếp theo gửi JWT:

Authorization: Bearer <JWT>

Điểm quan trọng: JWT không phải là một phương thức mã hóa password. JWT là token được sử dụng sau quá trình xác thực.

1.9. JWT khác Session Authentication như thế nào?

Đây là phần rất quan trọng.

1.9.1. Session Authentication

Sau khi login:

Client
   │
   │ username + password
   ▼

   │
   │ tạo Session
   ▼

   │
   ▼
Client

Server lưu thông tin Session:

Server
 │
 └── Session
       ├── sessionId
       ├── username
       └── authentication

Client thường giữ Session ID trong Cookie.

Request tiếp theo:

Client
   │

   ▼
Server
   │
   ▼
Tìm Session
   │
   ▼
Xác định User

1.10. Stateless Authentication là gì?

1.10.1. Stateful

Stateful nghĩa là Server phải duy trì trạng thái của Client.

Client
   │
   │ Session ID
   ▼
Server
   │
   ▼
Session Store
   │
   └── User = admin

Server phải biết:

Session ID abc123
        ↓
User admin

1.10.2. Stateless

Stateless Authentication nghĩa là Server không cần lưu trạng thái đăng nhập của từng Client giữa các request.

Mỗi request chứa đủ thông tin để Server xác định và xác thực người dùng.

Request
   │
   ├── URL
   ├── Method
   └── JWT
        │
        ▼
      Server
        │
        ├── Verify Signature
        ├── Check Expiration
        └── Read Claims
                │
                ▼
          Authentication

Server không cần truy vấn:

Session ID
      ↓
Session Store
      ↓
User

1.11. Vì sao JWT thường được dùng cho Stateless Authentication?

JWT có thể chứa:

Ví dụ JWT Payload
{
  "sub": "admin",
  "role": "ADMIN",
  "exp": 1720003600
}

Khi nhận request:

JWT
 ↓
Verify
 ↓
Đọc sub
 ↓
Đọc role
 ↓
Tạo Authentication

Do đó Server có thể xử lý request dựa trên token mà không cần duy trì Session cho người dùng.

10. Cho phép / từ chối truy cập
Ghi nhớ trọng tâm
  • JWT là chuỗi token gồm 3 phần: Header, Payload, Signature.
  • Authentication → xác thực người dùng.
  • Authorization → phân quyền dựa trên claims (role).
  • JWT thường được ký, không mã hóa payload.
  • JWT giúp Stateless, server không cần lưu session.
  • Không đưa thông tin bí mật (password, secret) vào Payload.
  • JWT khác Basic Auth (gửi user/pass mỗi request) và khác Session Auth (server lưu session).
