1.1. Authentication là gì?

1. Authentication nghĩa là gì?

Authentication là quá trình xác thực danh tính của người dùng.

Nói đơn giản: Hệ thống cần kiểm tra xem người đang gửi request có thực sự là người dùng mà họ tự nhận hay không.

Ví dụ người dùng đăng nhập:

  • Username: manh123
  • Password: 123456

Hệ thống sẽ kiểm tra:

Username có tồn tại không?
        ↓
Có
        ↓
Password có đúng không?
        ↓
Đúng
        ↓
Authentication thành công

Sau khi xác thực thành công, hệ thống biết: Người dùng hiện tại là ai?

Ví dụ:

  • User ID: 1
  • Username: manh123
  • Role: ADMIN

2. Vấn đề sau khi đăng nhập

Giả sử người dùng gửi request đăng nhập: POST /login

Sau khi đăng nhập thành công:

  • Username: manh123
  • Password: 123456

Server kiểm tra: Đúng thông tin

Bây giờ người dùng tiếp tục gọi: GET /profile

Server cần biết: Request này được gửi bởi ai?

Nếu không có cơ chế lưu trạng thái đăng nhập, server sẽ không biết người dùng hiện tại là ai.

Người dùng lại tiếp tục gọi: GET /orders. Server vẫn phải biết: Ai đang gửi request này?

Vì HTTP là stateless.

3. HTTP là Stateless

HTTP không tự động ghi nhớ người dùng.

Ví dụ:

Request 1

POST /login
Username: manh123
Password: 123456
Server xác thực thành công.

Sau đó:
Request 2

GET /profile
Về bản chất, request thứ 2 là một request mới.
Server không tự động biết:
Request này có phải của manh123 không?

Do đó chúng ta cần một cơ chế để duy trì trạng thái đăng nhập. Hai cách phổ biến là: Session và JWT.

1.2. Session-based Authentication

1. Session là gì?

Session-based Authentication là cơ chế xác thực trong đó: Server lưu thông tin trạng thái đăng nhập của người dùng.

Sau khi người dùng đăng nhập thành công, server tạo một Session.

Ví dụ:

  • Session ID: abc123xyz

Server lưu thông tin:

Session ID: abc123xyz

User:
    id = 1
    username = manh123
    role = ADMIN

Sau đó server gửi Session ID về cho client. Thông thường Session ID được lưu trong Cookie.

1.3. JWT-based Authentication

1. JWT là gì?

JWT là viết tắt của: JSON Web Token

JWT là một chuỗi token chứa thông tin đã được ký bằng một khóa bí mật hoặc khóa bất đối xứng.

Ví dụ:

eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiJtYW5oMTIzIiwicm9sZSI6IkFETUlOIn0
.
abcxyzsignature

JWT thường gồm 3 phần: HEADER . PAYLOAD . SIGNATURE

Ví dụ: xxxxx.yyyyy.zzzzz

2. Header

Header chứa thông tin về loại token và thuật toán ký.

Ví dụ:

Header
{
    "alg": "HS256",
    "typ": "JWT"
}

Ý nghĩa: HS256 là thuật toán được sử dụng để ký token.

3. Payload

Payload chứa thông tin về người dùng.

Ví dụ:

Payload
{
    "sub": "manh123",
    "role": "ADMIN"
}

Ngoài ra thường có: sub, iat, exp

Payload đầy đủ
{
    "sub": "manh123",
    "iat": 1760000000,
    "exp": 1760100000
}
Thuộc tính Ý nghĩa
sub Subject - người dùng
iat Thời gian tạo token
exp Thời gian hết hạn

4. Signature

Signature dùng để đảm bảo token không bị thay đổi.

Ví dụ:

Header
+
Payload
+
Secret Key
        ↓
Signature

Nếu hacker thay đổi {"role": "ADMIN"} thì Signature sẽ không còn hợp lệ.

Server kiểm tra:
Signature hợp lệ?
        ↓
Không
        ↓
Token không hợp lệ

1.5. Ưu điểm và hạn chế của Session

Ưu điểm

1. Dễ quản lý đăng nhập

Server quản lý Session. Muốn logout: Xóa Session → Ngay lập tức Session không còn hiệu lực.

2. Có thể thu hồi Session

Ví dụ: User bị khóa. Server có thể: Xóa toàn bộ Session của User → Người dùng sẽ bị logout.

3. Không cần chứa nhiều thông tin nhạy cảm trên Client

Client thường chỉ giữ: Session ID. Thông tin người dùng nằm phía server.

4. Phù hợp với ứng dụng Web truyền thống

Ví dụ: Website quản lý nội bộ, Website thương mại điện tử truyền thống, Ứng dụng sử dụng Spring MVC. Session hoạt động rất tự nhiên với Cookie của trình duyệt.

Hạn chế

1. Server phải lưu Session

Nếu có: 10.000 User online, Server cần quản lý Session của 10.000 User.

2. Khó scale nhiều Server hơn

               ┌── Server 1
Client ────────►│
                └── Server 2

User đăng nhập ở Server 1, Session nằm tại Server 1. Request tiếp theo lại đi tới Server 2. Server 2 không có Session.

Cần giải pháp như: Sticky Session hoặc Redis Session.

3. Session phụ thuộc vào Server

Nếu Server restart và Session chỉ được lưu trong memory: Session mất → User bị logout.

1.6. Ưu điểm và hạn chế của JWT

Ưu điểm

1. Stateless

Server không cần lưu Session của từng User. Request nào cũng mang token: Authorization: Bearer JWT. Server chỉ cần: Verify JWT.

2. Dễ scale

              ┌── Server 1
Client ───────►│
               ├── Server 2
               │
               └── Server 3

Server nào cũng có thể kiểm tra JWT. Không cần biết User trước đó đăng nhập ở server nào.

3. Phù hợp REST API

Frontend và Backend tách riêng: React, Vue, Angular, Mobile App → REST API → Spring Boot. Client chỉ cần gửi: Authorization: Bearer TOKEN.

4. Hoạt động tốt với Mobile

Mobile App không hoạt động giống Browser truyền thống. JWT giúp Mobile dễ gửi token trong request. Ví dụ: Android, iOS, Flutter, React Native đều có thể gọi API bằng: Authorization: Bearer TOKEN.

Hạn chế

1. Logout phức tạp hơn

Với Session: Xóa Session là xong. Nhưng JWT đã được phát hành và có thể còn hiệu lực đến khi hết hạn.

Ví dụ: Token hết hạn sau 1 giờ. User logout sau 10 phút. Nếu chỉ sử dụng access token đơn thuần thì token đó về lý thuyết vẫn có thể được dùng trong thời gian còn lại nếu bị giữ lại.

Vì vậy thực tế thường dùng: Access Token + Refresh Token hoặc cơ chế thu hồi/blacklist tùy yêu cầu hệ thống.

2. Không nên nhét quá nhiều thông tin vào JWT

Ví dụ không nên:

{
    "username": "manh123",
    "email": "...",
    "address": "...",
    "phone": "...",
    "password": "..."
}

JWT không phải nơi để chứa toàn bộ User. Thông thường chỉ nên chứa thông tin cần thiết như: {"sub": "manh123", "iat": "...", "exp": "..."}

3. Token bị lộ có thể bị sử dụng

Nếu attacker lấy được JWT hợp lệ: JWT hợp lệ + Chưa hết hạn thì token có thể bị sử dụng như thông tin xác thực.

Do đó cần: HTTPS, Token expiration, Bảo vệ nơi lưu token, Không đưa thông tin nhạy cảm vào payload.

1.7. Khi nào sử dụng Session?

Nên cân nhắc Session khi xây dựng:

  1. Web Application truyền thống – Ví dụ: Spring MVC, Thymeleaf, JSP. Frontend và Backend thường gắn liền với nhau.
  2. Ứng dụng quản trị nội bộ – Ví dụ: Hệ thống quản lý nhân viên, Hệ thống quản lý bệnh viện, Hệ thống quản lý kho. Nếu hệ thống không yêu cầu kiến trúc phân tán phức tạp, Session có thể là lựa chọn đơn giản.
  3. Cần quản lý Session trực tiếp – Ví dụ: Logout ngay lập tức, Khóa tài khoản, Đăng xuất khỏi tất cả thiết bị, Quản lý thiết bị đăng nhập. Session có thể thuận tiện vì trạng thái nằm phía server.

1.8. Khi nào sử dụng JWT?

JWT thường phù hợp với:

  1. REST API – Ví dụ: Spring Boot REST API với Client là React, Vue, Angular. Giao tiếp: Frontend → HTTP → REST API.
  2. Mobile Application – Ví dụ: Android, iOS, Flutter, React Native. Mobile gửi token: Authorization: Bearer TOKEN.
  3. Frontend và Backend tách riêng – Ví dụ: React Application → Spring Boot API → MySQL. JWT rất phù hợp với mô hình này.
  4. Hệ thống nhiều Server – Ví dụ: Load Balancer → API Server 1, API Server 2, API Server 3. JWT giúp mỗi server có thể tự xác minh request mà không nhất thiết phải lưu session của từng user trên chính server đó.

2. KIẾN TRÚC JWT AUTHENTICATION

Sau khi đã hiểu JWT là gì và vì sao REST API thường sử dụng JWT, phần này sẽ tìm hiểu kiến trúc tổng quát của JWT Authentication trong Spring Boot.

Mục tiêu của phần này không phải là đi sâu vào từng dòng code ngay lập tức, mà là giúp người học nhìn được toàn bộ luồng hoạt động của hệ thống.

JWT Authentication có thể chia thành 2 luồng chính:

  • Luồng đăng nhập – JWT Login Flow
  • Luồng xử lý Request sau khi người dùng đã đăng nhập

2.1. JWT Login Flow

Khi người dùng đăng nhập, hệ thống cần thực hiện hai nhiệm vụ:

  • Kiểm tra thông tin đăng nhập có hợp lệ hay không.
  • Nếu hợp lệ, tạo JWT và trả về cho Client.

Luồng tổng quát:

Client
   ↓
POST /api/auth/login
   ↓
AuthController
   ↓
AuthService
   ↓
AuthenticationManager
   ↓
Authentication thành công
   ↓
JwtService
   ↓
Access Token

1. Client gửi yêu cầu đăng nhập

Người dùng nhập: Username và Password

Ví dụ:

Login Request 
{
    "username": "manh123",
    "password": "123456"
}

Client gửi request: POST /api/auth/login

Body:

Body
{
    "username": "manh123",
    "password": "123456"
}

CLIENT
   │
   │ POST /api/auth/login
   │ username + password
   ▼
SERVER

Ở thời điểm này, Client chưa có JWT. Do đó, đây là request dùng để xác thực Username và Password.

2. AuthController nhận Request

Request đầu tiên đi vào: AuthController

Client
   ↓
AuthController

AuthController có nhiệm vụ chính là:

  • Nhận Login Request.
  • Chuyển dữ liệu xuống tầng Service.
  • Trả Response về Client.

Về mặt kiến trúc:

AuthController
        ↓
AuthService

Controller không nên trực tiếp xử lý toàn bộ logic xác thực. Ví dụ không nên để Controller tự: Tìm User → Kiểm tra Password → Tạo JWT → Trả Token

Thay vào đó:

Controller → Service

Controller chỉ đóng vai trò là điểm tiếp nhận HTTP Request.

3. AuthService xử lý nghiệp vụ đăng nhập

Sau khi nhận request từ Controller:

AuthController → AuthService

AuthService sẽ điều phối quá trình đăng nhập. Tại đây, hệ thống cần thực hiện:

        ↓

        ↓

Nếu thông tin chính xác:

Authentication thành công → Tạo JWT

    │
    │ authenticate()
    ▼

Đây là thành phần của Spring Security mà chúng ta đã học ở phần Authentication trước đó.

Nhiệm vụ của nó là:

Nhận thông tin đăng nhập
        ↓
Thực hiện Authentication
        ↓
Trả kết quả Authentication

1. AuthenticationManager

Chúng ta đã biết: AuthenticationManager có nhiệm vụ thực hiện Authentication.

Trong Login Flow:

Trong bài JWT, chúng ta chỉ sử dụng lại thành phần này.

2. UserDetailsService

Username → UserDetailsService → Database → UserDetails

Trong bài JWT, chúng ta không học lại cách xây dựng UserDetailsService. Chúng ta chỉ tái sử dụng.

Password trong Database thường được mã hóa. Do đó cần: PasswordEncoder để kiểm tra:

Password người dùng nhập → So sánh với → Password đã mã hóa trong Database

JWT không thay thế PasswordEncoder. JWT chỉ được tạo sau khi Authentication thành công.

4. Spring Security

Spring Security vẫn chịu trách nhiệm bảo vệ các API.

Ví dụ: /api/auth/login có thể được: permitAll()

Trong khi: /api/users, /api/orders, /api/admin cần: authenticated()

JWT chỉ thay đổi cách Spring Security xác định: User hiện tại là ai?

Điểm quan trọng: JWT không thay thế AuthenticationManager, UserDetailsService hay PasswordEncoder. JWT được bổ sung vào sau quá trình xác thực để duy trì trạng thái xác thực giữa các request.

2.4. Những thành phần mới trong bài JWT

Trong phần này, chúng ta sẽ học các thành phần mới sau.

1. JWT

JWT là: JSON Web Token

Đây là token được cấp cho Client sau khi đăng nhập thành công.

Ví dụ: xxxxx.yyyyy.zzzzz

Sau khi Login thành công:

Access Token được Client sử dụng để truy cập các API được bảo vệ.

Ví dụ: Authorization: Bearer ACCESS_TOKEN

Mỗi request có thể mang Access Token để chứng minh danh tính người dùng.

3. JwtService

JwtService là Service chúng ta xây dựng để xử lý các công việc liên quan đến JWT.

Ví dụ: Generate JWT, Decode JWT, Validate JWT, Lấy Username từ JWT, Kiểm tra thời gian hết hạn

JwtDecoder được sử dụng để: Đọc và xác thực JWT

Bearer JWT → JwtDecoder → Kiểm tra Token → Lấy Claims

Ví dụ: JWT → JwtDecoder → sub = manh123

6. Bearer Token

JWT thường được gửi trong HTTP Header: Authorization: Bearer TOKEN

Trong đó:

  • Authorization là tên Header.
  • Bearer là Authentication Scheme.
  • TOKEN là JWT.

Cấu trúc: Authorization: Bearer JWT

Đây là cách phổ biến để Client gửi Access Token đến REST API.

7. Claims

Claims là các thông tin được chứa trong JWT.

Ví dụ:

Claims
{
    "sub": "manh123",
    "role": "ADMIN",
    "iat": 1760000000,
    "exp": 1760100000
}
Claim Ý nghĩa
sub Subject – định danh người dùng
iat Issued At – thời điểm tạo token
exp Expiration – thời điểm hết hạn

Ngoài ra chúng ta có thể tạo thêm Custom Claims.

Ví dụ: {"sub": "manh123", "role": "ADMIN"}

Tuy nhiên không nên đưa toàn bộ thông tin User vào JWT.

8. Secret Key

Secret Key được sử dụng để ký JWT.

Claims + Secret Key → JwtEncoder → JWT

Khi nhận JWT:

JWT + Secret Key → Verify

Nếu JWT bị thay đổi:

Payload thay đổi → Signature không còn hợp lệ → JWT bị từ chối

Secret Key cần được bảo vệ. Không nên: Hard-code trực tiếp vào Controller. Thông thường được cấu hình riêng cho ứng dụng.

9. Expiration

JWT không nên có thời hạn vô hạn.

Ví dụ: Access Token có hiệu lực 1 giờ

Claims có thể chứa: exp

iat = 10:00
exp = 11:00

Sau 11:00:

JWT hết hạn → Không thể sử dụng → Client cần xác thực lại hoặc sử dụng cơ chế refresh token nếu hệ thống có triển khai

Expiration giúp giảm rủi ro nếu Access Token bị lộ.

public class CustomUserDetailsService
        implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {

                .findByUsername(username)
                .orElseThrow(() ->
                        new UsernameNotFoundException(
                                "User not found"
                        )
                );

                .withUsername(user.getUsername())
                .password(user.getPassword())
                .roles(user.getRole())
                .build();
    }
}

Phần này tập trung giải thích cấu trúc và nội dung của JWT trước khi sang phần tiếp theo xây dựng JwtService.

4.1. JWT là gì?

JWT là viết tắt của: JSON Web Token

JWT là một dạng token được sử dụng để truyền thông tin giữa các bên dưới dạng JSON, thường được sử dụng trong Authentication và Authorization.

Trong hệ thống Login:

Username + Password
        ↓
Authentication thành công
        ↓
Tạo JWT
        ↓
Trả JWT cho Client

Client sẽ lưu Access Token và sử dụng nó trong những request tiếp theo.

Ví dụ:

JWT Token 
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJtYW5oMTIzIn0.abc123...

Nhìn JWT có vẻ là một chuỗi ký tự ngẫu nhiên, nhưng thực tế nó có cấu trúc rõ ràng.

JWT gồm 3 phần: Header.Payload.Signature

Ba phần được ngăn cách bởi dấu: .

Ví dụ: xxxxx.yyyyy.zzzzz

Trong đó:

  • xxxxx → Header
  • yyyyy → Payload
  • zzzzz → Signature

4.2. JWT dùng để làm gì?

JWT thường được sử dụng để xác thực và truyền thông tin về người dùng giữa Client và Server.

Trong hệ thống của chúng ta, JWT có nhiệm vụ chính là: Giúp Server nhận biết User đã đăng nhập và xác thực User trong các request tiếp theo.

Ví dụ User đăng nhập:

Server
   │
   │ Authentication thành công
   ▼
JWT
   │
   ▼
Client

Sau đó Client gọi: GET /api/users và gửi: Authorization: Bearer JWT 

Server nhận JWT:

 ↓
Xác định User
 ↓
Authentication
 ↓
Cho phép truy cập API
JWT thay thế việc gửi Username + Password mỗi lần

Thay vào đó:

JWT có cấu trúc: Header.Payload.Signature

Ví dụ:

Giải thích:

  • Payload – Chứa các thông tin được gọi là Claims.
  • Signature – Dùng để kiểm tra JWT có bị thay đổi hay không.

Trong phần này tập trung vào: Header, Payload, Claims.

Phần Signature sẽ được giải thích kỹ hơn khi học Secret Key, JwtEncoder và JwtDecoder.

4.4. Header

Header là phần đầu tiên của JWT.

Ví dụ sau khi giải mã Header:

Header

    "alg": "HS256",
    "typ": "JWT"
}
Thuộc tính Ý nghĩa
alg Cho biết thuật toán được sử dụng để ký JWT. Ví dụ: HS256

thì: Header → Phần thứ nhất

Ví dụ:

4.5. Payload

Payload là phần thứ hai của JWT. Đây là nơi chứa các thông tin được gọi là: Claims

Ví dụ:

Payload 
{
    "sub": "manh123",
    "iat": 1760000000,
    "exp": 1760003600
}

Có thể hiểu:

Payload → Chứa Claims → Thông tin về User / Token

Ví dụ: sub = manh123 có thể biểu thị User đang được xác thực.

Payload có phải là dữ liệu bí mật không?

Không.

Đây là điểm cực kỳ quan trọng khi dạy JWT.

JWT được encode, không đồng nghĩa với encrypt.

Client có thể Decode Payload để đọc nội dung.

Ví dụ nếu Payload chứa:

{
    "sub": "manh123",
    "role": "ADMIN"
}

Do đó không nên đưa thông tin nhạy cảm vào Payload, chẳng hạn:

  • Password
  • Số thẻ ngân hàng
  • Thông tin bí mật

4.6. Claims

Claims là các thông tin được chứa bên trong Payload của JWT.

Ví dụ:

Claims
{
    "sub": "manh123",
    "role": "ADMIN",
    "iat": 1760000000,
    "exp": 1760003600
}

Trong đó mỗi cặp: key : value là một Claim.

Ví dụ:

  • sub → manh123
  • role → ADMIN
  • iat → thời điểm tạo
  • exp → thời điểm hết hạn

1. sub – Subject

sub viết tắt của: Subject

Thường được sử dụng để xác định đối tượng mà JWT đại diện cho.

Ví dụ:

sub
{
    "sub": "manh123"
}

Trong hệ thống của chúng ta có thể hiểu: JWT này thuộc về User "manh123"

2. iat – Issued At

iat viết tắt của: Issued At

Cho biết thời điểm JWT được tạo.

Ví dụ:

iat
{
    "iat": 1760000000
}

3. exp – Expiration Time

exp là thời điểm JWT hết hạn.

Ví dụ:

exp
{
    "exp": 1760003600
}

Khi thời gian hiện tại vượt quá exp:

JWT → Đã hết hạn → Không được chấp nhận

4. Custom Claims

Ngoài các Claim tiêu chuẩn, chúng ta có thể thêm Claim riêng.

Ví dụ:

Custom Claims 
{
    "sub": "manh123",
    "role": "ADMIN"
}

Trong đó:

  • sub là Claim phổ biến.
  • role là Custom Claim do ứng dụng tự định nghĩa.

Có thể thêm:

Ví dụ

    "sub": "manh123",

Bây giờ chúng ta xây dựng method:

Mục tiêu:

Code:

generateToken() 
public String generateToken(UserDetails userDetails) {

    return Jwts.builder()

            .subject(userDetails.getUsername())

            .claim(
                    "role",
                    userDetails.getAuthorities()
                            .stream()
                            .findFirst()
                            .map(GrantedAuthority::getAuthority)
                            .orElse("")
            )

            .issuedAt(new Date())

            .expiration(
                    new Date(
                            System.currentTimeMillis()
                                    + expiration
                    )
            )

            .signWith(getKey())

            .compact();
}

Bây giờ chúng ta phân tích từng phần.

    "sub": "manh123",
    "role": "ROLE_ADMIN"
}

5.15. Hoàn thiện JwtService

Sau khi ghép tất cả các phần:

JwtService.java 
package com.example.demo.service;

import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.util.Date;

@Service
public class JwtService {

    @Value("${jwt.secret-key}")
    private String secretKey;

    @Value("${jwt.expiration}")
    private long expiration;

    public String generateToken(UserDetails userDetails) {

        return Jwts.builder()

                // Subject
                .subject(userDetails.getUsername())

                // Custom Claim
                .claim(
                        "role",
                        userDetails.getAuthorities()
                                .stream()
                                .findFirst()
                                .map(GrantedAuthority::getAuthority)
                                .orElse("")
                )

                // Thời điểm tạo Token
                .issuedAt(new Date())

                // Thời điểm hết hạn
                .expiration(
                        new Date(
                                System.currentTimeMillis()
                                        + expiration
                        )
                )

                // Ký JWT
                .signWith(getKey())

                // Tạo JWT String
                .compact();
    }

    private SecretKey getKey() {

        return Keys.hmacShaKeyFor(
                Decoders.BASE64.decode(secretKey)
        );
    }
}

import com.example.security2.entity.User;
import com.example.security2.repository.UserRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class CustomUserDetailsService
        implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {

        User user = userRepository
                .findByUsername(username)
                .orElseThrow(() ->
                        new UsernameNotFoundException(
                                "User not found"
                        )
                );

        return org.springframework.security.core.userdetails.User
                .withUsername(user.getUsername())
                .password(user.getPassword())
                .roles(user.getRole())
                .build();
    }
}

@EnableWebSecurity
@RequiredArgsConstructor

            HttpSecurity http

                .csrf(csrf -> csrf.disable())

                .sessionManagement(session ->
                        session.sessionCreationPolicy(

                        .authenticated()

    }

    @Bean

    ) throws Exception {

        return configuration.getAuthenticationManager();
    }
