1. JWT Claim và Role

1.1. JWT Claim là gì?

JWT Claim là một thông tin được lưu trong phần Payload của JWT.

Ví dụ 
{
    "sub": "user2",
    "exp": 1756903600
}

Trong đó:

  • sub là Claim xác định Subject của Token.
  • exp là Claim xác định thời gian Token hết hạn.

Ngoài các Claim có sẵn, ứng dụng có thể tự thêm các Claim riêng.

1.2. Custom Claim

Custom Claim là Claim do ứng dụng tự định nghĩa để đưa thêm thông tin vào JWT.

Ví dụ 
{
    "sub": "user2",
    "email": "user2@gmail.com",
    "department": "IT"
}

Ở đây:

  • email
  • department

là những thông tin do ứng dụng tự thiết kế.

Ví dụ khác:

Ví dụ 
{
    "sub": "user2",
    "role": "ROLE_USER"
}

Trong trường hợp này, role cũng có thể được thiết kế như một Custom Claim.

1.3. Claim role

Trong hệ thống có phân quyền, JWT thường cần chứa thông tin về Role của người dùng.

Ví dụ 
{
    "sub": "user2",
    "role": "ROLE_USER"
}

Có thể hiểu:

user2
  ↓
ROLE_USER

Khi Server nhận JWT, thông tin Role này có thể được sử dụng trong quá trình Authorization.

Ví dụ:

  • ROLE_USER
  • ROLE_ADMIN
  • ROLE_MANAGER

1.4. Role dạng String

Nếu một User chỉ có một Role, có thể lưu Role dưới dạng String:

Ví dụ 
{
    "sub": "user2",
    "role": "ROLE_USER"
}

Hoặc:

Ví dụ 
{
    "sub": "admin",
    "role": "ROLE_ADMIN"
}

Đây là cách thiết kế đơn giản và dễ sử dụng khi mỗi User chỉ có một Role.

1.5. Role dạng nhiều giá trị

Một User có thể có nhiều Role.

Ví dụ:

user2
 ├── ROLE_USER
 └── ROLE_ADMIN

Khi đó có thể lưu Role dưới dạng mảng:

Ví dụ 
{
    "sub": "user2",
    "role": [
        "ROLE_USER",
        "ROLE_ADMIN"
    ]
}

Như vậy:

  • role
↓
[
    ROLE_USER,
    ROLE_ADMIN
]

Cách này phù hợp khi một User có thể đảm nhận nhiều Role.

1.6. Thiết kế JWT chứa Role

Có hai cách cơ bản cần biết:

Một Role

Ví dụ

    "sub": "user2",

Ý nghĩa:

Ví dụ

        "ROLE_USER",

hasAnyAuthority() hasAnyAuthority("ROLE_USER", "ROLE_ADMIN") ROLE_USER, ROLE_ADMIN

Nếu hệ thống đang tổ chức quyền theo Role

CustomUserDetailsService.java
import com.example.security2.entity.User;
import com.example.security2.repository.UserRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class CustomUserDetailsService
        implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {

        User user = userRepository
                .findByUsername(username)
                .orElseThrow(() ->
                        new UsernameNotFoundException(
                                "User not found"
                        )
                );

        return org.springframework.security.core.userdetails.User
                .withUsername(user.getUsername())
                .password(user.getPassword())
                .roles(user.getRole())
                .build();
    }
}

Giải thích:

  • implements UserDetailsService – Interface của Spring Security để tải User
  • loadUserByUsername(String username) – Phương thức được Spring Security gọi
  • findByUsername(username).orElseThrow(...) – Nếu không tìm thấy User, ném UsernameNotFoundException
  • User.withUsername() – Tạo đối tượng UserDetails từ User trong DB
  • .roles(user.getRole()) – Gán Role cho User

Class này không cần gọi trực tiếp. Spring Security tự gọi nó khi: authenticationManager.authenticate(...) được thực hiện.

10. JwtService

Đây là class chuyên tạo JWT.

JwtService.java 
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.util.Date;

@Service
public class JwtService {

    @Value("${jwt.secret-key}")
    private String secretKey;

    @Value("${jwt.expiration}")
    private long expiration;

    public String generateToken(UserDetails userDetails) {

        return Jwts.builder()

                // Subject
                .subject(userDetails.getUsername())

                // Custom Claim
                .claim(
                        "role",
                        userDetails.getAuthorities()
                                .stream()
                                .findFirst()
                                .map(GrantedAuthority::getAuthority)
                                .orElse("")
                )

                // Thời điểm tạo Token
                .issuedAt(new Date())

                // Thời điểm hết hạn
                .expiration(
                        new Date(
                                System.currentTimeMillis()
                                        + expiration
                        )
                )

                // Ký JWT
                .signWith(getKey())

                // Tạo JWT String
                .compact();
    }

    private SecretKey getKey() {

        return Keys.hmacShaKeyFor(
                Decoders.BASE64.decode(secretKey)
        );
    }
}
Giải thích JwtService:
  • @Value("${jwt.secret-key}") – Lấy Secret Key từ application.yml
  • @Value("${jwt.expiration}") – Lấy thời gian hết hạn từ application.yml
  • subject(userDetails.getUsername()) – Đặt username vào Subject của JWT
  • claim("role", ...) – Thêm Role vào Custom Claim
  • issuedAt(new Date()) – Thời gian tạo Token
  • expiration(...) – Thời gian hết hạn = hiện tại + expiration
  • signWith(getKey()) – Ký JWT bằng Secret Key
  • compact() – Tạo JWT String
  • getKey() – Chuyển Secret Key từ Base64 String → SecretKey

import com.example.security2.DTO.repquert.LoginRequest;
import com.example.security2.DTO.response.LoginResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class AuthService {

    private final AuthenticationManager authenticationManager;

    private final JwtService jwtService;

    public LoginResponse login(LoginRequest request) {

        Authentication authentication =
                authenticationManager.authenticate(
                        new UsernamePasswordAuthenticationToken(
                                request.getUsername(),
                                request.getPassword()
                        )
                );

        UserDetails userDetails =
                (UserDetails) authentication.getPrincipal();

        String token = jwtService.generateToken(userDetails);

        return new LoginResponse(token);
    }
}

  • authentication.getPrincipal() – Lấy UserDetails đã được xác thực
  • jwtService.generateToken(userDetails) – Tạo JWT
  • Trả về LoginResponse chứa Access Token

SecurityConfig.java 
package com.example.demosecurity.config;

import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import lombok.RequiredArgsConstructor;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;

import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.oauth2.jwt.JwtDecoder;
import org.springframework.security.oauth2.jwt.NimbusJwtDecoder;

import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationConverter;
import org.springframework.security.oauth2.server.resource.authentication.JwtGrantedAuthoritiesConverter;

import org.springframework.security.web.SecurityFilterChain;

import javax.crypto.SecretKey;

@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    @Value("${jwt.secret-key}")
    private String secretKeyValue;

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http
    ) throws Exception {

        http
                .csrf(csrf -> csrf.disable())

                .sessionManagement(session ->
                        session.sessionCreationPolicy(
                                SessionCreationPolicy.STATELESS
                        )
                )

                .authorizeHttpRequests(auth -> auth

                        .requestMatchers(
                                "/api/auth/login"
                        ).permitAll()

                        .requestMatchers(
                                "/api/demo/user"
                        ).hasAnyRole("USER", "ADMIN")

                        .anyRequest()
                        .authenticated()
                )

                .oauth2ResourceServer(oauth2 ->
                        oauth2.jwt(jwt ->
                                jwt.jwtAuthenticationConverter(
                                        jwtAuthenticationConverter()
                                )
                        )
                );

        return http.build();
    }

    @Bean
    public JwtDecoder jwtDecoder() {

        SecretKey secretKey = Keys.hmacShaKeyFor(
                Decoders.BASE64.decode(secretKeyValue)
        );

        return NimbusJwtDecoder
                .withSecretKey(secretKey)
                .build();
    }

    @Bean
    public JwtAuthenticationConverter jwtAuthenticationConverter() {

        JwtGrantedAuthoritiesConverter authoritiesConverter =
                new JwtGrantedAuthoritiesConverter();

        // Lấy quyền từ claim "role"
        authoritiesConverter.setAuthoritiesClaimName("role");

        // JWT đã có ROLE_USER nên không thêm tiền tố
        authoritiesConverter.setAuthorityPrefix("");

        JwtAuthenticationConverter converter =
                new JwtAuthenticationConverter();

        converter.setJwtGrantedAuthoritiesConverter(
                authoritiesConverter
        );

        return converter;
    }

    @Bean
    public PasswordEncoder passwordEncoder() {

        return new BCryptPasswordEncoder();
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration configuration
    ) throws Exception {

        return configuration.getAuthenticationManager();
    }
}
Giải thích SecurityConfig:
  • @EnableWebSecurity – Kích hoạt Spring Security
  • csrf().disable() – Tắt CSRF (phù hợp với REST API)
  • sessionCreationPolicy(SessionCreationPolicy.STATELESS) – Không tạo Session (Stateless)
  • requestMatchers("/api/auth/login").permitAll() – Cho phép truy cập login không cần xác thực
  • anyRequest().authenticated() – Tất cả API khác cần xác thực
  • BCryptPasswordEncoder – Mã hóa password
  • authenticationManager – Bean để xác thực

1. Method Security

Method Security là cơ chế của Spring Security cho phép kiểm tra quyền truy cập trực tiếp trên Method của Controller, Service hoặc Bean.

Thay vì chỉ kiểm tra quyền dựa trên URL, Method Security cho phép xác định:

User nào được phép thực hiện Method nào.

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Chỉ user có ADMIN mới được phép thực hiện Method deleteUser().

1.1. @EnableMethodSecurity

@EnableMethodSecurity dùng để bật chức năng Method Security trong Spring Security.

Java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {
}

Sau khi bật, có thể sử dụng các annotation như:

Java
@PreAuthorize
@PostAuthorize
@Secured

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Nếu không bật Method Security thì các annotation bảo vệ Method sẽ không hoạt động.

1.2. Cấu hình Method Security

Method Security được cấu hình thông qua:

Java
@EnableMethodSecurity

Ví dụ:

Java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    // Security configuration
}

Sau đó có thể đặt annotation bảo mật trên Method:

Java
@Service
public class UserService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long id) {
        // Xử lý nghiệp vụ
    }
}

Có thể sử dụng Method Security ở:

Controller
    ↓
Method Security

Service
    ↓
Method Security

Trong đó, Service thường là vị trí phù hợp khi quyền liên quan đến nghiệp vụ của hệ thống.

1.3. Khi nào sử dụng Method Security?

Sử dụng Method Security khi cần phân quyền chi tiết ở mức Method.

Ví dụ đơn giản:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Hoặc khi điều kiện phức tạp hơn:

Java
@PreAuthorize(
    "hasRole('ADMIN') or #userId == authentication.principal.id"
)
public User getUser(Long userId) {
}

Method Security đặc biệt hữu ích khi:

  • Phân quyền theo Role.
  • Phân quyền theo Authority.
  • Kiểm tra user hiện tại.
  • Kiểm tra tham số của Method.
  • Bảo vệ nghiệp vụ tại Service.

Có thể hình dung:

SecurityFilterChain
        ↓
   Bảo vệ Request/URL
        ↓
     Controller
        ↓
   Method Security
        ↓
      Service
        ↓
   Business Logic
Tóm lại

SecurityFilterChain chủ yếu kiểm soát API/URL, còn Method Security cho phép kiểm soát quyền thực hiện từng Method, giúp phân quyền chi tiết và linh hoạt hơn.

2. @PreAuthorize

@PreAuthorize là annotation của Spring Security dùng để kiểm tra quyền truy cập trước khi Method được thực thi.

Đây là một trong những annotation quan trọng nhất khi sử dụng Method Security.

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    // Logic xóa user
}

Khi Method được gọi, Spring Security sẽ kiểm tra biểu thức:

Java
hasRole('ADMIN')

Nếu điều kiện đúng → Method được phép chạy.

Nếu điều kiện sai → Method không được thực thi và Spring Security từ chối quyền truy cập.

2.1.1. @PreAuthorize là gì?

Cú pháp tổng quát:

Java

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Trong đó:

@PreAuthorize
      ↓
Annotation dùng để kiểm tra quyền

"hasRole('ADMIN')"
      ↓
Điều kiện kiểm tra

      ↓
Method được bảo vệ

Tên PreAuthorize có thể hiểu là:

Pre = trước
Authorize = phân quyền

→ Kiểm tra quyền trước khi thực hiện Method.

2.1.2. Điều kiện phải đúng thì Method mới chạy

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    System.out.println("Xóa user");
}

Luồng hoạt động:

Client
   ↓
Request
   ↓
Spring Security
   ↓
Authentication
   ↓
Gọi deleteUser()
   ↓
@PreAuthorize kiểm tra
   ↓
hasRole('ADMIN') ?
   ↓
 ┌───────────────┐
 │               │
ĐÚNG           SAI
 │               │
 ↓               ↓
Method chạy    Từ chối

Điểm quan trọng: Nếu điều kiện của @PreAuthorize không đúng thì phần code bên trong Method không được chạy.

2.1.3. Cần bật Method Security

Muốn sử dụng @PreAuthorize, trước đó phải bật Method Security:

Java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

}

Sau đó mới có thể:

Java
@PreAuthorize("hasRole('ADMIN')")

Nếu không có @EnableMethodSecurity thì @PreAuthorize sẽ không hoạt động như mong muốn.

2.2. Kiểm tra Role

Đây là trường hợp phổ biến nhất.

2.2.1. hasRole()

Cú pháp:

Java
@PreAuthorize("hasRole('ADMIN')")

Ví dụ:

Java
@Service
public class UserService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long id) {
        System.out.println("Xóa user");
    }
}

Ý nghĩa:

Chỉ user có Role ADMIN mới được gọi deleteUser().

2.2.2. Role trong Spring Security

Một Role trong Spring Security thường có dạng:

ROLE_ADMIN
ROLE_USER
ROLE_MANAGER

Ví dụ Authentication chứa:

ROLE_ADMIN

Khi viết:

Java
hasRole('ADMIN')

Spring Security sẽ kiểm tra:

ROLE_ADMIN

Tức là không cần viết ROLE_ trong hasRole().

Đúng:

Java
@PreAuthorize("hasRole('ADMIN')")

Không nên viết:

Java
@PreAuthorize("hasRole('ROLE_ADMIN')")

Vì hasRole() mặc định đã xử lý prefix ROLE_.

2.2.3. Kiểm tra nhiều Role

Nếu muốn cho phép nhiều Role:

Java
@PreAuthorize("hasAnyRole('ADMIN', 'MANAGER')")
public void updateProduct(Long id) {
}

Có nghĩa:

ADMIN OR MANAGER

User có:

ROLE_ADMIN

→ được phép.

User có:

ROLE_MANAGER

→ được phép.

User chỉ có:

ROLE_USER

→ bị từ chối.

2.3. Kiểm tra Authority

Ngoài Role, Spring Security còn có Authority.

Authority thường biểu diễn một quyền cụ thể.

Ví dụ:

USER_READ
USER_CREATE
USER_UPDATE
USER_DELETE
PRODUCT_READ
PRODUCT_DELETE

2.3.1. hasAuthority()

Cú pháp:

Java
@PreAuthorize("hasAuthority('USER_DELETE')")

Ví dụ:

Java
@PreAuthorize("hasAuthority('USER_DELETE')")
public void deleteUser(Long id) {
    System.out.println("Xóa user");
}

Ý nghĩa:

User phải có Authority USER_DELETE mới được thực hiện Method.

2.3.2. hasAnyAuthority()

Có thể kiểm tra nhiều Authority:

Java
@PreAuthorize("hasAnyAuthority('USER_UPDATE', 'USER_ADMIN')")
public void updateUser(Long id) {
}

User chỉ cần có một trong hai quyền:

USER_UPDATE

hoặc:

USER_ADMIN

là được phép.

2.3.3. hasRole() và hasAuthority()

Hai cách này khá giống nhau nhưng mục đích thường khác nhau.

hasRole() hasAuthority()
Kiểm tra Role Authority
Ví dụ ADMIN USER_DELETE
Spring thường lưu ROLE_ADMIN USER_DELETE
Cú pháp hasRole('ADMIN') hasAuthority('USER_DELETE')

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")

→ kiểm tra vai trò.

Trong khi:

Java
@PreAuthorize("hasAuthority('USER_DELETE')")

→ kiểm tra quyền cụ thể.

2.4. Kết hợp nhiều điều kiện

Một trong những điểm mạnh của @PreAuthorize là có thể kết hợp nhiều điều kiện.

Spring Security hỗ trợ các toán tử logic như:

and
or
!

2.4.1. or

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN') or hasRole('MANAGER')")

Có nghĩa:

ADMIN
   OR
MANAGER

Chỉ cần thỏa một điều kiện.

2.4.2. and

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN') and hasAuthority('USER_DELETE')")

User phải đồng thời có:

ROLE_ADMIN

và:

USER_DELETE

Mới được phép.

2.4.3. Phủ định !

Có thể phủ định điều kiện:

Java
@PreAuthorize("!hasRole('BANNED')")

Ý nghĩa:

User không được có Role BANNED.

2.4.4. Kết hợp Role và Authority

Ví dụ:

Java
@PreAuthorize(
    "hasRole('ADMIN') or hasAuthority('USER_DELETE')"
)
public void deleteUser(Long id) {
}

Có hai trường hợp được phép:

ROLE_ADMIN
      ↓
     OK

hoặc:

USER_DELETE
      ↓
     OK

Không có cả hai:

ROLE_USER
      ↓
   Từ chối

2.5. Sử dụng tham số Method

Đây là phần rất quan trọng của @PreAuthorize.

Không chỉ kiểm tra Role hoặc Authority, chúng ta còn có thể sử dụng tham số của Method trong biểu thức.

Ví dụ:

Java
@PreAuthorize("#userId == authentication.principal.id")
public User getUser(Long userId) {
    // ...
}

Ở đây:

Java
#userId

là tham số của Method.

Ví dụ Method:

Java
public User getUser(Long userId)

thì:

#userId

chính là giá trị userId được truyền vào.

2.5.1. Ví dụ thực tế

Giả sử user hiện tại:

id = 10

Client gọi:

HTTP
GET /api/users/10

Method:

Java
@PreAuthorize("#userId == authentication.principal.id")
public User getUser(Long userId) {
    return userRepository.findById(userId);
}

Spring kiểm tra:

#userId = 10

authentication.principal.id = 10

So sánh:

10 == 10

→ true

→ cho phép Method chạy.

Nếu user gọi:

HTTP
GET /api/users/20

thì:

#userId = 20

authentication.principal.id = 10

So sánh:

20 == 10

→ false

→ bị từ chối.

Như vậy user không thể xem thông tin của user khác.

2.5.2. Kết hợp tham số với Role

Ví dụ:

Java
@PreAuthorize(
    "hasRole('ADMIN') or #userId == authentication.principal.id"
)
public User getUser(Long userId) {
    // ...
}

Ý nghĩa:

             Gọi getUser()
                    ↓
          ┌─────────┴─────────┐
          ↓                   ↓
       ADMIN?         Có phải user của mình?
          ↓                   ↓
         Có                  Có
          ↓                   ↓
          └───────── OK ──────┘

Do đó:

  • ADMIN → xem được user bất kỳ.
  • USER → chỉ xem được chính mình.

Đây là một ví dụ rất thực tế của Method Security.

2.6. Kiểm tra quyền của user hiện tại

@PreAuthorize có thể truy cập thông tin về user đang đăng nhập thông qua đối tượng:

Java

Ví dụ:

Java
@PreAuthorize("authentication.name == #username")
public User getUser(String username) {
    // ...
}

Ở đây:

Java
authentication.name

là thông tin username của user hiện tại.

2.6.1. authentication

Spring Security lưu thông tin xác thực của user trong:

SecurityContext
      ↓
Authentication

Có thể hình dung:

SecurityContext
      ↓
Authentication
      ├── username
      ├── authorities
      └── principal

Trong @PreAuthorize, chúng ta có thể sử dụng:

Java
authentication

để kiểm tra user hiện tại.

2.6.2. Lấy username của user hiện tại

Ví dụ:

Java
@PreAuthorize("authentication.name == #username")
public User getUser(String username) {
    return userRepository.findByUsername(username);
}

Nếu user hiện tại là:

nguyenan

và gọi:

Java
getUser("nguyenan")

thì:

authentication.name
        =
"nguyenan"

#username
        =
"nguyenan"

→ điều kiện đúng.

2.6.3. Kiểm tra thông tin trong principal

principal đại diện cho thông tin của user đã xác thực.

Ví dụ:

Java
@PreAuthorize("#userId == authentication.principal.id")
public User getUser(Long userId) {
}

Ở đây:

Java
authentication.principal

là đối tượng đại diện cho user hiện tại.

Nếu project sử dụng UserDetails custom, có thể có:

Java
public class CustomUserDetails implements UserDetails {

    private Long id;
    private String username;
    private String password;

    // ...
}

Khi đó có thể sử dụng:

Java
authentication.principal.id

để lấy ID của user hiện tại.

Tổng hợp @PreAuthorize

3. @PostAuthorize

@PostAuthorize là annotation của Spring Security dùng để kiểm tra quyền sau khi Method đã thực thi và đã có kết quả trả về.

Điểm khác biệt quan trọng nhất:

  • @PreAuthorize → kiểm tra trước khi Method chạy.
  • @PostAuthorize → kiểm tra sau khi Method chạy.

@PostAuthorize đặc biệt hữu ích khi điều kiện phân quyền phụ thuộc vào dữ liệu mà Method trả về.

3.1. Khái niệm

Cú pháp:

Java
@PostAuthorize("biểu_thức_điều_kiện")

Ví dụ:

Java
@PostAuthorize("returnObject.username == authentication.name")
public User getUser(Long id) {
    return userRepository.findById(id).orElseThrow();
}

Ở đây, Spring Security không thể kiểm tra returnObject trước khi Method chạy, vì lúc đó chưa có kết quả trả về.

Do đó, Method sẽ:

Gọi Method
    ↓
Method thực thi
    ↓
Có kết quả User
    ↓
@PostAuthorize kiểm tra
    ↓
Cho phép / từ chối kết quả

3.2. Cơ chế kiểm tra sau khi Method thực thi

Ví dụ:

Java
@PostAuthorize("hasRole('ADMIN')")
public User getUser(Long id) {
    return userRepository.findById(id).orElseThrow();
}

Luồng thực thi:

Client
  ↓
Gọi getUser(10)
  ↓
Method bắt đầu chạy
  ↓
Truy vấn Database
  ↓
User được trả về
  ↓
@PostAuthorize kiểm tra
  ↓
Có ROLE_ADMIN?
  ├── Có → trả kết quả cho Client
  └── Không → từ chối

Điểm cần chú ý: Method đã được thực thi trước khi @PostAuthorize kiểm tra quyền.

Điều này khác hoàn toàn với:

Java
@PreAuthorize(...)

vì @PreAuthorize có thể ngăn Method chạy ngay từ đầu.

Ví dụ

Java
@PostAuthorize("hasRole('ADMIN')")
public User getUser(Long id) {

    System.out.println("Method đang chạy...");

    return userRepository.findById(id)
            .orElseThrow();
}

Nếu user không có ADMIN, dòng:

Java
System.out.println("Method đang chạy...");

vẫn được thực hiện.

Sau đó Spring mới kiểm tra:

@PostAuthorize
      ↓
Có ROLE_ADMIN?
      ↓
Không
      ↓
Từ chối kết quả

Vì vậy, không nên dùng @PostAuthorize thay cho @PreAuthorize trong những trường hợp chỉ cần kiểm tra Role/Authority đơn giản.

3.3. Sử dụng returnObject

Đây là điểm quan trọng nhất của @PostAuthorize.

returnObject đại diện cho đối tượng mà Method vừa trả về.

Ví dụ:

Java
@PostAuthorize("returnObject.username == authentication.name")
public User getUser(Long id) {

    return userRepository.findById(id)
            .orElseThrow();
}

Sau khi Method chạy:

Java
return user;

Spring Security có thể hiểu:

returnObject
      ↓
User vừa được trả về

Sau đó kiểm tra:

Java
returnObject.username == authentication.name

Ví dụ thực tế

Giả sử user hiện tại:

username = "nguyenan"

Method trả về:

User
 ├── id = 10
 └── username = "nguyenan"

Điều kiện:

Java
returnObject.username == authentication.name

trở thành:

"nguyenan" == "nguyenan"

→ true

→ Cho phép trả kết quả.

Nếu Method trả về:

User
 ├── id = 20
 └── username = "nguyenbinh"

thì:

"nguyenbinh" == "nguyenan"

→ false

→ Spring Security từ chối quyền truy cập.

Một ví dụ thực tế hơn

Giả sử API lấy thông tin Order:

Java
@PostAuthorize(
    "returnObject.customer.username == authentication.name"
)
public Order getOrder(Long id) {

    return orderRepository.findById(id)
            .orElseThrow();
}

Method lấy Order từ database trước:

Order
 ├── id = 100
 └── customer
       └── username = "nguyenan"

User hiện tại:

authentication.name = "nguyenan"

Spring kiểm tra:

returnObject.customer.username
              =
authentication.name

Nếu đúng → trả Order.

Nếu sai → từ chối.

Điều này phù hợp với tình huống:

User chỉ được xem những dữ liệu thuộc về chính mình.

returnObject hoạt động với nhiều kiểu dữ liệu

Không chỉ User.

Ví dụ Method trả về Product:

Java
@PostAuthorize("returnObject.owner == authentication.name")
public Product getProduct(Long id) {
    return productRepository.findById(id).orElseThrow();
}

Hoặc Method trả về Order:

Java
@PostAuthorize("returnObject.userId == authentication.principal.id")
public Order getOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}

3.4. So sánh @PreAuthorize và @PostAuthorize

Đây là phần rất quan trọng cần phân biệt.

@PreAuthorize @PostAuthorize
Thời điểm kiểm tra Trước Method Sau Method
Method có được chạy không? Không nếu bị từ chối Có
Có thể dùng returnObject? ❌ Không ✅ Có
Phù hợp kiểm tra Role ✅ Có nhưng thường không cần
Phù hợp kiểm tra kết quả trả về ❌ ✅
Phù hợp kiểm tra dữ liệu sở hữu Có ✅ Rất hữu ích

@PreAuthorize

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Luồng:

Kiểm tra quyền
     ↓
   Đúng?
  ↙    ↘
Có      Không
↓        ↓
Chạy    Không chạy
Method

@PostAuthorize

Java
@PostAuthorize("returnObject.username == authentication.name")
public User getUser(Long id) {
    return userRepository.findById(id).orElseThrow();
}

Luồng:

Method chạy
    ↓
Trả về User
    ↓
Kiểm tra User vừa trả về
    ↓
 ┌─────────────┐
 │             │
Đúng         Sai
 │             │
 ↓             ↓
Trả User     Từ chối

Khi nào dùng cái nào?

Dùng @PreAuthorize khi:

Bạn có thể biết quyền trước khi Method chạy.

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Hoặc:

Java
@PreAuthorize("#userId == authentication.principal.id")
public User updateProfile(Long userId) {
}

Dùng @PostAuthorize khi:

Điều kiện phụ thuộc vào kết quả mà Method trả về.

Ví dụ:

Java
@PostAuthorize(
    "returnObject.username == authentication.name"
)
public User getUser(Long id) {
    return userRepository.findById(id).orElseThrow();
}

Ở đây phải lấy User từ database trước thì mới biết User đó thuộc về ai.

Có thể nhớ đơn giản:

@PreAuthorize
     ↓
KIỂM TRA TRƯỚC
     ↓
Có được chạy Method không?


@PostAuthorize
     ↓
METHOD CHẠY TRƯỚC
     ↓
KIỂM TRA KẾT QUẢ
     ↓
Có được trả kết quả không?
Cốt lõi cần nhớ
  • @PreAuthorize phù hợp với việc kiểm tra quyền trước khi thực hiện nghiệp vụ.
  • @PostAuthorize phù hợp khi cần kiểm tra chính dữ liệu mà Method vừa trả về, thông qua returnObject.

4. @Secured

@Secured là annotation của Spring Security dùng để giới hạn quyền truy cập vào Method dựa trên Role/Authority.

Ví dụ:

Java
@Secured("ROLE_ADMIN")
public void deleteUser(Long id) {
    // ...
}

Chỉ user có ROLE_ADMIN mới được phép thực hiện Method này.

So với @PreAuthorize, @Secured có cú pháp đơn giản hơn, nhưng khả năng biểu đạt điều kiện phân quyền hạn chế hơn.

4.1. Khái niệm

@Secured được đặt trực tiếp trên Method:

Java
@Secured("ROLE_ADMIN")
public void deleteUser(Long id) {
}

Spring Security sẽ kiểm tra quyền của user trước khi Method được thực thi.

Luồng:

Client
   ↓
Request
   ↓
Gọi Method
   ↓
@Secured kiểm tra Role
   ↓
 ┌──────────────┐
 │              │
Đúng           Sai
 │              │
 ↓              ↓
Chạy Method    Từ chối

Có thể khai báo nhiều Role:

Java
@Secured({"ROLE_ADMIN", "ROLE_MANAGER"})
public void updateUser(Long id) {
}

User có một trong các Role được khai báo thì được phép thực hiện.

4.2. Cấu hình securedEnabled

Để sử dụng @Secured, cần bật tính năng Secured trong Method Security.

Java
@Configuration
@EnableMethodSecurity(securedEnabled = true)
public class SecurityConfig {
}

Trong đó:

Java
securedEnabled = true

có nghĩa:

Cho phép Spring Security xử lý annotation @Secured.

Ví dụ đầy đủ:

Java
@Configuration
@EnableMethodSecurity(
    securedEnabled = true
)
public class SecurityConfig {

    // Security configuration
}

Sau đó có thể sử dụng:

Java
@Secured("ROLE_ADMIN")

4.3. Sử dụng @Secured

4.3.1. Kiểm tra một Role

Java
@Secured("ROLE_ADMIN")
public void deleteUser(Long id) {
    System.out.println("Delete user");
}

User phải có:

ROLE_ADMIN

mới được phép.

Lưu ý: Với @Secured, chúng ta thường viết đầy đủ ROLE_:

Java
@Secured("ROLE_ADMIN")

Không viết:

Java
@Secured("ADMIN")

Điểm này khác với @PreAuthorize("hasRole('ADMIN')").

4.3.2. Nhiều Role

Java
@Secured({
    "ROLE_ADMIN",
    "ROLE_MANAGER"
})
public void updateUser(Long id) {
}

Có nghĩa:

ROLE_ADMIN
     OR
ROLE_MANAGER

User có một trong hai Role → được phép.

4.3.3. Ví dụ trong Service

Java
@Service
public class UserService {

    @Secured("ROLE_ADMIN")
    public void deleteUser(Long id) {
        System.out.println("Xóa user");
    }

    @Secured({"ROLE_ADMIN", "ROLE_MANAGER"})
    public void updateUser(Long id) {
        System.out.println("Cập nhật user");
    }
}

Ở đây:

deleteUser()
    ↓
Chỉ ADMIN


updateUser()
    ↓
ADMIN hoặc MANAGER

4.4. So sánh @Secured và @PreAuthorize

Cả hai đều có thể dùng để bảo vệ Method, nhưng @PreAuthorize mạnh và linh hoạt hơn.

@Secured @PreAuthorize
Kiểm tra trước Method ✅ ✅
Kiểm tra Role ✅ ✅
Kiểm tra Authority ✅ ✅
Nhiều Role ✅ ✅
and, or, ! ❌ ✅
Kiểm tra tham số Method ❌ ✅
Kiểm tra authentication ❌ ✅
Kiểm tra returnObject ❌ ❌
Cú pháp Đơn giản Linh hoạt hơn

@Secured

Java
@Secured("ROLE_ADMIN")
public void deleteUser(Long id) {
}

Chủ yếu dùng để:

Role nào được phép gọi Method?

@PreAuthorize

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Ngoài Role còn có thể:

Java
@PreAuthorize(
    "hasRole('ADMIN') or hasAuthority('USER_DELETE')"
)

Hoặc kiểm tra tham số:

Java
@PreAuthorize(
    "#userId == authentication.principal.id"
)
public User getUser(Long userId) {
}

Vì vậy có thể hiểu đơn giản:

@Secured
    ↓
Đơn giản
    ↓
Chủ yếu kiểm tra Role


@PreAuthorize
    ↓
Mạnh và linh hoạt
    ↓
Role + Authority + điều kiện + tham số

Trong dự án mới

Nếu đang xây dựng một project Spring Security hiện đại, @PreAuthorize thường được ưu tiên hơn @Secured vì biểu thức phân quyền linh hoạt hơn.

@Secured phù hợp khi bài toán chỉ đơn giản là:

Java
@Secured("ROLE_ADMIN")
Cốt lõi cần nhớ
  • @Secured("ROLE_ADMIN") → ADMIN được phép, các Role khác không được phép.
  • Phải bật @EnableMethodSecurity(securedEnabled = true).
  • Phải viết đầy đủ ROLE_ (khác với @PreAuthorize).
  • Không hỗ trợ and, or, !, tham số Method, hay authentication.
  • Khuyến nghị: dùng @PreAuthorize cho dự án mới.

5. Phân quyền tại Controller

Trong Spring Security, có thể phân quyền API ngay tại Controller bằng hai cách phổ biến:

  1. Phân quyền trong SecurityFilterChain.
  2. Phân quyền trực tiếp trên Method bằng @PreAuthorize.

Mục tiêu là xác định user nào được phép gọi API nào.

5.1. Phân quyền API bằng SecurityFilterChain

Đây là cách phân quyền dựa trên URL của API.

Ví dụ:

Java
@Bean
public SecurityFilterChain securityFilterChain(
        HttpSecurity http
) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .requestMatchers("/api/users/**").hasAnyRole("USER", "ADMIN")
            .anyRequest().authenticated()
        );

    return http.build();
}

Ví dụ:

/api/auth/**   → Không cần đăng nhập

/api/admin/**  → ADMIN

/api/users/**  → USER hoặc ADMIN

Luồng:

Request
   ↓
SecurityFilterChain
   ↓
Kiểm tra URL
   ↓
Kiểm tra Role/Authority
   ↓
Cho phép / Từ chối
   ↓
Controller

Ví dụ

Client gửi:

HTTP
GET /api/admin/users

Spring Security kiểm tra:

Java
.requestMatchers("/api/admin/**")
.hasRole("ADMIN")

Nếu user có:

ROLE_ADMIN

→ Request được phép đi tiếp đến Controller.

Nếu chỉ có:

ROLE_USER

→ bị từ chối.

5.2. Phân quyền bằng @PreAuthorize

Có thể đặt @PreAuthorize trực tiếp trên Method của Controller.

Trước tiên bật:

Java
@EnableMethodSecurity

Sau đó:

Java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @PreAuthorize("hasRole('ADMIN')")
    @DeleteMapping("/{id}")
    public void deleteUser(@PathVariable Long id) {
        // ...
    }
}

Ý nghĩa:

Chỉ ADMIN mới được gọi API DELETE /api/users/{id}.

Có thể kết hợp nhiều điều kiện:

Java
@PreAuthorize(
    "hasRole('ADMIN') or hasAuthority('USER_DELETE')"
)
@DeleteMapping("/{id}")
public void deleteUser(@PathVariable Long id) {
}

Điểm mạnh của @PreAuthorize là có thể kiểm tra cả tham số:

Java
@PreAuthorize(
    "#id == authentication.principal.id"
)
@GetMapping("/{id}")
public User getUser(@PathVariable Long id) {
    // ...
}

5.3. Ưu điểm và hạn chế

5.3.1. Phân quyền bằng SecurityFilterChain

Ưu điểm

  • Cấu hình tập trung.
  • Dễ nhìn toàn bộ quyền của các API.
  • Phù hợp với những quy tắc đơn giản.
  • Kiểm tra sớm, trước khi request đi vào Controller.

Ví dụ:

Java
.requestMatchers("/api/admin/**")
.hasRole("ADMIN")

Rất dễ hiểu.

Hạn chế

Khó xử lý các điều kiện phức tạp.

Ví dụ:

User chỉ được xem thông tin của chính mình.

Hoặc:

ADMIN được xem tất cả, USER chỉ được xem dữ liệu của mình.

Những trường hợp này không phù hợp nếu chỉ dựa vào URL.

5.3.2. Phân quyền bằng @PreAuthorize

Ưu điểm

Có thể đặt quyền ngay tại API:

Java
@PreAuthorize("hasRole('ADMIN')")

Có thể xử lý điều kiện phức tạp:

Java
@PreAuthorize(
    "hasRole('ADMIN') or #id == authentication.principal.id"
)

Code phân quyền nằm ngay cạnh Method cần bảo vệ nên dễ hiểu Method này dành cho ai.

Hạn chế

Nếu Controller có rất nhiều API, các annotation có thể xuất hiện dày đặc:

Java
@PreAuthorize(...)
@GetMapping(...)

@PreAuthorize(...)
@PostMapping(...)

@PreAuthorize(...)
@PutMapping(...)

@PreAuthorize(...)
@DeleteMapping(...)

Khi đó việc quản lý quyền tổng thể có thể khó nhìn hơn SecurityFilterChain.

5.4. Khi nào nên phân quyền tại Controller?

Nên sử dụng phân quyền tại Controller khi quyền truy cập gắn trực tiếp với từng API và cần thể hiện rõ API nào được Role nào sử dụng.

Ví dụ:

Java
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void deleteUser(@PathVariable Long id) {
}

Phù hợp với các API có quy tắc rõ ràng:

GET    /api/products       → USER, ADMIN
POST   /api/products       → ADMIN
PUT    /api/products/{id}  → ADMIN
DELETE /api/products/{id}  → ADMIN

Có thể kết hợp cả hai

Trong project thực tế thường không nhất thiết phải chọn một trong hai.

Có thể dùng:

SecurityFilterChain
        ↓
Bảo vệ tổng quát API
        ↓
Controller
        ↓
@PreAuthorize
        ↓
Kiểm tra quyền chi tiết

Ví dụ:

Java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .anyRequest().authenticated()
)

Sau đó tại Controller:

Java
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void deleteUser(@PathVariable Long id) {
}

Như vậy:

SecurityFilterChain → kiểm soát tổng quát ở tầng API.

@PreAuthorize → kiểm soát chi tiết tại từng Method.
Cốt lõi cần nhớ
  • SecurityFilterChain → phân quyền theo URL, tập trung, phù hợp quy tắc đơn giản.
  • @PreAuthorize → phân quyền theo Method, chi tiết, phù hợp quy tắc phức tạp.
  • Kết hợp cả hai → bảo vệ tổng quát + kiểm tra chi tiết.

6. Phân quyền tại Service

Trong ứng dụng Spring Boot, ngoài việc phân quyền tại Controller, chúng ta có thể đặt Method Security tại Service.

Đây là cách rất hữu ích khi quyền truy cập gắn với nghiệp vụ của hệ thống, thay vì chỉ gắn với URL.

Ví dụ:

Java
@Service
public class OrderService {

    @PreAuthorize("hasRole('ADMIN')")
    public void cancelOrder(Long orderId) {
        // nghiệp vụ hủy đơn hàng
    }
}

Ở đây, quyền được kiểm tra ngay tại Method nghiệp vụ.

6.1. Phân quyền nghiệp vụ bằng @PreAuthorize

Trước tiên cần bật Method Security:

Java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {
}

Sau đó có thể sử dụng @PreAuthorize trong Service:

Java
@Service
public class UserService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long userId) {
        // Xóa user
    }
}

Ý nghĩa:

Chỉ ADMIN mới được thực hiện nghiệp vụ deleteUser().

Có thể sử dụng các điều kiện phức tạp hơn.

Ví dụ:

Java
@PreAuthorize(
    "hasRole('ADMIN') or #userId == authentication.principal.id"
)
public User getUser(Long userId) {
    // ...
}

Ý nghĩa:

  • ADMIN → được xem bất kỳ user nào.
  • USER → chỉ được xem chính mình.

Điểm quan trọng là Service chứa business logic, vì vậy những quy tắc như:

Ai được xóa đơn hàng?

Ai được sửa thông tin user?

Ai được duyệt hóa đơn?

thường có thể được bảo vệ ngay tại Service.

6.2. Controller gọi Service có phân quyền

Thông thường Controller không tự xử lý nghiệp vụ mà gọi Service.

Ví dụ:

Java
@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @DeleteMapping("/{id}")
    public void deleteUser(@PathVariable Long id) {
        userService.deleteUser(id);
    }
}

Service:

Java
@Service
public class UserService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long userId) {
        // Xử lý nghiệp vụ
    }
}

Luồng:

Client
   ↓
Controller
   ↓
UserService.deleteUser()
   ↓
@PreAuthorize
   ↓
Có ROLE_ADMIN?
   ├── Có → thực hiện nghiệp vụ
   └── Không → từ chối

Controller không cần tự kiểm tra Role trong trường hợp này.

6.3. Controller Security và Service Security

Có thể đặt @PreAuthorize ở cả Controller và Service.

Phân quyền tại Controller

Java
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void deleteUser(@PathVariable Long id) {
    userService.deleteUser(id);
}

Phân quyền tại Service

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    // Business logic
}

Hai cách có vị trí khác nhau:

Controller Security
        ↓
Bảo vệ API
        ↓
Controller
        ↓
Service Security
        ↓
Bảo vệ nghiệp vụ
        ↓
Business Logic

Điểm khác biệt quan trọng

Nếu chỉ đặt quyền ở Controller:

Java
@PreAuthorize("hasRole('ADMIN')")

thì quyền đó chỉ được kiểm tra khi đi qua Controller đó.

Nhưng Service có thể được gọi từ nhiều nơi:

Controller A ──┐
               ↓
Controller B → Service
               ↑
Job/Process ───┘

Nếu quyền được đặt tại Service:

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

thì bất kỳ nơi nào gọi Method này cũng phải vượt qua kiểm tra quyền.

Đây là lý do Service Security thường phù hợp với các quy tắc bảo mật gắn với nghiệp vụ.

6.4. Khi nào nên phân quyền tại Service?

Nên phân quyền tại Service khi quyền truy cập liên quan trực tiếp đến business logic.

Ví dụ:

Xóa tài khoản

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Duyệt đơn hàng

Java
@PreAuthorize("hasRole('MANAGER')")
public void approveOrder(Long orderId) {
}

Hủy đơn hàng của chính mình

Java
@PreAuthorize(
    "hasRole('ADMIN') or #userId == authentication.principal.id"
)
public void cancelOrder(Long orderId, Long userId) {
}

Khi Service được sử dụng bởi nhiều Controller

Nếu nhiều API cùng gọi một Service Method thì đặt quyền ở Service giúp tập trung quy tắc bảo mật nghiệp vụ.

Controller Security hay Service Security?

Có thể nhớ đơn giản:

Vị trí Mục đích
SecurityFilterChain Bảo vệ URL/API tổng quát
Controller Bảo vệ từng API
Service Bảo vệ nghiệp vụ
Service thường phù hợp hơn cho business rule

Ví dụ một project thực tế:

Request
   ↓
SecurityFilterChain
   ↓
Authentication
   ↓
Controller
   ↓
Service
   ↓
@PreAuthorize
   ↓
Business Logic
   ↓
Database
Nguyên tắc dễ nhớ
  • Controller trả lời câu hỏi: "Ai được gọi API này?"
  • Service trả lời câu hỏi: "Ai được thực hiện nghiệp vụ này?"
  • Với những quy tắc phân quyền quan trọng của nghiệp vụ, đặt tại Service thường an toàn và có khả năng tái sử dụng tốt hơn.

7. So sánh các cơ chế phân quyền

Trong Spring Security, có nhiều vị trí và cách thức để thực hiện phân quyền. Mỗi cơ chế phù hợp với một loại yêu cầu khác nhau.

7.1. SecurityFilterChain

Phân quyền dựa trên URL và HTTP Request.

Java
.requestMatchers("/api/admin/**")
.hasRole("ADMIN")

Phù hợp với các quy tắc đơn giản:

/api/admin/** → ADMIN
/api/users/** → USER, ADMIN

7.2. @PreAuthorize

Phân quyền trực tiếp trên Method.

Java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}

Có thể kiểm tra:

  • Role
  • Authority
  • Tham số Method
  • User hiện tại
  • Nhiều điều kiện

Ví dụ:

Java
@PreAuthorize(
    "hasRole('ADMIN') or #id == authentication.principal.id"
)

Đây là cơ chế linh hoạt nhất trong các cơ chế đã học.

7.3. @PostAuthorize

Phân quyền sau khi Method thực thi.

Java
@PostAuthorize(
    "returnObject.username == authentication.name"
)
public User getUser(Long id) {
    return userRepository.findById(id).orElseThrow();
}

Phù hợp khi điều kiện phân quyền phụ thuộc vào kết quả trả về.

7.4. @Secured

Phân quyền Method dựa trên Role.

Java
@Secured("ROLE_ADMIN")
public void deleteUser(Long id) {
}

Cách sử dụng đơn giản nhưng ít linh hoạt hơn @PreAuthorize.

7.5. So sánh tổng hợp

Cơ chế Vị trí Kiểm tra Độ linh hoạt Phù hợp
SecurityFilterChain Security Config URL, Request ⭐⭐ Phân quyền API tổng quát
@PreAuthorize Controller/Service Role, Authority, điều kiện ⭐⭐⭐⭐⭐ Phân quyền chi tiết
@PostAuthorize Controller/Service Kết quả trả về ⭐⭐⭐⭐ Kiểm tra dữ liệu sau Method
@Secured Controller/Service Role ⭐⭐ Phân quyền Role đơn giản

7.6. Nên sử dụng cơ chế nào?

Có thể lựa chọn theo nhu cầu:

Phân quyền API theo URL
        ↓
SecurityFilterChain
Phân quyền Method
        ↓
@PreAuthorize
Phân quyền dựa trên kết quả trả về
        ↓
@PostAuthorize
Chỉ cần kiểm tra Role đơn giản
        ↓
@Secured

Trong một project thực tế, có thể kết hợp nhiều cơ chế:

                    Request
                       ↓
              SecurityFilterChain
                       ↓
                Authentication
                       ↓
                  Controller
                       ↓
               @PreAuthorize
                       ↓
                   Service
                       ↓
               @PreAuthorize
                       ↓
                Business Logic

Cách tiếp cận thường dùng

  • SecurityFilterChain: bảo vệ tổng quát các API.
  • @PreAuthorize ở Controller: khi cần phân quyền cụ thể cho API.
  • @PreAuthorize ở Service: khi quyền gắn với nghiệp vụ quan trọng.
  • @PostAuthorize: khi phải dựa vào kết quả trả về.
  • @Secured: khi chỉ cần Role đơn giản.
Ghi nhớ

SecurityFilterChain thiên về bảo vệ Request/API, còn Method Security (@PreAuthorize, @PostAuthorize, @Secured) thiên về bảo vệ Method và nghiệp vụ.
