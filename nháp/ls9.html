1. LOMBOK TRONG JAVA VÀ SPRING BOOT

Mục tiêu

Sau khi học xong phần này, học viên có thể:

  • Hiểu Lombok là gì.
  • Hiểu tại sao cần sử dụng Lombok.
  • Cài đặt Lombok trong dự án Java/Spring Boot.
  • Hiểu và sử dụng các annotation phổ biến.
  • Phân biệt được các loại constructor của Lombok.
  • Sử dụng Lombok trong Entity, DTO, Service và Controller.
  • Hiểu những trường hợp không nên sử dụng Lombok.

1.1. Lombok là gì?

1.1.1. Khái niệm

Lombok là một thư viện dành cho Java, được sử dụng để giảm các đoạn boilerplate code – những đoạn code lặp đi lặp lại và ít chứa logic nghiệp vụ.

Trong Java, khi xây dựng một class, chúng ta thường phải viết:

  • Getter.
  • Setter.
  • Constructor.
  • toString().
  • equals().
  • hashCode().

Ví dụ không sử dụng Lombok:

Student.java
public class Student {

    private Long id;
    private String name;
    private String email;

    public Student() {
    }

    public Student(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }
}

Có thể nhận thấy phần lớn code ở trên chỉ phục vụ cho việc đọc, ghi và khởi tạo dữ liệu. Nếu class có 10 hoặc 20 thuộc tính, số lượng code lặp lại sẽ rất lớn.

Lombok giải quyết vấn đề này bằng cách cho phép chúng ta sử dụng annotation.

Student.java với Lombok
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
    private String email;
}

Code ngắn hơn rất nhiều nhưng vẫn có getter, setter và constructor tương ứng.

1.1.2. Boilerplate Code là gì?

Boilerplate Code là những đoạn code cần thiết nhưng thường được lặp lại trong nhiều class.

public String getName() {
    return name;
}

Đây là code hợp lệ và cần thiết, nhưng nếu class có 20 field thì chúng ta phải viết rất nhiều getter tương tự. Lombok giúp tự động sinh các đoạn code này.

1.1.3. Lombok hoạt động như thế nào?

Lombok sử dụng cơ chế Annotation Processing của Java.

@Getter
public class Student {
    private String name;
}

Annotation @Getter nói cho Lombok biết rằng class cần getter.

Về mặt tư duy, có thể hình dung:

Java Source Code
       ↓
Lombok Annotation
       ↓
Annotation Processing
       ↓
Sinh code cần thiết
       ↓
Java Compiler
       ↓
.class

Do đó, Lombok không phải là một “phép thuật” làm thay đổi Java. Nó chỉ giúp sinh tự động những phần code mà lập trình viên có thể viết thủ công.

1.1.4. Lombok sử dụng Annotation

Annotation là những thông tin được đặt trước class, method hoặc field.

@Getter
public class Student {
}

Một số annotation thường gặp:

  • @Getter
  • @Setter
  • @Data
  • @Builder
  • @NoArgsConstructor
  • @AllArgsConstructor
  • @RequiredArgsConstructor
  • @ToString
  • @EqualsAndHashCode

1.1.5. Khi nào nên sử dụng Lombok?

Lombok đặc biệt hữu ích trong các project:

  • Spring Boot.
  • Spring MVC.
  • Spring Data JPA.
  • REST API.
  • Các project có nhiều DTO.
  • Các project có nhiều Entity/model.

Ví dụ một project Spring Boot có: User, Product, Order, Medicine, Invoice, Customer, Employee... Nếu mỗi class đều phải viết getter, setter, constructor thì lượng code sẽ rất lớn. Lombok giúp giảm đáng kể phần code này.

1.2. Cài đặt Lombok

1.2.1. Cài Lombok bằng Maven

Trong project Maven, mở file: pom.xml

Thêm dependency:

<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>

1.2.2. Giải thích cú pháp

<dependency> – Đây là phần khai báo một thư viện mà project cần sử dụng.

<groupId> – org.projectlombok xác định nhóm/tổ chức phát hành thư viện.

<artifactId> – lombok xác định tên thư viện.

<optional> – true đánh dấu Lombok là dependency hỗ trợ cho project.

1.2.3. Import Lombok

Sau khi cài đặt, trong Java có thể import annotation:

import lombok.Getter;
import lombok.Setter;

Ví dụ:

import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
public class Student {

    private String name;
}

1.2.4. Kiểm tra Lombok

Tạo:

@Getter
@Setter
public class Student {

    private String name;
}

Sau đó:

public class Main {

    public static void main(String[] args) {

        Student student = new Student();

        student.setName("Nguyễn Văn An");

        System.out.println(student.getName());
    }
}

Nếu chương trình hoạt động bình thường thì Lombok đã được cấu hình.

1.3. @Getter, @Setter

1.3.1. Lý thuyết về Getter

Trong Java, thuộc tính thường được khai báo private. Do đó class bên ngoài không nên truy cập trực tiếp. Thay vào đó, sử dụng getter để lấy giá trị của thuộc tính.

Ví dụ:

private String name;

Getter có nhiệm vụ: Lấy giá trị của một thuộc tính.

1.3.2. Cú pháp getter truyền thống

public String getName() {
    return name;
}

Giải thích:

  • public – phương thức có thể được gọi từ bên ngoài class.
  • String – kiểu dữ liệu trả về.
  • getName() – tên phương thức getter.
  • return name; – trả về giá trị của thuộc tính name.

1.3.3. @Getter

Thay vì viết getter thủ công, có thể sử dụng @Getter trên field hoặc class.

@Getter
private String name;

Hoặc:

@Getter
public class Student {

    private String name;
    private String email;
}

Lombok tự tạo getter.

1.3.4. Getter ở cấp class

@Getter
public class Student {

    private Long id;
    private String name;
    private int age;
}

Lombok sẽ tạo tương ứng:

public Long getId() {
    return id;
}

public String getName() {
    return name;
}

public int getAge() {
    return age;
}

1.3.5. Getter ở cấp field

Có thể chỉ tạo getter cho một field cụ thể.

public class User {

    @Getter
    private String username;

    private String password;
}

Khi đó: user.getUsername(); có thể sử dụng, nhưng user.getPassword(); không được Lombok tạo.

1.3.6. Lý thuyết về Setter

Setter được sử dụng để thay đổi giá trị của thuộc tính.

public void setName(String name) {
    this.name = name;
}

Giải thích:

  • void – setter không trả về giá trị.
  • setName(...) – phương thức thay đổi thuộc tính name.
  • this.name – thuộc tính của object hiện tại.
  • name – tham số được truyền vào.

1.3.7. @Setter

Thay vì viết setter thủ công, có thể sử dụng @Setter.

@Setter
private String name;

Hoặc:

@Setter
public class Student {

    private String name;
    private String email;
}

1.3.8. Sử dụng cả Getter và Setter

@Getter
@Setter
public class Student {

    private Long id;
    private String name;
    private String email;
}

Sử dụng:

Student student = new Student();

student.setName("An");

String name = student.getName();

System.out.println(name);

Luồng hoạt động: setName("An") → name = "An" → getName() → "An".

1.3.9. Lưu ý khi sử dụng Setter

Không phải field nào cũng nên có setter. Ví dụ id chỉ có getter, còn email có cả getter và setter. Cách này giúp kiểm soát tốt hơn việc thay đổi dữ liệu.

1.4. @NoArgsConstructor, @AllArgsConstructor

1.4.1. Constructor là gì?

Constructor là phương thức đặc biệt được gọi khi tạo object. Constructor có cùng tên với class và không có kiểu trả về.

Ví dụ:

Student student = new Student();

Java gọi constructor: public Student() { }

1.4.2. @NoArgsConstructor

Tạo constructor không tham số.

@NoArgsConstructor
public class Student {
}

Lombok tạo: public Student() { }

Do đó Student student = new Student(); có thể thực hiện bình thường.

1.4.3. Khi nào sử dụng @NoArgsConstructor?

Thường sử dụng khi:

  • Cần constructor mặc định.
  • Làm việc với JPA Entity.
  • Framework cần tạo object.
  • DTO cần khởi tạo rỗng.

Ví dụ Entity:

@Entity
@NoArgsConstructor
public class Product {

    @Id
    private Long id;

    private String name;
}

1.4.4. @AllArgsConstructor

Tạo constructor với tất cả tham số.

@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
    private int age;
}

Lombok tạo:

public Student(Long id, String name, int age) {
    this.id = id;
    this.name = name;
    this.age = age;
}

Có thể: Student student = new Student(1L, "An", 20);

1.4.5. Kết hợp

Có thể kết hợp cả hai annotation để có cả constructor rỗng và constructor đầy đủ.

@NoArgsConstructor
@AllArgsConstructor
public class Student {

    private Long id;
    private String name;
}

Có: new Student(); và new Student(1L, "An");

1.5. @RequiredArgsConstructor

1.5.1. Khái niệm

@RequiredArgsConstructor tạo constructor chứa các field bắt buộc. Trường hợp quan trọng nhất: private final.

Ví dụ:

@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
}

Lombok tạo:

public UserService(UserRepository userRepository) {
    this.userRepository = userRepository;
}

1.5.2. Vì sao dùng final?

private final UserRepository userRepository; – final đảm bảo biến phải được khởi tạo và không thể gán sang dependency khác sau đó. Điều này phù hợp với constructor injection.

1.5.3. Sử dụng trong Spring Boot

Không dùng Lombok:

@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}

Dùng Lombok:

@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
}

Đây là một trong những cách sử dụng Lombok phổ biến nhất trong Spring Boot.

1.6. @Data

1.6.1. Khái niệm

@Data là annotation tổng hợp bao gồm các chức năng tương tự: @Getter, @Setter, @RequiredArgsConstructor, @ToString, @EqualsAndHashCode.

1.6.2. Cú pháp

@Data
public class Student {

    private Long id;
    private String name;
    private String email;
}

Lombok hỗ trợ sinh: getId(), setId(), getName(), setName(), getEmail(), setEmail(), toString(), equals(), hashCode().

1.6.3. Ví dụ thực tế

@Data
public class ProductRequest {

    private String name;
    private Double price;
    private Integer quantity;
}

Có thể:

ProductRequest request = new ProductRequest();

request.setName("Laptop");
request.setPrice(20000000.0);
request.setQuantity(2);

1.6.4. Kết hợp constructor

Nếu cần cả hai constructor:

@Data
@NoArgsConstructor
@AllArgsConstructor
public class ProductRequest {

    private String name;
    private Double price;
}

1.6.5. Lưu ý

Không nên mặc định dùng @Data cho mọi Entity. Đối với DTO, @Data thường phù hợp hơn.

1.7. @Builder

1.7.1. Khái niệm Builder Pattern

Builder Pattern là cách xây dựng object bằng cách thiết lập từng thuộc tính, dễ đọc hơn constructor có quá nhiều tham số.

Ví dụ:

User.builder()
    .name("An")
    .email("an@gmail.com")
    .age(20)
    .build();

1.7.2. Cú pháp

@Builder
public class User {

    private Long id;
    private String name;
    private String email;
}

Sau đó:

User user = User.builder()
    .id(1L)
    .name("An")
    .email("an@gmail.com")
    .build();

1.7.3. Giải thích cú pháp

  • User.builder() – bắt đầu quá trình xây dựng object.
  • .id(1L) – thiết lập id.
  • .name("An") – thiết lập name.
  • .email("an@gmail.com") – thiết lập email.
  • .build() – kết thúc và tạo object.

1.7.4. Builder trong DTO

@Data
@Builder
public class UserResponse {

    private Long id;
    private String username;
    private String email;
}

Sử dụng:

UserResponse response = UserResponse.builder()
    .id(1L)
    .username("admin")
    .email("admin@gmail.com")
    .build();

1.8. @ToString

1.8.1. Khái niệm

toString() dùng để chuyển object thành chuỗi biểu diễn. @ToString giúp sinh tự động.

Ví dụ:

System.out.println(user);

Java sẽ gọi: user.toString(); Nếu không override, kết quả thường khó đọc.

1.8.2. Sử dụng @ToString

@ToString
public class User {

    private Long id;
    private String username;
}

Kết quả có thể dạng: User(id=1, username=admin)

1.8.3. Cú pháp loại trừ field

@ToString
public class User {

    private Long id;

    private String username;

    @ToString.Exclude
    private String password;
}

password sẽ không được đưa vào toString().

1.8.4. Tại sao cần loại trừ password?

Không nên log password=123456 vì log có thể được lưu lại hoặc được người khác truy cập. Do đó @ToString.Exclude là một biện pháp hữu ích để tránh vô tình đưa dữ liệu nhạy cảm vào chuỗi debug.

1.9. @EqualsAndHashCode

1.9.1. equals()

equals() dùng để xác định hai object có được xem là bằng nhau hay không.

Ví dụ:

User user1 = new User(1L, "An");
User user2 = new User(1L, "An");

Có thể định nghĩa rằng hai object này bằng nhau dựa trên id.

1.9.2. hashCode()

hashCode() tạo ra một giá trị hash cho object, đặc biệt quan trọng với HashSet, HashMap. Java sử dụng kết hợp hashCode() và equals() để xử lý việc so sánh object trong các cấu trúc dữ liệu dựa trên hash.

1.9.3. Sử dụng Lombok

@EqualsAndHashCode
public class User {

    private Long id;
    private String username;
}

Lombok tự sinh equals() và hashCode().

1.9.4. Chỉ định field

@EqualsAndHashCode(onlyExplicitlyIncluded = true)
public class User {

    @EqualsAndHashCode.Include
    private Long id;

    private String username;

    private String email;
}

Ở đây chỉ id được đánh dấu để tham gia vào equals() và hashCode().

1.10. Lombok trong Spring Boot

1.10.1. Lombok trong Entity

@Entity
@Getter
@Setter
@NoArgsConstructor
public class Medicine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Double price;
}

Giải thích:

  • @Entity – biến class thành JPA Entity.
  • @Getter – tạo getter.
  • @Setter – tạo setter.
  • @NoArgsConstructor – tạo constructor không tham số.

1.10.2. Lombok trong DTO

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class MedicineResponse {

    private Long id;

    private String name;

    private Double price;
}

Class này có: Getter, Setter, toString(), equals(), hashCode(), Constructor, Builder.

1.10.3. Lombok trong Service

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;
}

Lombok tự sinh constructor để Spring Boot inject MedicineRepository.

1.10.4. Lombok trong Controller

@RestController
@RequestMapping("/medicines")
@RequiredArgsConstructor
public class MedicineController {

    private final MedicineService medicineService;
}

1.11. Ví dụ tổng hợp

Một cấu trúc Spring Boot có thể như sau:

entity
    Medicine.java

repository
    MedicineRepository.java

service
    MedicineService.java

controller
    MedicineController.java

dto
    MedicineResponse.java

Entity

@Entity
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
public class Medicine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Double price;
}

Repository

public interface MedicineRepository
        extends JpaRepository<Medicine, Long> {
}

DTO

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class MedicineResponse {

    private Long id;
    private String name;
    private Double price;
}

Service

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;

    public MedicineResponse findById(Long id) {

        Medicine medicine = medicineRepository.findById(id).orElseThrow();

        return MedicineResponse.builder()
            .id(medicine.getId())
            .name(medicine.getName())
            .price(medicine.getPrice())
            .build();
    }
}

Controller

@RestController
@RequestMapping("/medicines")
@RequiredArgsConstructor
public class MedicineController {

    private final MedicineService medicineService;

    @GetMapping("/{id}")
    public MedicineResponse findById(@PathVariable Long id) {

        return medicineService.findById(id);
    }
}

1.12. Bảng ghi nhớ

Annotation Ý nghĩa Thường dùng ở đâu
@GetterSinh getterEntity, DTO
@SetterSinh setterEntity, DTO
@NoArgsConstructorConstructor rỗngEntity, DTO
@AllArgsConstructorConstructor đầy đủDTO, Model
@RequiredArgsConstructorConstructor cho field bắt buộcService, Controller
@DataGetter + Setter + nhiều chức năng khácDTO
@BuilderXây dựng objectDTO, Response
@ToStringSinh toString()DTO, Model
@EqualsAndHashCodeSinh equals/hashCodeModel, một số DTO

Quy tắc quan trọng cần nhớ

  • DTO → @Data + @Builder
  • Service → @RequiredArgsConstructor
  • Controller → @RequiredArgsConstructor
  • Entity → @Getter + @Setter + @NoArgsConstructor
  • Không sử dụng @Data một cách máy móc cho JPA Entity, nhất là Entity có quan hệ @OneToMany, @ManyToOne, @ManyToMany, @OneToOne.

Nếu soạn theo chuẩn giáo trình tự học, mỗi phần từ 1.3 đến 1.10 nên giữ đúng cấu trúc này: Lý thuyết → Cú pháp → Giải thích từng thành phần cú pháp → Ví dụ → Phân tích ví dụ → Ứng dụng Spring Boot → Lưu ý. Đây sẽ phù hợp hơn nhiều so với kiểu chỉ liệt kê annotation và code.

2. MAPPER TRONG SPRING BOOT

Trong các ứng dụng Spring Boot, đặc biệt là những project sử dụng Entity – DTO – Service – Controller, chúng ta thường xuyên phải chuyển đổi dữ liệu giữa các object.

Ví dụ:

Database
   ↓
Entity
   ↓
Mapper
   ↓
DTO
   ↓
Controller
   ↓
Client

Hoặc theo chiều ngược lại:

Client
   ↓
Request DTO
   ↓
Mapper
   ↓
Entity
   ↓
Database

Mapper giúp tách biệt object dùng để làm việc với database và object dùng để giao tiếp với client/API.

2.1. Mapper là gì?

2.1.1. Khái niệm Mapper

Mapper là thành phần có nhiệm vụ chuyển đổi dữ liệu từ một object sang một object khác.

Ví dụ trong Spring Boot chúng ta có Entity:

@Entity
public class Medicine {

    private Long id;
    private String name;
    private Double price;
}

Và DTO:

public class MedicineResponse {

    private Long id;
    private String name;
    private Double price;
}

Hai class có cấu trúc tương đối giống nhau nhưng chúng là hai object khác nhau. Chúng ta cần chuyển Medicine → MedicineResponse. Đây chính là công việc của Mapper.

2.1.2. Tại sao cần Mapper?

Trong một ứng dụng Spring Boot, chúng ta thường không muốn trả trực tiếp Entity ra API.

@GetMapping("/{id}")
public Medicine getById(@PathVariable Long id) {
    return medicineRepository.findById(id).orElseThrow();
}

Cách này có thể khiến API trả trực tiếp toàn bộ dữ liệu của Entity. Trong thực tế, Entity có thể chứa:

  • Thông tin nội bộ.
  • Quan hệ với Entity khác.
  • Field không muốn trả về client.
  • Dữ liệu phục vụ database nhưng không phục vụ API.

Do đó thường sử dụng: Entity → Mapper → DTO → API Response.

@GetMapping("/{id}")
public MedicineResponse getById(@PathVariable Long id) {

    Medicine medicine = medicineService.findById(id);

    return medicineMapper.toResponse(medicine);
}

2.1.3. Entity và DTO có vai trò khác nhau

Entity – đại diện cho dữ liệu được quản lý bởi JPA/Hibernate và thường ánh xạ với database.

@Entity
public class Medicine {

    @Id
    private Long id;

    private String name;

    private Double price;
}

DTO – Data Transfer Object – được sử dụng để truyền dữ liệu giữa các tầng hoặc giữa server và client.

public class MedicineResponse {

    private Long id;

    private String name;

    private Double price;
}

Có thể hình dung: Entity → phục vụ persistence/database, DTO → phục vụ truyền dữ liệu. Mapper đứng giữa hai object này.

2.2. Mapping thủ công

2.2.1. Mapping thủ công là gì?

Mapping thủ công là cách lập trình viên tự viết code để lấy dữ liệu từ object nguồn và gán sang object đích.

public MedicineResponse toResponse(Medicine medicine) {

    MedicineResponse response = new MedicineResponse();

    response.setId(medicine.getId());
    response.setName(medicine.getName());
    response.setPrice(medicine.getPrice());

    return response;
}

Đây là mapping thủ công.

2.2.2. Phân tích quá trình mapping

Object nguồn: Medicine medicine; Object đích: MedicineResponse response.

Các bước: medicine.getId() → response.setId(); medicine.getName() → response.setName(); medicine.getPrice() → response.setPrice().

2.2.3. Ví dụ đầy đủ

Entity

@Entity
@Getter
@Setter
@NoArgsConstructor
public class Medicine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Double price;
}

DTO

@Data
@NoArgsConstructor
@AllArgsConstructor
public class MedicineResponse {

    private Long id;
    private String name;
    private Double price;
}

Mapper

@Component
public class MedicineMapper {

    public MedicineResponse toResponse(Medicine medicine) {

        MedicineResponse response = new MedicineResponse();

        response.setId(medicine.getId());
        response.setName(medicine.getName());
        response.setPrice(medicine.getPrice());

        return response;
    }
}

2.2.4. Sử dụng Mapper trong Service

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {

        Medicine medicine = medicineRepository.findById(id).orElseThrow();

        return medicineMapper.toResponse(medicine);
    }
}

Service thực hiện: Repository → Medicine Entity → MedicineMapper → MedicineResponse.

2.3. Hạn chế của Mapping thủ công

Mapping thủ công dễ hiểu và không phụ thuộc thư viện bên ngoài. Tuy nhiên, khi project lớn, cách này có nhiều hạn chế.

2.3.1. Nhiều code lặp lại

Ví dụ DTO có 10 field: response.setId(entity.getId());, response.setName(entity.getName());, v.v. Nếu có 50 DTO, số lượng code mapping sẽ rất lớn.

2.3.2. Dễ quên field

Entity có nhiều field nhưng lập trình viên chỉ viết một số, bỏ sót các field khác. Chương trình vẫn chạy nhưng dữ liệu trả về không đầy đủ.

2.3.3. Khó bảo trì

Khi Entity thêm field mới, Mapper cũng cần sửa. Với project lớn, việc này trở nên mất thời gian.

2.3.4. Mapping danh sách dài

Nếu có List<Medicine>, phải lặp mapping cho từng phần tử. Bản thân đoạn này không quá phức tạp, nhưng nếu logic mapping ngày càng nhiều thì việc quản lý thủ công sẽ trở nên khó khăn.

2.4. ModelMapper

2.4.1. ModelMapper là gì?

ModelMapper là thư viện Java hỗ trợ tự động mapping dữ liệu giữa các object.

Thay vì phải viết thủ công, có thể sử dụng:

MedicineResponse response = modelMapper.map(medicine, MedicineResponse.class);

ModelMapper sẽ dựa trên tên và kiểu dữ liệu của các thuộc tính để thực hiện mapping.

2.4.2. Cơ chế hoạt động cơ bản

Giả sử Medicine có id, name, price và MedicineResponse cũng có các field tương tự. ModelMapper hiểu: Medicine.id → MedicineResponse.id, Medicine.name → MedicineResponse.name, v.v.

2.4.3. Điều kiện mapping cơ bản

ModelMapper hoạt động thuận lợi nhất khi:

  • Tên field giống nhau.
  • Kiểu dữ liệu tương thích.
  • Object nguồn và object đích có cấu trúc tương đối tương đồng.

2.5. Cài đặt và cấu hình ModelMapper

2.5.1. Thêm dependency

Trong pom.xml:

<dependency>
    <groupId>org.modelmapper</groupId>
    <artifactId>modelmapper</artifactId>
    <version>3.2.4</version>
</dependency>

Khi sử dụng trong project thực tế, nên kiểm tra version hiện hành tương thích với project của bạn.

2.5.2. Tạo Bean ModelMapper

Tạo class cấu hình:

@Configuration
public class MapperConfig {

    @Bean
    public ModelMapper modelMapper() {
        return new ModelMapper();
    }
}

2.5.3. Giải thích cấu hình

  • @Configuration – đánh dấu class là class cấu hình của Spring.
  • @Bean – cho Spring biết method này trả về một object mà Spring cần quản lý.
  • return new ModelMapper(); – tạo instance của ModelMapper.

Sau đó có thể inject: private final ModelMapper modelMapper;

2.6. Entity → DTO

Đây là trường hợp phổ biến nhất khi trả dữ liệu từ API.

2.6.1. Entity

Cú pháp: modelMapper.map(source, Destination.class);

Trong đó: source là object nguồn, Destination.class là class của object đích.

2.7. DTO → Entity

Mapping không chỉ có chiều Entity → DTO mà còn chiều DTO → Entity, thường xuất hiện khi client gửi request tạo hoặc cập nhật dữ liệu.

2.7.1. Request DTO

Medicine medicine = modelMapper.map(request, Medicine.class);

ModelMapper thực hiện: MedicineRequest.name → Medicine.name, MedicineRequest.price → Medicine.price.

2.7.4. Ví dụ trong Service

Quy trình: Client → MedicineRequest → ModelMapper → Medicine → Repository → Database.

2.8. Mapping danh sách

2.8.1. Vấn đề

Repository thường trả về List<Medicine>, trong khi API cần List<MedicineResponse>. Cần mapping từng phần tử.

2.8.2. Sử dụng Stream API

List<MedicineResponse> responses = medicines.stream()
    .map(medicine -> modelMapper.map(medicine, MedicineResponse.class))
    .toList();

2.8.3. Giải thích

Giả sử List<Medicine> medicines;. Thực hiện mapping từng phần tử: Medicine 1 → ModelMapper → Response 1, Medicine 2 → Response 2, v.v.

2.8.4. Ví dụ Service

public List<MedicineResponse> findAll() {

    List<Medicine> medicines = medicineRepository.findAll();

    return medicines.stream()
        .map(medicine -> modelMapper.map(medicine, MedicineResponse.class))
        .toList();
}

2.9. Mapping thuộc tính khác tên

2.9.1. Vấn đề

ModelMapper hoạt động tốt khi tên field giống nhau. Nếu khác tên (ví dụ Entity: name, DTO: medicineName), ModelMapper không thể tự động mapping.

2.9.2. Mapping thủ công

Có thể tự xử lý: response.setMedicineName(medicine.getName());

2.9.3. Cấu hình ModelMapper

Có thể cấu hình typeMap để chỉ định mapping:

ModelMapper modelMapper = new ModelMapper();

modelMapper.typeMap(Medicine.class, MedicineResponse.class)
    .addMapping(Medicine::getName, MedicineResponse::setMedicineName);

Ý nghĩa: Medicine.name → MedicineResponse.medicineName.

2.9.4. Khi nào cần mapping đặc biệt?

Mapping tùy chỉnh thường cần khi: tên field khác nhau, kiểu dữ liệu khác nhau, cần tính toán dữ liệu, Entity có quan hệ phức tạp, DTO có field không tồn tại trong Entity.

Ví dụ: Entity: firstName + lastName → DTO: fullName. Không thể đơn giản firstName → fullName mà cần firstName + lastName → fullName. Đây là lúc mapping custom hoặc mapping thủ công trở nên cần thiết.

2.10. MapStruct

2.10.1. MapStruct là gì?

MapStruct là một thư viện hỗ trợ mapping object trong Java. Điểm khác biệt quan trọng: MapStruct tạo code mapping tại thời điểm compile thay vì thực hiện mapping chủ yếu bằng reflection lúc runtime như ModelMapper.

Ví dụ khai báo:

@Mapper(componentModel = "spring")
public interface MedicineMapper {

    MedicineResponse toResponse(Medicine medicine);

    Medicine toEntity(MedicineRequest request);
}

MapStruct sẽ tạo implementation tương ứng trong quá trình build.

2.10.2. Cài đặt MapStruct

Với Maven, thường cần dependency API:

<dependency>
    <groupId>org.mapstruct</groupId>
    <artifactId>mapstruct</artifactId>
    <version>1.6.3</version>
</dependency>

Và cấu hình annotation processor cho Maven Compiler Plugin:

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.mapstruct</groupId>
                <artifactId>mapstruct-processor</artifactId>
                <version>1.6.3</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>

Version minh họa ở trên cần được đồng bộ với version MapStruct mà project sử dụng.

2.10.3. Tạo Mapper

@Mapper(componentModel = "spring")
public interface MedicineMapper {

    MedicineResponse toResponse(Medicine medicine);

    Medicine toEntity(MedicineRequest request);
}

2.10.4. Giải thích @Mapper

  • @Mapper – đánh dấu interface là MapStruct Mapper.
  • @Mapper(componentModel = "spring") – cho phép implementation do MapStruct sinh ra được đăng ký vào Spring Container, nhờ đó có thể inject private final MedicineMapper medicineMapper;.

2.10.5. Entity → DTO

Khai báo: MedicineResponse toResponse(Medicine medicine); – MapStruct sẽ tự sinh code tương ứng. Code được sinh ra tương tự:

@Override
public MedicineResponse toResponse(Medicine medicine) {

    if (medicine == null) {
        return null;
    }

    MedicineResponse response = new MedicineResponse();

    response.setId(medicine.getId());
    response.setName(medicine.getName());
    response.setPrice(medicine.getPrice());

    return response;
}

Lập trình viên không cần tự viết implementation này.

2.10.6. DTO → Entity

Có thể khai báo: Medicine toEntity(MedicineRequest request); – MapStruct sẽ sinh code chuyển MedicineRequest → Medicine.

2.10.7. Sử dụng trong Service

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {

        Medicine medicine = medicineRepository.findById(id).orElseThrow();

        return medicineMapper.toResponse(medicine);
    }
}

So với ModelMapper: modelMapper.map(medicine, MedicineResponse.class); thì MapStruct: medicineMapper.toResponse(medicine); – cách sử dụng rất rõ ràng.

2.11. So sánh ModelMapper và MapStruct

2.11.1. ModelMapper

Ưu điểm: Dễ cài đặt, dễ học, cú pháp đơn giản, mapping nhanh trong các trường hợp cơ bản, phù hợp với project nhỏ và vừa, có thể cấu hình mapping động.

Nhược điểm: Mapping dựa nhiều vào cơ chế runtime. Với mapping phức tạp cần cấu hình thêm. Một số lỗi mapping có thể chỉ phát hiện khi chạy chương trình. Với project lớn, việc kiểm soát mapping có thể khó hơn.

2.11.2. MapStruct

Ưu điểm: Sinh code mapping khi compile, không cần reflection cho mapping được sinh, hiệu năng tốt, kiểu dữ liệu và mapping rõ ràng, compiler có thể hỗ trợ phát hiện nhiều vấn đề mapping, phù hợp với project lớn, dễ kiểm soát logic mapping.

Nhược điểm: Cấu hình ban đầu phức tạp hơn ModelMapper, cần hiểu annotation processor, với người mới học Spring Boot, cú pháp ban đầu có thể khó hơn.

2.12. Nên sử dụng ModelMapper hay MapStruct?

Không có câu trả lời tuyệt đối rằng thư viện nào luôn tốt hơn.

Khi học Spring Boot, có thể bắt đầu với: Mapping thủ công → ModelMapper → MapStruct.

Lý do: Mapping thủ công giúp hiểu bản chất (response.setName(entity.getName());). Sau đó học ModelMapper để hiểu automatic mapping (modelMapper.map(entity, DTO.class);). Cuối cùng học MapStruct để hiểu cách xây dựng mapper rõ ràng, type-safe và phù hợp với các project lớn (mapper.toResponse(entity);).

2.13. Mô hình tổng hợp trong Spring Boot

Một project có thể tổ chức: controller → service → mapper → entity → repository → database.

Khi trả dữ liệu: Database → Repository → Entity → Mapper → Response DTO → Controller → Client.

Khi nhận dữ liệu: Client → Request DTO → Mapper → Entity → Repository → Database.

Đây chính là lý do Mapper trở thành một thành phần quan trọng trong kiến trúc Spring Boot sử dụng DTO.

Entity

@Setter
@NoArgsConstructor
@AllArgsConstructor
public class Medicine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Double price;
}

Request DTO

@Data
@NoArgsConstructor

public class MedicineRequest {

Response DTO

@Data
@Builder

2.15. Tổng kết

Cần ghi nhớ 3 cấp độ mapping:

  • Cấp độ 1 – Mapping thủ công: response.setName(entity.getName()); – dễ hiểu, toàn quyền kiểm soát.
  • Cấp độ 2 – ModelMapper: modelMapper.map(entity, MedicineResponse.class); – đơn giản, nhanh triển khai.
  • Cấp độ 3 – MapStruct: medicineMapper.toResponse(entity); – rõ ràng, sinh code khi compile, phù hợp với project lớn.

Kiến thức quan trọng nhất: Học viên không nên chỉ nhớ ModelMapper hay MapStruct, mà phải hiểu bản chất: Entity ≠ DTO. Entity phục vụ persistence/database, còn DTO phục vụ trao đổi dữ liệu. Mapper có nhiệm vụ: Entity → DTO và DTO → Entity. Nếu hiểu được luồng này, học viên sẽ hiểu tại sao trong một project Spring Boot thực tế thường có Entity, Request DTO, Response DTO và Mapper thay vì dùng trực tiếp Entity trong Controller.

3. CHUẨN HÓA RESPONSE TRONG SPRING BOOT

Mục tiêu bài học

Sau khi hoàn thành phần này, học viên có thể:

  • Hiểu Response trong REST API là gì.
  • Hiểu tại sao cần chuẩn hóa cấu trúc Response.
  • Xây dựng class ApiResponse.
  • Hiểu và sử dụng Generic trong ApiResponse.
  • Xây dựng Response cho trường hợp thành công.
  • Xây dựng Response cho trường hợp lỗi.
  • Kết hợp ApiResponse với ResponseEntity.
  • Hiểu và sử dụng các HTTP Status Code phổ biến.
  • Xây dựng cấu trúc Response phù hợp cho project Spring Boot thực tế.

3.1. Response trong REST API

3.1.1. Response là gì?

Trong REST API, Response là dữ liệu mà server gửi trả về cho client sau khi nhận và xử lý một HTTP Request.

Ví dụ client gửi: GET /api/medicines/1 – Server xử lý và trả về JSON.

3.1.2. Response gồm những thành phần nào?

Một HTTP Response thường gồm: Status Code, Headers, Body.

Ví dụ:

HTTP/1.1 200 OK
Content-Type: application/json
Body:
{
    "id": 1,
    "name": "Paracetamol"
}

Status Code – cho biết kết quả xử lý Request (200 thành công, 201 tạo thành công, 400 Request không hợp lệ, 404 không tìm thấy, 500 lỗi server).

Headers – chứa thông tin bổ sung về Response (ví dụ Content-Type).

Body – chứa dữ liệu thực tế mà server muốn trả về.

3.1.3. Response đơn giản trong Spring Boot

Trong Spring Boot, Controller có thể trả trực tiếp một object. Spring Boot sẽ tự chuyển object Java thành JSON.

@GetMapping("/{id}")
public MedicineResponse getById(@PathVariable Long id) {

    return medicineService.findById(id);
}

Ví dụ response: {"id": 1, "name": "Paracetamol", "price": 15000.0}

Cách này hoàn toàn hợp lệ. Tuy nhiên, khi project phát triển lớn, chúng ta thường muốn Response có một cấu trúc thống nhất.

3.2. Tại sao cần chuẩn hóa Response?

3.2.1. Vấn đề khi không chuẩn hóa

Giả sử project có nhiều API. API 1 trả {"id": 1, "name": "Paracetamol"}, API 2 trả mảng, API 3 trả {"message": "Medicine not found"}, API 4 trả {"error": "Invalid medicine"}, API 5 trả {"status": 400, "message": "Validation failed"}. Như vậy cấu trúc Response không thống nhất, frontend phải xử lý rất nhiều kiểu dữ liệu khác nhau.

3.2.2. Chuẩn hóa Response là gì?

Chuẩn hóa Response là việc quy định một cấu trúc Response thống nhất cho các API trong hệ thống.

Ví dụ thống nhất:

{
    "status": 200,
    "message": "Success",
    "data": {}
}

Khi đó frontend luôn biết status, message, data nằm ở đâu.

3.2.3. Lợi ích của chuẩn hóa Response

  • API thống nhất.
  • Frontend dễ xử lý (response.data).
  • Dễ bảo trì.
  • Dễ xử lý lỗi.
  • API chuyên nghiệp hơn.

3.3. Xây dựng ApiResponse

3.3.1. ApiResponse là gì?

ApiResponse là một class dùng để đóng gói Response của API vào một cấu trúc thống nhất.

Thay vì trả trực tiếp object, chúng ta trả new ApiResponse<>(200, "Success", medicineResponse);

3.3.2. Thiết kế ApiResponse cơ bản

public class ApiResponse<T> {

    private int status;
    private String message;
    private T data;
}

Ở đây có 3 thành phần: status, message, data.

3.3.3. Getter và Setter

Nếu chưa sử dụng Lombok, code khá dài. Vì đã học Lombok, có thể sử dụng:

@Data
@NoArgsConstructor
@AllArgsConstructor
public class ApiResponse<T> {

    private int status;
    private String message;
    private T data;
}

3.3.4. Giải thích cấu trúc

  • private int status; – lưu mã trạng thái (200, 201, 400, 404, 500).
  • private String message; – chứa thông báo.
  • private T data; – chứa dữ liệu Response. T là Generic Type.

3.4. Generic trong ApiResponse

3.4.1. Generic là gì?

Generic cho phép một class hoặc method làm việc với nhiều kiểu dữ liệu khác nhau mà vẫn đảm bảo kiểm tra kiểu dữ liệu tại compile time.

Ví dụ class Box<T> với T là kiểu chưa xác định. Khi sử dụng Box<String> thì T = String.

3.4.2. Tại sao ApiResponse cần Generic?

Nếu dùng private Object data; sẽ mất type safety. Generic tốt hơn: private T data;.

3.4.3. T hoạt động như thế nào?

Khi ApiResponse<MedicineResponse>, T = MedicineResponse, do đó data có kiểu MedicineResponse. Tương tự cho List<MedicineResponse>.

3.4.4. Ví dụ

ApiResponse<MedicineResponse> response = new ApiResponse<>(200, "Success", medicine);

Với danh sách:

ApiResponse<List<MedicineResponse>> response = new ApiResponse<>(200, "Success", medicines);

3.4.5. Generic giúp kiểm tra kiểu dữ liệu

Ví dụ ApiResponse<MedicineResponse> yêu cầu data phải là MedicineResponse, không thể truyền UserResponse. Điều này giúp phát hiện lỗi kiểu dữ liệu sớm.

3.5. Response thành công

3.5.1. Response thành công là gì?

Khi server xử lý Request thành công, Response thường sử dụng HTTP Status Code nhóm 2xx: 200 OK, 201 Created, 204 No Content.

3.5.2. Response lấy một object

@GetMapping("/{id}")
public ApiResponse<MedicineResponse> findById(@PathVariable Long id) {

    MedicineResponse medicine = medicineService.findById(id);

    return new ApiResponse<>(200, "Get medicine successfully", medicine);
}

Response:

{
    "status": 200,
    "message": "Get medicine successfully",
    "data": { "id": 1, "name": "Paracetamol", "price": 15000 }
}

3.5.3. Response danh sách

@GetMapping
public ApiResponse<List<MedicineResponse>> findAll() {

    List<MedicineResponse> medicines = medicineService.findAll();

    return new ApiResponse<>(200, "Get medicines successfully", medicines);
}

Điểm quan trọng: ApiResponse<List<MedicineResponse>> không phải ApiResponse<MedicineResponse> vì data là một danh sách.

3.5.4. Response tạo mới

Khi tạo Resource thành công, thông thường sử dụng 201 Created.

@PostMapping
public ApiResponse<MedicineResponse> create(@RequestBody MedicineRequest request) {

    MedicineResponse medicine = medicineService.create(request);

    return new ApiResponse<>(201, "Create medicine successfully", medicine);
}

3.5.5. Response cập nhật

Thông thường sử dụng 200 OK.

@PutMapping("/{id}")
public ApiResponse<MedicineResponse> update(@PathVariable Long id, @RequestBody MedicineRequest request) {

    MedicineResponse medicine = medicineService.update(id, request);

    return new ApiResponse<>(200, "Update medicine successfully", medicine);
}

3.6. Response lỗi

3.6.1. Tại sao Response lỗi cũng cần chuẩn hóa?

Không chỉ Response thành công, Response lỗi cũng cần có cấu trúc rõ ràng. Ví dụ {"status": 404, "message": "Medicine not found", "data": null} giúp frontend xử lý thống nhất.

3.6.2. Lỗi không tìm thấy dữ liệu

Client gọi GET /api/medicines/100 nhưng không tồn tại, trả {"status": 404, "message": "Medicine not found", "data": null}.

3.6.3. Tạo Response lỗi

return new ApiResponse<>(404, "Medicine not found", null);

3.6.4. Không nên trả lỗi tùy tiện

Không nên để API này trả {"message": "Not found"}, API khác trả {"error": "User does not exist"}. Nên thống nhất cấu trúc {"status": 404, "message": "...", "data": null}.

3.6.5. Response lỗi Validation

Ví dụ DTO có @NotBlank, @Positive. Nếu validation thất bại, có thể trả:

{
    "status": 400,
    "message": "Validation failed",
    "data": {
        "name": "Name must not be blank",
        "price": "Price must be greater than 0"
    }
}

Điều này giúp frontend biết chính xác field nào bị lỗi.

3.6.6. Response lỗi Server

Nếu server xảy ra lỗi không mong muốn (500), trả {"status": 500, "message": "Internal server error", "data": null}. Trong production, không nên trả stack trace hoặc thông tin nội bộ.

3.7. Kết hợp ApiResponse với ResponseEntity

3.7.1. ResponseEntity là gì?

ResponseEntity là class của Spring dùng để biểu diễn toàn bộ HTTP Response, cho phép kiểm soát HTTP Status Code, Headers, Body.

Ví dụ: return ResponseEntity.ok(data); – 200 OK với data là Body.

3.7.2. Tại sao kết hợp ApiResponse và ResponseEntity?

ApiResponse quản lý cấu trúc dữ liệu bên trong Body. ResponseEntity quản lý HTTP Response (status, headers). Có thể hình dung:

ResponseEntity
│
├── HTTP Status
├── Headers
└── Body
      │
      └── ApiResponse
             ├── status
             ├── message
             └── data

3.7.3. Ví dụ cơ bản

@GetMapping("/{id}")
public ResponseEntity<ApiResponse<MedicineResponse>> findById(@PathVariable Long id) {

    MedicineResponse medicine = medicineService.findById(id);

    ApiResponse<MedicineResponse> response = new ApiResponse<>(200, "Get medicine successfully", medicine);

    return ResponseEntity.ok(response);
}

3.7.4. ResponseEntity.ok()

ResponseEntity.ok(response) tương đương HTTP Status 200 OK, Body = response.

3.7.5. Sử dụng ResponseEntity.status()

Nếu muốn trả 201 Created: return ResponseEntity.status(HttpStatus.CREATED).body(response);

3.7.6. Ví dụ Create

@PostMapping
public ResponseEntity<ApiResponse<MedicineResponse>> create(@RequestBody MedicineRequest request) {

    MedicineResponse medicine = medicineService.create(request);

    ApiResponse<MedicineResponse> response = new ApiResponse<>(201, "Create medicine successfully", medicine);

    return ResponseEntity.status(HttpStatus.CREATED).body(response);
}

3.7.7. Response lỗi với ResponseEntity

Có thể kiểm tra nếu không tìm thấy và trả 404. Tuy nhiên, khi project lớn, nên sử dụng Global Exception Handler để xử lý tập trung.

3.7.8. Nên đặt HTTP Status ở đâu?

Khi sử dụng ApiResponse<T>, chúng ta có private int status; và ResponseEntity cũng có HTTP Status. Một số project giữ cả hai để frontend dễ xử lý. Điều quan trọng là project phải có quy ước nhất quán.

3.8. HTTP Status Code

3.8.1. HTTP Status Code là gì?

Mã số server sử dụng để thông báo kết quả xử lý Request. Chia thành 5 nhóm: 1xx Informational, 2xx Success, 3xx Redirection, 4xx Client Error, 5xx Server Error. Trong REST API, chủ yếu làm việc với 2xx, 4xx, 5xx.

3.8.2. 200 OK

Request được xử lý thành công. Ví dụ GET trả dữ liệu. Spring Boot: return ResponseEntity.ok(response);

3.8.3. 201 Created

Dùng khi Resource mới được tạo thành công. return ResponseEntity.status(HttpStatus.CREATED).body(response);

3.8.4. 204 No Content

Request thành công nhưng không có dữ liệu Body cần trả về (ví dụ DELETE). Thường không cần ApiResponse.

3.8.5. 400 Bad Request

Request từ client không hợp lệ (ví dụ validation thất bại).

3.8.6. 401 Unauthorized

Client chưa được xác thực hoặc thông tin xác thực không hợp lệ.

3.8.7. 403 Forbidden

Client đã xác thực nhưng không có quyền thực hiện hành động.

3.8.8. Phân biệt 401 và 403

401 – "Bạn là ai?" – chưa xác thực. 403 – "Tôi biết bạn là ai, nhưng bạn không có quyền."

3.8.9. 404 Not Found

Resource được yêu cầu không tồn tại.

3.8.10. 409 Conflict

Request xung đột với trạng thái hiện tại của Resource (ví dụ username đã tồn tại).

3.8.11. 500 Internal Server Error

Server gặp lỗi không mong muốn. Trong production, không trả stack trace cho client.

3.11. Tổng kết kiến thức

Sau phần này, học viên cần nắm được luồng: Client → Controller → Service → Repository → Database.

Khi trả dữ liệu: Database → Entity → Mapper → DTO → ApiResponse → ResponseEntity → HTTP Response → Client.

Trong đó: DTO – đại diện cho dữ liệu muốn truyền đi; Mapper – chuyển đổi Entity ↔ DTO; ApiResponse – chuẩn hóa Body; ResponseEntity – quản lý HTTP Response (status, headers, body); HTTP Status Code – cho client biết kết quả Request.

Điểm quan trọng nhất: ApiResponse và ResponseEntity không phải là hai thứ giống nhau. ApiResponse giúp chuẩn hóa dữ liệu trong Body, còn ResponseEntity giúp điều khiển HTTP Response. Khi kết hợp chúng, ta có một cấu trúc API vừa thống nhất vừa đúng với cơ chế HTTP.

4. XỬ LÝ EXCEPTION TRONG SPRING BOOT

Trong các ứng dụng Spring Boot, Exception là một vấn đề rất quan trọng cần được xử lý đúng cách. Một API thực tế không thể chỉ xử lý trường hợp thành công. Trong quá trình chạy, rất nhiều lỗi có thể xảy ra: Không tìm thấy dữ liệu, dữ liệu bị trùng, Request không hợp lệ, Validation thất bại, người dùng không có quyền, lỗi database, lỗi logic nghiệp vụ, lỗi không xác định.

Nếu không xử lý Exception đúng cách, client có thể nhận được những Response khó hiểu. Trong một API chuyên nghiệp, chúng ta thường muốn biến những Exception đó thành Response có cấu trúc rõ ràng, ví dụ {"status": 404, "message": "Medicine not found", "data": null}.

4.1. Exception trong REST API

4.1.1. Exception là gì?

Exception là một tình huống bất thường xảy ra trong quá trình chương trình thực thi, khiến luồng xử lý bình thường bị gián đoạn.

Ví dụ: int a = 10; int b = 0; int result = a / b; gây ra ArithmeticException.

Hoặc Medicine medicine = medicineRepository.findById(id).orElse(null); return medicine.getName(); nếu medicine == null → NullPointerException.

4.1.2. Exception trong API

Giả sử client gọi GET /api/medicines/100 nhưng Medicine ID 100 không tồn tại. Trong Service có thể viết medicineRepository.findById(id).orElseThrow(); – khi không tìm thấy, Spring/JPA phát sinh Exception. Nếu không xử lý, client nhận 500 Internal Server Error, trong khi lỗi thực sự là "Medicine không tồn tại", nên trả 404 Not Found và {"status": 404, "message": "Medicine not found", "data": null}.

4.1.3. Tại sao cần xử lý Exception?

  • API trả HTTP Status phù hợp (404, 400, 409, 500).
  • Client dễ hiểu lỗi (thay vì stack trace).
  • Không để lộ thông tin nội bộ (stack trace, SQL, class name).
  • Dễ bảo trì – các lỗi được xử lý tập trung thay vì try-catch ở hàng chục Controller.

4.1.4. Exception Handling trong Spring Boot

Một kiến trúc thường gặp: Controller → Service → Exception xảy ra → Global Exception Handler → ApiResponse → Client.

Ví dụ: GET /api/medicines/100 → MedicineService → ResourceNotFoundException → GlobalExceptionHandler → 404 → JSON Response.

4.2. Custom Exception

4.2.1. Custom Exception là gì?

Custom Exception là Exception do lập trình viên tự định nghĩa để biểu diễn những lỗi nghiệp vụ cụ thể của hệ thống. Thay vì chỉ sử dụng RuntimeException, có thể tạo ResourceNotFoundException hoặc DuplicateResourceException.

4.2.2. Tại sao cần Custom Exception?

Giả sử throw new RuntimeException("Medicine not found"); quá chung chung. Nếu sử dụng throw new ResourceNotFoundException("Medicine not found");, nhìn vào code đã hiểu: Resource mà client yêu cầu không tồn tại.

4.2.3. Cú pháp tạo Custom Exception

public class ResourceNotFoundException
        extends RuntimeException {

    public ResourceNotFoundException(String message) {
        super(message);
    }
}

4.2.4. Giải thích cú pháp

  • extends RuntimeException – Custom Exception kế thừa từ RuntimeException.
  • Constructor – truyền message vào super(message).

4.3. ResourceNotFoundException

4.3.1. ResourceNotFoundException là gì?

Thường sử dụng khi Resource mà client yêu cầu không tồn tại (ví dụ Medicine ID 100 không có trong database).

4.3.2. Tạo Exception

public class ResourceNotFoundException
        extends RuntimeException {

    public ResourceNotFoundException(String message) {
        super(message);
    }
}

4.3.3. Sử dụng trong Service

Thay vì medicineRepository.findById(id).orElse(null);, có thể:

Medicine medicine = medicineRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("Medicine not found"));

4.3.4. Phân tích orElseThrow()

Nếu tìm thấy → trả về Medicine; nếu không tìm thấy → throw ResourceNotFoundException.

4.3.5. Ví dụ Service hoàn chỉnh

@Service
@RequiredArgsConstructor
public class MedicineService {

    private final MedicineRepository medicineRepository;
    private final MedicineMapper medicineMapper;

    public MedicineResponse findById(Long id) {

        Medicine medicine = medicineRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Medicine not found with id: " + id));

        return medicineMapper.toResponse(medicine);
    }
}

4.4. DuplicateResourceException

4.4.1. DuplicateResourceException là gì?

Dùng khi client cố tạo dữ liệu đã tồn tại (ví dụ email đã được đăng ký).

public class DuplicateResourceException
        extends RuntimeException {

    public DuplicateResourceException(String message) {
        super(message);
    }
}

4.4.2. Ví dụ kiểm tra dữ liệu trùng

Repository: boolean existsByEmail(String email);

Service:

if (userRepository.existsByEmail(request.getEmail())) {
    throw new DuplicateResourceException("Email already exists");
}

4.4.3. Luồng xử lý

Client → POST /users → Service → Email đã tồn tại? → YES → DuplicateResourceException → Global Exception Handler → 409 Conflict → Response {"status": 409, "message": "Email already exists", "data": null}.

4.5. @ExceptionHandler

4.5.1. @ExceptionHandler là gì?

Annotation của Spring MVC dùng để đánh dấu method chuyên xử lý một hoặc nhiều loại Exception.

Ví dụ:

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<?> handleResourceNotFound(ResourceNotFoundException ex) {
    ...
}

4.5.2. Ví dụ cơ bản

@RestController
public class MedicineController {

    @GetMapping("/{id}")
    public MedicineResponse findById(@PathVariable Long id) {
        throw new ResourceNotFoundException("Medicine not found");
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<String> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(ex.getMessage());
    }
}

4.5.3. Hạn chế của @ExceptionHandler trong Controller

Nếu có nhiều Controller, phải lặp lại @ExceptionHandler ở mỗi Controller → code trùng lặp, khó bảo trì. Giải pháp: @RestControllerAdvice.

4.6. @RestControllerAdvice

4.6.1. @RestControllerAdvice là gì?

Cho phép tạo nơi xử lý Exception tập trung cho toàn bộ REST Controller. Có thể hiểu: @RestControllerAdvice = Global Exception Handler cho REST API.

4.6.2. Cấu trúc cơ bản

@RestControllerAdvice
public class GlobalExceptionHandler {

}

4.6.3. Ví dụ ResourceNotFoundException

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>> handleResourceNotFound(ResourceNotFoundException ex) {

        ApiResponse<Void> response = new ApiResponse<>(404, ex.getMessage(), null);

        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(response);
    }
}

4.6.4. ApiResponse<Void> là gì?

ApiResponse với Void có nghĩa Response không có dữ liệu cụ thể trong data, do đó data = null. Ví dụ JSON: {"status": 404, "message": "Medicine not found", "data": null}.

4.7. Global Exception Handler

4.7.1. Global Exception Handler là gì?

Class chịu trách nhiệm xử lý Exception tập trung cho toàn bộ ứng dụng. Thông thường: @RestControllerAdvice public class GlobalExceptionHandler { }

4.7.2. Tại sao cần Global Exception Handler?

Thay vì mỗi Controller có ExceptionHandler riêng, tất cả Controller dùng chung một nơi xử lý lỗi.

4.7.3. Xử lý ResourceNotFoundException

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<ApiResponse<Void>> handleResourceNotFound(ResourceNotFoundException ex) {
    ApiResponse<Void> response = new ApiResponse<>(404, ex.getMessage(), null);
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(response);
}

4.7.4. Xử lý DuplicateResourceException

@ExceptionHandler(DuplicateResourceException.class)
public ResponseEntity<ApiResponse<Void>> handleDuplicateResource(DuplicateResourceException ex) {
    ApiResponse<Void> response = new ApiResponse<>(409, ex.getMessage(), null);
    return ResponseEntity.status(HttpStatus.CONFLICT).body(response);
}

4.7.5. Global Handler hoàn chỉnh

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>> handleResourceNotFound(ResourceNotFoundException ex) {
        ApiResponse<Void> response = new ApiResponse<>(404, ex.getMessage(), null);
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(response);
    }

    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>> handleDuplicateResource(DuplicateResourceException ex) {
        ApiResponse<Void> response = new ApiResponse<>(409, ex.getMessage(), null);
        return ResponseEntity.status(HttpStatus.CONFLICT).body(response);
    }
}

4.8. Xử lý Exception chung

Ngoài các Exception nghiệp vụ cụ thể, hệ thống còn có thể phát sinh nhiều Exception khác như NullPointerException, IllegalArgumentException, DataAccessException, SQLException, RuntimeException. Không thể tạo Handler riêng cho mọi Exception, do đó có thể tạo Handler chung.

4.8.1. Xử lý Exception

@ExceptionHandler(Exception.class)
public ResponseEntity<ApiResponse<Void>> handleException(Exception ex) {
    ApiResponse<Void> response = new ApiResponse<>(500, "Internal server error", null);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(response);
}

4.8.2. Tại sao dùng Exception.class?

@ExceptionHandler(Exception.class) nghĩa là nếu Exception không có Handler cụ thể, hãy sử dụng Handler này. Ví dụ ResourceNotFoundException → Handler riêng → 404. NullPointerException → không có Handler riêng → Exception.class → 500.

4.8.3. Thứ tự xử lý Exception

Exception xảy ra → Có phải ResourceNotFoundException? → YES → 404. NO → Có phải DuplicateResourceException? → YES → 409. NO → Exception chung → 500.

4.8.4. Không nên trả ex.getMessage() cho mọi Exception

Không nên làm return ResponseEntity.status(500).body(ex.getMessage()); vì ex.getMessage() có thể chứa thông tin nội bộ (SQL, database connection, file path). Nên client nhận message an toàn, còn thông tin chi tiết được log ở server.

4.8.5. Log Exception

Có thể sử dụng Logger:

private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

Sau đó: log.error("Unexpected error occurred", ex); – client nhận message an toàn, server lưu thông tin Exception để debug.

4.9. Chuẩn hóa Error Response

4.9.1. Error Response là gì?

Cấu trúc JSON được server trả về khi Request thất bại. Có thể sử dụng chính ApiResponse để chuẩn hóa cả Success và Error Response.

4.9.2. Success Response

{ "status": 200, "message": "Get medicine successfully", "data": { "id": 1, "name": "Paracetamol" } }

4.9.3. Not Found Response

{ "status": 404, "message": "Medicine not found", "data": null }

4.9.4. Duplicate Response

{ "status": 409, "message": "Email already exists", "data": null }

4.9.5. Server Error Response

{ "status": 500, "message": "Internal server error", "data": null }

4.9.6. Xử lý Validation Exception

Giả sử DTO có @NotBlank, @NotNull, @Positive. Controller dùng @Valid. Nếu validation thất bại, Spring phát sinh MethodArgumentNotValidException.

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ApiResponse<Map<String, String>>> handleValidationException(MethodArgumentNotValidException ex) {

    Map<String, String> errors = new HashMap<>();

    ex.getBindingResult().getFieldErrors().forEach(error ->
        errors.put(error.getField(), error.getDefaultMessage())
    );

    ApiResponse<Map<String, String>> response = new ApiResponse<>(400, "Validation failed", errors);

    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(response);
}

4.9.7. Response Validation

Client nhận: {"status": 400, "message": "Validation failed", "data": {"name": "Name is required", "price": "Price must be greater than 0"}} – frontend dễ dàng hiển thị lỗi tại từng field.

4.9.8. Global Exception Handler hoàn chỉnh

@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiResponse<Void>> handleResourceNotFound(ResourceNotFoundException ex) {
        ApiResponse<Void> response = new ApiResponse<>(404, ex.getMessage(), null);
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(response);
    }

    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ApiResponse<Void>> handleDuplicateResource(DuplicateResourceException ex) {
        ApiResponse<Void> response = new ApiResponse<>(409, ex.getMessage(), null);
        return ResponseEntity.status(HttpStatus.CONFLICT).body(response);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Map<String, String>>> handleValidationException(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(error -> errors.put(error.getField(), error.getDefaultMessage()));
        ApiResponse<Map<String, String>> response = new ApiResponse<>(400, "Validation failed", errors);
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(response);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleException(Exception ex) {
        log.error("Unexpected error occurred", ex);
        ApiResponse<Void> response = new ApiResponse<>(500, "Internal server error", null);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(response);
    }
}

4.11. Ví dụ thực tế hoàn chỉnh

Giả sử API GET /api/medicines/10

Bước 1: Controller

@GetMapping("/{id}")
public ResponseEntity<ApiResponse<MedicineResponse>> findById(@PathVariable Long id) {
    return ResponseEntity.ok(new ApiResponse<>(200, "Get medicine successfully", medicineService.findById(id)));
}

Bước 2: Service

public MedicineResponse findById(Long id) {
    Medicine medicine = medicineRepository.findById(id)
        .orElseThrow(() -> new ResourceNotFoundException("Medicine not found with id: " + id));
    return medicineMapper.toResponse(medicine);
}

Bước 3: Nếu tìm thấy – Repository → Medicine → Mapper → MedicineResponse → ApiResponse → 200 OK.

Bước 4: Nếu không tìm thấy – Service throw ResourceNotFoundException → Spring tìm @ExceptionHandler → Global Handler trả 404 Not Found với {"status": 404, "message": "Medicine not found with id: 10", "data": null}.

Controller không cần try-catch – đây là ưu điểm của Global Exception Handler.

4.13. Tổng kết kiến thức

Học viên cần hiểu mối quan hệ giữa các thành phần: DTO ↔ Mapper ↔ Entity ↔ Repository.

Khi thành công: Entity → Mapper → DTO → ApiResponse → ResponseEntity → Client.

Khi xảy ra lỗi: Service throw Exception → GlobalExceptionHandler → ApiResponse → ResponseEntity → Client.

Các Exception cần nhớ: ResourceNotFoundException (404), DuplicateResourceException (409), MethodArgumentNotValidException (400), Exception (500).

Các annotation quan trọng: @ExceptionHandler – xử lý một loại Exception; @RestControllerAdvice – xử lý Exception tập trung cho REST Controller.

Kiến thức cốt lõi: Một API Spring Boot được tổ chức tốt thường không xử lý lỗi bằng try-catch ở mọi Controller. Thay vào đó: Exception → Custom Exception → Global Exception Handler → Error Response → Client. Và Response được chuẩn hóa {"status": 404, "message": "Medicine not found", "data": null}.

Như vậy, sau 4 phần Lombok → Mapper → Chuẩn hóa Response → Exception, học viên đã có nền tảng để xây dựng một REST API Spring Boot theo cấu trúc tương đối chuyên nghiệp, thay vì chỉ viết Controller trả Entity trực tiếp.

5. KẾT HỢP LOMBOK, MAPPER, RESPONSE VÀ EXCEPTION

Mục tiêu bài học

Sau khi hoàn thành phần này, học viên có thể:

  • Thiết kế cấu trúc một project Spring Boot có tổ chức.
  • Sử dụng Lombok trong Entity, DTO và các class khác.
  • Sử dụng Mapper để chuyển đổi giữa Entity và DTO.
  • Sử dụng ApiResponse<T> để chuẩn hóa Response.
  • Xử lý Exception tập trung bằng @RestControllerAdvice.
  • Hiểu toàn bộ luồng xử lý của một REST API.
  • Biết cách kết hợp các thành phần đã học thành một kiến trúc hoàn chỉnh.

5.1. Thiết kế cấu trúc Project

5.1.1. Tại sao cần tổ chức Project?

Khi mới học Spring Boot, học viên thường viết tất cả code trong một vài class: Controller → Repository hoặc thậm chí Controller → Repository → Database. Cách này có thể chạy được với project nhỏ nhưng sẽ trở nên khó quản lý khi hệ thống phát triển.

Một project thực tế thường được chia thành nhiều tầng: Controller → Service → Repository → Database.

5.2. Cấu trúc chi tiết

  • Controller – Nhận request từ client, gọi Service, trả về Response.
  • Service – Xử lý nghiệp vụ, gọi Repository, thực hiện logic.
  • Repository – Tương tác với database (JPA).
  • Entity – Ánh xạ với table trong database.
  • DTO – Data Transfer Object, dùng để truyền dữ liệu giữa các tầng hoặc với client.
  • Mapper – Chuyển đổi giữa Entity và DTO.
  • ApiResponse – Chuẩn hóa cấu trúc Response.
  • Exception Handling – Xử lý lỗi tập trung.

5.3. Luồng xử lý tổng thể

Khi trả dữ liệu:

Database → Repository → Entity → Mapper → Response DTO → ApiResponse → Controller → Client

Khi nhận dữ liệu:

Client → Request DTO → Controller → Service → Mapper → Entity → Repository → Database

5.4. Ví dụ hoàn chỉnh

Xây dựng API CRUD cho Medicine với đầy đủ các thành phần.

  • Entity: Medicine (Lombok: @Getter, @Setter, @NoArgsConstructor)
  • Request DTO: MedicineRequest (Lombok: @Data)
  • Response DTO: MedicineResponse (Lombok: @Data, @Builder)
  • Mapper: MedicineMapper (MapStruct hoặc ModelMapper)
  • Service: MedicineService (@RequiredArgsConstructor, private final repository và mapper)
  • Controller: MedicineController (@RequiredArgsConstructor, private final service)
  • ApiResponse: generic
  • GlobalExceptionHandler: xử lý ResourceNotFoundException, DuplicateResourceException, Validation, Exception chung.

5.5. Tổng kết

Sau khi hoàn thành 4 phần Lombok → Mapper → Chuẩn hóa Response → Exception, học viên đã có nền tảng để xây dựng một REST API Spring Boot theo cấu trúc tương đối chuyên nghiệp, thay vì chỉ viết Controller trả Entity trực tiếp.

Điểm quan trọng nhất: Entity ≠ DTO. Entity phục vụ persistence/database, DTO phục vụ trao đổi dữ liệu. Mapper đứng giữa để chuyển đổi.
